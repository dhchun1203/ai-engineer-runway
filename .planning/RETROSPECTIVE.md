# Project Retrospective

*A living document updated after each milestone. Lessons feed forward into future planning.*

## Milestone: v1.0 — 사전학습 사이트

**Shipped:** 2026-08-27
**Phases:** 7 (1~6, 8) | **Plans:** 51 | **Quick tasks:** 7 | **Commits:** 403 | **기간:** 4일

### What Was Built

- **학습 루프 전체** — Step→모듈→레슨 탐색, 완료 토글(Supabase 저장·기기 간 유지), 모듈·Step·전체 진행률. Supabase Auth 없이 공유 시크릿 쿠키 + 서버 전용 `service_role` + RLS 기본 차단으로 1인용 최소 마찰을 지켰다.
- **레슨 35편 (MDX 7,024줄)** — eli5 × 6단 표준. Step 1·2 핵심은 심화, Step 3는 개념 훑기. 실습 프로젝트 5종은 준비 가이드로.
- **일정과 오늘의 학습** — 매니페스트 파생 일정, D-day, 시간 가중 3단계 페이스 판정, 밀린 레슨, 오늘 행 자동 스크롤.
- **성능·인터랙션** — 콘텐츠 라우트 완전 정적(프로덕션 TTFB 33~40ms), 폰트 서브셋 2.06MB→448KB, 탭 피드백·에러 회복·rAF 스크롤 스로틀.
- **자동 게이트 20종** — 정적 12(브랜드·디자인 토큰·매니페스트 불변식·레슨 구조·진도 수학·라우트 렌더 모드·폰트 커버리지 등) + e2e 8(실 Supabase 왕복).

### What Worked

- **게이트를 먼저 세우고 빨간불로 시작하는 순서.** Phase 8이 08-01에서 목표 상태를 코드로 고정하고(39건 위반 = 정상) 이후 7개 플랜이 하나씩 초록불로 만들었다. 완료 여부를 사람 판단이 아니라 게이트 하나로 판정할 수 있어 뒤따르는 플랜의 판단 비용이 실제로 줄었다 — 8개 플랜 전부 30~55분에 끝났고 스코프 확장 0건.
- **파일럿 1편 먼저 → 승인 → 나머지 확장.** 레슨 35편을 한 번에 쓰지 않고 톤·구조를 1편으로 굳힌 뒤 확장했다. Phase 5에서 가독성 결함(문단 간격 역전)이 나왔을 때도 13편 재문단화로 끝났지, 35편이 아니었다.
- **측정이 판단을 대신하게 한 것.** "폰트를 줄일까"를 논의하지 않고 먼저 쟀다 — 76%라는 숫자가 나오자 결정할 것이 없었다. 임계값(D8-B)을 미리 정해 두고 실측과 대조하는 형태가 반복해서 잘 작동했다.
- **1차 자료 교차검증.** KS X 1001 완성형 2,350자를 기억으로 재현하지 않고 Unicode.org 매핑 테이블에서 받아 코드포인트 단위로 diff했다. 검증 불가능한 재현은 막으려는 결함과 같은 종류라는 원칙.

### What Was Inefficient

- **`npm run lint`이 어떤 게이트에도 없었다.** Phase 1부터 이월된 3건 위에 Phase 8이 3건을 더 얹었고, 아무 데서도 걸리지 않은 채 마일스톤 마감 감사에서야 드러났다. 게이트 20종을 만들면서 정작 기본 lint를 빠뜨린 것.
- **격리 워크트리에 자격증명이 없어 검증 부채가 8개 플랜에 걸쳐 쌓였다.** 08-01~08-07이 전부 더미 Supabase 값 + route mock으로 돌아 `status: unknown` 커버리지가 계속 누적됐고, 08-08의 첫 실자격증명 실행에서야 정산됐다. 그때 `e2e-progress.mjs` g4가 08-03 이후 계속 깨져 있었다는 것도 드러났다 — 앞 시나리오가 먼저 실패해 뒤 시나리오는 실행된 적이 없었다.
- **문서 정합이 코드보다 늦게 따라왔다.** CONT-02/CONT-03은 Phase 4 UAT가 2026-08-25에 닫혔는데 REQUIREMENTS.md 표는 마일스톤 마감까지 Pending으로 남아 있었다. STATE.md의 "다음에 할 일"도 Phase 4 시절 안내에 멈춰 있었다.
- **로컬 성능 측정에 시간을 들였지만 판정 근거가 되지 못했다.** 정적 전환 전후 로컬 TTFB가 6.00→6.10ms로 사실상 동일했다. 실제 이득은 CDN 엣지 캐시에서 나오므로 프로덕션 실측 전까지는 방향 지표일 뿐이었다.

### Patterns Established

- **정적 게이트 3단계 골격** — 산출물 부재 시 skip+exit 0 → 독립 재계산(앱 코드 import 금지) → `fail()` 배열 누적 후 일괄 보고.
- **진도 아일랜드 3계층** — Route Handler(쿠키 게이트 최우선) → Provider(4상태) → Slot 소비자. 확장 시 Provider/Skeleton은 건드리지 않고 Slot만 추가.
- **`renderedHtml()` 수화 후 DOM 검증 헬퍼** — 공유 모듈로 빼지 않고 파일마다 복제. 반환 타입이 `res.text()`와 같아 downstream 어설션을 안 바꾸고 이행된다.
- **`sm:contents` 픽셀 보존** — 모바일만 재배치하고 640px 이상 렌더를 원본과 픽셀 단위로 동일하게 유지.
- **브라우저 재계산 아일랜드** — 정적 셸에 초기값을 심고 클라이언트가 같은 순수 로직으로 재계산. ISR의 "창 만료 후 첫 요청이 낡은 값" 구멍을 구조적으로 없앤다.
- **측정 문서 이력 보존** — 값을 덮어쓰지 않고 전/후 + 출처 각주로 남긴다. 후속 독자가 "왜 숫자가 바뀌었는지" 재구성할 수 있어야 한다.

### Key Lessons

1. **자동 게이트가 실기기를 대체하지 못한다.** Phase 6과 8에서 두 번 확인했다. 두 번 다 게이트가 전부 초록불인 상태에서 사용자가 실기기 결함을 찾았고(Phase 8은 폰 헤더 내비 3줄 접힘), 게이트가 잡은 크기(위반 1건)와 사람이 느낀 크기(화면 1/4 잠식)가 정반대였다. 페이즈 마지막의 실기기 UAT는 형식이 아니라 유일한 검출 수단이다.
2. **"게이트가 있다"와 "게이트가 실행된다"는 다른 이야기다.** 전제 조건(자격증명)이 필요한 e2e 스위트는 "끝까지 도달한 적이 있는가"를 따로 추적해야 한다. 병렬 워크트리를 쓸 거면 실자격증명 검증을 모아 닫는 플랜이 페이즈 안에 반드시 하나 있어야 한다.
3. **"안전하게 넓게 잡자"는 직관이 반대 결과를 낼 수 있다.** 한글 음절 전체(11,172자) 서브셋은 15%만 줄었고, KS X 1001 2,350자로 좁히자 78% 줄었다. 폴백 스택과 커버리지 게이트라는 안전망이 이미 있는데 집합까지 넓게 잡을 이유가 없었다.
4. **측정 코드를 먼저 의심하라.** 폰트 비중이 100%로 나왔을 때 원인은 폰트가 아니라 `Content-Length` 없는 응답을 0바이트로 세던 측정 콜백이었다. 결과가 극단적으로 깔끔하면 대상이 아니라 자를 의심할 것.
5. **검증 스크립트 자체가 거짓 통과/실패를 낸다.** 문서 전체 정규식이 `D-34`를 `D-02`로 읽었다. 마커 뒤 N자 윈도우로 범위를 좁히는 관례가 필요하다.
6. **범위 밖 결함은 고치지 말되 반드시 숫자와 함께 넘겨라.** 375px M3 잔존 120건은 게이트 정의를 바꾸지 않고 실기기 UAT로 넘겼고, 실제로 승인됐다. 게이트가 불편하다고 게이트를 바꾸면 그 게이트는 아무것도 지키지 않는다.
