## 1. 학습 목표

이 프로젝트에서 무엇을 만들고 무엇을 증명하는지 먼저 짚고 넘어갑니다.

- **무엇을 만드나:** AI 쇼핑몰의 백엔드 — Express.js RESTful API가 PostgreSQL·Prisma ORM으로 데이터를 저장하고, LLM API로 추천 문구를 생성해 프론트엔드에 응답하는 서버입니다.
- **무엇을 증명하나:** 자원 설계·인증·데이터 저장·LLM 연동이 하나의 서비스로 묶일 수 있음을 증명합니다. 직접 구현하는 것이 아니라, 무엇이 준비되어 있어야 개강 첫날 팀 작업을 바로 시작할 수 있는지를 확인하는 것이 이 레슨의 목표입니다.
- 개강 후 팀 프로젝트에서 이 백엔드를 실제로 만들 때, 오늘 준비해둔 것들이 그대로 출발점이 됩니다.

## 2. 왜 배우나

이 프로젝트는 앞서 배운 여러 모듈이 하나의 서버로 합쳐지는 자리입니다.

`2-1-ai-data-modeling`에서 다진 데이터 구조 설계, `2-5-express-rest-api`에서 다진 엔드포인트 설계, `2-5-auth-and-prisma`에서 다진 인증·데이터 저장 방식이 전부 여기서 필요합니다.

짝이 되는 프론트엔드는 `2-4-project-ai-shop-frontend`입니다. 그 레슨의 화면이 호출할 API를 지금 이 레슨에서 준비합니다.

아직 이 레슨들을 보지 않았어도 slug만 기억해뒀다가, 프로젝트를 실제로 시작할 때 막히는 부분이 있으면 해당 레슨으로 돌아가 복습하면 됩니다.

## 3. 개념 설명

### 무엇을 만드나 — 전체 구조

```text
클라이언트 요청 → Express 라우터 → 인증 미들웨어 → Prisma → PostgreSQL / LLM API → 응답
```

| 구성 요소 | 맡는 일 | 어느 레슨에서 나왔나 |
|-----------|---------|----------------------|
| Express 라우터 | 어떤 URL·메서드 요청을 어떤 함수가 처리할지 연결 | `2-5-express-rest-api` |
| 인증 미들웨어 | 요청을 보낸 사용자가 누구인지 확인 | `2-5-auth-and-prisma` |
| Prisma | 코드에서 데이터베이스를 다루는 도구(ORM) | `2-5-auth-and-prisma` |
| PostgreSQL | 상품·주문·사용자 데이터를 저장하는 데이터베이스 | `2-1-postgres-and-supabase` |
| LLM API 호출 | 상품 설명을 바탕으로 추천 문구를 생성 | `2-1-ai-data-modeling` |

## 4. 실무 예제

### 사전 준비 체크리스트

이 프로젝트를 개강 첫날 바로 시작하려면 아래를 미리 준비해둡니다.

| 준비물 | 왜 필요한가 | 지금 할 일 |
|--------|-------------|-----------|
| PostgreSQL 데이터베이스 | 상품·주문·사용자 데이터를 저장할 곳이 필요합니다 | Supabase 프로젝트의 접속 정보(URL·키)를 미리 확보해두기 |
| LLM API 키 | 상품 추천 문구를 AI가 생성하려면 API 호출 권한이 필요합니다 | 발급받아 `.env.local`에 저장해두기(코드나 대화창에 붙여넣지 않기) |
| Node·npm 설치 확인 | 서버 코드를 실행할 기반 환경이 필요합니다 | `2-3-typescript-setup`을 완료했는지 확인하기 |
| API 명세 초안 | 프론트와 백이 같은 약속으로 통신해야 합니다 | 만들 엔드포인트 6~8개를 메서드·경로·설명 표로 미리 적어두기 |
| API 호출 도구 | 완성 전 엔드포인트를 눈으로 확인할 방법이 필요합니다 | 브라우저 확장이나 데스크톱 클라이언트 중 하나를 설치해두기 |

> ⚠️ 이 체크리스트는 무엇을 준비할지만 알려줍니다. 실제 구현 방법은 개강 후
> 본 과정에서 팀과 함께 설계합니다.

환경변수는 아래처럼 키 이름만 미리 정리해두면 됩니다. 값은 각자 발급받은 것을 넣습니다.

```text
# .env.local — 키 이름만 적어둡니다. 실제 값은 각자 발급받은 것을 넣습니다.
DATABASE_URL=
LLM_API_KEY=
JWT_SECRET=
```

## 5. 실무 팁

- **팀원마다 데이터베이스가 달라 데이터가 안 맞는 상황이 자주 생깁니다.** 팀이 함께 쓸 시드 데이터(seed data, 확인용으로 미리 넣어두는 샘플 데이터)를 미리 정해두면 각자 환경에서도 같은 화면을 확인할 수 있습니다.
- **환경변수는 안전하게 나눕니다.** API 키를 디스코드나 카카오톡 대화창에 평문으로 붙여넣지 않습니다. 팀 노션의 비공개 페이지나 비밀번호 관리자로 공유하는 습관을 미리 들여둡니다.
- **API 명세를 먼저 합의하지 않으면 프론트와 백이 서로 다른 것을 만듭니다.** 엔드포인트 경로·요청 형식·응답 형식을 코드 작성 전에 표로 맞춰두는 것이 시간을 가장 크게 아낍니다.
- **시간 배분과 역할 분담을 미리 정합니다.** 데이터 설계 → 인증 → 자원 API → LLM 연동 순으로 진행하면 앞 단계가 막혀 뒤 단계 전체가 밀리는 상황을 줄일 수 있습니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- [ ] 데이터베이스 접속 정보를 확보하고 연결을 확인했다
- [ ] LLM API 키를 발급받아 `.env.local`에 저장했다(코드에는 쓰지 않았다)
- [ ] `node --version`으로 Node 실행 환경을 확인했다
- [ ] 엔드포인트 6~8개를 담은 API 명세 초안을 작성했다
- [ ] 팀원과 역할 분담(설계·인증·자원 API·LLM 연동)을 합의했다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| API 명세 | 어떤 요청에 어떤 응답이 오는지 미리 정해둔 약속 |
| 시드 데이터 | 화면·API 확인용으로 미리 넣어두는 샘플 데이터 |
| 환경변수 | 코드에 직접 적지 않고 실행 환경에 따로 저장해두는 값 |
| 마이그레이션 | 데이터베이스의 표 구조를 코드로 기록하고 적용하는 절차 |
| 엔드포인트 | API가 응답하는 하나의 URL 경로와 메서드 조합 |
| 인가 | 로그인한 사용자가 특정 동작을 할 권한이 있는지 확인하는 것 |
| 미들웨어 | 요청이 실제 처리 함수에 도달하기 전에 거치는 중간 처리 단계 |

<details>
<summary>정답 보기</summary>

프론트엔드 담당자는 백엔드가 아직 완성되지 않아도 합의된 명세를 기준으로 화면 작업을 먼저 진행할 수 있습니다. 반대로 백엔드가 명세와 다른 형식으로 응답을 만들면 나중에 연결할 때 양쪽을 다시 뜯어고쳐야 하므로, 먼저 맞춰두는 쪽이 전체 시간을 아낍니다.

</details>
