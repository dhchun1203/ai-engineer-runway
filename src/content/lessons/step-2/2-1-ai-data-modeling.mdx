## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- AI 서비스에 필요한 테이블을 직접 설계할 수 있다
- 1:N, N:M 관계를 표현하고, N:M 관계를 위한 연결 테이블을 만들 수 있다
- 정규화와 비정규화 중 어느 쪽을 택할지 상황에 맞게 판단할 수 있다
- 인덱스가 왜 필요한지 설명하고, 실제로 만들어 조회 속도를 비교할 수 있다

## 2. 왜 배우나

Step 2 뒤쪽의 AI 쇼핑몰 프로젝트(2-4·2-6)에서 실제로 이 레슨의 테이블 구조를 그대로 만들게 됩니다.

데이터 구조를 잘못 잡으면 화면과 API 코드를 전부 다시 고쳐야 합니다. 앞에서 구조를 제대로 설계해두는 쪽이 나중에 훨씬 적게 고칩니다.

### 🔗 관계 표현 — 1:N과 N:M

1:N(일대다) 관계는 하나가 여러 개를 가질 수 있는 관계입니다. 대화 세션 하나에 메시지가 여러 개 달리는 것이 대표적입니다.

`대화 세션 → 메시지`

N:M(다대다) 관계는 양쪽 모두 여러 개를 가질 수 있는 관계입니다. 상품 하나가 태그 여러 개를 가지고, 태그 하나도 상품 여러 개에 붙을 수 있는 경우가 그렇습니다.

| 관계 종류 | 예시 | 표현 방법 |
|-----------|------|-----------|
| 1:N | 세션 → 메시지 | 메시지 표에 세션을 가리키는 외래키 하나 |
| N:M | 상품 ↔ 태그 | 상품·태그 사이에 연결 테이블(중간 표)을 둔다 |

### 📇 인덱스가 필요한 이유

인덱스(index, 특정 열을 빠르게 찾도록 미리 만들어둔 자료구조)는 책의 찾아보기와 같습니다. 찾아보기가 없으면 책 전체를 처음부터 넘겨야 합니다.

행이 몇 개 안 될 때는 차이가 안 보이지만, 수만 행이 쌓이면 인덱스 없는 조회는 눈에 띄게 느려집니다.

## 5. 실무 팁

- 사용자 입력을 문자열 결합으로 쿼리에 넣지 않습니다 — 파라미터 바인딩 방식을 씁니다.
- 대화 로그처럼 계속 쌓이는 테이블은 처음부터 보관 기간(retention)을 정해둡니다. 무한정 쌓이면 나중에 지우는 작업 자체가 위험한 대규모 작업이 됩니다.
- 개인정보가 들어갈 수 있는 컬럼(예: 사용자 실명, 연락처)은 설계 단계에서 표시해둡니다. Step 3의 LLMOps 레슨에서 이 표시가 다시 쓰입니다.
- 연습이 끝나면(또는 처음부터 다시 하려면) 아래 "실습 되돌리기" 블록을 실행해 `practice` 서랍을 비웁니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 정규화는 중복을 줄이려 표를 나누는 것이고, 비정규화는 조회 속도를 위해 미리 묶어두는 것이다
- 1:N 관계는 외래키 하나로, N:M 관계는 연결 테이블로 표현한다
- AI 서비스에는 대화 세션·메시지 로그, 프롬프트 버전, 임베딩 저장소 같은 테이블이 자주 등장한다
- 인덱스는 특정 열의 조회를 빠르게 하는 자료구조이며, 행이 많아질수록 효과가 커진다
- 개인정보 컬럼은 설계 단계에서 미리 표시해둔다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 정규화 | 중복을 줄이려 데이터를 여러 표로 나누는 것 |
| 외래키 | 다른 표의 기본키를 가리켜 두 표를 연결하는 값 |
| 연결 테이블 | N:M 관계를 표현하기 위해 두 표 사이에 두는 중간 표 |
| 인덱스 | 특정 열을 빠르게 찾도록 미리 만들어둔 자료구조 |
| N:M 관계 | 양쪽 모두 여러 개를 가질 수 있는 관계 |
| 보관 기간 | 로그성 데이터를 얼마나 오래 남겨둘지 정한 기준 |
| 임베딩 | 문장을 숫자 벡터로 바꿔 저장한 것(Step 3에서 다룸) |
