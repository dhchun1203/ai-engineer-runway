## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- AI 서비스에 필요한 테이블을 직접 설계할 수 있다
- 1:N, N:M 관계를 표현하고, N:M 관계를 위한 연결 테이블을 만들 수 있다
- 정규화와 비정규화 중 어느 쪽을 택할지 상황에 맞게 판단할 수 있다
- 인덱스가 왜 필요한지 설명하고, 실제로 만들어 조회 속도를 비교할 수 있다

## 2. 왜 배우나

Step 2 뒤쪽의 AI 쇼핑몰 프로젝트(2-4·2-6)에서 실제로 이 레슨의 테이블 구조를 그대로 만들게 됩니다.

데이터 구조를 잘못 잡으면 화면과 API 코드를 전부 다시 고쳐야 합니다. 앞에서 구조를 제대로 설계해두는 쪽이 나중에 훨씬 적게 고칩니다.

## 3. 개념 설명

### 🗂️ 정규화와 비정규화 — 서랍 정리 비유

정규화(normalization, 중복을 줄이려 데이터를 여러 표로 나누는 것)는 물건을 종류별 서랍에 나눠 넣는 것과 같습니다. 중복이 줄고 수정이 한 곳에서 끝납니다.

비정규화는 자주 같이 쓰는 정보를 한 표에 미리 묶어두는 것입니다. 조회는 빨라지지만, 같은 값이 여러 곳에 중복되어 수정할 때 여러 곳을 함께 고쳐야 합니다.

### 🔗 관계 표현 — 1:N과 N:M

1:N(일대다) 관계는 하나가 여러 개를 가질 수 있는 관계입니다. 대화 세션 하나에 메시지가 여러 개 달리는 것이 대표적입니다.

`대화 세션 → 메시지`

N:M(다대다) 관계는 양쪽 모두 여러 개를 가질 수 있는 관계입니다. 상품 하나가 태그 여러 개를 가지고, 태그 하나도 상품 여러 개에 붙을 수 있는 경우가 그렇습니다.

| 관계 종류 | 예시 | 표현 방법 |
|-----------|------|-----------|
| 1:N | 세션 → 메시지 | 메시지 표에 세션을 가리키는 외래키 하나 |
| N:M | 상품 ↔ 태그 | 상품·태그 사이에 연결 테이블(중간 표)을 둔다 |

### 🤖 AI 서비스에 자주 나오는 테이블 3종

AI 서비스를 만들 때 반복해서 등장하는 테이블 세 종류가 있습니다.

| 종류 | 담는 내용 | 이 레슨에서 |
|------|-----------|-------------|
| 대화 세션·메시지 로그 | 누가 언제 무슨 대화를 나눴는지 | 직접 만들어 실습 |
| 프롬프트 버전 | AI에게 보내는 지시문의 변경 이력 | 이름만 소개 |
| 임베딩 저장소 | 문장을 숫자 벡터로 바꿔 저장한 것 | 이름만 소개, Step 3에서 다룸 |

### 📇 인덱스가 필요한 이유

인덱스(index, 특정 열을 빠르게 찾도록 미리 만들어둔 자료구조)는 책의 찾아보기와 같습니다. 찾아보기가 없으면 책 전체를 처음부터 넘겨야 합니다.

행이 몇 개 안 될 때는 차이가 안 보이지만, 수만 행이 쌓이면 인덱스 없는 조회는 눈에 띄게 느려집니다.

## 4. 실무 예제

**실행: 브라우저의 Supabase SQL 에디터.** 앞 레슨과 마찬가지로 이 모듈은 브라우저에서 전부 실습합니다.

⚠️ 이 레슨의 모든 SQL은 `practice` 스키마 안에서만 실행합니다 — 이 사이트의 진도 데이터가 들어 있는 `public.progress`는 건드리지 않습니다.

```sql
create schema if not exists practice;

create table practice.ai_chat_sessions (
  id serial primary key,
  user_label text not null,
  started_at timestamptz default now()
);

create table practice.ai_messages (
  id serial primary key,
  session_id int not null references practice.ai_chat_sessions(id),
  role text not null,
  content text not null,
  created_at timestamptz default now()
);

create index practice_ai_messages_session_idx on practice.ai_messages(session_id);
```

`ai_messages.session_id`가 `references`로 `ai_chat_sessions(id)`를 가리키는 외래키입니다. 이것이 1:N 관계를 표현하는 방법입니다.

```sql
insert into practice.ai_chat_sessions (user_label) values
  ('상담1'),
  ('상담2');

insert into practice.ai_messages (session_id, role, content) values
  (1, 'user', '배송 언제 오나요?'),
  (1, 'assistant', '내일 도착 예정입니다.'),
  (1, 'user', '감사합니다'),
  (2, 'user', '환불 가능한가요?'),
  (2, 'assistant', '네, 7일 이내 가능합니다.'),
  (2, 'user', '알겠습니다');
```

세션 2개, 각 세션에 메시지 3개씩 총 6개를 넣었습니다.

```sql
select s.user_label as 세션, count(m.id) as 메시지수, max(m.created_at) as 마지막메시지
from practice.ai_chat_sessions s
join practice.ai_messages m on m.session_id = s.id
group by s.user_label
order by s.user_label;
```

세션별로 메시지가 몇 개 쌓였는지, 가장 최근 메시지가 언제인지를 한 번에 계산합니다.

### 해보기

`practice.ai_messages`에 `token_count`(int) 컬럼을 추가하고 전체 메시지에 20을 채운 뒤, 세션별 토큰 합계를 구해보세요.

<details>
<summary>정답 보기</summary>

```sql
alter table practice.ai_messages add column token_count int;

update practice.ai_messages set token_count = 20;

select session_id, sum(token_count) as 토큰합계
from practice.ai_messages
group by session_id;
```

먼저 컬럼을 추가하고 값을 채운 뒤, `group by session_id`로 세션별 합계를 냅니다. 두 세션 모두 메시지 3개씩이라 합계는 각각 60이 나옵니다.

</details>

### 해보기

메시지에 태그(예: "배송 문의", "환불 문의")를 여러 개 붙일 수 있게 `practice.tags`와 연결 테이블 `practice.message_tags`를 만들어보세요.

<details>
<summary>정답 보기</summary>

```sql
create table practice.tags (
  id serial primary key,
  name text not null
);

create table practice.message_tags (
  message_id int not null references practice.ai_messages(id),
  tag_id int not null references practice.tags(id),
  primary key (message_id, tag_id)
);
```

메시지 하나가 태그 여러 개를, 태그 하나가 메시지 여러 개를 가질 수 있는 N:M 관계라 중간에 연결 테이블을 하나 더 둡니다. 연결 테이블의 기본키는 두 외래키를 합친 것입니다.

</details>

### 해보기

`role` 컬럼에 인덱스를 만들기 전후로 `explain` 결과가 어떻게 달라지는지 비교해보세요.

<details>
<summary>정답 보기</summary>

```sql
explain select * from practice.ai_messages where role = 'user';

create index practice_ai_messages_role_idx on practice.ai_messages(role);

explain select * from practice.ai_messages where role = 'user';
```

인덱스를 만들기 전에는 `Seq Scan`(표 전체를 순서대로 훑음)이 나오고, 만든 뒤에는 `Index Scan`(인덱스로 바로 찾아감)이 나옵니다. 지금처럼 행이 몇 개뿐일 땐 체감 차이가 작지만 원리는 같습니다.

</details>

## 5. 실무 팁

- 사용자 입력을 문자열 결합으로 쿼리에 넣지 않습니다 — 파라미터 바인딩 방식을 씁니다.
- 대화 로그처럼 계속 쌓이는 테이블은 처음부터 보관 기간(retention)을 정해둡니다. 무한정 쌓이면 나중에 지우는 작업 자체가 위험한 대규모 작업이 됩니다.
- 개인정보가 들어갈 수 있는 컬럼(예: 사용자 실명, 연락처)은 설계 단계에서 표시해둡니다. Step 3의 LLMOps 레슨에서 이 표시가 다시 쓰입니다.
- 연습이 끝나면 아래 정리 SQL로 `practice` 서랍을 비워둡니다.

```sql
drop schema if exists practice cascade;
```

이 문장은 `practice` 스키마만 대상으로 하므로 사이트 진도 데이터에는 아무 영향이 없습니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 정규화는 중복을 줄이려 표를 나누는 것이고, 비정규화는 조회 속도를 위해 미리 묶어두는 것이다
- 1:N 관계는 외래키 하나로, N:M 관계는 연결 테이블로 표현한다
- AI 서비스에는 대화 세션·메시지 로그, 프롬프트 버전, 임베딩 저장소 같은 테이블이 자주 등장한다
- 인덱스는 특정 열의 조회를 빠르게 하는 자료구조이며, 행이 많아질수록 효과가 커진다
- 개인정보 컬럼은 설계 단계에서 미리 표시해둔다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 정규화 | 중복을 줄이려 데이터를 여러 표로 나누는 것 |
| 외래키 | 다른 표의 기본키를 가리켜 두 표를 연결하는 값 |
| 연결 테이블 | N:M 관계를 표현하기 위해 두 표 사이에 두는 중간 표 |
| 인덱스 | 특정 열을 빠르게 찾도록 미리 만들어둔 자료구조 |
| N:M 관계 | 양쪽 모두 여러 개를 가질 수 있는 관계 |
| 보관 기간 | 로그성 데이터를 얼마나 오래 남겨둘지 정한 기준 |
| 임베딩 | 문장을 숫자 벡터로 바꿔 저장한 것(Step 3에서 다룸) |

**스스로 점검**

1. 메시지 표에 `session_id`를 외래키로 넣지 않고, 세션 정보를 메시지마다 통째로 복사해서 넣으면 어떤 문제가 생길까요?

<details>
<summary>정답 보기</summary>

세션 이름이 바뀌면 그 세션에 속한 메시지 전부를 찾아 하나하나 고쳐야 합니다. 외래키로 세션을 가리키기만 했다면 세션 표 한 줄만 고치면 끝납니다.

이것이 정규화가 중복을 줄여주는 이유입니다 — 같은 정보를 여러 곳에 복사해두지 않고 한 곳만 고치면 되게 만듭니다.

</details>

2. 상품과 태그처럼 양쪽 모두 여러 개를 가질 수 있는 관계에서 왜 연결 테이블이 필요할까요?

<details>
<summary>정답 보기</summary>

상품 표에 태그를 직접 넣으려면 한 칸에 여러 값을 넣어야 하는데, 관계형 데이터베이스의 한 칸은 값 하나만 담도록 되어 있습니다.

대신 "이 상품과 이 태그가 연결됐다"는 한 줄 한 줄을 연결 테이블에 저장하면, 상품 하나가 태그 여러 개를, 태그 하나가 상품 여러 개를 갖는 관계를 자연스럽게 표현할 수 있습니다.

</details>
