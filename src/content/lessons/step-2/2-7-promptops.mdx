## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 프롬프트에 버전을 붙여 파일로 관리할 수 있다
- 기준 예시 묶음(골든셋)으로 프롬프트를 자동 평가할 수 있다
- 프롬프트를 바꿨을 때 무엇이 나빠졌는지 회귀 결과로 찾아낼 수 있다
- API 키 없이도 평가 실습을 끝까지 실행할 수 있다

## 2. 왜 배우나

프롬프트를 고칠 때마다 "좋아진 것 같다"는 감으로만 판단하면 어느 순간 조용히 나빠집니다. 어제는 되던 케이스가 오늘 손본 뒤 깨져도 눈치채지 못할 수 있습니다.

팀 프로젝트에서는 누가 언제 무엇을 바꿨는지 추적되지 않으면 문제가 생겼을 때 원인을 찾기 어렵습니다. 앞 레슨(`2-7-prompt-patterns`)에서 만든 프롬프트를 이번에는 "관리 대상"으로 승격시켜 봅니다.

## 3. 개념 설명

### 📁 프롬프트를 코드처럼 다루기

요리 레시피를 머릿속으로만 기억하지 않고 노트에 적어 판마다 번호를 매기는 것과 같습니다. 프롬프트도 파일로 분리해서 저장소에 두고, 바뀔 때마다 버전을 매기고 리뷰를 거칩니다.

머릿속에만 있던 프롬프트를 파일로 꺼내면 "이전 버전에서 뭐가 바뀌었는지"를 diff로 비교할 수 있게 됩니다. 이것이 프롬프트 관리의 첫걸음입니다.

### 🎯 골든셋과 회귀 확인

골든셋은 정답이 정해진 입력·기대 출력 목록입니다. 프롬프트를 바꿀 때마다 이 목록을 다시 돌려 예전에는 통과하던 케이스가 이번에도 통과하는지 확인합니다.

통과하던 케이스가 갑자기 실패하면 그것이 바로 회귀(regression)입니다. 골든셋이 없으면 회귀를 사람이 우연히 발견할 때까지 아무도 모릅니다.

### 📊 평가 지표의 종류

자동으로 잴 수 있는 것과 아닌 것을 구분해야 합니다. 형식 통과율(JSON이 스키마를 지켰는가), 필수 키워드 포함 여부, 길이 제약은 코드로 자동 채점할 수 있습니다.

반면 "문구가 자연스러운가"처럼 톤이나 뉘앙스는 사람이 봐야 합니다. 실무에서는 자동 채점으로 큰 문제를 먼저 걸러내고, 남은 것만 사람이 확인하는 방식을 씁니다.

### ⏱️ 운영 지표도 처음부터 함께 본다

프롬프트가 잘 작동해도 비용이 너무 크거나 응답이 느리면 서비스에서 쓸 수 없습니다. 비용·지연·성공률 같은 운영 지표는 나중에 붙이지 않고 평가 스크립트를 만들 때부터 같이 잽니다.

구성은 네 조각으로 나눠서 봅니다.

**① `prompts/product-copy.v1.md`** — 프롬프트 원문을 파일로 분리합니다. 파일로 두면 버전 비교와 리뷰가 코드 리뷰와 똑같은 절차로 가능해집니다.

```text
당신은 이커머스 카피라이터입니다.
아래 상품 정보로 홍보 문구를 만드세요.
반드시 JSON 형식으로만 답하세요: { title, tagline, hashtags(3개) }
```

**② `prompts/registry.ts`** — 버전 문자열을 키로 프롬프트 파일 내용을 불러오는 작은 맵과 현재 활성 버전 상수입니다.

```typescript
// prompts/registry.ts
import { readFileSync } from "node:fs";
import path from "node:path";

const PROMPT_DIR = path.join(process.cwd(), "prompts");

// 버전 문자열 → 프롬프트 파일 경로
const PROMPT_FILES: Record<string, string> = {
  v1: "product-copy.v1.md",
};

export const ACTIVE_VERSION = "v1";

export function loadPrompt(version: string): string {
  const fileName = PROMPT_FILES[version];
  if (!fileName) {
    throw new Error(`등록되지 않은 프롬프트 버전입니다: ${version}`);
  }
  return readFileSync(path.join(PROMPT_DIR, fileName), "utf-8");
}
```

**④ `eval.ts`** — 골든셋을 순회하며 프롬프트를 조립하고 모의 호출 함수 `callModel`로 응답을 받아 검증합니다.

```typescript
// eval.ts
import { z } from "zod";
import { loadPrompt, ACTIVE_VERSION } from "./prompts/registry";
import golden from "./golden.json";

const ProductCopySchema = z.object({
  title: z.string(),
  tagline: z.string(),
  hashtags: z.array(z.string()).length(3),
});

interface GoldenCase {
  input: string;
  expectHashtags: number;
  maxTitleLength: number;
  bannedWords: string[];
}

// callModel은 기본적으로 결정적인 모의 응답을 돌려준다 — 키가 없어도 실습이 끝까지 돈다.
// process.env.ANTHROPIC_API_KEY가 있으면 아래 분기를 실제 SDK 호출로 바꿀 수 있다.
async function callModel(prompt: string, input: string): Promise<string> {
  if (process.env.ANTHROPIC_API_KEY) {
    // 실제 호출 분기 — 이 실습에서는 다루지 않는다. 필요하면
    // 2-7-prompt-patterns의 client.messages.create 패턴을 여기에 연결한다.
  }
  return JSON.stringify({
    title: `${input} 추천`,
    tagline: `${input}로 하루를 더 편하게`,
    hashtags: [input.slice(0, 4), "추천템", "필수템"],
  });
}

async function runEval() {
  const prompt = loadPrompt(ACTIVE_VERSION);
  const cases = golden as GoldenCase[];
  let passCount = 0;
  const failures: string[] = [];

  for (const testCase of cases) {
    const raw = await callModel(prompt, testCase.input);
    const parsed = ProductCopySchema.safeParse(JSON.parse(raw));

    if (!parsed.success) {
      failures.push(`${testCase.input}: 스키마 검증 실패`);
      continue;
    }

    const { title, hashtags } = parsed.data;
    const hasBannedWord = testCase.bannedWords.some((word) => title.includes(word));
    const titleTooLong = title.length > testCase.maxTitleLength;

    if (hasBannedWord || titleTooLong || hashtags.length !== testCase.expectHashtags) {
      failures.push(`${testCase.input}: 조건 위반 (금지어=${hasBannedWord}, 길이초과=${titleTooLong})`);
      continue;
    }

    passCount += 1;
  }

  console.log(`통과 ${passCount} / 실패 ${failures.length}`);
  failures.forEach((f) => console.log(`  - ${f}`));
}

runEval();
```

`callModel`의 모의 응답은 여전히 해시태그 3개만 돌려주므로, v2로 바꿔도 `eval.ts`의 결과 자체는 똑같습니다 — "모의 응답은 실제 모델 행동을 대신할 수 없다"는 한계를 확인하게 됩니다.

실제 모델을 붙이면 v2에서는 해시태그 개수가 달라질 가능성이 있습니다.

</details>

### 해보기

`golden.json`에 실패 사례를 하나 추가해보세요. `maxTitleLength`를 5처럼 아주 짧게 설정한 케이스를 추가해 회귀가 실제로 잡히는지 확인합니다.

<details>
<summary>정답 보기</summary>

```json
{ "input": "게이밍 마우스", "expectHashtags": 3, "maxTitleLength": 5, "bannedWords": ["최고", "완벽"] }
```

`callModel`의 모의 응답 제목은 5자를 넘으므로 `titleTooLong`이 `true`가 되어 이 케이스가 실패 목록에 추가됩니다.

콘솔에 "조건 위반 (길이초과=true)"가 찍히는 것으로 회귀 감지가 실제로 동작함을 확인할 수 있습니다.

</details>

<details>

const elapsedMs = Date.now() - start;

각 반복에서 `elapsedMs`를 배열에 모아두고 루프가 끝난 뒤 평균을 계산해 출력하면 됩니다.

모의 호출은 거의 0ms에 가깝지만, 실제 모델을 붙이면 이 지표가 진짜 의미를 가지기 시작합니다 — 비용·지연은 프롬프트 품질과 별개로 항상 함께 관리해야 하는 값입니다.

</details>

## 5. 실무 팁

- 프롬프트 변경은 코드 변경과 같은 절차(리뷰·기록)를 거칩니다. "그냥 슬쩍 고쳐본다"는 습관이 회귀의 가장 흔한 원인입니다.
- 골든셋은 이상적인 케이스가 아니라 실제로 문제가 났던 입력부터 채웁니다. 과거에 실패했던 사례가 가장 값진 테스트 케이스입니다.
- 비용·지연을 나중에 붙이면 이미 늦습니다. 평가 스크립트를 처음 만들 때부터 함께 측정합니다.
- 카나리 배포·모니터링·거버넌스는 이 레슨의 범위를 넘습니다. Step 3의 3-6 모듈이 개념으로 다시 짚어줍니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 프롬프트를 파일로 분리하고 버전을 매기면 무엇이 바뀌었는지 추적할 수 있다
- 골든셋으로 회귀를 자동으로 잡아낼 수 있다
- 형식 통과율 같은 지표는 자동 채점, 톤 같은 지표는 사람이 확인한다
- 비용·지연 같은 운영 지표는 프롬프트 품질과 별개로 처음부터 함께 잰다
- 평가 실습은 API 키 없이도 모의 호출만으로 끝까지 실행할 수 있다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 골든셋 | 정답이 정해진 입력·기대 출력 목록 |
| 회귀 | 이전에는 통과하던 케이스가 갑자기 실패하는 것 |
| 버전 태그 | 프롬프트 파일에 매기는 버전 식별자 |
| 형식 통과율 | 응답이 스키마를 지킨 비율 |
| 지연(latency) | 요청부터 응답까지 걸리는 시간 |
| 토큰 비용 | 모델 호출에 드는 비용, 토큰 사용량으로 계산됨 |
| 롤백 | 문제가 생긴 버전을 이전 버전으로 되돌리는 것 |

**스스로 점검**

1. 골든셋에 실패 사례부터 채우라고 하는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

이상적으로 상상한 케이스는 실제 서비스에서 벌어지는 문제를 재현하지 못할 가능성이 높습니다. 반면 과거에 실제로 실패했던 입력은 이 프롬프트가 다시 그 문제를 일으키지 않는지 정확히 확인해줍니다.

그래서 회귀를 잡아내는 힘이 가장 큽니다.

</details>

2. 이 레슨의 평가 실습이 `callModel`을 모의 함수로 만든 이유를 설명해보세요.

<details>
<summary>정답 보기</summary>

실습 완주가 API 키 보유 여부에 걸려서는 안 되기 때문입니다. 모의 함수는 결정적인 응답을 돌려주므로 키가 없는 학습자도 골든셋 평가·회귀 확인·지연 측정까지 전체 흐름을 끝까지 경험할 수 있습니다.

`process.env.ANTHROPIC_API_KEY`가 있을 때 실제 호출로 바꾸는 분기 지점만 주석으로 남겨, 나중에 실제 서비스로 확장할 때 이어붙일 자리를 표시해둡니다.

</details>
