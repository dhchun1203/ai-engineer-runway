## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 데이터(자원)를 기준으로 API 엔드포인트를 설계할 수 있다
- Express로 라우터와 미들웨어를 붙여 서버를 구성할 수 있다
- `zod`로 요청 본문을 검증하고 실패 시 적절한 오류를 돌려줄 수 있다
- 상황에 맞는 HTTP 상태 코드를 올바르게 반환할 수 있다

## 2. 왜 배우나

2-2·2-3에서 만든 화면은 지금까지 화면 안의 값만 다뤘습니다. 이 값을 실제로 어디서 가져오고 어디에 저장하는지는 이 레슨에서 정해집니다.

Express로 만든 서버가 바로 그 데이터를 주고받는 창구입니다. 2-6 프로젝트(AI 쇼핑몰 백엔드)도 이 레슨에서 만드는 구조를 그대로 확장한 것입니다.

## 3. 개념 설명

### 🏪 서버는 주문 창구

서버(server)는 매장의 주문 창구와 비슷합니다. 손님(클라이언트)이 주문서(요청)를 내밀면, 창구 직원이 확인하고 물건이나 답변(응답)을 돌려줍니다.

Express는 이 창구를 코드로 쉽게 만들게 해주는 라이브러리입니다. "어떤 주소로 어떤 요청이 오면 무엇을 돌려줄지"를 함수 하나로 정의합니다.

### 📋 HTTP 메서드와 상태 코드

요청에는 목적을 나타내는 메서드(method)가 붙습니다. 응답에는 결과를 나타내는 상태 코드(status code)가 붙습니다.

| 메서드 | 뜻 | 자주 쓰는 상태 코드 |
|--------|-----|----------------------|
| GET | 조회 | 200(성공), 404(없음) |
| POST | 생성 | 201(생성됨), 400(잘못된 요청) |
| PUT | 전체 수정 | 200, 404 |
| PATCH | 일부 수정 | 200, 404 |
| DELETE | 삭제 | 200, 404 |

서버 오류가 나면 500을 돌려줍니다. 인증이 없으면 401, 권한이 없으면 403을 씁니다.

### 🔤 자원은 명사로, 행동은 메서드가 맡는다

REST(자원 중심 설계 방식)의 핵심 규칙은 "URL은 명사, 행동은 메서드"입니다. `/products` 주소 하나에 GET·POST를 각각 붙이면 조회와 생성이 됩니다.

`/getProducts`, `/createProduct`처럼 URL에 동사를 넣지 않습니다. 메서드가 이미 동사 역할을 하기 때문입니다.

### 🚪 미들웨어는 문 앞의 직원들

미들웨어(middleware)는 요청이 최종 처리 함수(핸들러)에 닿기 전 순서대로 거치는 함수입니다. 손님이 매장에 들어올 때 안내·확인·번호표 발급을 차례로 거치는 것과 같습니다.

로그 남기기, CORS 허용, 요청 본문을 객체로 바꾸는 파싱이 대표적인 미들웨어입니다. 요청의 전체 흐름은 아래와 같습니다.

`요청 → 미들웨어(로그·CORS·본문 파싱) → 라우터 → 핸들러 → 응답`

## 4. 실무 예제

**실행: PC 로컬 VS Code.** 아래 명령과 코드는 로컬 Node 프로젝트 폴더에서 그대로 따라 하면 동작합니다. Node가 아직 없다면 `2-3-typescript-setup` 레슨을 먼저 보고 오세요.

```powershell
npm init -y
npm install express@^5 zod cors
npm install -D typescript tsx @types/node @types/express @types/cors
```

`src/server.ts` 파일을 만들고 아래 코드를 그대로 붙여 넣습니다. 상품 목록을 메모리 배열로 관리하는 최소 API입니다.

```typescript
// src/server.ts
import express from "express";
import cors from "cors";
import { z } from "zod";

const app = express();
app.use(cors());
app.use(express.json());

// 메모리 배열 — 서버를 껐다 켜면 사라진다. 저장은 다음 레슨(Prisma)이 맡는다.
type Product = { id: number; name: string; category: string; price: number };
const products: Product[] = [
  { id: 1, name: "무선 이어폰", category: "전자기기", price: 89000 },
  { id: 2, name: "머그컵", category: "생활용품", price: 12000 },
  { id: 3, name: "노트북 파우치", category: "전자기기", price: 25000 },
  { id: 4, name: "손목시계", category: "패션", price: 150000 },
  { id: 5, name: "텀블러", category: "생활용품", price: 18000 },
];

const productInputSchema = z.object({
  name: z.string().min(1),
  category: z.string().min(1),
  price: z.number().positive(),
});

app.get("/products", (req, res) => {
  const { category } = req.query;
  const result = category
    ? products.filter((p) => p.category === category)
    : products;
  res.status(200).json(result);
});

app.get("/products/:id", (req, res) => {
  const product = products.find((p) => p.id === Number(req.params.id));
  if (!product) {
    res.status(404).json({ error: "상품을 찾을 수 없습니다" });
    return;
  }
  res.status(200).json(product);
});

app.post("/products", (req, res) => {
  const parsed = productInputSchema.safeParse(req.body);
  if (!parsed.success) {
    res.status(400).json({ error: parsed.error.issues });
    return;
  }
  const newProduct: Product = { id: products.length + 1, ...parsed.data };
  products.push(newProduct);
  res.status(201).json(newProduct);
});

const port = process.env.PORT ?? 3000;
app.listen(port, () => {
  console.log(`서버 실행 중: http://localhost:${port}`);
});
```

app.delete("/products/:id", (req, res) => {
  const index = products.findIndex((p) => p.id === Number(req.params.id));

요청 처리 시간을 재서 콘솔에 남기는 미들웨어를 하나 추가해 보세요. 각 요청이 몇 밀리초 걸렸는지 로그로 확인합니다.

<details>
<summary>정답 보기</summary>

```typescript
app.use((req, res, next) => {
  const start = Date.now();
  res.on("finish", () => {
    console.log(`${req.method} ${req.path} - ${Date.now() - start}ms`);

  next();
});
```

이 미들웨어를 `app.use(express.json())` 바로 다음 줄에 추가하면 이후 모든 라우터 호출에 적용됩니다. `res.on("finish", ...)`는 응답이 실제로 나간 시점을 알려줍니다.

## 5. 실무 팁

- **검증 로직을 라우터 안에 흩뿌리지 않습니다.** `zod` 스키마 하나에 모아두면 나중에 규칙이 바뀔 때 한 곳만 고치면 됩니다.
- **오류 응답 형식을 처음부터 하나로 정합니다.** `{ error: ... }` 같은 일관된 모양을 정해두면 프론트엔드가 오류 처리를 매번 다시 짜지 않아도 됩니다.
- **포트나 비밀 값은 코드에 직접 적지 않고 환경변수로 읽습니다.** 지금은 `PORT` 하나뿐이지만, 다음 레슨의 시크릿·접속 정보도 같은 원칙을 따릅니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- REST API는 URL을 명사(자원)로, 행동은 HTTP 메서드로 표현한다
- 미들웨어는 요청이 핸들러에 닿기 전 순서대로 거치는 처리 단계다
- `zod`로 요청 본문을 검증하면 잘못된 데이터가 서버 로직까지 들어오지 않는다
- 상태 코드는 결과를 정확히 표현해야 클라이언트가 성공·실패를 구분할 수 있다
- 메모리 배열은 서버를 재시작하면 사라진다 — 영구 저장은 다음 레슨(Prisma)이 담당한다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 엔드포인트 | URL과 메서드로 정해지는 API 호출 지점 |
| 미들웨어 | 요청이 핸들러에 닿기 전 거치는 처리 함수 |
| 상태 코드 | 응답의 성공·실패를 숫자로 나타낸 값 |
| 라우터 | 특정 URL 패턴에 대한 처리 함수를 등록하는 장치 |
| 직렬화 | 객체를 JSON 문자열로 바꿔 응답으로 보내는 과정 |
| CORS | 다른 출처의 브라우저 요청을 허용하는 설정 |
| 스키마 검증 | 데이터가 정해진 형태를 따르는지 확인하는 절차 |

**스스로 점검**

1. `POST /products`에서 `zod` 검증을 라우터 함수 안에서 직접 `if`문으로 하지 않고 스키마 객체로 분리한 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

검증 규칙이 여러 라우터에서 반복되거나 바뀔 때, `if`문으로 흩어져 있으면 모든 곳을 찾아 고쳐야 합니다. 스키마 객체 하나로 모아두면 규칙 변경이 한 곳에서 끝나고, 같은 스키마를 다른 라우터에서도 재사용할 수 있습니다.

</details>

2. `GET /products/:id`에서 존재하지 않는 id를 요청했을 때 200과 빈 응답을 돌려주지 않고 404를 돌려주는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

200은 "요청이 정상적으로 처리되어 원하는 자원을 찾았다"는 뜻입니다. 자원이 없는데 200을 돌려주면 클라이언트는 응답 본문을 직접 열어봐야만 실패를 알 수 있습니다. 404로 명확히 알려주면 클라이언트가 상태 코드만 보고도 존재하지 않음을 바로 처리할 수 있습니다.

</details>
