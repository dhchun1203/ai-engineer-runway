## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 주소창에 URL을 입력한 뒤 화면이 뜨기까지의 단계를 설명할 수 있다
- 개발자도구(DevTools)로 그 단계를 직접 관찰할 수 있다
- 동기 코드와 비동기 코드가 화면을 각각 언제 바꾸는지 예측할 수 있다
- 이벤트 루프와 `Promise`/`async`·`await`가 어떻게 맞물려 동작하는지 설명할 수 있다

## 2. 왜 배우나

화면이 느리거나 안 뜰 때 "왜 그런지 모른 채 고치는" 상태에서 벗어나는 것이 이 레슨의 목표입니다.

2-4 프로젝트에서 LLM 응답을 기다리는 동안 화면을 어떻게 다뤄야 하는지도 여기서 배운 비동기 원리가 그대로 쓰입니다.

## 3. 개념 설명

### 🌐 주소 입력부터 화면까지

주소 입력 → DNS 조회 → HTTP 요청 → HTML 응답 → 파싱(DOM·CSSOM) → 렌더 트리 → 레이아웃 → 페인트

각 단계가 정확히 무슨 일을 하는지는 아래 표로 정리했습니다.

| 단계 | 하는 일 |
|------|--------|
| DNS 조회 | 도메인 이름을 서버의 실제 주소(IP)로 바꾼다 |
| HTTP 요청 | 그 주소로 "이 페이지를 주세요"라고 요청을 보낸다 |
| HTML 응답 | 서버가 HTML 문서를 돌려준다 |
| 파싱 | 브라우저가 HTML을 DOM으로, CSS를 CSSOM으로 해석한다 |
| 렌더 트리 | DOM과 CSSOM을 합쳐 화면에 보일 것만 추린 트리를 만든다 |
| 레이아웃 | 각 요소가 화면 어디에 얼마나 크게 놓일지 계산한다 |
| 페인트 | 계산된 위치에 실제 픽셀을 그린다 |

### 🍽️ 이벤트 루프와 비동기

JavaScript는 한 번에 한 가지 일만 처리합니다. 카운터 직원이 한 손님을 응대하는 동안 다른 손님은 잠시 기다리는 것과 같습니다.

시간이 걸리는 일(서버 응답 기다리기, 타이머)을 만나면 그 일을 옆으로 미뤄두고 다음 코드를 먼저 처리합니다. 미뤄둔 일이 끝나면 다시 돌아와 처리하는데, 이 순서를 관리하는 것이 이벤트 루프(event loop)입니다.

`Promise`는 "나중에 끝날 일의 약속표"이고, `async`/`await`는 그 약속표를 순서대로 진행되는 코드처럼 읽히게 해주는 문법입니다.

### 🎨 재계산과 다시 그리기

요소의 크기나 위치가 바뀌면 브라우저는 레이아웃을 다시 계산합니다. 이를 리플로우(reflow)라고 부릅니다.

색이나 그림자처럼 위치에 영향을 주지 않는 변화는 리플로우 없이 다시 그리기(repaint)만 일어납니다. 리플로우가 다시 그리기보다 비용이 훨씬 크므로, 반복문 안에서 요소를 계속 건드리면 화면이 느려집니다.

## 4. 실무 예제

**실행: PC 로컬 VS Code, 설치는 필요 없습니다.** 아래 코드를 `shop-list.html` 파일 하나에 그대로 저장하면 예제가 완성됩니다.

```html
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <title>상품 목록</title>
  </head>
  <body>
    <button id="loadButton">불러오기</button>
    <p id="status"></p>
    <ul id="productList"></ul>
    <script>
      const products = [
        { name: "무선 이어폰", price: 59000 },
        { name: "머그컵", price: 12000 },
        { name: "노트북 파우치", price: 25000 },
        { name: "블루투스 스피커", price: 45000 },
        { name: "휴대용 충전기", price: 18000 },
        { name: "키보드", price: 89000 },
      ];

      function delay(ms) {
        return new Promise((resolve) => setTimeout(resolve, ms));
      }

      async function loadProducts() {
        const status = document.querySelector("#status");
        const list = document.querySelector("#productList");
        status.textContent = "불러오는 중...";
        await delay(800);
        status.textContent = "";
        for (const product of products) {
          const item = document.createElement("li");
          item.textContent = `${product.name} — ${product.price}원`;
          list.appendChild(item);
        }
      }

      document.querySelector("#loadButton").addEventListener("click", loadProducts);
    </script>
  </body>
</html>
```

상품 데이터는 파일 안 상수 배열이고, 외부 서버를 호출하지 않습니다. 대신 `setTimeout`으로 만든 `delay` 함수가 "응답을 기다리는 시간"을 흉내 냅니다.

`async`/`await` 부분만 따로 보면, 로딩 문구를 먼저 보여준 뒤 지연이 끝나면 목록을 그리는 순서를 한 줄씩 읽듯이 따라갈 수 있습니다.

```javascript
async function loadProducts() {
  const status = document.querySelector("#status");
  status.textContent = "불러오는 중...";
  await delay(800);
  status.textContent = "";
  // 여기서부터 목록을 하나씩 화면에 그립니다
}
```

버튼을 누른 뒤 개발자도구에서 세 가지를 관찰해보세요. Elements 탭에서 `<li>`가 실제로 늘어나는 것, Network 탭에서 문서 요청 하나만 있고 별도 API 호출이 없는 것, Console에서 코드가 실행되는 순서입니다.

저장한 뒤 `shop-list.html` 파일을 더블클릭하면 기본 브라우저에서 바로 열립니다. 명령으로 열고 싶다면 아래처럼 실행합니다.

```powershell
start shop-list.html
```

macOS에서는 터미널에서 `open shop-list.html`을 실행하면 같은 방식으로 열립니다.

지금 코드는 반복문 안에서 `appendChild`를 매번 호출해 `<li>`를 하나씩 붙입니다. `DocumentFragment`에 먼저 모아뒀다가 한 번에 붙이도록 고쳐서 개발자도구 Performance 탭에서 차이를 관찰해보세요.

<details>
<summary>정답 보기</summary>

```javascript
const fragment = document.createDocumentFragment();
for (const product of products) {
  const item = document.createElement("li");
  item.textContent = `${product.name} — ${product.price}원`;
  fragment.appendChild(item);
}
list.appendChild(fragment);
```

반복문 안에서 매번 `list.appendChild`를 부르면 그때마다 브라우저가 화면 갱신을 시도할 수 있습니다. `DocumentFragment`에 모아뒀다가 마지막에 한 번만 붙이면 갱신이 한 번으로 줄어듭니다.

</details>

<details>
<summary>정답 보기</summary>

`head`로 옮기면 브라우저가 스크립트를 실행하는 시점에 아직 `<button id="loadButton">`이 파싱되지 않았습니다. `document.querySelector("#loadButton")`이 `null`을 돌려줍니다.

그 뒤에 `.addEventListener`를 부르는 순간 오류가 발생합니다. `defer` 속성을 붙이거나 스크립트를 `body` 끝에 두면 이 문제가 생기지 않습니다.

</details>

## 5. 실무 팁

- **스크립트는 `body` 끝이나 `defer`로 둡니다.** `head`에 그냥 두면 아직 존재하지 않는 요소를 찾다가 오류가 나기 쉽습니다.
- **DOM을 반복문 안에서 매번 건드리면 느려집니다.** 여러 번 나눠 갱신하는 대신 한 번에 모아서 반영하는 것이 유리합니다.
- **개발자도구의 네트워크 속도 제한(throttling)으로 느린 환경을 흉내 낼 수 있습니다.** 실제 사용자가 겪는 로딩 화면을 미리 확인하는 데 유용합니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 주소 입력부터 화면까지는 DNS 조회 → HTTP 요청 → 파싱 → 렌더 트리 → 레이아웃 → 페인트 순서로 진행된다
- 파싱 중 만난 동기 `<script>`는 렌더링을 막으므로 `defer`나 `body` 끝 배치로 피한다
- 이벤트 루프가 시간이 걸리는 일을 미뤄두고 다음 코드를 먼저 처리한다
- `Promise`와 `async`/`await`는 비동기 코드를 순서대로 읽히게 해주는 문법이다
- 위치를 바꾸는 리플로우가 색만 바꾸는 리페인트보다 비용이 크다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 렌더 트리(render tree) | DOM과 CSSOM을 합쳐 화면에 보일 것만 추린 트리 |
| 파싱(parsing) | HTML·CSS 문서를 브라우저가 해석 가능한 구조로 바꾸는 과정 |
| 이벤트 루프(event loop) | 미뤄둔 작업을 순서대로 다시 꺼내 처리하는 관리자 |
| 비동기(asynchronous) | 결과를 기다리는 동안 다른 코드를 먼저 실행하는 방식 |
| 프로미스(Promise) | 나중에 끝날 일의 결과를 담게 될 약속표 |
| 리플로우(reflow) | 레이아웃을 다시 계산하는 것, 비용이 크다 |
| 개발자도구(DevTools) | 브라우저 안에서 화면·네트워크·콘솔을 관찰하는 도구 |
