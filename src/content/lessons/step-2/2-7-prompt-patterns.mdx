## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 프롬프트를 역할·지시·예시·제약 네 부분으로 나눠 쓸 수 있다
- LLM 응답을 정해진 JSON 형식으로 받아내도록 요청을 설계할 수 있다
- 응답이 형식을 어겼을 때 코드가 이를 감지하고 재시도하도록 만들 수 있다
- API 키를 환경변수로만 다루고 실제 서비스 코드에 안전하게 배치할 수 있다

## 2. 왜 배우나

"잘 되는 것 같은데 가끔 이상한 답이 온다"는 LLM 서비스에서 가장 흔하고 가장 치명적인 문제입니다. 화면에 그대로 붙일 텍스트인데 형식이 흔들리면 그 화면이 깨집니다.

2-4·2-6 프로젝트에서는 LLM 응답을 상품 카드나 채팅 말풍선에 그대로 렌더링합니다. 응답 형식이 예측 가능하지 않으면 프론트엔드 코드는 항상 방어 코드로 뒤덮이게 됩니다.

이 레슨에서는 프롬프트를 구조적으로 설계하고, 응답을 스키마로 검증하는 습관을 만듭니다. 이 습관이 실무에서 LLM을 안정적으로 쓰는 첫 번째 조건입니다.

## 3. 개념 설명

### 🧩 프롬프트의 네 부분

프롬프트는 신입 사원에게 일을 시킬 때 주는 안내문과 같습니다. "당신은 카피라이터입니다"(역할), "홍보 문구를 만드세요"(지시), "이런 형식으로"(예시), "해시태그는 3개까지"(제약) 네 조각으로 나눠서 씁니다.

네 조각을 뒤섞어 한 문장으로 몰아 쓰면 모델이 어느 것이 진짜 규칙인지 헷갈립니다. 조각을 나눠 쓰면 나중에 한 조각만 바꿔서 결과를 조정하기도 쉬워집니다.

### 🎯 예시 제공(few-shot)

예시 제공은 원하는 답을 몇 개 미리 보여주고 "이런 식으로"라고 맡기는 방법입니다. 말로 설명하기 어려운 톤이나 형식은 규칙을 나열하는 것보다 예시 두세 개를 보여주는 쪽이 훨씬 정확합니다.

반대로 결과가 이미 안정적이라면 예시 없이도 충분합니다. 예시는 프롬프트를 길게 만들므로 필요한 만큼만 추가합니다.

### 📐 구조화 출력(structured output)

구조화 출력은 모델의 답을 자연어 문장이 아니라 정해진 틀(JSON 등)로 받는 것입니다. "JSON으로 답해주세요"라고 부탁만 하고 나중에 텍스트를 파싱하는 방식은 위험합니다 — 모델이 설명을 덧붙이면 파싱이 그 자리에서 깨집니다.

더 안전한 방법은 스키마(zod 같은 도구로 필드 형식을 미리 정의한 것)로 응답을 강제로 검사하는 것입니다. 파싱이 아니라 검증이 핵심입니다.

### 🔁 검증 실패 시의 선택지

스키마 검증에 실패했다는 것은 모델이 약속을 어겼다는 뜻입니다. 이때 선택지는 세 가지입니다 — 같은 요청을 한 번 더 보내 재시도하기, 미리 정해둔 기본값으로 대체하기, 사람에게 확인을 넘기기입니다.

이 레슨의 예제는 재시도를 씁니다. 전체 흐름은 다음과 같습니다.

```text
요청 조립 → 모델 호출 → 스키마 검증 → 통과하면 사용 / 실패하면 재시도
```

## 4. 실무 예제

**실행: PC 로컬 VS Code.** 아래 명령으로 필요한 패키지를 설치합니다. Node가 아직 없다면 `2-3-typescript-setup` 레슨을 먼저 확인하세요.

```powershell
npm install @anthropic-ai/sdk zod dotenv
npm install -D typescript tsx @types/node
```

`.env` 파일에 아래처럼 키 이름만 저장해둡니다. 값 자리에는 실제 키 대신 자리표시자를 씁니다 — 실제 키 형태 문자열을 코드나 이 문서 어디에도 적지 않습니다.

```text
ANTHROPIC_API_KEY=<발급받은-키>
```

상품 정보를 받아 정해진 JSON 형식(제목, 한 줄 소개, 해시태그 3개)의 홍보 문구를 만들고, 응답을 zod 스키마로 검증한 뒤 실패하면 한 번만 재시도하는 완결 코드입니다.

```typescript
// src/product-copy.ts
import Anthropic from "@anthropic-ai/sdk";
import { z } from "zod";
import "dotenv/config";

// 응답이 반드시 지켜야 하는 형식을 스키마로 강제한다 — 파싱이 아니라 검증
const ProductCopySchema = z.object({
  title: z.string(),
  tagline: z.string(),
  hashtags: z.array(z.string()).length(3),
});

type ProductCopy = z.infer<typeof ProductCopySchema>;

interface ProductInfo {
  name: string;
  features: string[];
}

if (!process.env.ANTHROPIC_API_KEY) {
  console.error("ANTHROPIC_API_KEY가 설정되지 않았습니다. .env 파일을 확인하세요.");
  process.exit(1);
}

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

// 모델 이름은 날짜 접미사 없이 씁니다.
// 모델 이름은 바뀔 수 있으니 공식 문서에서 현재 이름을 확인하세요.
const MODEL_NAME = "claude-sonnet-5";

function buildPrompt(product: ProductInfo): string {
  return [
    "당신은 이커머스 카피라이터입니다.", // 역할
    "아래 상품 정보로 홍보 문구를 만드세요.", // 지시
    `상품명: ${product.name}`,
    `특징: ${product.features.join(", ")}`,
    "반드시 JSON 형식으로만 답하세요: { title, tagline, hashtags(3개) }", // 제약
  ].join("\n");
}

async function requestProductCopy(product: ProductInfo): Promise<ProductCopy> {
  const message = await client.messages.create({
    model: MODEL_NAME,
    max_tokens: 300,
    messages: [{ role: "user", content: buildPrompt(product) }],
  });

  const textBlock = message.content.find((block) => block.type === "text");
  const raw = textBlock && "text" in textBlock ? textBlock.text : "";
  const parsed = JSON.parse(raw);
  return ProductCopySchema.parse(parsed); // 실패하면 여기서 예외가 던져진다
}

async function generateProductCopy(product: ProductInfo): Promise<ProductCopy> {
  try {
    return await requestProductCopy(product);
  } catch {
    // 검증 실패 시 선택지 중 "재시도"를 택한다 — 딱 한 번만
    try {
      return await requestProductCopy(product);
    } catch (error) {
      throw new Error(`형식 검증에 두 번 연속 실패했습니다: ${error}`);
    }
  }
}

const sample: ProductInfo = {
  name: "무선 이어폰",
  features: ["노이즈 캔슬링", "20시간 배터리", "방수"],
};

generateProductCopy(sample).then((copy) => console.log(copy));
```

기대 응답은 아래와 비슷한 형태입니다.

```json
{
  "title": "하루 종일 조용한 나만의 시간",
  "tagline": "노이즈 캔슬링과 20시간 배터리로 어디서든 몰입하세요",
  "hashtags": ["무선이어폰", "노이즈캔슬링", "방수"]
}
```

실행은 아래 한 줄입니다.

```powershell
npx tsx src/product-copy.ts
```

## 5. 실무 팁

- 키는 코드가 아니라 환경변수에 둡니다. `.env` 파일은 저장소에 절대 올리지 않고 `.gitignore`에 추가해둡니다.
- 사용자 입력을 프롬프트에 그대로 이어 붙이면 앞서 준 지시가 덮어써질 수 있습니다. 사용자 입력은 구분자나 별도 역할로 감싸서 지시와 분리합니다.
- 모델 응답을 화면에 그대로 넣기 전에 항상 스키마로 검증합니다. 검증 없이 렌더링하면 필드 누락이 화면 깨짐으로 바로 이어집니다.
- 재시도는 무한정 반복하지 않습니다. 한두 번으로 제한하고, 그래도 실패하면 사용자에게 알리거나 기본값으로 대체합니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 프롬프트는 역할·지시·예시·제약 네 부분으로 나눠 쓰면 모델이 규칙을 더 잘 지킨다
- 구조화 출력은 파싱이 아니라 스키마 검증으로 강제해야 안전하다
- 검증 실패 시 선택지는 재시도·기본값 대체·사람에게 넘기기 세 가지다
- LLM API 키는 항상 환경변수로만 다루고 코드에 리터럴로 적지 않는다
- 모델 이름은 날짜 접미사 없이 쓰고 공식 문서에서 현재 이름을 확인한다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 프롬프트 | 모델에게 보내는 요청 텍스트 전체 |
| 시스템 지시 | 모델의 역할과 행동 규칙을 정하는 프롬프트 조각 |
| 예시 제공(few-shot) | 원하는 답의 예시를 미리 보여주고 나머지를 맡기는 방법 |
| 구조화 출력 | 자연어 대신 정해진 형식(JSON 등)으로 응답을 받는 것 |
| 스키마 검증 | 응답이 정해진 형식을 지켰는지 코드로 확인하는 것 |
| 토큰 | 모델이 텍스트를 처리하는 최소 단위, 비용·길이 제한의 기준 |
| 온도(temperature) | 응답의 다양성·무작위성을 조절하는 값 |

1. 구조화 출력을 "JSON으로 답해주세요"라는 요청만으로 끝내지 않고 `zod` 스키마로 다시 검증하는 이유는 무엇일까요?

모델이 요청을 대체로 따르더라도 항상 완벽하게 지킨다는 보장은 없기 때문입니다. 설명을 덧붙이거나 필드를 빠뜨리는 등 형식이 어긋나는 경우가 실제로 발생하고, 그 응답을 검증 없이 그대로 화면에 넣으면 서비스가 깨집니다.

스키마 검증은 "모델을 믿지 않고 코드로 확인한다"는 방어선입니다.

2. 검증 실패 시 재시도 대신 곧바로 사람에게 넘기는 편이 더 나은 상황은 어떤 경우일지 생각해보세요.

<details>
<summary>정답 보기</summary>

재시도해도 계속 같은 이유로 실패할 가능성이 높은 상황이거나, 잘못된 응답이 사용자에게 그대로 노출됐을 때 피해가 큰 상황(결제 금액, 법적 문구 등)에서는 사람 검토로 넘기는 편이 안전합니다.

전자는 프롬프트 자체의 설계 문제일 가능성이 크므로 재시도로는 해결되지 않습니다.

</details>
