## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 테이블 · 행 · 열이 각각 무엇에 해당하는지 설명할 수 있다
- 기본키가 왜 필요한지 말할 수 있다
- 외래키로 두 테이블을 연결해 만들 수 있다
- 만든 테이블에 데이터를 넣고 조회해 확인할 수 있다

## 2. 왜 배우나

앞 레슨에서 파일에 데이터를 저장해봤다면, 데이터가 많아질수록 찾기 어렵고 중복이 쌓이고 여러 사람이 동시에 고치면 꼬인다는 걸 느꼈을 겁니다. 관계형 데이터베이스(relational database, 표들을 서로 연결해 데이터를 정리해 두는 저장소)는 이 문제를 표 여러 개로 나누고 서로 잇는 방식으로 풉니다. 이 커리큘럼에서 만들 서비스는 결국 전부 이 구조 위에 데이터를 쌓습니다. 이 레슨은 Supabase SQL 에디터라는 브라우저 화면에서 전부 실습하므로 아이패드만 있어도 됩니다.

## 3. 개념 설명

### 📊 표 하나 = 테이블

테이블(table, 같은 종류의 데이터를 모아두는 표)을 엑셀 시트라고 생각하면 쉽습니다. 시트 하나가 테이블 하나, 시트의 한 줄이 행(row, 표의 한 줄 — 레코드 하나) 하나, 시트의 세로 칸이 열(column, 표의 세로 칸 — 정해진 자료형을 가짐) 하나입니다. 다른 점은, 열마다 어떤 자료형(`text`, `int`, `serial` 등)만 들어갈지 미리 정해둔다는 것입니다.

| 엑셀 | 데이터베이스 | 예시 |
|------|--------------|------|
| 시트 | 테이블 | `students` 표 |
| 줄(행) | 행(레코드) | 학생 한 명 |
| 칸(열) | 열(컬럼) | `name`(이름), `grade`(학년) |

### 🔑 기본키 — 누가 누구인지 가리는 이름표

기본키(primary key, 표 안에서 각 행을 유일하게 구분하는 값)가 없으면 이름이 같은 학생 두 명을 구분할 방법이 없습니다. 그래서 표를 만들 때 절대 중복되지 않는 값(보통 자동으로 늘어나는 번호)을 한 열에 정해두고, 그 열을 기본키로 지정합니다. 어떤 행을 콕 집어 가리키고 싶을 땐 항상 이 값을 씁니다.

### 🧵 외래키 — 두 표를 잇는 실

외래키(foreign key, 다른 표의 기본키를 가리켜 두 표를 연결하는 값)는 한 표의 열이 다른 표의 기본키를 가리키게 만드는 방법입니다. 학생 표와 과목 표를 직접 잇는 대신, 그 사이에 "누가 어떤 과목을 듣는지"를 적는 수강 표를 하나 더 두고 두 개의 외래키로 양쪽을 가리키게 합니다.

`학생 → 수강 → 과목`

### 🗄️ 스키마 — 표들을 담는 서랍

스키마(schema, 여러 테이블을 묶어 담는 이름 붙은 서랍)는 테이블들을 그룹으로 묶는 이름표입니다. 이 사이트의 진도 데이터는 같은 Supabase 프로젝트의 다른 서랍(공유 스키마)에 들어 있습니다. 이번 실습은 그 서랍을 절대 건드리지 않도록, `practice`라는 연습용 서랍을 따로 만들어 그 안에서만 표를 만들고 지웁니다.

## 4. 실무 예제

아래 SQL을 순서대로 Supabase 대시보드의 SQL 에디터에 붙여넣고 실행하면, 서로 연결된 표 세 개를 세우고 데이터를 넣어 확인하는 과정을 전부 브라우저에서 끝낼 수 있습니다.

```sql
-- Supabase 대시보드 → SQL 에디터에서 실행합니다.
-- 이 블록은 연습용 서랍(practice 스키마) 안에서만 동작하며, 사이트 진도 데이터와는 무관합니다.
CREATE SCHEMA IF NOT EXISTS practice;

CREATE TABLE practice.students (
  id serial PRIMARY KEY,
  name text NOT NULL,
  grade int
);

CREATE TABLE practice.subjects (
  id serial PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE practice.enrollments (
  id serial PRIMARY KEY,
  student_id int NOT NULL REFERENCES practice.students(id),
  subject_id int NOT NULL REFERENCES practice.subjects(id)
);
```

이 블록을 실행하면 에디터 하단에 성공 메시지가 뜨고, 왼쪽 테이블 목록에 `practice` 서랍 아래로 표 세 개가 나타납니다.

```sql
-- 각 표에 데이터를 몇 행씩 넣습니다.
INSERT INTO practice.students (name, grade) VALUES
  ('김지현', 2),
  ('이민준', 1),
  ('박서연', 3);

INSERT INTO practice.subjects (name) VALUES
  ('수학'),
  ('영어'),
  ('과학');

INSERT INTO practice.enrollments (student_id, subject_id) VALUES
  (1, 1),
  (1, 2),
  (2, 1),
  (3, 3);
```

각 `INSERT`문이 성공하면 몇 행이 추가됐는지 메시지로 알려줍니다(예: "Success. 3 rows affected").

```sql
-- 넣은 데이터를 확인합니다.
SELECT * FROM practice.students ORDER BY id;

SELECT s.name AS 학생, sub.name AS 과목
FROM practice.enrollments e
JOIN practice.students s ON s.id = e.student_id
JOIN practice.subjects sub ON sub.id = e.subject_id
ORDER BY e.id;
```

첫 번째 조회는 학생 3명이 담긴 표 그대로를 보여줍니다. 두 번째 조회는 수강 표의 외래키 두 개를 따라가 "누가 어떤 과목을 듣는지"를 한 줄씩 이어 붙여 보여줍니다 — 결과는 총 4행입니다.

<details>

`insert or update on table "enrollments" violates foreign key constraint`라는 에러가 발생합니다. `student_id`가 가리키는 `999`번 학생이 `students` 표에 없기 때문에, 외래키 제약이 이 행을 막습니다. 존재하지 않는 것을 가리키는 실이 생기는 걸 데이터베이스가 미리 거부하는 것입니다.

</details>

## 5. 실무 팁

- 테이블 · 열 이름은 소문자와 밑줄(snake_case)로 짓는 관례를 따릅니다 — `student_name`처럼.
- `NOT NULL`은 처음부터 걸어두는 편이 나중에 빈 값을 찾아 다시 채우는 것보다 쉽습니다.
- 연습은 반드시 `practice` 스키마 안에서만 합니다 — 실수로 다른 서랍을 건드리면 되돌릴 수 없습니다.
- 실습이 끝나면 아래 정리 SQL로 연습용 서랍을 치워둡니다 — 다음에 처음부터 다시 해볼 수 있습니다.

```sql
-- 실습을 되돌립니다. practice 서랍(스키마)을 통째로 지웁니다.
-- 이 문장은 practice 스키마만 대상으로 하므로 사이트 진도 데이터에는 아무 영향이 없습니다.
DROP SCHEMA IF EXISTS practice CASCADE;
```

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 테이블 하나는 같은 종류의 데이터를 모아두는 표이고, 행은 한 건, 열은 항목이다
- 기본키는 각 행을 유일하게 구분하는 값이다
- 외래키는 다른 표의 기본키를 가리켜 두 표를 연결하는 값이다
- 스키마는 여러 테이블을 묶어 담는 서랍이며, 연습은 별도 서랍(`practice`)에서만 한다
- 실습은 Supabase SQL 에디터라는 브라우저 화면에서 이뤄지므로 아이패드에서도 그대로 할 수 있다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 테이블 | 같은 종류의 데이터를 모아두는 표 |
| 행 | 표의 한 줄 — 레코드 하나 |
| 열 | 표의 세로 칸 — 정해진 자료형을 가짐 |
| 기본키 | 표 안에서 각 행을 유일하게 구분하는 값 |
| 외래키 | 다른 표의 기본키를 가리켜 두 표를 연결하는 값 |
| 스키마 | 여러 테이블을 묶어 담는 이름 붙은 서랍 |
| 제약조건 | 표에 넣을 수 있는 값의 규칙(`NOT NULL`, 기본키 등) |

**스스로 점검**

1. 학생 표에서 기본키로 `id` 대신 `name`(이름)을 쓰면 어떤 문제가 생길까요?

<details>
<summary>정답 보기</summary>

이름이 같은 학생이 두 명 이상 있으면 서로 구분할 수 없습니다. 예를 들어 "김지현"이라는 학생이 두 명이면 어느 쪽을 가리키는지 알 수 없어, 수강 기록을 정확히 연결할 수 없게 됩니다.

</details>

2. 수강 표(`enrollments`)의 `student_id` 열에서 `REFERENCES practice.students(id)`를 빼면 어떤 일이 생길까요?

<details>
<summary>정답 보기</summary>

외래키 제약이 사라져, 존재하지 않는 학생 번호를 넣어도 데이터베이스가 막지 않습니다. 위 해보기 3번에서 본 에러가 더는 발생하지 않고, 아무 것도 가리키지 않는 "끊어진 실"이 조용히 쌓이게 됩니다.

</details>
