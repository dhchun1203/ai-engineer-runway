## 1. 학습 목표

이 레슨을 마치면 다음을 할 수 있습니다.

- 브랜치를 만들어 원본을 건드리지 않고 작업할 수 있다
- 변경을 커밋으로 묶고 원격 저장소에 올릴 수 있다
- PR을 열어 변경 내용을 설명하고 머지할 수 있다
- 머지 후 로컬을 최신 상태로 되돌릴 수 있다

## 2. 왜 배우나

혼자 코드를 짤 때는 파일을 그냥 고치면 끝이지만, 여럿이 같이 만들 때는 "누가 무엇을 왜 바꿨는지"가 남아야 합니다. 브랜치와 PR은 그 흔적을 남기는 가장 기본적인 협업 단위입니다.

실제로 이 사전학습 사이트 자체도 지금 여러분이 배우는 것과 똑같은 방식(브랜치 → PR → 머지)으로 만들어지고 있습니다. 오늘 익힌 흐름이 곧 실무에서 매일 쓰는 흐름입니다.

## 3. 개념 설명

### 🗂️ 저장소·커밋·브랜치

Git(버전 관리 도구, 파일이 바뀐 이력을 통째로 저장하는 프로그램)은 파일이 아니라 "이력"을 저장합니다. 원격 저장소(remote repository, GitHub 서버에 있는 저장소)와 로컬 저장소(local repository, 내 컴퓨터에 있는 저장소)는 같은 이력을 각자 들고 있는 복사본입니다.

커밋(commit, 변경 내용을 하나로 묶어 저장한 기록)은 "이 시점에 파일이 이렇게 바뀌었다"는 스냅샷이고, 브랜치(branch, 작업을 따로 복사해 두는 갈래)는 그 스냅샷들이 이어지는 하나의 줄기입니다.

| 개념 | 하는 일 | 일상 비유 |
|------|---------|-----------|
| 저장소 | 파일과 그 변경 이력을 통째로 보관한다 | 문서의 모든 개정판을 다 갖고 있는 캐비닛 |
| 커밋 | 특정 시점의 변경을 하나로 묶어 기록한다 | 캐비닛에 넣는 "개정판 한 장" |
| 브랜치 | 원본과 별도로 작업할 수 있는 갈래를 만든다 | 원본 문서를 복사해 낙서해도 되는 사본 |

### 🌊 한 바퀴의 흐름

전체 흐름은 이렇게 이어집니다.

```text
clone → branch → commit → push → PR → merge → pull
```

각 단계가 어디서 일어나는지 표로 정리하면 다음과 같습니다.

| 단계 | 어디서 |
|------|--------|
| clone, branch, commit, push, pull | 로컬 터미널 |
| PR 열기, merge | GitHub 웹 |

로컬에서 저장소를 내려받고(clone) 갈래를 뻗어(branch) 작업을 커밋(commit)한 뒤 원격에 올리면(push), 그다음부터는 GitHub 웹으로 넘어가 PR을 열고 머지합니다. 마지막으로 다시 로컬 터미널로 돌아와 최신 상태를 받습니다(pull).

### 🚧 왜 원줄기에서 바로 고치지 않나

브랜치(branch, 작업을 따로 복사해 두는 갈래) 없이 원줄기(주 브랜치, `master` 또는 `main`)에서 바로 고치면, 실수했을 때 되돌리기가 훨씬 번거롭고 다른 사람이 리뷰할 기회 없이 바로 배포될 수 있습니다. 브랜치를 뻗어 작업하면 원줄기는 항상 "검증된 상태"로 남고, 문제가 생겨도 그 브랜치만 버리면 됩니다.

이 사이트 저장소(`ai-engineer-runway`)도 실제로 이 흐름을 씁니다 — PR(풀 리퀘스트, pull request, 변경을 원줄기에 합쳐 달라는 요청)을 열면 자동으로 미리보기 주소가 생겨서, 머지하기 전에 실제 화면으로 먼저 확인할 수 있습니다.

<TwistBox>

브랜치로 작업하면 원줄기는 항상 안전하다고 배웠습니다. 그런데 같은 브랜치를 여러 명이 쓸 때 아래 명령을 실행하면 무슨 일이 생길까요?

```powershell
git push --force origin update-readme
```

평소 `git push`는 원격에 없는 내 커밋만 추가하지만, `--force`는 원격의 이력을 내 로컬 이력으로 통째로 덮어씁니다.

동료가 먼저 올려둔 커밋이 있어도 경고 없이 사라질 수 있습니다. "브랜치는 안전하다"는 규칙이 강제로 뒤집히는 거의 유일한 지점입니다.

</TwistBox>

## 4. 실무 예제

아래는 연습용 저장소(1-1 레슨에서 만든 빈 저장소)를 대상으로, 브랜치를 뻗어 파일을 고치고 PR을 열어 머지한 뒤 로컬을 동기화하는 한 바퀴 전체입니다. 저장소 주소만 여러분 것으로 바꾸면 그대로 따라 칠 수 있습니다.

**1단계 — 저장소를 내려받고 브랜치를 뻗습니다.**

<PredictPrompt />

```powershell
# 연습용 저장소를 로컬로 클론합니다 (주소는 여러분의 GitHub 저장소로 바꿉니다)
git clone https://github.com/내계정/git-pr-practice.git
cd git-pr-practice

# master를 건드리지 않고 새 갈래를 뻗습니다
git switch -c update-readme
```

macOS는 터미널 앱(Terminal)에서 그대로 같은 명령을 씁니다 — `git` 명령 자체는 Windows와 동일합니다.

여기까지 하면 `update-readme`라는 새 브랜치 위에 서 있게 됩니다. `master`는 전혀 바뀌지 않았습니다.

**2단계 — 파일을 고치고 커밋한 뒤 원격에 올립니다.**

```powershell
# README.md에 한 줄을 추가합니다 (편집기로 직접 열어 고쳐도 됩니다)
Add-Content -Path README.md -Value "브랜치 실습 중입니다."

# 변경을 커밋으로 묶습니다
git add README.md
git commit -m "docs: 브랜치 실습 문구 추가"

# 원격 저장소(GitHub)에 올립니다 -u는 다음부터 push만 쳐도 되게 연결해 둡니다
git push -u origin update-readme
```

`git push`가 끝나면 터미널에 GitHub가 알려주는 PR 생성 링크가 함께 출력됩니다.

**3단계 — GitHub 웹에서 PR을 열고 머지합니다.**

브라우저로 저장소 페이지를 열면 방금 올린 브랜치에 대해 "Compare & pull request" 버튼이 보입니다.

클릭 → 제목·설명을 간단히 적고 "Create pull request" → 변경 내용을 확인한 뒤 "Merge pull request" → "Confirm merge" 순서로 누르면 `update-readme`의 변경이 `master`에 합쳐집니다.

**4단계 — 머지 후 로컬을 최신 상태로 되돌립니다.**

```powershell
git switch master
git pull
```

`git pull`을 하지 않으면 로컬의 `master`는 여전히 머지 전 상태입니다 — 다음 브랜치를 여기서 새로 뻗으면 낡은 지점에서 시작하게 됩니다.

가장 최근 커밋이 맨 위에 오는 목록이 출력됩니다. 두 번의 PR을 머지했다면 `docs: 브랜치 실습 문구 추가`, `add-note` 브랜치의 커밋 메시지, 그리고 각 PR의 머지 커밋(예: `Merge pull request #2 from ...`)까지 확인할 수 있습니다.

</details>

## 5. 실무 팁

- **브랜치 이름은 하는 일을 담아서 짓습니다.** `update-readme`, `fix-typo`처럼 무엇을 바꾸는지 이름만 보고 알 수 있게 짓습니다.
- **커밋 메시지는 한 줄 요약으로 씁니다.** "수정함" 대신 "docs: 브랜치 실습 문구 추가"처럼 무엇을 왜 바꿨는지가 드러나게 씁니다.
- **원줄기 이름은 저장소마다 다를 수 있습니다.** `main`이 흔하지만 이 사이트 저장소는 `master`를 씁니다 — 명령을 칠 때 실제 저장소의 원줄기 이름을 확인합니다.
- **머지 후에는 반드시 `pull`로 로컬을 맞춥니다.** 그러지 않으면 다음 브랜치가 낡은 지점에서 갈라져 나중에 불필요한 충돌이 생깁니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 원격 저장소와 로컬 저장소는 같은 이력을 각자 들고 있는 복사본이다
- 커밋은 변경을 하나로 묶은 기록, 브랜치는 그 기록이 이어지는 갈래다
- 한 바퀴는 clone → branch → commit → push(로컬) → PR → merge(GitHub 웹) → pull(로컬) 순서로 돈다
- 브랜치로 작업하면 원줄기는 항상 검증된 상태로 남고, 문제가 생겨도 브랜치만 버리면 된다
- 머지 후 `pull`을 빼먹으면 다음 브랜치가 낡은 지점에서 시작된다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 저장소 | 파일과 그 변경 이력을 통째로 보관하는 공간 |
| 클론 | 원격 저장소를 로컬로 통째로 복사해 오는 것 |
| 브랜치 | 작업을 따로 복사해 두는 갈래 |
| 커밋 | 변경 내용을 하나로 묶어 저장한 기록 |
| 푸시 | 로컬 커밋을 원격 저장소에 올리는 것 |
| 풀 리퀘스트 | 변경을 원줄기에 합쳐 달라는 요청 |
| 머지 | 브랜치의 변경을 다른 브랜치에 합치는 것 |
| 원격 저장소 | GitHub 서버에 있는 저장소 |

**스스로 점검**

1. 브랜치를 쓰지 않고 원줄기(`master`)에서 바로 파일을 고쳤다면 어떤 문제가 생길 수 있을까요?

<details>
<summary>힌트 보기</summary>

3장 "왜 원줄기에서 바로 고치지 않나" 부분을 떠올려보세요. 실수를 되돌리는 일과, 다른 사람이 미리 살펴볼 기회 두 가지 측면에서 생각해봅니다.

</details>

<details>
<summary>정답 보기</summary>

실수했을 때 되돌리기가 번거롭고, 다른 사람의 리뷰 없이 변경이 바로 원줄기에 반영됩니다. 원줄기가 항상 "검증된 상태"로 남아야 하는데 그 안전장치가 사라지는 것입니다. 브랜치를 쓰면 문제가 생겨도 그 브랜치만 버리면 됩니다.

</details>

2. `git push -u origin update-readme`를 실행한 뒤 실제로 머지가 일어나는 곳은 로컬 터미널일까요, GitHub 웹일까요? 왜 그럴까요?

<details>
<summary>힌트 보기</summary>

`push`가 하는 일은 로컬 커밋을 원격 저장소에 올리는 것뿐이라는 점을 떠올려보세요. 그 이후 "합쳐 달라"고 요청하고, 실제로 버튼을 눌러 합치는 행동은 누가 어디서 하는지 이어서 생각해봅니다.

</details>

<details>
<summary>정답 보기</summary>

GitHub 웹입니다. `push`까지는 로컬에서 만든 커밋을 원격 저장소에 올리는 것일 뿐이고, PR을 열어 "합쳐 달라"고 요청한 뒤 실제로 합치는(머지하는) 동작은 GitHub 웹에서 버튼을 눌러 이뤄집니다.

</details>
