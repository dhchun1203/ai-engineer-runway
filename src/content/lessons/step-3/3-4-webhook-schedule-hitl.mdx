## 1. 학습 목표

이 레슨을 마치면 다음을 알아듣습니다.

- Webhook·스케줄·HITL이 각각 무엇을 가리키는 말인지 한 문장으로 말할 수 있다
- 자동화가 언제 시작되어야 하는지, 어디서 사람이 개입해야 하는지 말할 수 있다
- 이 개념들이 앞 레슨의 여러 AI 구조 위 어디에 놓이는지 안다

## 2. 왜 배우나

자동화는 "무엇을 하는가"만큼 "언제 시작하고 어디서 멈추는가"가 자주 문제가 됩니다.

사람이 개입하는 지점을 설계 단계에서 빼놓으면, 나중에 다시 끼워 넣기가 훨씬 번거롭습니다.

## 3. 개념 설명

### ⚡ 트리거 세 가지 — 무엇이 자동화를 시작시키나

자동화를 시작시키는 계기를 트리거(trigger)라고 부르며, 크게 세 가지로 나뉩니다.

| 트리거 종류 | 무엇이 시작시키나 | 언제 쓰나 |
|---|---|---|
| 이벤트 (Webhook) | 다른 서비스가 어떤 일이 일어났다고 알려줌 | "무언가 발생했을 때" 바로 반응해야 할 때 |
| 시간 (스케줄) | 정해진 주기가 됨(매일 아침 등) | 정기적으로 확인·처리해야 할 때 |
| 사람 (수동·승인) | 사람이 직접 버튼을 누르거나 승인함 | 시작 여부를 사람이 판단해야 할 때 |

### 📩 Webhook — 남이 내 주소로 보내는 알림

Webhook(웹훅)은 남의 서비스가 어떤 일이 생겼을 때 내가 만든 주소로 알림을 보내주는 것입니다. 택배가 도착하면 문자가 오는 것과 비슷합니다.

2-5 레슨에서 만든 API 엔드포인트가 "내가 요청을 보내는 곳"이었다면, Webhook은 반대로 "남이 나에게 요청을 보내는 곳"입니다.

### ⏰ 스케줄 — 정해진 주기로 실행하기

스케줄은 "매일 아침 9시", "10분마다"처럼 정해진 주기로 자동화를 실행하는 방식입니다. 정확한 문법을 외울 필요는 없고, 주기를 정하는 개념만 알아두면 됩니다.

### ✋ HITL — 사람이 중간에 끼는 지점

HITL(Human In The Loop)은 자동화 중간에 사람이 승인하거나 수정하는 지점을 두는 것입니다. 회사의 결재 라인과 비슷합니다.

승인을 기다리는 동안 그 상태를 어딘가에 저장해 두어야, 담당자가 나중에 확인해도 이어서 처리할 수 있습니다.

## 4. 실무 예제

### 실무에서 이게 어떻게 쓰이나

고객 문의 메일이 도착하면 메일 서비스가 Webhook으로 우리 시스템에 알려줍니다. 시스템은 문의를 분류하고 초안까지 만든 다음, 담당자의 승인을 기다립니다.

이 대기 상태에서 앞 레슨의 "검수 담당" 역할이 바로 HITL 지점입니다. 담당자가 승인하면 발송되고, 만약 하루가 지나도 승인이 없으면 매일 아침 스케줄이 미처리 건을 다시 확인해 알려줍니다.

같은 문의 메일에 대한 Webhook 알림이 network 문제로 두 번 오더라도, 이미 처리한 이벤트 식별자를 기억해두면 답변이 두 번 발송되는 일을 막을 수 있습니다.

```typescript
    return respond(401, "invalid signature");
  }

  // 2. 중복 알림 식별자 확인 — 같은 이벤트가 두 번 와도 한 번만 처리(멱등성)
  if (await isAlreadyProcessed(req.body.eventId)) {
    return respond(200, "already processed"); // 재시도는 성공으로 응답
  }

  // 3. 처리 큐에 넣고 즉시 200 응답 — 실제 처리는 나중에, 응답은 먼저
  await enqueue("inbound-inquiry", req.body);
  return respond(200, "accepted");
}
```

## 5. 실무 팁

- Webhook은 누구나 호출할 수 있는 주소이므로, 서명이나 토큰으로 진짜 발신자가 맞는지 반드시 확인합니다.
- 같은 알림이 여러 번 올 수 있으니 이벤트 식별자로 중복을 걸러내 멱등성을 지킵니다.
- 승인 대기가 영원히 남아있지 않도록 만료 시간을 정해 둡니다.

<details>
<summary>정답 보기</summary>

모범 답안 예: "매주 월요일 지난주 매출을 정리해 메일로 보내기"는 시간(스케줄) 트리거가 맞습니다. 특정 사건이 발생해서가 아니라 정해진 주기마다 실행되어야 하는 일이기 때문입니다.

반대로 "결제가 완료되면 영수증을 발송하기"는 이벤트(Webhook) 트리거가 맞습니다. 결제 완료라는 사건이 발생한 순간 바로 반응해야 하기 때문입니다.

</details>

### 해보기

공유 시나리오(문의 메일 → 분류 → 검색 → 초안 → 승인 → 발송)에서 사람이 반드시 개입해야 하는 지점을 찾고, 그 이유와 대기 만료 시간을 정해보세요.

<details>
<summary>정답 보기</summary>

담당자 승인 지점이 사람이 반드시 개입해야 하는 곳입니다. AI가 쓴 초안을 그대로 발송하면 잘못된 답변이 고객에게 나갈 위험이 있기 때문입니다.

대기 만료 시간은 예를 들어 24시간으로 정하고, 만료되면 담당자에게 알림을 다시 보내거나 다른 담당자에게 넘기는 규칙을 함께 둘 수 있습니다.

</details>

### 해보기

같은 알림이 두 번 왔을 때 무슨 일이 생길 수 있는지 적고, 이를 막을 방법을 적어보세요.

<details>
<summary>정답 보기</summary>

같은 문의 메일에 대한 처리가 두 번 실행되어, 답변이 두 번 발송되거나 같은 작업이 중복 기록될 수 있습니다.

이를 막으려면 각 알림에 담긴 고유 이벤트 식별자를 저장해두고, 이미 처리한 식별자가 다시 들어오면 새로 처리하지 않고 이전과 같은 응답만 돌려주면 됩니다. 이것이 멱등성을 지키는 방법입니다.

</details>

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 자동화를 시작시키는 트리거는 이벤트(Webhook)·시간(스케줄)·사람(수동) 세 가지로 나뉜다
- Webhook은 남의 서비스가 내 주소로 알림을 보내주는 방식이다
- HITL은 자동화 중간에 사람이 승인하거나 수정하는 지점을 두는 것이다
- 멱등성은 같은 요청이 여러 번 와도 결과가 한 번만 반영되게 만드는 성질이다
- 이 레슨의 코드는 읽기용이며, 실제로 손으로 돌려보는 것은 개강 후 본 과정에서 다룬다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| Webhook | 다른 서비스가 어떤 일이 생기면 내가 만든 주소로 보내주는 알림 |
| 트리거 | 자동화를 시작시키는 계기 |
| 스케줄 | 정해진 주기로 자동화를 실행하는 방식 |
| HITL | 자동화 중간에 사람이 승인·수정하는 지점(Human In The Loop) |
| 멱등성 | 같은 요청이 여러 번 와도 결과가 한 번만 반영되는 성질 |
| 재시도 | 실패하거나 응답이 없을 때 같은 요청을 다시 보내는 것 |
| 큐 | 처리를 기다리는 작업을 순서대로 쌓아두는 대기열 |
