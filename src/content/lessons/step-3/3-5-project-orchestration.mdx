## 1. 학습 목표

이 프로젝트에서 무엇을 만들고 무엇을 증명하는지 먼저 짚고 넘어갑니다.

- **무엇을 만드나:** 실제 업무 하나를 자동화하는 워크플로우입니다. 트리거(webhook, 신호를 받아 작업을 시작하는 방식)로 시작해 외부 도구 세 개를 거치고, 사람 승인(HITL)까지 이어지는 흐름입니다.
- **무엇을 증명하나:** 이 흐름을 설계할 수 있고, 잘못됐을 때 되돌릴 수 있음을 증명합니다. 구현 능력이 아니라 프로젝트 전체 구조를 이해하는 것이 이 레슨의 목표입니다.
- 개강 후 팀 프로젝트에서 이 자동화를 실제로 만들 때, 오늘 준비해둔 것들이 그대로 출발점이 됩니다.

## 2. 왜 배우나

이 프로젝트는 앞선 세 편이 여기서 하나로 합쳐지는 자리입니다.

`3-4-multi-agent-structure`에서 다진 역할 분담(여러 AI가 어떤 일을 나눠 맡는지)이 이 자동화 안의 각 단계를 누가 처리할지 정하는 기준이 됩니다.

`3-4-webhook-schedule-hitl`에서 다진 트리거와 승인 지점 설계가 이 자동화를 언제 시작하고 어디서 사람이 확인할지 그대로 결정합니다.

`3-4-n8n-langgraph`에서 다진 도구 선택 감각이 이 자동화를 어떤 방식으로 조립할지 고를 때 필요합니다.

아직 이 레슨들을 보지 않았어도 slug만 기억해뒀다가, 프로젝트를 실제로 시작할 때 막히는 부분이 있으면 해당 레슨으로 돌아가 복습하면 됩니다.

## 3. 개념 설명

### 무엇을 만드나 — 전체 구조

```text
트리거(웹훅·스케줄) → 워크플로 실행 → 외부 도구 3개 연동 → 사람 승인(HITL) → 결과 기록(감사로그) → 실패 시 롤백
```

| 단계 | 하는 일 | 어느 레슨에서 나왔나 |
|------|---------|----------------------|
| 트리거 | 무엇이 이 자동화를 시작시키는지 정한다(웹훅 또는 정해진 시간) | `3-4-webhook-schedule-hitl` |
| 워크플로 실행 | 정해진 순서대로 각 단계를 실행한다 | `3-4-n8n-langgraph` |
| 외부 도구 3개 연동 | 메신저·문서·표 같은 실제 도구를 자동으로 조작한다 | `3-4-n8n-langgraph` |
| 사람 승인(HITL) | 자동으로 끝까지 진행하지 않고 사람이 확인하는 지점을 둔다 | `3-4-webhook-schedule-hitl` |
| 결과 기록(감사로그) | 누가·언제·무엇을·어떤 결과로 처리했는지 남긴다 | `3-4-multi-agent-structure` |
| 실패 시 롤백 | 잘못 실행됐을 때 되돌릴 방법을 미리 정해둔다 | `3-4-webhook-schedule-hitl` |

## 4. 실무 예제

### 사전 준비 체크리스트

이 프로젝트를 개강 첫날 바로 시작하려면 아래를 미리 준비해둡니다.

| 준비물 | 왜 필요한가 | 지금 할 일 |
|--------|-------------|-----------|
| 자동화할 실제 업무 1개 | 지금 사람이 손으로 하는 절차가 있어야 자동화 대상이 명확해집니다 | 그 업무의 절차를 단계별로 적어 두기 |
| 외부 도구 3개 계정 | 메신저·문서·표 계열 도구를 실제로 연동해야 합니다 | 팀이 실제로 쓰는 도구로 고르고 자동화 연동이 가능한지 확인해두기 |
| 트리거 방식 결정 | 무엇이 이 자동화를 시작시키는지 정해야 워크플로 설계가 시작됩니다 | 웹훅으로 시작할지, 정해진 시간에 시작할지 미리 정해두기 |
| 승인자 지정 | HITL 지점에서 누가 확인할지 정해야 흐름이 끊기지 않습니다 | 팀 안에서 승인 담당을 미리 합의해두기 |
| 감사로그에 남길 항목 목록 | 나중에 문제가 생겼을 때 무엇을 봐야 할지 정해둬야 합니다 | 누가·언제·무엇을·결과 네 항목을 목록으로 적어두기 |

## 5. 실무 팁

- **자동화 대상 업무를 너무 크게 잡으면 끝나지 않습니다.** 한 사이클이 10분 안에 끝나는 업무를 골라야 프로젝트 기간 안에 완성할 수 있습니다.
- **외부 도구 연동 권한을 받는 데 생각보다 오래 걸립니다.** 관리자 승인이나 API 발급이 필요한 경우가 많으니 첫 주에 미리 신청해둡니다.
- **롤백 시나리오를 나중에 붙이면 이미 늦습니다.** 자동화가 잘못 실행됐을 때 무엇을 되돌려야 하는지 처음부터 설계에 넣어둡니다.
- **시간 배분과 역할 분담.** 오늘 60분은 준비까지만입니다. 트리거 담당·외부 도구 연동 담당·승인 흐름 담당처럼 미리 역할을 나눠두면 개강 첫날 회의가 짧아집니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- [ ] 자동화할 업무를 선정하고 절차를 문서화했다
- [ ] 외부 도구 3개의 계정을 만들고 연동 가능 여부를 확인했다
- [ ] 트리거 방식(웹훅 또는 스케줄)을 결정했다
- [ ] 승인자를 팀과 합의했다
- [ ] 감사로그에 남길 항목 목록을 정리했다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 감사로그 | 누가·언제·무엇을·어떤 결과로 처리했는지 남기는 기록 |
| 롤백 | 잘못 실행된 작업을 이전 상태로 되돌리는 것 |
| 승인 대기 | 자동화가 다음 단계로 넘어가기 전 사람의 확인을 기다리는 상태 |
| 외부 연동 | 워크플로가 메신저·문서 같은 외부 도구를 자동으로 조작하는 것 |
| 실행 이력 | 자동화가 언제 무엇을 처리했는지 모아둔 기록 |
| 드라이런 | 실제로 실행하지 않고 결과만 미리 확인해보는 시험 실행 |

**스스로 점검**

1. 자동화 대상 업무를 고를 때 "한 사이클이 10분 안에 끝나는가"를 기준으로 삼는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

한 사이클이 너무 길거나 복잡한 업무는 트리거부터 승인까지 전체 흐름을 설계하고 테스트하는 데 시간이 오래 걸려 프로젝트 기간 안에 끝내기 어렵습니다. 짧고 명확한 업무로 시작해야 트리거·외부 연동·승인·롤백까지 전체 구조를 한 바퀴 완성해볼 수 있습니다.

</details>

2. 감사로그와 롤백 시나리오를 자동화 설계 초반에 넣어야 하는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

자동화는 사람이 매번 확인하지 않고 실행되기 때문에, 문제가 생겼을 때 무슨 일이 있었는지 기록이 없으면 원인을 찾기 어렵습니다. 롤백 방법도 나중에 붙이려고 하면 이미 자동화가 여러 번 실행된 뒤라 되돌릴 범위를 정하기 어려워지므로, 설계 단계에서 함께 정해두는 것이 안전합니다.

</details>
