## 1. 학습 목표

이 레슨을 마치면 다음을 알아듣습니다.

- "오케스트레이션(orchestration)"이 무엇을 가리키는 말인지 한 문장으로 말할 수 있다
- 여러 AI가 왜 역할을 나눠 일하는지, 언제 이런 구조가 필요한지 말할 수 있다
- 순차·병렬·감독자 세 연결 방식이 각각 무엇이 다른지 안다
- 이 구조가 전체 자동화 파이프라인에서 어디에 놓이는지 안다

## 2. 왜 배우나

한 AI에게 기획부터 검수까지 전부 맡기면 프롬프트가 길어지고 실수가 쌓입니다.

역할을 나누면 각자 맡은 일만 잘하면 되므로 결과가 안정됩니다.

개강 후 프로젝트 4·5는 여러 AI가 역할을 나눠 협업하는 구조 위에서 진행됩니다. 이 레슨은 그 구조를 미리 알아듣기 위한 준비입니다.

## 3. 개념 설명

### 🎭 단일 에이전트의 한계 — 한 사람이 다 하면 생기는 일

한 사람이 기획·집필·검수를 전부 맡으면 어딘가에서 놓치기 마련입니다. 한 AI에게 전체 작업을 한 번에 시키는 것도 같은 문제를 겪습니다.

### 🏢 역할 분담 — 편집국의 데스크·기자·교열

신문사는 기사를 한 사람이 처음부터 끝까지 쓰지 않습니다. 데스크가 방향을 정하고, 기자가 취재해 쓰고, 교열이 검수합니다.

여러 AI로 이루어진 구조도 이렇게 역할을 나눠 각자 한 가지만 맡게 합니다. 이 역할 하나하나를 에이전트(agent)라고 부릅니다.

### 🔗 연결 방식 — 순차·병렬·감독자

역할들을 어떻게 이어 붙이는지에 따라 크게 세 가지로 나뉩니다.

| 연결 방식 | 무엇인가 | 언제 쓰나 |
|---|---|---|
| 순차 (sequential) | 앞 역할의 출력이 다음 역할의 입력이 됨 | 단계가 정해진 순서로 이어질 때 |
| 병렬 (parallel) | 여러 역할이 동시에 각자 작업함 | 서로 독립적인 작업을 동시에 처리할 때 |
| 감독자 (supervisor) | 감독자 역할이 다음에 누구를 부를지 그때그때 정함 | 상황에 따라 다음 단계가 달라질 때 |

### 💾 상태 공유와 위험

역할들은 무엇을 주고받았는지 어딘가에 남겨야 다음 역할이 이어받을 수 있습니다. 이 기록을 상태(state)라고 부릅니다.

역할들이 서로를 계속 부르도록 잘못 짜이면 끝나지 않는 루프가 생기고, 그만큼 비용도 함께 늘어납니다.

이 레슨에서는 아래 시나리오를 계속 씁니다.

`문의 도착 → 분류 담당 → 검색 담당 → 초안 담당 → 검수 담당 → 승인 → 발송`

## 4. 실무 예제

### 실무에서 이게 어떻게 쓰이나

고객센터에 문의 메일이 도착하면, 한 AI가 문의 내용을 분류합니다. 급한 건인지, 어떤 카테고리인지 먼저 가려냅니다.

분류 결과를 받은 다음 AI는 사내 문서에서 관련 내용을 찾고, 또 다른 AI가 그 내용을 바탕으로 답변 초안을 씁니다. 마지막으로 담당자가 초안을 보고 승인하면 발송됩니다.

이렇게 나누면 "분류를 담당하는 AI"만 잘 만들면 되고, "초안을 쓰는 AI"는 검색된 문서만 잘 활용하면 되므로 각 부분을 따로 점검하고 고치기 쉬워집니다.

> 아래 코드는 개념을 눈으로 보기 위한 예시입니다 — 지금 실행할 필요는 없습니다.
> 개강 후 본 과정에서 실제로 돌려보게 됩니다.

```python
# 개념 예시 — 여러 AI 역할을 그래프로 선언하는 방식(개강 후 실습에서 다룸)
workflow = {
    "nodes": {
        "classifier": "문의 내용을 분류하는 AI",        # 분류 담당
        "researcher": "관련 문서를 찾는 AI",            # 검색 담당
        "drafter": "답변 초안을 쓰는 AI",               # 초안 담당
        "reviewer": "사람 — 초안을 검수하고 승인",       # 사람이 개입하는 지점
    },
    "edges": [
        ("classifier", "researcher"),   # 분류 다음 검색으로
        ("researcher", "drafter"),      # 검색 다음 초안 작성으로
        ("drafter", "reviewer"),        # 초안 다음 사람 승인으로
    ],
    "max_loops": 3,  # 승인이 반복 반려될 때 무한 루프를 막는 상한
}
```

## 5. 실무 팁

- 역할(에이전트)을 늘릴수록 호출 횟수가 늘어나 비용과 응답 시간이 함께 늘어납니다.
- 각 단계의 출력 형식을 먼저 정해 두어야 다음 단계가 그 형식을 믿고 이어받을 수 있습니다. 2-7 구조화 출력에서 본 내용과 이어집니다.
- 루프에는 반드시 최대 반복 횟수를 둡니다. 그렇지 않으면 실수 하나가 무한 반복으로 이어질 수 있습니다.

이 시나리오에는 순차·병렬·감독자 중 어느 연결 방식이 맞을지 고르고, 그렇게 고른 이유를 적어보세요.

<details>
<summary>정답 보기</summary>

다만 "관련 문서 검색"과 "과거 유사 문의 검색"처럼 서로 독립적인 검색이 여러 개라면 그 부분만 병렬로 동시에 처리할 수도 있습니다.

</details>

### 해보기

<details>
<summary>정답 보기</summary>

담당자가 초안을 계속 반려하면 "초안 담당 → 검수 담당 → 다시 초안 담당"이 끝없이 반복될 수 있습니다.

이를 막으려면 반려 횟수에 상한(예: 최대 3회)을 두고, 상한을 넘으면 사람에게 직접 알려 처리를 넘기는 규칙을 함께 설계해야 합니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 한 AI에게 전부 시키는 대신 역할을 나눠 각자 한 가지만 맡기는 것이 여러 AI 구조의 기본 발상이다
- 역할(에이전트)을 잇는 방식은 크게 순차·병렬·감독자 세 가지다
- 역할들이 주고받은 내용을 상태로 기록해야 다음 역할이 이어받을 수 있다
- 루프에는 반드시 최대 반복 횟수를 두어야 한다
- 이 레슨의 코드는 읽기용이며, 실제로 손으로 돌려보는 것은 개강 후 본 과정에서 다룬다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 오케스트레이션 | 여러 AI(에이전트)의 역할과 순서를 짜서 하나의 작업을 완성하게 하는 것 |
| 에이전트 | 전체 작업 중 한 가지 역할을 맡은 AI |
| 감독자 | 다음에 어느 에이전트를 부를지 그때그때 정하는 역할 |
| 노드 | 그래프에서 하나의 역할(에이전트)을 나타내는 지점 |
| 상태 | 역할들이 주고받은 내용을 기록해 다음 역할이 이어받을 수 있게 하는 값 |
| 도구 호출 | 에이전트가 검색·계산 등 외부 기능을 불러 쓰는 것 |
| 루프 제한 | 같은 역할이 반복 호출될 때 무한히 돌지 않도록 두는 최대 횟수 |

<details>
<summary>정답 보기</summary>

순차 연결은 다음 역할이 미리 정해져 있어 항상 같은 순서로 진행됩니다. 감독자 연결은 감독자 역할이 지금 상황을 보고 다음에 누구를 부를지 그때그때 정하므로, 상황에 따라 순서가 달라질 수 있습니다.

</details>
