## 1. 학습 목표

이 레슨을 마치면 다음을 알아듣습니다.

- 프롬프트 버전관리(prompt versioning)와 평가 자동화(eval automation)가 무엇을 가리키는지 한 문장으로 말할 수 있다
- 프롬프트 변경에도 배포 파이프라인처럼 자동 검사가 필요한 이유를 말할 수 있다
- 골든셋 평가가 배포 흐름의 어느 자리에서 도는지 안다
- 평가 결과를 버전별로 남겨두는 이유를 알아듣는다

## 2. 왜 배우나

`2-7-promptops`에서 골든셋으로 프롬프트를 손으로 평가해 봤습니다. 이 레슨은 그 평가를 사람이 매번 기억해서 돌리지 않고 배포 흐름에 자동으로 묶어 두는 운영 방식을 다룹니다.

사람이 잊으면 회귀도 함께 놓칩니다. 개강 후 실습에서 "평가 파이프라인"이라는 말이 나오면 이 흐름을 가리킨다는 것을 알면 됩니다.

## 3. 개념 설명

### 🏷️ 프롬프트 버전 관리 — 계약서 개정 이력처럼 남기기

파일과 태그로 프롬프트를 관리하면 어떤 버전이 언제 운영에 있었는지 남길 수 있습니다. 계약서를 개정할 때마다 새 판을 찍고 이전 판을 보관해 두는 것과 같은 방식입니다.

### 🚦 평가 자동화가 붙는 위치 — 출하 전 검사대

변경이 배포 파이프라인에 올라오면 자동으로 평가가 돌고, 기준을 채우지 못하면 배포가 막힙니다. 공장에서 제품이 출하되기 전 검사대를 통과해야 하는 것과 같은 구조입니다.

**흐름:** 프롬프트 변경 → 자동 평가 실행 → 기준 통과 여부 → 통과하면 배포 / 실패하면 차단

### 📈 평가 결과를 버전별로 남기기

평가가 끝날 때마다 점수를 버전과 함께 기록해 두면, 나중에 어떤 버전에서 무엇이 떨어졌는지를 이력으로 비교할 수 있습니다.

### 🙋 자동화되는 것과 사람 몫의 경계

형식 통과율처럼 코드로 잴 수 있는 기준은 자동화되고, 톤처럼 사람이 판단해야 하는 기준은 남습니다. `2-7-promptops`에서 본 구분과 같은 원칙입니다.

## 4. 실무 예제

### 실무에서 이게 어떻게 쓰이나

프롬프트 한 줄을 고쳐 톤을 부드럽게 바꿨더니, 특정 유형의 질문에서만 답이 짧아지고 필수 항목이 빠지기 시작했습니다. 사람이 매번 눈으로 확인했다면 이 변화를 놓쳤을 가능성이 큽니다.

이 팀은 프롬프트 파일이 바뀔 때마다 배포 파이프라인이 골든셋 평가를 자동으로 돌리도록 설정해 두었습니다. 평가 점수가 기준선에 못 미치자 배포가 자동으로 막혔고, 담당자는 배포 전에 원인을 확인할 수 있었습니다.

> 아래 설정은 개념을 눈으로 보기 위한 예시입니다 — 지금 실행할 필요는 없습니다.
> 개강 후 본 과정에서 실제로 다뤄보게 됩니다.

```yaml
# .github/workflows/prompt-eval.yml — 프롬프트 파일이 바뀌면 자동으로 평가가 도는 설정 예시
name: prompt-eval
on:
  pull_request:
    paths:
      - "prompts/**"                 # 프롬프트 파일이 바뀔 때만 이 워크플로가 돈다
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 골든셋 평가 실행
        run: npx tsx eval.ts          # 2-7-promptops에서 손으로 돌려본 그 평가 스크립트
      - name: 기준선과 비교
        run: npx tsx compare-baseline.ts   # 이전 버전 점수와 비교해 회귀 여부 판단
    # 평가가 기준선에 못 미치면 이 워크플로가 실패로 끝나고 배포가 막힌다
```

## 5. 실무 팁

- 평가 기준선을 처음부터 100점으로 잡으면 아무것도 배포되지 않습니다. 낮은 기준에서 시작해 천천히 올려 나갑니다.
- 골든셋은 이상적인 케이스가 아니라 실제 실패 사례로 채웁니다. `2-7-promptops`에서 다룬 것과 같은 원칙입니다.
- 어떤 버전이 언제 운영에 있었는지 기록이 남아야 사고가 났을 때 원인을 찾을 수 있습니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 프롬프트 버전관리는 파일과 태그로 어떤 버전이 언제 운영에 있었는지 남기는 것이다
- 평가 자동화는 프롬프트 변경이 배포 파이프라인에 올라올 때 자동으로 도는 검사다
- 평가 결과를 버전별로 기록해야 이후에 비교하고 원인을 찾을 수 있다
- 자동으로 잴 수 있는 기준과 사람이 봐야 하는 기준은 다르다
- 이 레슨의 코드는 읽기용이며, 실제로 손으로 돌려보는 것은 개강 후 본 과정에서 다룬다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 버전 태그 | 프롬프트 파일에 매기는 버전 식별자 |
| 골든셋 | 정답이 정해진 입력·기대 출력 목록 |
| 회귀 | 이전에는 통과하던 케이스가 갑자기 실패하는 것 |
| 기준선 | 평가 점수가 넘어야 하는 최소 기준 |
| 자동 평가 | 프롬프트 변경 시 배포 파이프라인이 자동으로 돌리는 평가 |
| 배포 차단 | 평가 기준을 못 채웠을 때 배포를 막는 것 |
| 실행 이력 | 어떤 버전이 언제 운영에 있었는지 남긴 기록 |

**스스로 점검**

1. 평가 자동화가 없다면, 프롬프트를 고친 뒤 회귀가 생겼다는 것을 누가 어떻게 알아챌 수 있을까요?

<details>
<summary>정답 보기</summary>

사람이 우연히 이상한 답을 보거나, 사용자가 불만을 제기해야만 알아챌 수 있습니다. 상황에 따라 다르게 나타나므로, 원인을 프롬프트 변경으로 좁히기까지 시간이 오래 걸립니다.

평가 자동화는 이 발견을 사람의 우연이 아니라 배포 파이프라인의 필수 단계로 만듭니다.

</details>

2. 골든셋에 실제 실패 사례를 채워야 하는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

이상적으로 상상한 케이스는 실제 서비스에서 벌어지는 문제를 재현하지 못할 가능성이 높기 때문입니다. 과거에 실제로 실패했던 입력이어야 이번 변경이 같은 문제를 다시 일으키지 않는지 정확히 확인할 수 있습니다.

`2-7-promptops`에서 다룬 것과 같은 원칙입니다.

</details>
