## 1. 학습 목표

이 레슨을 마치면 다음을 알아듣습니다.

- 모니터링(monitoring)이 LLM 서비스에서 왜 일반 서버 모니터링과 다른지 말할 수 있다
- 시스템 지표와 품질 지표가 각각 무엇을 보는지 구분해서 말할 수 있다
- 개인정보(PII)가 프롬프트·로그·평가 데이터 중 어디를 타고 흐를 수 있는지 안다
- 프롬프트 인젝션(prompt injection)이 무엇을 노리는 공격인지 알아듣는다

## 2. 왜 배우나

LLM 서비스는 오류 없이 잘 돌아가는데도 답이 이상한 상태가 가능합니다. 일반 서버 모니터링(오류율·응답 시간)만 보면 이런 문제는 잡히지 않습니다.

게다가 사용자가 입력한 문장이 프롬프트·로그를 타고 흘러 나갈 수 있어, 그 안에 개인정보가 섞여 있으면 뜻하지 않게 유출될 수 있습니다.

## 3. 개념 설명

### 📊 무엇을 보는가 — 시스템 지표와 품질 지표

두 지표는 서로 다른 것을 봅니다. 하나가 정상이어도 다른 하나가 문제일 수 있습니다.

| 구분 | 무엇을 보는가 | 예시 |
|------|--------------|------|
| 시스템 지표 | 서비스가 정상적으로 돌고 있는가 | 오류율, 응답 지연, 비용 |
| 품질 지표 | 응답의 내용이 쓸 만한가 | 형식 통과율, 거절률, 사용자 피드백 |

### 🔔 알림 설계 — 평소 값 위에 기준을 얹기

알림 임계값을 정하는 원칙은 평소 값을 먼저 재고 그 위에서 정하는 것입니다. 아무 근거 없이 숫자를 먼저 정하면 알림이 항상 울리거나 전혀 안 울리게 됩니다.

알림이 너무 잦으면 아무도 들여다보지 않게 됩니다. 구체적인 숫자는 서비스마다 다르므로 팀이 직접 정합니다.

### 🔒 개인정보 취급 — 어디에 남고 어디에 남으면 안 되는가

개인정보는 프롬프트, 로그, 평가 데이터 세 곳을 타고 흐를 수 있습니다. 남겨야 하는 항목과 남기면 안 되는 항목을 미리 정해 마스킹(masking, 민감한 값을 가려서 저장하는 것)으로 처리합니다.

### 🛡️ 프롬프트 인젝션과 감사 추적

프롬프트 인젝션은 사용자 입력이 원래 지시를 덮어쓰려 하는 것을 말합니다. `2-7-prompt-patterns`에서 본 "사용자 입력을 구분자로 감싸기"가 이 공격에 대한 대응입니다.

감사 추적(audit trail)은 누가 언제 무엇을 요청했고 어떤 응답이 나갔는지 남기는 기록으로, 사고가 났을 때 되짚어 볼 근거가 됩니다.

**흐름:** 요청 → 처리 → 지표 수집 → 임계값 비교 → 알림 → 사람 판단 → 기록

## 4. 실무 예제

### 실무에서 이게 어떻게 쓰이나

오류율은 정상 범위인데 사용자 불만이 늘어난 적이 있었습니다. 시스템 지표만 보던 팀은 원인을 찾지 못하다가, 품질 지표(형식 통과율)를 확인하고서야 특정 입력 유형에서 응답이 자주 깨지고 있다는 것을 발견했습니다.

같은 팀이 로그를 점검하다가 사용자 입력 원문에 연락처로 보이는 값이 마스킹 없이 그대로 남아 있는 것을 발견하고, 로그 저장 전에 마스킹 단계를 추가했습니다.

## 5. 실무 팁

- 로그에 남길 항목과 남기지 않을 항목은 설계 단계에서 미리 정합니다. 나중에 이미 쌓인 로그에서 지우기는 훨씬 어렵습니다.
- 알림은 사람이 지금 바로 행동할 수 있는 것에만 겁니다. 행동할 수 없는 알림은 소음이 됩니다.
- 사용자 입력과 시스템 지시는 구분자로 감싸 분리합니다. `2-7-prompt-patterns`에서 다룬 것과 같은 습관입니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- LLM 서비스는 오류 없이도 답이 이상할 수 있어 품질 지표를 따로 봐야 한다
- 시스템 지표는 서비스가 정상인지, 품질 지표는 응답이 쓸 만한지를 본다
- 개인정보는 프롬프트·로그·평가 데이터 세 곳을 타고 흐를 수 있어 마스킹이 필요하다
- 프롬프트 인젝션은 사용자 입력이 지시를 덮어쓰려는 공격이며 구분자로 감싸 대응한다
- 구체적인 임계값·정책 수치는 서비스마다 다르므로 팀이 직접 정한다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 관측(observability) | 서비스 내부 상태를 지표·로그로 들여다볼 수 있게 하는 것 |
| 시스템 지표 | 서비스가 정상적으로 돌고 있는지 보여주는 지표 |
| 품질 지표 | 응답의 내용이 쓸 만한지 보여주는 지표 |
| 임계값 | 알림을 울릴지 판단하는 기준값 |
| 마스킹 | 민감한 값을 가려서 저장하거나 기록하는 것 |
| 개인정보(PII) | 개인을 식별할 수 있는 정보 |
| 프롬프트 인젝션 | 사용자 입력이 원래 지시를 덮어쓰려 하는 공격 |
| 감사 추적 | 요청·응답을 나중에 되짚어 볼 수 있게 남기는 기록 |

**스스로 점검**

1. 오류율이 정상인데도 사용자 불만이 늘어날 수 있는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

오류율은 요청이 실패 없이 처리됐는지만 보여줍니다. 응답이 형식은 정상이어도 내용이 부정확하거나 쓸모없다면 오류율에는 잡히지 않습니다.

그래서 시스템 지표만이 아니라 품질 지표를 함께 봐야 이런 문제를 발견할 수 있습니다.

</details>

2. 알림 임계값을 아무 근거 없이 먼저 정하면 안 되는 이유는 무엇일까요?

<details>
<summary>정답 보기</summary>

평소 값이 어느 범위에서 움직이는지 모르는 채로 숫자를 정하면, 그 숫자가 평소에도 자주 넘거나 반대로 절대 넘지 않는 값이 될 수 있습니다.

전자는 알림이 너무 잦아 아무도 보지 않게 되고, 후자는 실제 문제가 생겨도 알림이 울리지 않게 됩니다. 그래서 평소 값을 먼저 재고 그 위에서 기준을 정합니다.

</details>
