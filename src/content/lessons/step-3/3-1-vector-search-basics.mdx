## 1. 학습 목표

이 레슨을 마치면 다음을 알아듣습니다.

- 임베딩(embedding)과 벡터 검색(vector search)이 무엇을 하는 기술인지 한 문장으로 말할 수 있다
- 언제, 왜 벡터 검색이 필요한지(키워드 검색과 무엇이 다른지) 말할 수 있다
- 벡터 검색이 RAG(검색 증강 생성) 파이프라인에서 어느 자리에 놓이는지 안다
- 청크(chunk)와 메타데이터 필터가 벡터 검색의 결과 품질에 어떤 영향을 주는지 알아듣는다

## 2. 왜 배우나

개강 후 Step 3 실습에서 강사가 "이 문서를 임베딩해서 벡터DB에 넣고, 유사도로 검색한다"라고 말하는 순간이 옵니다. 이 레슨은 그 말을 알아듣기 위한 준비이지, 여러분이 지금 벡터 검색 시스템을 직접 만들게 하려는 것이 아닙니다. 개념과 용어를 미리 알아두면 개강 후 실습 시간을 설명 듣는 데 쓰지 않고 바로 손을 움직이는 데 쓸 수 있습니다.

## 3. 개념 설명

### 🗺️ 임베딩 — 글을 지도 위의 점으로 바꾸기

임베딩(embedding, 글을 숫자 배열로 바꾼 것)은 문장을 의미가 비슷한 문장끼리 가깝게 모이는 지도 위의 한 점으로 옮기는 작업입니다. "강아지"와 "반려견"은 같은 단어가 아니어도 이 지도 위에서는 아주 가까운 점이 됩니다.

### 🔍 벡터 검색 — 지도에서 가장 가까운 점 찾기

벡터 검색(vector search)은 이 지도 위에 "질문"이라는 점을 하나 찍고, 그 점에서 가장 가까운 점(문서)들을 찾는 것입니다. 키워드 검색이 "같은 단어가 있는가"를 보는 것과 달리, 벡터 검색은 "뜻이 비슷한가"를 봅니다.

### ✂️ 청크 — 긴 문서를 검색 단위로 자르기

청크(chunk, 문서를 검색하기 좋은 크기로 잘라낸 조각)는 책 한 권을 통째로 임베딩하지 않고, 문단이나 몇 문장 단위로 잘라서 각각을 지도 위의 점으로 만드는 단위입니다. 청크가 너무 크면 점 하나에 여러 주제가 뭉뚱그려져 흐릿해지고, 너무 작으면 문맥이 끊깁니다.

### 🏷️ 메타데이터 필터 — 지도에서 구역 먼저 좁히기

메타데이터(metadata, 문서에 붙는 부가 정보 — 카테고리·날짜 등)는 벡터 검색을 하기 전에 지도의 특정 구역만 먼저 골라내는 역할을 합니다. "전자제품 카테고리 안에서만 가까운 점을 찾아줘" 같은 조건을 걸 수 있습니다.

## 4. 실무 예제

### 실무에서 이게 어떻게 쓰이나

전자상거래 서비스의 "이 상품과 비슷한 상품" 추천 기능이 대표적인 예입니다. 상품 설명을 미리 임베딩해 지도 위에 점으로 찍어두고, 사용자가 상품 하나를 보고 있으면 그 상품의 점에서 가장 가까운 점 5개를 찾아 "비슷한 상품"으로 보여줍니다.

이때 메타데이터 필터를 함께 쓰면 "같은 카테고리 안에서만" 비슷한 상품을 찾도록 좁힐 수 있습니다 — 아무리 뜻이 비슷해도 신발을 보고 있는데 신발 관리용 브러시가 추천되는 것은 원하는 결과가 아니기 때문입니다.

> 아래 코드는 개념을 눈으로 보기 위한 예시입니다 — 지금 실행할 필요는 없습니다.
> 개강 후 본 과정에서 실제로 돌려보게 됩니다.

```typescript
// 개념 예시 — pgvector를 쓰는 Supabase 테이블에서 "비슷한 상품 5개" 찾기
const { data: similarProducts } = await supabase.rpc("match_products", {
  query_embedding: productEmbedding, // 지금 보고 있는 상품을 임베딩한 벡터
  match_category: "shoes",           // 메타데이터 필터 — 같은 카테고리로 좁히기
  match_count: 5,                    // 가장 가까운 점 5개
});
```

## 5. 실무 팁

- 청크가 너무 크면 점 하나에 여러 주제가 섞여 검색 결과가 흐릿해지고, 너무 작으면 문맥 없이 조각난 답이 나옵니다.
- 메타데이터는 문서를 저장할 때 미리 붙여둬야 합니다 — 나중에 필터가 필요해졌다고 그때 붙이면 이미 저장해둔 문서를 전부 다시 처리해야 합니다.
- 임베딩 모델을 바꾸면 지도 자체가 바뀌는 것과 같습니다 — 예전에 만든 벡터는 새 지도 위에서 더 이상 의미가 없어 전부 다시 임베딩해야 합니다.

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- 임베딩은 글을 의미가 비슷한 것끼리 가까이 모이는 지도 위의 점으로 바꾸는 것이다
- 벡터 검색은 그 지도에서 질문과 가장 가까운 점(문서)을 찾는 것이다
- 청크는 문서를 검색 단위로 자른 조각이고, 크기가 너무 크거나 작으면 검색 품질이 떨어진다
- 메타데이터 필터는 벡터 검색 전에 후보군을 미리 좁히는 역할을 한다
- 이 레슨의 코드는 읽기용이며, 실제로 손으로 돌려보는 것은 개강 후 본 과정에서 다룬다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 임베딩 | 글을 의미가 비슷한 것끼리 가깝게 모이도록 숫자 배열로 바꾼 것 |
| 벡터 | 임베딩의 결과물인 숫자 배열, 지도 위의 한 점 |
| 유사도 | 두 벡터(점)가 얼마나 가까운지를 나타내는 값 |
| 청크 | 문서를 검색 단위로 잘라낸 조각 |
| 메타데이터 | 문서에 붙는 부가 정보(카테고리·날짜 등) |
| 벡터 DB | 벡터를 저장하고 가까운 점을 빠르게 찾아주는 데이터베이스 |
| pgvector | PostgreSQL에서 벡터를 저장·검색할 수 있게 해주는 확장 기능 |

**스스로 점검**

1. "강아지"를 검색했는데 "반려견"이라는 단어가 들어간 문서가 결과에 나왔습니다. 왜 이런 일이 가능할까요?

<details>
<summary>정답 보기</summary>

벡터 검색은 "같은 단어인가"가 아니라 "뜻이 비슷한가"를 보기 때문입니다. "강아지"와 "반려견"은 다른 단어지만 임베딩 지도 위에서는 아주 가까운 점으로 놓이므로, 단어가 일치하지 않아도 검색될 수 있습니다.

</details>

2. 회사가 임베딩 모델을 A에서 B로 교체하기로 했습니다. 기존에 저장해둔 수만 개 문서의 벡터를 그대로 두고 새 질문만 모델 B로 임베딩해서 검색해도 될까요?

<details>
<summary>정답 보기</summary>

안 됩니다. 서로 다른 임베딩 모델은 서로 다른 지도를 만듭니다 — 모델 A로 만든 점과 모델 B로 만든 점은 같은 지도 위에 있지 않으므로 거리(유사도) 비교 자체가 의미가 없습니다. 모델을 바꾸면 기존 문서를 전부 새 모델로 다시 임베딩해야 합니다.

</details>
