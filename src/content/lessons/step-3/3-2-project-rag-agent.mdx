## 1. 학습 목표

이 프로젝트에서 무엇을 만들고 무엇을 증명하는지 먼저 짚고 넘어갑니다.

- **무엇을 만드나:** 사내 문서를 근거로 답하는 지식 에이전트(Knowledge Agent)를 준비합니다.
- **무엇을 증명하나:** 답변이 어느 문서에서 나왔는지 근거를 제시하고, 그 품질을 평가셋으로 측정할 수 있음을 준비 단계에서 확인합니다.
- 개강 후 팀 프로젝트에서 이 에이전트를 실제로 만들 때, 오늘 준비해둔 것들이 그대로 출발점이 됩니다.

## 2. 왜 배우나

이 프로젝트는 지금까지 배운 여러 모듈이 처음으로 한 흐름에 합쳐지는 자리입니다.

- `3-1-vector-search-basics` — 임베딩·청크가 문서를 검색 가능한 형태로 만드는 재료가 됩니다
- `3-1-hybrid-search-reranking` — 검색 품질을 어떻게 끌어올릴지에 대한 개념을 가져옵니다
- `2-7-prompt-patterns` — 구조화 출력으로 답변과 근거를 함께 받는 방법을 가져옵니다

아직 이 레슨들을 보지 않았어도 slug만 기억해뒀다가, 프로젝트를 실제로 시작할 때 막히는 부분이 있으면 해당 레슨으로 돌아가 복습하면 됩니다.

## 3. 개념 설명

### 무엇을 만드나 — 전체 구조

이 프로젝트의 흐름은 `문서 수집 → 청크 나누기 → 임베딩 → 벡터 저장소 → 질문 검색 → LLM 답변 + 근거 표시` 순서로 이어집니다.

| 단계 | 하는 일 | 어느 레슨에서 나왔나 |
|------|---------|----------------------|
| 문서 수집 | 팀이 자주 찾는 문서를 모은다 | 이 레슨 ④ 체크리스트 |
| 청크 나누기 | 문서를 검색 단위로 자른다 | `3-1-vector-search-basics` |
| 임베딩 | 청크를 지도 위의 점으로 바꾼다 | `3-1-vector-search-basics` |
| 벡터 저장소 | 임베딩을 저장하고 가까운 점을 찾아준다 | `3-1-vector-search-basics` |
| 질문 검색 | 키워드+벡터 검색으로 관련 청크를 찾는다 | `3-1-hybrid-search-reranking` |
| LLM 답변 + 근거 표시 | 찾은 청크를 근거로 답변을 구조화해 돌려준다 | `2-7-prompt-patterns` |

## 4. 실무 예제

### 사전 준비 체크리스트

이 프로젝트를 개강 첫날 바로 시작하려면 아래를 미리 준비해둡니다.

| 준비물 | 왜 필요한가 | 지금 할 일 |
|--------|-------------|-----------|
| 대상 문서 5~10개 | 팀이 실제로 자주 찾는 문서라야 실습 의미가 있습니다 | 문서 형식·길이를 확인하고, 외부로 내보내도 되는 문서인지 먼저 점검해두기 |
| 임베딩·LLM API 키 | 문서를 벡터로 바꾸고 답변을 생성하려면 필요합니다 | 발급받아 `.env.local`에 저장해두기(코드·대화창에 붙여넣지 않기) |
| 벡터 저장소 | 임베딩을 저장하고 검색할 공간이 필요합니다 | Supabase 프로젝트에서 벡터 확장 기능을 켤 수 있는지 확인해두기 |
| 평가셋 초안 | 답변 품질을 감이 아니라 근거로 판단하기 위해 필요합니다 | 질문-정답-근거 10문항을 표로 미리 적어두기 |
| 근거 표시 방식 합의 | 답변이 어느 문서에서 나왔는지 보여줄 형태를 미리 정해야 합니다 | 문서명만 보여줄지, 문단을 인용할지 팀과 합의해두기 |

> 이 체크리스트는 무엇을 준비할지만 알려줍니다 — 실제 구현 방법은 개강 후
> 본 과정에서 팀과 함께 설계합니다.

## 5. 실무 팁

- 문서를 나중에 모으면 프로젝트 절반이 지나갑니다 — 첫 주에 다 모아두는 편이 안전합니다.
- 평가셋 없이 "좋아진 것 같다"로 판단하면 나중에 무엇이 문제였는지 못 찾습니다.
- 근거 없이 답만 주는 순간 신뢰가 무너집니다 — 어느 문서에서 나온 답인지 항상 표시합니다.
- 시간과 역할을 미리 나눠두면 개강 첫날 회의가 짧아집니다(문서 수집·파이프라인·평가·화면 담당).

## 6. 핵심 정리 및 스스로 점검

**핵심 정리**

- [ ] 팀이 자주 찾는 문서 5~10개를 모았다(외부로 내보내도 되는지 확인 완료)
- [ ] 임베딩·LLM API 키를 발급받아 `.env.local`에 저장했다(코드에는 쓰지 않았다)
- [ ] Supabase 프로젝트에서 벡터 확장 기능을 켤 수 있는지 확인했다
- [ ] 질문-정답-근거 평가셋 10문항 초안을 표로 작성했다
- [ ] 근거 표시 방식(문서명만 vs 문단 인용)을 팀과 합의했다

**이 레슨의 단어**

| 단어 | 뜻 |
|------|-----|
| 지식 에이전트 | 사내 문서를 근거로 질문에 답하는 RAG 기반 챗봇 |
| 평가셋 | 질문-정답-근거 세트를 모아 답변 품질을 측정하는 표 |
| 근거 | 답변이 어느 문서·어느 부분에서 나왔는지 보여주는 표시(citation) |
| 청크 겹침 | 청크 경계에서 문맥이 끊기지 않도록 앞뒤를 조금씩 겹쳐 자르는 방식 |
| 검색 정확도 | 질문에 실제로 관련 있는 청크를 얼마나 잘 찾아오는지 나타내는 값 |
| 환각 | 근거 없이 그럴듯하게 지어낸 답변을 내놓는 현상 |

**스스로 점검**

1. 왜 평가셋을 프로젝트를 시작하기 전에 미리 준비해두면 좋을까요?

<details>
<summary>정답 보기</summary>

평가셋이 없으면 "예전보다 좋아진 것 같다"는 감으로만 판단하게 되어, 나중에 어떤 부분이 실제로 개선됐는지 원인을 짚어내기 어렵습니다. 질문-정답-근거를 미리 정해두면 무엇이 바뀔 때 답변이 좋아지고 나빠지는지 비교할 기준이 생깁니다.

</details>

2. 근거(citation) 없이 답변만 주는 지식 에이전트를 만들면 왜 문제가 될까요?

<details>
<summary>정답 보기</summary>

근거가 없으면 사용자는 답변이 실제 문서에 기반한 것인지, 아니면 환각인지 확인할 방법이 없습니다. 어느 문서에서 나온 답인지 보여줘야 사용자가 스스로 검증할 수 있고, 신뢰할 수 있는 도구가 됩니다.

</details>
