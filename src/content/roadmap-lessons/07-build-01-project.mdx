## 왜 0에서 1이 가장 강한 이력인가

이력서에 강의 수료증을 열 개 붙이는 것보다, 작더라도 내 손으로 처음부터 끝까지 만들어 세상에 내놓은 프로젝트 하나가 훨씬 강합니다.

이유는 단순합니다. 수료증은 "배웠다"를 증명하지만, 출시한 프로젝트는 "만들 수 있다"를 증명합니다. 문제를 정의하고, 스코프를 정하고, 막히는 곳을 뚫고, 배포까지 밀어붙인 사람만이 가진 흔적이 거기 남기 때문입니다.

이 레슨은 그 하나를 실제로 끝내는 방법을 다룹니다. 거창한 게 아니라, 작지만 진짜 동작하고 남에게 보여 줄 수 있는 것을 만드는 실전 순서입니다.

## 채널톡이 이 경험을 우대하는 이유

채널톡의 Forward Deployed Engineer 채용에는 0에서 1을 만들어 본 경험, 개념 증명(<Term id="poc">PoC</Term>)을 돌려 본 경험, 시행착오를 겪어 본 경험을 우대한다고 적혀 있습니다.

이건 회사가 실제로 하는 일과 정확히 맞닿아 있습니다. 고객사 앞에서 모호한 요구를 듣고, 그걸 빠르게 동작하는 무언가로 바꿔 보여 주고, 반응을 보고 고치는 일이 곧 0에서 1이기 때문입니다.

그래서 "완성된 대형 서비스를 유지보수한 경험"보다 "아무것도 없는 상태에서 무언가를 세워 본 경험"을 더 쳐줍니다. 후자가 훨씬 드물고, 가르치기 어려운 능력이라서 그렇습니다.

## 좋은 프로젝트 고르기

좋은 0에서 1 프로젝트에는 세 가지 조건이 있습니다.

첫째, 작고 진짜인 문제를 풉니다. 상상 속 사용자가 아니라 나 자신이나 곁의 누군가가 실제로 겪는 불편이어야 합니다. 내가 매주 반복하는 귀찮은 일, 친구가 늘 손으로 하는 정리 같은 것입니다.

둘째, AI가 곁다리가 아니라 핵심 역할을 합니다. 버튼 몇 개짜리 앱에 AI를 구색으로 얹은 게 아니라, AI가 없으면 그 프로젝트가 성립하지 않아야 합니다. 채널톡이 보는 건 AI를 다뤄 본 흔적입니다.

셋째, 한 사람이 몇 주 안에 끝낼 만한 크기입니다. 반년짜리 야심작은 대개 완성되지 못한 채 이력에서 사라집니다. 작게 끝내고 하나 더 만드는 편이 언제나 낫습니다.

## 모호한 문제를 AI 문제로 바꾸기

채널톡이 필수로 꼽는 역량이 "모호한 비즈니스 문제를 AI 문제로 치환해 빠르게 가설을 검증하는 것"입니다. 프로젝트 시작이 바로 이 연습의 장입니다.

모호한 문제는 대개 이렇게 생겼습니다. "고객 문의를 정리하는 게 너무 힘들어." 이걸 AI 문제로 바꾼다는 건, AI가 실제로 답할 수 있는 뾰족한 질문으로 다시 쓰는 것입니다. 예를 들면 "들어온 문의 한 건을 환불, 배송, 기타 중 하나로 분류할 수 있는가"입니다.

이렇게 좁히면 곧바로 시험해 볼 수 있습니다. 문의 스무 건을 손으로 분류해 정답을 만들어 두고, 모델에게 같은 걸 시켜 몇 개나 맞히는지 봅니다. 이 작은 시험 하나가 "될 것 같다"는 감을 "이 정도는 된다"는 숫자로 바꿔 줍니다.

```python
# 가설: "문의를 세 갈래로 분류할 수 있는가"를 30분 만에 검증한다.
# 답을 정해진 형식으로 받아(구조화 출력) 자동 채점이 되게 한다.
from anthropic import Anthropic

client = Anthropic()  # ANTHROPIC_API_KEY 환경변수에서 자동으로 읽는다

CATEGORIES = ["환불", "배송", "기타"]

def classify(inquiry: str) -> str:
    resp = client.messages.create(
        model="claude-opus-5",
        max_tokens=256,
        # 출력을 정해진 값들 중 하나로 강제해, 프로그램이 바로 채점할 수 있게 한다.
        output_config={
            "format": {
                "type": "json_schema",
                "schema": {
                    "type": "object",
                    "properties": {"category": {"type": "string", "enum": CATEGORIES}},
                    "required": ["category"],
                    "additionalProperties": False,
                },
            }
        },
        messages=[{"role": "user", "content": f"다음 문의를 분류하세요:\n{inquiry}"}],
    )
    # 늘 같은 형식의 JSON이 오므로 손으로 파싱하다 깨질 일이 없다.
    import json
    for block in resp.content:
        if block.type == "text":
            return json.loads(block.text)["category"]
    return "기타"

# 손으로 만든 정답 20건과 대조해 정확도를 재면 가설이 검증된다.
```

이 코드가 <Term id="structured-output">구조화 출력</Term>으로 답을 정해진 형식으로 받는 이유는, 결과를 사람이 아니라 프로그램이 곧바로 채점하게 하기 위해서입니다. 가설검증의 핵심은 감이 아니라 숫자로 확인하는 것입니다.

## 스코프를 줄이는 기술

첫 프로젝트가 실패하는 가장 흔한 이유는 스코프가 너무 커서입니다. 이걸 막는 무기가 <Term id="vertical-slice">수직 슬라이스</Term>입니다.

수직 슬라이스란, 기능을 옆으로 넓게 벌이는 대신 처음부터 끝까지 관통하는 얇은 한 줄기를 먼저 완성하는 것입니다. 케이크를 만들 때 층을 다 쌓은 뒤 자르는 게 아니라, 처음부터 한 조각만 온전하게(빵과 크림과 장식까지) 만들어 보는 것과 같습니다.

예를 들어 문서 질의응답 서비스를 만든다면, 처음 목표는 "문서 백 개를 예쁜 화면에서 검색"이 아닙니다. "문서 딱 하나를 넣고, 질문 하나에, 답 하나가 화면에 뜨는" 가장 얇은 한 줄기입니다. 이게 되면 이미 전체 골격이 동작하는 것입니다.

이 얇은 줄기 하나가 동작하고 나면, 그 위에 문서 수를 늘리고 화면을 다듬는 건 곁가지일 뿐입니다. 얇게라도 끝에서 끝까지 한 번 이어 본 프로젝트는 이미 절반 이상 온 것입니다.

이때 경계할 게 <Term id="scope-creep">스코프 크리프</Term>입니다. 만들다 보면 "이것도 있으면 좋겠다"가 계속 붙어 프로젝트가 끝없이 부풀어 오르는 현상입니다. 떠오르는 추가 기능은 지우지 말고 "나중에 목록"에 적어만 두고, 지금 줄기부터 끝내세요.

## 얇게라도 동작하는 것부터

여기서 헷갈리기 쉬운 게 <Term id="mvp">MVP</Term>(최소 기능 제품)와 그냥 미완성의 차이입니다.

MVP는 기능이 적지만 그 적은 기능만큼은 진짜로 동작해 사람에게 가치를 주는 것입니다. 반면 미완성은 여기저기 만들다 만 것이라, 어느 것도 온전히 동작하지 않습니다. 앞의 수직 슬라이스가 바로 MVP를 만드는 방법입니다.

판단 기준은 하나입니다. "이걸 지금 남에게 보여 주면 한 가지 일은 확실히 해낼 수 있는가." 답이 그렇다면 MVP이고, 이미 이력이 됩니다. 화면이 투박해도, 기능이 하나뿐이어도 괜찮습니다. 동작하는 하나가 화려한 계획서보다 강합니다.

## 끝까지 가기: 배포

내 컴퓨터에서만 도는 것과 인터넷 주소로 남이 열어 볼 수 있는 것은 이력의 무게가 다릅니다. 배포까지 가는 것이 0에서 1의 마지막 1입니다.

다행히 요즘은 배포가 아주 쉬워졌습니다. 코드를 깃 저장소에 올리고 배포 플랫폼(예: Vercel)에 연결하면, 이후로는 코드를 밀어 올릴 때마다 자동으로 새 버전이 인터넷에 올라갑니다. 무료 범위 안에서 개인 프로젝트 하나는 충분히 돌아갑니다.

배포하면 실제 환경에서만 드러나는 문제도 만나게 됩니다. 내 컴퓨터에선 빨랐는데 서버에선 응답이 느린 <Term id="latency">지연시간</Term> 문제, 환경변수(예: API 키)가 서버에 없어서 나는 오류 같은 것입니다. 이런 걸 직접 겪고 해결한 경험 자체가 면접에서 이야기할 거리가 됩니다.

## README와 데모로 보여주기

만든 것을 남이 30초 안에 이해하지 못하면, 안 만든 것과 크게 다르지 않습니다. 그래서 README와 데모가 코드만큼 중요합니다.

README에는 다음을 담습니다. 무슨 문제를 푸는지 한 줄, 어떻게 동작하는지 그림이나 짧은 설명, 왜 이렇게 설계했는지의 핵심 판단, 그리고 직접 돌려 보는 법입니다. 특히 "왜 이렇게 했는가"가 중요합니다. 채널톡이 보는 건 완성도만이 아니라 판단의 흔적입니다.

데모는 30초짜리 화면 녹화 하나면 충분합니다. 실제로 동작하는 걸 눈으로 보여 주는 것이, 잘 썼다는 백 줄의 설명을 이깁니다. 배포된 주소와 이 녹화를 README 맨 위에 두세요.

## 시작할 만한 프로젝트 아이디어

무엇을 만들지 막막하다면, 로드맵에서 배운 기술을 곧장 쓰는 작은 것부터 고르세요.

내 문서로 답하는 질의응답 봇을 만들 수 있습니다. 내가 읽은 자료(PDF나 메모)를 넣고, 질문하면 그 안의 근거로 답하는 <Term id="rag">RAG</Term> 챗봇입니다. 검색은 뜻이 비슷한 조각을 찾는 <Term id="vector-search">벡터 검색</Term>으로 하고, 근거 밖의 이야기를 지어내지 않는지 스무 문항으로 채점해 보면 그 자체로 훌륭한 프로젝트입니다.

반복 작업을 대신하는 작은 도구도 좋습니다. 매주 손으로 하던 분류나 요약(예: 받은 메일을 주제별로 나누기, 회의록에서 할 일만 뽑기)을 자동화하는 것입니다. 문제가 뾰족해서 며칠이면 동작하는 형태가 나옵니다.

이미지가 섞인 자료를 다루는 것도 좋은 도전입니다. 스크린샷이나 표 이미지에서 값을 읽어 정리해 주는 도구는, 글과 이미지를 함께 다루는 경험을 이력에 더해 줍니다. 어느 아이디어든 핵심은 같습니다. 작게, 진짜 문제로, AI가 중심이 되게 고르세요.

## 흔한 함정

스코프를 크게 잡는 것이 가장 흔한 실패입니다. 야심작은 대개 미완성으로 끝납니다. 얇은 수직 슬라이스 하나부터 끝내세요.

완벽주의도 함정입니다. 화면을 예쁘게 다듬느라 정작 핵심 기능을 못 끝내는 경우가 많습니다. 동작이 먼저, 다듬기는 나중입니다.

배포를 미루는 것도 흔합니다. "다 되면 올려야지" 하면 영영 안 올라갑니다. 얇은 줄기가 되는 순간 바로 배포해 두고, 그 위에 쌓으세요.

마지막으로, 만들고 보여 주지 않는 것도 손해입니다. 아무리 좋아도 README와 데모가 없으면 남은 알아보지 못합니다. 만드는 시간의 일부는 반드시 보여 주는 데 쓰세요.

## 직접 해보기

작은 것 하나를 골라 이번 주 안에 배포까지 가 보세요.

1. 내가 실제로 겪는 불편 하나를 AI 문제로 좁혀 한 문장으로 적으세요. "무엇을, 어떤 입력으로 받아, 어떤 출력으로 내는가"가 드러나야 합니다.
2. 그 문제의 가장 얇은 수직 슬라이스를 정하세요. 입력 하나가 들어와 출력 하나가 나오는 최소 줄기입니다. 그것만 먼저 동작시키세요.
3. 동작하는 순간 배포하고, README 맨 위에 배포 주소와 30초 데모를 다세요. 떠오른 추가 기능은 전부 "나중에 목록"으로 미루세요.

여기까지 하면 면접에서 "혼자 무언가를 처음부터 만들어 본 적 있나요"라는 질문에, 링크 하나로 답할 수 있습니다.
