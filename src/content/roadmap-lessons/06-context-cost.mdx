## 이 레슨의 목표와 눈높이

이건 선행학습이 아닙니다. 채널톡 Applied AI Engineer가 실제로 맞닥뜨리는 문제, 그 깊이 그대로 갑니다.

상담 에이전트가 하루 수만 건을 처리하면, 응답 하나의 몇 원 차이가 월말 청구서에서 큰 숫자가 됩니다. 채널톡 채용 공고의 주요 업무에도 "멀티 LLM 인프라 비용 최적화"가 들어 있고, 기술블로그에는 "컨텍스트 비용을 줄이는 설계 패턴"이 따로 정리돼 있습니다.

핵심은 이겁니다. 품질을 깎아 비용을 줄이는 건 누구나 합니다. 어려운 건 품질을 지키면서 비용을 줄이는 설계입니다. 이 레슨을 끝내면 다음을 직접 할 수 있습니다.

1. `usage`로 요청 한 건의 <Term id="token">토큰</Term>과 비용을 정확히 재고, 어디서 돈이 새는지 찾기
2. <Term id="prompt-caching">프롬프트 캐싱</Term>으로 매번 반복되는 앞부분을 재사용해 입력 비용을 크게 줄이기
3. 컨텍스트 다이어트, 검색 결과 압축, 대화 이력 압축, 모델 <Term id="routing">라우팅</Term>, <Term id="batch-api">배치 API</Term>를 상황에 맞게 골라 쓰기

## 왜 비용은 대부분 입력 토큰에서 나오는가

먼저 직관부터 잡읍시다. LLM 요금은 두 부분으로 나뉩니다. 모델에게 넣는 글(입력 토큰)과 모델이 뱉는 글(출력 토큰)입니다. 상담 답변은 보통 몇 문장이라 출력은 짧습니다. 그런데 그 짧은 답을 만들려고 넣는 입력은 훨씬 깁니다.

무엇이 입력에 들어가는지 세어 보면 압니다. 시스템 프롬프트와 상담 규칙, <Term id="rag">RAG</Term>로 검색해 온 지식 문서 여러 조각, 지금까지의 대화 이력, 그리고 마지막에 붙는 고객의 실제 질문입니다. 질문은 한 줄인데 그 앞에 붙는 짐이 수천 토큰인 경우가 흔합니다.

식당에 비유하면 이렇습니다. 손님이 주문한 요리(출력)는 접시 하나인데, 매번 주방 전체를 새로 차리고 재료를 처음부터 손질(입력)하는 셈입니다. 비용을 줄이는 싸움은 대부분 이 입력 쪽에서 벌어집니다.

그래서 이 레슨의 패턴들은 거의 다 "입력 토큰을 어떻게 줄이거나 재사용하느냐"로 모입니다. 줄이는 쪽(컨텍스트 다이어트, 압축)과 재사용하는 쪽(캐싱), 그리고 애초에 싼 창구로 보내는 쪽(라우팅, 배치)입니다.

## 먼저 재라: usage로 토큰과 비용 측정

측정하지 않으면 최적화는 감으로 하는 일이 됩니다. 앞 레슨에서 품질을 숫자로 봤듯이, 비용도 숫자로 봐야 합니다. 다행히 Anthropic API는 모든 응답에 `usage`를 담아 줘서, 요청 한 건이 정확히 몇 토큰을 썼는지 알 수 있습니다.

`usage`에는 네 가지가 있습니다. `input_tokens`는 이번에 새로 계산한 입력, `cache_creation_input_tokens`는 캐시에 새로 써 둔 입력, `cache_read_input_tokens`는 캐시에서 재사용한 입력, `output_tokens`는 생성한 출력입니다. 이 넷을 각자의 단가로 곱해 더하면 그 요청의 실제 비용이 나옵니다.

캐시 읽기는 보통의 입력가보다 훨씬 쌉니다(대략 10분의 1). 반대로 캐시에 처음 써 둘 때는 조금 더 비쌉니다(대략 1.25배). 그래서 같은 앞부분을 여러 번 재사용할수록 이득이 커집니다. 아래는 그 계산을 그대로 코드로 옮긴 것입니다.

```python
# cost.py
# 요청 한 건의 usage를 받아 달러 비용을 계산한다.
# 단가는 100만 토큰당 달러(입력/출력). 아래는 예시값이므로
# 실제 요금표로 갱신해서 쓴다.
PRICES = {
    "claude-opus-5":   {"input": 5.0, "output": 25.0},
    "claude-sonnet-5": {"input": 2.0, "output": 10.0},
    "claude-haiku-4-5": {"input": 1.0, "output": 5.0},
}

# 캐시 읽기는 입력가의 약 10%, 캐시 쓰기는 약 125%로 매겨진다.
CACHE_READ_RATE = 0.10
CACHE_WRITE_RATE = 1.25


def usage_cost(model: str, usage) -> float:
    p = PRICES[model]
    # 캐시 필드는 없을 때 None으로 오기도 하므로 0으로 방어한다.
    fresh = usage.input_tokens
    cache_write = usage.cache_creation_input_tokens or 0
    cache_read = usage.cache_read_input_tokens or 0
    out = usage.output_tokens

    dollars = (
        fresh * p["input"]
        + cache_write * p["input"] * CACHE_WRITE_RATE
        + cache_read * p["input"] * CACHE_READ_RATE
        + out * p["output"]
    ) / 1_000_000
    return dollars
```

여기서 습관 하나를 들이면 좋습니다. 프로덕션 로그에 요청마다 이 네 숫자를 남기는 것입니다. 그러면 "어제보다 비용이 왜 20% 늘었지"를 감이 아니라 로그로 추적할 수 있습니다. 채널톡이 말하는 비용 최적화는 이 측정에서 출발합니다. 못 재는 건 못 줄입니다.

## 프롬프트 캐싱: 반복되는 앞부분 재사용

이제 가장 효과가 큰 패턴입니다. 상담 에이전트는 요청마다 앞부분이 거의 똑같습니다. 같은 상담 규칙, 같은 회사 지식 문서, 같은 말투 지침이 매번 반복되지요. 바뀌는 건 맨 끝의 고객 질문 하나뿐입니다.

프롬프트 캐싱은 이 반복되는 앞부분을 서버가 기억해 뒀다가 재사용하게 하는 기능입니다. 오픈북 시험에서 매번 책을 처음부터 다시 읽지 않고, 이미 펼쳐 둔 페이지를 그대로 쓰는 것과 같습니다. 같은 내용을 다시 계산하지 않으니 응답도 빨라지고(<Term id="latency">지연시간</Term> 감소) 비용도 크게 줍니다.

작동 방식을 이해할 때 딱 하나만 기억하면 됩니다. 캐싱은 앞부분(prefix) 통째로 맞춰 보는 방식이라, 캐시해 둔 구간 안에서 한 글자라도 바뀌면 그 뒤가 전부 무효가 됩니다. 그래서 설계 원칙은 단순합니다. 안 바뀌는 것(시스템 프롬프트, 지식 문서)을 앞에 두고, 매번 바뀌는 것(고객 질문, 지금 시각)을 맨 뒤에 둡니다.

코드에서는 캐시하고 싶은 구간의 마지막 블록에 `cache_control`을 붙입니다. 그러면 그 블록까지의 앞부분이 캐시됩니다.

```python
# cached_agent.py
from anthropic import Anthropic
from cost import usage_cost

client = Anthropic()  # ANTHROPIC_API_KEY 환경변수에서 자동으로 읽는다

# 매 요청 동일한 큰 지식 문서. 수천 토큰짜리라고 하자.
KNOWLEDGE = """[회사 정책 전문]
환불 정책: 미개봉 상품은 구매 후 7일 이내 전액 환불 가능합니다.
배송 정책: ...
멤버십 등급별 혜택: ...
"""  # 실제로는 RAG로 검색해 온 안정적인 상위 문서를 넣는다


def answer(question: str) -> str:
    resp = client.messages.create(
        model="claude-opus-5",
        max_tokens=1024,
        # system은 리스트로 준다. 앞의 지침과 뒤의 지식 문서가 모두
        # 매번 같으므로, 지식 문서 블록 끝에 cache_control을 걸어
        # 여기까지의 앞부분을 통째로 캐시한다.
        system=[
            {"type": "text", "text": "당신은 정확하고 친절한 고객 상담 도우미입니다."},
            {
                "type": "text",
                "text": KNOWLEDGE,
                # 기본 캐시 유지시간은 5분. 트래픽이 뜸하면 "1h"로 늘릴 수 있다.
                "cache_control": {"type": "ephemeral"},
            },
        ],
        # 바뀌는 건 이 질문뿐이라 캐시 구간 뒤에 온다.
        messages=[{"role": "user", "content": question}],
    )
    u = resp.usage
    print(
        f"신규 {u.input_tokens} / 캐시쓰기 {u.cache_creation_input_tokens or 0} "
        f"/ 캐시읽기 {u.cache_read_input_tokens or 0} / 출력 {u.output_tokens} "
        f"= ${usage_cost('claude-opus-5', u):.4f}"
    )
    return "".join(b.text for b in resp.content if b.type == "text")


# 첫 호출은 캐시에 써 두느라(cache_creation) 조금 비싸지만,
# 두 번째부터는 지식 문서가 cache_read로 잡혀 입력 비용이 확 떨어진다.
answer("3일 전에 산 미개봉 상품 환불 되나요?")
answer("배송은 보통 며칠 걸려요?")
```

효과를 확인하는 방법은 명확합니다. 두 번째 호출부터 `cache_read_input_tokens`가 크게 잡히면 성공입니다. 이 값을 전체 입력으로 나눈 것이 <Term id="cache-hit-rate">캐시 적중률</Term>입니다. 이 값이 계속 0에 가깝다면 뭔가가 앞부분을 매번 바꾸고 있다는 뜻입니다.

흔한 범인은 정해져 있습니다. 시스템 프롬프트에 현재 시각이나 요청 ID를 넣었거나, 지식 문서를 매번 다른 순서로 정렬해 넣었거나, 도구 목록이 요청마다 조금씩 달라지는 경우입니다. 캐시가 안 먹으면 이 셋부터 의심하세요.

한 가지 더. 캐시할 수 있는 최소 앞부분 크기가 정해져 있습니다(모델에 따라 대략 1천에서 4천 토큰). 앞부분이 그보다 짧으면 캐시가 조용히 걸리지 않습니다. 그래서 캐싱은 짧은 프롬프트가 아니라, 지식 문서처럼 덩치 큰 반복 컨텍스트에서 진가를 냅니다.

## 컨텍스트 다이어트: 정말 필요한 것만

캐싱이 "반복되는 걸 재사용"하는 것이라면, 컨텍스트 다이어트는 "애초에 덜 넣는" 것입니다. 둘은 반대가 아니라 함께 씁니다.

RAG에서 흔한 실수가 상위 문서를 무조건 많이 넣는 것입니다. "혹시 모르니 20개 넣자"는 마음이지요. 그런데 관계없는 조각이 많이 섞이면 두 가지가 나빠집니다. 입력 토큰이 늘어 비용이 오르고, 진짜 근거가 잡동사니에 묻혀 답 품질도 흔들립니다. 책상에 자료를 잔뜩 쌓아 두면 정작 필요한 종이를 못 찾는 것과 같습니다.

그래서 넣는 문서 수를 늘리기 전에, 먼저 검색을 정밀하게 만드는 게 순서입니다. 정확도 높은 소수의 근거가 부정확한 다수보다 싸고 좋습니다. 리랭킹으로 상위 몇 개만 추려 넣는 것이 대표적인 다이어트입니다.

무엇을 뺄지 판단하는 기준은 간단합니다. "이 조각이 없으면 답이 틀리는가"입니다. 없어도 답이 같다면 그건 비용만 먹는 짐입니다. 아래처럼 넣기 전에 예산을 정해 두고 자르면 통제가 됩니다.

```python
# context_diet.py
# 검색해 온 조각들을 점수순으로 받아, 토큰 예산 안에서만 담는다.
# 무조건 상위 N개가 아니라, 관련성 문턱을 넘는 것만 넣는 게 핵심이다.
def pack_context(chunks: list[dict], token_budget: int, min_score: float) -> list[dict]:
    """chunks: [{"text": str, "tokens": int, "score": float}, ...] 점수 내림차순"""
    packed, used = [], 0
    for c in chunks:
        # 관련성이 문턱보다 낮으면, 자리가 남아도 넣지 않는다.
        if c["score"] < min_score:
            break
        if used + c["tokens"] > token_budget:
            break
        packed.append(c)
        used += c["tokens"]
    return packed
```

주의할 점은 다이어트가 지나치면 정답 근거까지 빠져 할루시네이션이 늘 수 있다는 것입니다. 그래서 다이어트는 반드시 앞 레슨의 근거 충실성 평가와 함께 돌립니다. 문서를 줄였는데 근거 충실성이 유지되면 순이득이고, 떨어지면 너무 잘라낸 것입니다. 비용만 보고 품질을 안 보면 위험한 거래가 됩니다.

## 검색 결과 압축과 요약

문서를 뺄 수는 없는데 너무 길 때가 있습니다. 긴 정책 문서 하나가 통째로 근거로 필요한 경우가 그렇습니다. 이럴 때는 문서를 빼는 대신 짧게 눌러 담습니다.

방법은 값싼 모델에게 "이 질문에 답하는 데 필요한 부분만 남겨 요약해"라고 시키는 것입니다. 긴 원문을 매번 비싼 본 모델에 통째로 넣는 대신, 싼 모델로 한 번 압축해 두고 그 요약을 넣습니다. 두꺼운 설명서에서 지금 질문에 해당하는 대목만 형광펜으로 긋는 셈입니다.

여기서 트레이드오프를 분명히 봐야 합니다. 압축에도 모델 호출 비용이 듭니다. 그러니 압축이 이득인 건, 같은 문서를 여러 질문에서 재사용하거나(한 번 압축해 여러 번 쓰기), 원문이 압축본보다 훨씬 길 때입니다. 질문마다 원문이 매번 다르고 길이도 짧다면 압축이 오히려 손해일 수 있습니다.

```python
# compress.py
from anthropic import Anthropic

client = Anthropic()


def compress_for_query(question: str, long_doc: str) -> str:
    """긴 근거 문서에서 이 질문에 필요한 사실만 추려 짧게 만든다.
    압축은 품질 민감도가 낮고 대량이라, 싼 모델(haiku)로 처리한다."""
    resp = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=512,
        system="주어진 문서에서 질문에 답하는 데 필요한 사실만 남겨 불릿으로 요약한다. "
        "없는 내용을 지어내지 말고, 관련 없는 부분은 버린다.",
        messages=[
            {
                "role": "user",
                "content": f"질문: {question}\n\n문서:\n{long_doc}",
            }
        ],
    )
    return "".join(b.text for b in resp.content if b.type == "text")
```

압축에서 조심할 함정은 요약이 근거를 왜곡하는 것입니다. 요약 모델이 중요한 조건을 빠뜨리면, 본 모델은 멀쩡한데도 틀린 답이 나옵니다. 그래서 압축본으로도 근거 충실성이 유지되는지 골든셋으로 확인한 뒤에 켭니다. 압축은 공짜가 아니라 품질과 맞바꾸는 카드입니다.

## 대화 이력 압축

멀티턴 상담에서는 또 다른 데서 비용이 붑니다. API는 상태가 없어서, 대화가 길어질수록 매 요청에 지금까지의 전체 이력을 다시 실어 보내야 합니다. 10턴째가 되면 앞의 9턴을 통째로 매번 다시 넣는 것이지요. 이력이 길수록 요청 하나가 점점 무거워집니다.

해법은 오래된 이력을 원문 그대로 끌고 가지 않고, 핵심만 요약해 대체하는 것입니다. 회의록으로 비유하면, 지난 한 시간 대화를 그대로 낭독하는 대신 "고객은 3일 전 미개봉 상품을 샀고 환불을 원함, 주문번호 확인 완료" 같은 몇 줄 요약으로 접어 두는 것입니다. 최근 몇 턴은 원문으로 남기고, 그 이전은 요약으로 갈아 끼웁니다.

```python
# history_compression.py
from anthropic import Anthropic

client = Anthropic()

KEEP_RECENT = 4  # 최근 4개 메시지는 원문 그대로 둔다


def summarize_old(messages: list[dict]) -> str:
    """오래된 대화를 짧은 상태 요약으로 접는다."""
    old_text = "\n".join(f"{m['role']}: {m['content']}" for m in messages)
    resp = client.messages.create(
        model="claude-haiku-4-5",  # 요약은 싼 모델로 충분하다
        max_tokens=300,
        system="대화를 이어가는 데 꼭 필요한 사실만 3~5줄로 요약한다. "
        "고객 상황, 확인된 정보, 남은 할 일 위주로.",
        messages=[{"role": "user", "content": old_text}],
    )
    return "".join(b.text for b in resp.content if b.type == "text")


def compact_history(messages: list[dict]) -> list[dict]:
    # 이력이 짧으면 굳이 압축하지 않는다.
    if len(messages) <= KEEP_RECENT + 2:
        return messages
    old, recent = messages[:-KEEP_RECENT], messages[-KEEP_RECENT:]
    summary = summarize_old(old)
    # 접은 요약을 맨 앞 컨텍스트로 두고, 최근 대화는 원문으로 잇는다.
    return [{"role": "user", "content": f"[이전 대화 요약]\n{summary}"}] + recent
```

이 패턴은 편리하지만 위험도 있습니다. 요약이 놓친 정보는 영영 사라집니다. 고객이 앞에서 말한 주문번호가 요약에서 빠지면, 뒤에서 에이전트가 다시 묻는 어색한 상황이 생깁니다. 그래서 무엇을 반드시 보존할지(주문번호, 확인된 사실 같은 것)를 요약 지침에 못박고, 최근 몇 턴은 항상 원문으로 남깁니다. 참고로 매번 손으로 짜지 않고 서버가 알아서 오래된 맥락을 접어 주는 기능도 있으니, 직접 만들기 전에 그쪽을 먼저 살펴보는 것도 방법입니다.

## 싼 모델로 라우팅

모든 질문에 가장 비싼 모델을 쓸 이유는 없습니다. "영업시간 언제예요" 같은 질문은 값싼 모델도 정확히 답합니다. 반대로 여러 조건이 얽힌 환불 판단은 똑똑한 모델이 필요합니다. 라우팅은 쉬운 요청을 싼 모델로, 어려운 요청만 비싼 모델로 나눠 보내는 방식입니다.

병원 접수와 같습니다. 가벼운 증상은 일반의가 보고, 복잡한 건만 전문의에게 넘깁니다. 모두를 전문의에게 보내면 느리고 비쌉니다.

판단의 열쇠는 "무엇이 쉬운 질문인가"를 정하는 규칙입니다. 처음에는 단순한 신호로 시작해도 됩니다. 질문 길이, 검색된 근거의 명확성, 정책 판단이 필요한지 여부 같은 것입니다. 더 정교하게 가면 값싼 모델에게 난이도를 먼저 물어보고 배분할 수도 있습니다.

```python
# routing.py
from anthropic import Anthropic

client = Anthropic()


def route_model(question: str, top_score: float) -> str:
    """간단한 규칙 라우팅. 실제로는 골든셋으로 문턱을 튜닝한다."""
    q = question.strip()
    # 근거가 아주 명확하고 질문이 짧으면 싼 모델로 충분하다.
    if top_score > 0.85 and len(q) < 60:
        return "claude-haiku-4-5"
    # 판단이 필요한 신호가 보이면 본 모델로 올린다.
    if any(w in q for w in ["환불", "취소", "보상", "왜"]):
        return "claude-opus-5"
    return "claude-sonnet-5"


def answer(question: str, context: str, top_score: float) -> str:
    model = route_model(question, top_score)
    resp = client.messages.create(
        model=model,
        max_tokens=1024,
        system=f"다음 근거로만 답한다.\n{context}",
        messages=[{"role": "user", "content": question}],
    )
    return "".join(b.text for b in resp.content if b.type == "text")
```

라우팅의 함정은 잘못 내려보내는 것입니다. 어려운 질문을 싼 모델로 잘못 보내면 오답이 나고, 그 오답을 수습하는 비용이 아낀 돈보다 큽니다. 그래서 라우팅 규칙도 반드시 골든셋으로 검증합니다. 싼 모델로 보낸 질문들의 해결률이 유지되는지 확인하고, 떨어지면 문턱을 보수적으로 올립니다. 캐시는 모델별로 따로 관리되니, 너무 잘게 쪼개 보내면 캐시 재사용이 흩어지는 점도 감안합니다.

## 배치 처리

지금까지는 실시간 상담을 다뤘습니다. 그런데 급하지 않은 대량 작업도 많습니다. 야간에 어제 상담 1만 건을 평가하거나, 지식베이스 전체를 다시 요약해 색인하는 일 같은 것입니다. 이런 작업은 즉시 답이 필요 없습니다.

여기에 맞는 창구가 배치 API입니다. 요청 여러 개를 한꺼번에 비동기로 맡기면, 결과를 실시간이 아니라 잠시 뒤에 받는 대신 요금이 절반입니다. 급행 대신 완행을 골라 반값을 내는 셈입니다.

```python
# batch.py
from anthropic import Anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = Anthropic()


def submit_eval_batch(items: list[dict]) -> str:
    """상담 로그 대량 평가처럼 급하지 않은 작업을 배치로 맡긴다."""
    requests = [
        Request(
            custom_id=item["id"],  # 결과는 순서가 아니라 이 id로 맞춰야 한다
            params=MessageCreateParamsNonStreaming(
                model="claude-haiku-4-5",
                max_tokens=512,
                messages=[{"role": "user", "content": item["prompt"]}],
            ),
        )
        for item in items
    ]
    batch = client.messages.batches.create(requests=requests)
    return batch.id  # 나중에 이 id로 상태를 조회하고 결과를 받는다
```

주의할 점 하나. 배치 결과는 넣은 순서대로 오지 않습니다. 그래서 위치가 아니라 `custom_id`로 결과를 짝지어야 합니다. 그리고 배치는 사람이 기다리는 상담 응답에는 절대 쓰지 않습니다. 반값이 매력적이라고 실시간 경로에 끼워 넣으면 고객이 한참을 기다리게 됩니다. 배치는 "기다려도 되는 대량 작업" 전용입니다.

## 채널톡식으로 묶으면

패턴 하나하나가 아니라 조합이 실전입니다. 실제 상담 파이프라인이라면 이렇게 겹쳐 씁니다.

먼저 시스템 프롬프트와 안정적인 상위 지식 문서를 프롬프트 캐싱으로 고정해 재사용합니다. 검색은 리랭킹으로 상위 소수만 추려 컨텍스트 다이어트를 하고, 긴 문서는 싼 모델로 압축해 넣습니다. 대화가 길어지면 오래된 이력을 요약으로 접습니다. 질문 난이도에 따라 모델을 라우팅하고, 야간 대량 평가는 배치로 반값에 돌립니다. 그리고 이 모든 걸 `usage` 로그로 상시 측정합니다.

이 조합이 채용 공고의 "멀티 LLM 인프라 비용 최적화"이고, 기술블로그가 말한 컨텍스트 비용 절감 설계의 실체입니다. 중요한 건, 모든 절감의 옆에는 항상 품질 게이트가 붙는다는 점입니다. 앞 레슨의 골든셋과 근거 충실성 평가가 없으면, 비용 절감은 품질 하락을 못 보고 지나치는 위험한 도박이 됩니다.

## 흔한 함정

품질을 안 보고 비용만 줄이는 것이 가장 위험합니다. 문서를 잘라내고 이력을 압축하고 싼 모델로 보내는 모든 조치는 품질을 깎을 수 있습니다. 절감 조치마다 골든셋으로 품질 유지를 확인하세요.

캐시가 안 먹는 줄 모르고 캐싱을 켰다고 안심하는 것도 흔합니다. `cache_read_input_tokens`가 실제로 잡히는지 반드시 확인하세요. 시스템 프롬프트 속 현재 시각 하나가 캐시를 통째로 깨뜨립니다.

압축과 요약의 호출 비용을 잊는 것도 함정입니다. 압축 자체도 모델을 부르므로, 재사용 횟수가 적으면 오히려 손해입니다. 압축 전후 비용을 실제로 재서 이득인지 확인하세요.

측정 없이 감으로 최적화하는 것이 마지막 함정입니다. 어디서 토큰이 새는지 로그로 보지 않으면, 엉뚱한 데를 줄이느라 시간을 씁니다. 먼저 재고, 큰 것부터 줄이세요.
