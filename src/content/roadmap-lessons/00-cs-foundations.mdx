## 이 레슨의 목표와 눈높이

이건 선행학습이 아닙니다. 채널톡이 지원자에게서 실제로 확인하려는 기초, 그 깊이 그대로 갑니다.

채널톡 CTO는 여러 자리에서 같은 말을 합니다. 어떤 프레임워크를 아는지, 요즘 뜨는 스택을 써 봤는지보다, 기술을 대하는 태도와 자료구조, 알고리즘 같은 기초를 본다고요. AI 도구가 코드를 대신 써 주는 시대에 왜 이런 옛날 기초를 볼까요.

이유는 단순합니다. 자료구조와 알고리즘은 문법 지식이 아니라 문제를 다루는 사고력이기 때문입니다. 채널톡 Applied AI Engineer의 첫 번째 필수 역량은 "모호한 비즈니스 문제를 AI 문제로 치환해 빠르게 가설을 검증하는 것"입니다. 모호한 것을 다룰 줄 아는 사람은, 큰 문제를 작은 조각으로 쪼개고 무엇이 병목인지 짚어낼 줄 압니다. 자료구조와 알고리즘 훈련이 기르는 근육이 바로 그것입니다.

이 레슨을 끝내면 다음을 할 수 있습니다.

1. 코드가 입력이 커져도 버틸지를 <Term id="big-o">빅오 표기법</Term>으로 가늠하기
2. 핵심 자료구조와 알고리즘 패턴을 "언제 무엇을 꺼내 쓸지" 기준으로 구분하기
3. 이 기초가 벡터 인덱스, 캐시, 큐, 그래프 같은 AI 실무의 실제 부품으로 어떻게 이어지는지 보기

## 빅오: 입력이 커지면 무슨 일이 일어나는가

코드가 빠른지 느린지는 초시계로 재는 게 전부가 아닙니다. 진짜 질문은 "입력이 10배, 100배로 커지면 시간이 얼마나 늘어나는가"입니다.

식당으로 비유해 봅시다. 손님이 두 배로 왔을 때, 어떤 가게는 일이 두 배로 늘고, 어떤 가게는 네 배로 폭발하고, 어떤 가게는 거의 그대로입니다. 빅오는 이 "늘어나는 속도"에 이름을 붙인 것입니다. 상수 계수나 자잘한 항은 버리고, 커질 때의 경향만 봅니다.

자주 나오는 몇 가지만 감으로 익혀 두면 됩니다.

| 표기 | 뜻 | 예 |
| --- | --- | --- |
| O(1) | 입력이 커져도 시간이 그대로 | 딕셔너리에서 값 하나 꺼내기 |
| O(log n) | 입력이 두 배여도 한 단계만 더 | 정렬된 목록에서 이진 탐색 |
| O(n) | 입력에 비례해서 늘어남 | 리스트를 한 번 훑기 |
| O(n log n) | 대부분의 좋은 정렬 | 파이썬의 `sorted()` |
| O(n^2) | 입력이 두 배면 시간은 네 배 | 모든 짝을 이중 반복으로 보기 |

여기서 실무 감각 하나. 데이터가 백 개일 때는 O(n)이든 O(n^2)이든 눈 깜짝할 사이라 차이가 안 보입니다. 하지만 상담 로그가 백만 건으로 늘면, O(n^2) 코드는 그대로 멈춰 버립니다. 백만의 제곱은 1조라서요.

면접에서 "이 코드의 복잡도는요?"라고 물을 때 진짜 확인하는 건 표기법 암기가 아닙니다. 입력이 커졌을 때 내 코드가 어디서 터질지 스스로 짚을 줄 아느냐입니다.

## 자료구조 지도: 무엇을 언제 꺼내 쓰나

자료구조는 데이터를 담는 그릇입니다. 그릇마다 잘하는 일과 못하는 일이 다릅니다. 국을 포크로 먹으려 하면 안 되듯, 문제에 맞는 그릇을 고르는 게 절반입니다.

### 배열과 리스트

번호표를 붙여 한 줄로 세워 둔 것입니다. 파이썬의 리스트가 이것입니다.

번호(인덱스)로 콕 집어 꺼내는 건 O(1)로 빠릅니다. 하지만 "이 값이 어디 있지?"를 찾으려면 처음부터 훑어야 해서 O(n)입니다. 중간에 끼워 넣거나 빼면 뒤의 것들이 다 밀려서 이것도 O(n)입니다. 순서가 있고 번호로 접근하는 데이터에 씁니다.

### 해시맵

<Term id="hash-map">해시맵</Term>은 이 레슨에서 가장 중요한 그릇입니다. 파이썬의 딕셔너리(dict)가 바로 이것입니다.

사전을 떠올려 보세요. "사과"라는 단어를 찾으려고 첫 장부터 넘기지 않습니다. 'ㅅ' 부분으로 곧장 펼치지요. 해시맵은 열쇠(key)를 계산해 값이 있는 자리를 곧바로 알아냅니다. 그래서 넣기, 찾기, 지우기가 모두 평균 O(1)입니다.

"평균"이라는 단서에 주의하세요. 아주 드물게 열쇠들이 같은 자리로 몰리면 한 번의 조회가 느려질 수 있습니다. 그래서 정확히는 <Term id="amortized">분할 상환</Term> O(1)이라고 부릅니다. 어쩌다 한 번 느린 작업의 비용을 전체에 고르게 나눠 보면 평균은 O(1)이라는 뜻입니다. 실무에서는 거의 언제나 O(1)로 취급해도 됩니다.

무언가를 빠르게 찾아야 하는 순간 대부분의 답이 해시맵입니다. 뒤에서 O(n^2)을 O(n)으로 바꾸는 마법도 결국 해시맵입니다.

### 스택과 큐

둘 다 리스트인데, 꺼내는 순서의 규칙이 다릅니다.

스택은 접시 쌓기입니다. 마지막에 올린 접시를 먼저 꺼냅니다(후입선출). 되돌리기 기능, 함수 호출 기록, 괄호 짝 맞추기 같은 데 씁니다.

큐는 줄 서기입니다. 먼저 온 사람이 먼저 처리됩니다(선입선출). 처리해야 할 작업을 순서대로 쌓아 두는 데 씁니다. 파이썬에서는 `collections.deque`를 쓰면 양끝 넣고 빼기가 O(1)입니다.

### 트리와 그래프

트리는 조직도처럼 위에서 아래로 가지가 뻗는 구조입니다. 부모 하나에 자식 여럿, 순환은 없습니다. 파일 폴더, 카테고리 분류, 정렬된 데이터를 빠르게 찾는 이진 탐색 트리가 여기 속합니다.

그래프는 트리보다 자유롭습니다. 점(노드)들이 선(엣지)으로 이어지되, 어떤 식으로든 연결될 수 있고 순환도 됩니다. 지하철 노선도, 사람들의 친구 관계, 문서 사이의 참조 관계가 모두 그래프입니다. AI 쪽에서는 지식 그래프나 에이전트의 작업 의존 관계가 그래프로 표현됩니다.

정리하면 이렇습니다. 순서와 번호 접근은 배열, 빠른 조회는 해시맵, 순서 규칙이 필요하면 스택이나 큐, 계층은 트리, 자유로운 연결은 그래프입니다.

## 대표 알고리즘 패턴

패턴은 문제 유형을 알아보는 눈입니다. 코딩 인터뷰 문제의 상당수는 아래 몇 가지 패턴의 변형입니다. 하나씩 실제 코드로 봅니다.

### 해시맵으로 O(n^2)을 O(n)으로

가장 자주 나오고 가장 강력한 패턴입니다. "이미 본 것을 해시맵에 적어 두면, 다시 찾을 때 O(1)"이라는 아이디어 하나입니다.

문제를 봅시다. 리스트에서 더해서 목표값이 되는 두 수의 위치를 찾아라.

```python
# two_sum.py

# 방법 A: 모든 짝을 다 본다. 입력이 2배면 시간은 4배. O(n^2).
def two_sum_slow(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return (i, j)
    return None


# 방법 B: 지금까지 본 수를 해시맵에 적어 둔다. 각 수마다
# "짝이 되는 수를 전에 본 적 있나?"를 단번에 조회한다. 전체 O(n).
def two_sum_fast(nums, target):
    seen = {}  # 값 -> 그 값이 있던 위치
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:        # 딕셔너리 조회는 평균 O(1)
            return (seen[need], i)
        seen[x] = i
    return None
```

방법 A는 짝을 다 훑느라 이중 반복이고, 방법 B는 목록을 딱 한 번만 지나갑니다. 백만 개 입력에서 A는 사실상 멈추고 B는 순식간입니다. 자료구조 하나를 바꿨을 뿐인데 결과가 이렇게 갈립니다. 면접에서 O(n^2) 풀이를 낸 뒤 "해시맵으로 O(n)으로 줄일 수 있어요"라고 이어 말하는 것, 이게 정확히 그들이 보고 싶어 하는 흐름입니다.

### 이진 탐색

정렬돼 있다는 조건만 있으면, 매번 후보 범위를 절반으로 접어 O(log n)에 찾습니다.

```python
# binary_search.py

# 정렬된 리스트에서 target의 위치를 찾는다.
def binary_search(sorted_nums, target):
    lo, hi = 0, len(sorted_nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if sorted_nums[mid] == target:
            return mid
        if sorted_nums[mid] < target:
            lo = mid + 1        # 가운데보다 크니 오른쪽 절반만 남긴다
        else:
            hi = mid - 1        # 가운데보다 작으니 왼쪽 절반만 남긴다
    return -1
```

<Term id="binary-search">이진 탐색</Term>의 힘은 규모에서 드러납니다. 백만 개짜리 목록도 스무 번 안쪽이면 찾습니다. 단, 목록이 정렬돼 있어야 합니다. 이 "정렬돼 있으면 절반씩 줄인다"는 발상은 뒤에 나올 벡터 검색의 뿌리이기도 합니다.

### 투 포인터

<Term id="two-pointer">투 포인터</Term>는 손가락 두 개로 배열의 양끝(또는 앞뒤)을 짚고, 조건에 따라 안쪽으로 좁혀 오는 패턴입니다. 이중 반복으로 O(n^2)일 문제를 O(n)으로 줄입니다.

정렬된 배열에서 합이 목표값인 두 수를 찾는 문제를 이 패턴으로 풉니다.

```python
# two_pointer.py

# 정렬된 배열에서 합이 target인 두 수를 찾는다.
# 양끝에서 시작해, 합이 크면 오른쪽을 당기고 작으면 왼쪽을 민다.
def two_sum_sorted(sorted_nums, target):
    lo, hi = 0, len(sorted_nums) - 1
    while lo < hi:
        s = sorted_nums[lo] + sorted_nums[hi]
        if s == target:
            return (lo, hi)
        if s < target:
            lo += 1             # 합을 키워야 하니 왼쪽 포인터를 오른쪽으로
        else:
            hi -= 1             # 합을 줄여야 하니 오른쪽 포인터를 왼쪽으로
    return None
```

두 포인터가 한 번씩만 안쪽으로 이동하니 전체가 O(n)입니다. 정렬된 데이터에서 짝이나 구간을 다룰 때 먼저 떠올리는 패턴입니다.

### 슬라이딩 윈도우

<Term id="sliding-window">슬라이딩 윈도우</Term>는 연속된 구간(창)을 한 칸씩 밀며 훑는 패턴입니다. 핵심은 창을 옮길 때 전부 다시 계산하지 않고, 새로 들어온 값만 더하고 빠져나간 값만 빼는 것입니다.

길이 k짜리 연속 구간의 최대 합을 구해 봅시다.

```python
# sliding_window.py

# 매 위치마다 창 전체를 다시 더하면 O(n*k)로 느리다.
# 창을 한 칸 밀 때 '들어온 값'만 더하고 '빠진 값'만 빼면 O(n)이다.
def max_window_sum(nums, k):
    if len(nums) < k:
        return None
    window = sum(nums[:k])      # 첫 창은 한 번만 통째로 계산
    best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]   # 새로 들어온 값 - 빠져나간 값
        best = max(best, window)
    return best
```

이 발상은 실무에서 자주 등장합니다. 최근 k초 동안의 요청 수를 세는 속도 제한(rate limit), 최근 몇 개 메시지만 남기고 오래된 대화를 잘라 내는 대화 이력 관리가 모두 슬라이딩 윈도우의 변형입니다.

### BFS와 DFS: 그래프 훑기

그래프를 탐색하는 두 가지 기본기입니다. BFS(너비 우선)는 가까운 곳부터 물결처럼 퍼져 나가고, DFS(깊이 우선)는 한 길을 끝까지 파고든 뒤 돌아 나옵니다.

BFS는 큐를 쓰고, "시작점에서 몇 다리 건너야 닿는가" 같은 최단 거리에 강합니다.

```python
# bfs.py
from collections import deque

# 그래프를 가까운 곳부터 훑어, start에서 goal까지 최단 거리를 잰다.
# graph는 {노드: [이웃 노드들]} 형태의 딕셔너리(인접 리스트)다.
def bfs_shortest(graph, start, goal):
    seen = {start}
    queue = deque([(start, 0)])         # (노드, 지금까지의 거리)
    while queue:
        node, dist = queue.popleft()    # 큐: 먼저 넣은 것을 먼저 꺼낸다
        if node == goal:
            return dist
        for nxt in graph[node]:
            if nxt not in seen:         # 이미 본 노드는 건너뛴다
                seen.add(nxt)
                queue.append((nxt, dist + 1))
    return -1                           # 닿지 못함
```

`seen` 집합으로 이미 방문한 노드를 걸러 내는 부분이 중요합니다. 이게 없으면 순환이 있는 그래프에서 영원히 맴돕니다. DFS는 큐 대신 스택(또는 재귀)을 쓴다는 점만 다르고 뼈대는 같습니다. 의존 관계를 따라가거나, 도달 가능한 것들을 모으거나, 관계망을 파고들 때 쓰는 도구입니다.

## AI 실무에서 이게 진짜 쓰이는 자리

여기가 이 레슨의 핵심입니다. 자료구조와 알고리즘이 면접용 퀴즈로 끝나는 게 아니라, 채널톡 Applied AI Engineer가 매일 만지는 시스템의 뼈대라는 걸 보여 드리겠습니다.

### 벡터 인덱스는 결국 탐색 문제

<Term id="vector-search">벡터 검색</Term>은 질문을 숫자 목록(임베딩)으로 바꾼 뒤, 의미가 가장 가까운 문서 조각을 찾는 일입니다. 그런데 문서가 수백만 개라면, 질문 하나가 올 때마다 전부와 거리를 재는 건 O(n)이라 너무 느립니다.

그래서 실무의 벡터 인덱스는 <Term id="ann">근사 최근접 이웃</Term>이라는 자료구조를 씁니다. 정확히 제일 가까운 하나를 고집하는 대신, 아주 가까운 후보 몇 개를 훨씬 빠르게 찾아 주는 구조입니다. 그 내부는 그래프(가까운 벡터끼리 이어 둔 그물망을 따라가며 좁히기)나 트리 형태로 되어 있습니다. 이진 탐색이 "절반씩 줄인다"였다면, 이건 "가까운 이웃을 따라 점점 좁혀 든다"입니다. 방금 배운 그래프 탐색과 이진 탐색의 직계 후손인 셈입니다.

RAG 성능 고도화가 채널톡의 주요 업무인데, 벡터 인덱스가 어떻게 검색을 빠르게 하는지 그 원리를 모르면 왜 검색이 느리거나 엉뚱한 걸 가져오는지 진단할 수 없습니다.

### 캐시는 해시맵이다

같은 문장을 또 임베딩하려고 API를 다시 부르면 돈과 시간이 이중으로 샙니다. 한 번 계산한 결과를 열쇠로 딕셔너리에 적어 두면, 다음엔 O(1)로 꺼내 씁니다. 이게 캐시이고, 그 바탕은 해시맵입니다.

```python
# embed_cache.py

# 같은 텍스트의 임베딩을 매번 다시 계산하지 않도록 캐싱한다.
_embed_cache = {}   # 텍스트 -> 임베딩 벡터

def get_embedding(text, embed_fn):
    if text in _embed_cache:        # 해시맵 조회 O(1)
        return _embed_cache[text]
    vec = embed_fn(text)            # 진짜 계산(느리고 비쌈)은 여기서만
    _embed_cache[text] = vec
    return vec
```

프롬프트 캐싱, 응답 캐싱, 임베딩 캐싱까지 비용 최적화의 상당 부분이 "빠른 조회 자료구조에 적어 두고 재사용"이라는 한 문장으로 요약됩니다. 메모리가 한정돼 오래된 것부터 버려야 하면, 여기에 순서 개념을 더한 LRU 캐시가 되는데 이건 해시맵과 큐를 엮은 것입니다.

### 큐는 밀려드는 일을 순서대로

상담 요청이나 문서 색인 작업이 한꺼번에 몰릴 때, 전부 동시에 처리하려 들면 시스템이 무너집니다. 들어온 일을 큐에 줄 세우고 감당 가능한 속도로 하나씩 꺼내 처리합니다. 쉬운 요청은 싼 모델로, 어려운 요청만 비싼 모델로 나눠 보내는 <Term id="routing">모델 라우팅</Term>도, 요청을 성격에 따라 서로 다른 큐로 흘려보내는 구조로 볼 수 있습니다.

### 그래프는 지식과 에이전트의 뼈대

지식 그래프는 개념들을 노드로, 관계를 엣지로 이어 둔 그래프입니다. 에이전트가 여러 도구를 순서와 의존 관계에 따라 호출하는 흐름도 그래프이고, 그걸 실행하는 것은 방금 배운 그래프 탐색의 응용입니다.

정리하면, 벡터 인덱스, 캐시, 큐, 그래프라는 AI 인프라의 네 기둥이 전부 이 레슨의 자료구조 위에 서 있습니다. 기초가 남 일이 아니라는 건 이런 뜻입니다.

## 코딩 인터뷰를 대하는 법

문제 앞에서 곧장 코드부터 치는 건 가장 흔한 실수입니다. 채널톡이 보려는 건 정답 코드 자체보다, 모호한 문제를 다루는 사고 과정입니다. 아래 순서를 몸에 붙이세요.

첫째, 문제를 되묻습니다. 입력 크기는 얼마인지, 정렬돼 있는지, 중복이나 빈 입력 같은 예외는 어떻게 처리할지 확인합니다. 모호함을 그냥 넘기지 않고 조건을 좁히는 이 습관이, 사실 "모호한 비즈니스 문제를 AI 문제로 치환한다"는 채널톡 필수 역량의 축소판입니다.

둘째, 무식하지만 확실한 풀이(brute force)를 먼저 말합니다. O(n^2)이어도 좋으니 일단 되는 방법을 제시하고, 그 복잡도를 스스로 밝힙니다.

셋째, 어디가 병목인지 짚고 자료구조로 개선합니다. "이 안쪽 반복이 O(n)인데, 해시맵에 적어 두면 O(1)로 줄어서 전체가 O(n)이 됩니다"처럼요.

넷째, 예시로 손수 따라가며 검증하고, 빈 입력이나 경계값 같은 엣지케이스를 챙깁니다.

말하면서 푸는 것을 두려워하지 마세요. 면접관은 완성된 코드보다 생각의 흐름을 봅니다. AI 도구가 코드를 뽑아 주는 시대에, 사람에게 남는 가치는 바로 이 "무엇을 왜 그렇게 푸는지"의 판단이기 때문입니다.

4. 방금 짠 것 중 하나를 골라, 입력이 백만 개로 커지면 어디가 먼저 터질지 빅오로 설명해 보세요. 말로 설명할 수 있으면 진짜 이해한 것입니다.

## 흔한 함정

빅오만 외우고 감을 못 잡는 것이 가장 흔합니다. O(n^2)이라는 라벨보다, 입력이 커졌을 때 내 코드가 실제로 어디서 느려지는지 짚는 능력이 핵심입니다.

곧장 최적해부터 내려는 것도 함정입니다. 무식한 풀이를 먼저 말하고 개선하는 흐름이, 처음부터 완벽한 코드를 던지는 것보다 훨씬 좋은 신호입니다.

자료구조를 이름만 아는 것도 위험합니다. 해시맵이 무엇인지 아는 것과, 눈앞의 O(n^2) 문제에서 "여기에 해시맵을 넣으면 되겠다"를 떠올리는 것은 다른 능력입니다. 후자는 문제를 많이 풀어야만 생깁니다.

기초와 AI 실무를 따로 보는 것도 함정입니다. 벡터 인덱스, 캐시, 큐가 전부 이 기초 위에 서 있다는 걸 알면, 학습 동기가 달라지고 시스템을 보는 눈이 깊어집니다.
