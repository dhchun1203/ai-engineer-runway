## 이 레슨의 목표와 눈높이

이건 선행학습이 아닙니다. 채널톡 Applied AI Engineer가 실제로 하는 일, 그 깊이 그대로 갑니다.

채널톡 기술블로그에는 눈여겨볼 문장이 있습니다. 공개 리더보드에 없는 모델까지 직접 벤치마킹해 상담 에이전트의 모델을 갈아끼웠다는 이야기입니다. 채용 공고의 주요 업무에도 "멀티 LLM 인프라 비용 최적화"가 그대로 적혀 있습니다.

이 말은 곧, 어떤 모델을 쓸지가 남이 정해 준 순위표를 베끼는 일이 아니라, 엔지니어가 숫자로 판단하는 일이라는 뜻입니다.

이 레슨을 끝내면 다음을 직접 할 수 있습니다.

1. 공개 <Term id="benchmark">벤치마크</Term> 점수를 왜 그대로 믿으면 안 되는지 설명하기
2. 내 태스크용 <Term id="golden-set">골든셋</Term>으로 여러 후보 모델을 한 번에 돌려 품질과 비용과 지연을 표로 비교하기
3. 쉬운 요청은 싼 모델로 흘리는 <Term id="routing">모델 라우팅</Term>을 설계하고, 모델을 교체할 때 품질이 떨어지지 않았는지 확인하기

앞 레슨 "할루시네이션을 잡는 평가 시스템"에서 만든 골든셋과 <Term id="llm-judge">LLM 심판</Term>을 여기서 그대로 재사용합니다. 그 레슨을 먼저 보고 오면 이 레슨이 훨씬 매끄럽습니다.

## 모델 선택은 판단력의 문제다

모델을 고르는 일을 "가장 똑똑한 모델을 쓰면 되지"라고 생각하기 쉽습니다. 실제로는 그렇게 단순하지 않습니다.

상담 에이전트를 예로 들어 봅시다. 하루에 수만 건의 상담이 들어옵니다. 그중 절반은 "환불 되나요" "배송 언제 와요"처럼 근거 문서만 잘 찾으면 끝나는 쉬운 질문입니다. 나머지에 애매하고 여러 의도가 섞인 어려운 질문이 있습니다.

쉬운 질문 수만 건에까지 가장 비싼 모델을 쓰면, 품질은 아주 조금 좋아지는데 비용은 몇 배가 됩니다. 반대로 전부 가장 싼 모델로 처리하면 어려운 질문에서 사고가 납니다.

그래서 모델 선택은 "무엇이 제일 좋냐"가 아니라 "이 태스크에, 이 예산과 속도 안에서, 무엇이 제일 알맞냐"라는 판단입니다. 채널톡 CTO가 스택보다 "기술을 대하는 태도"를 본다고 말하는 지점이 바로 여기입니다. 정답이 정해져 있지 않고, 재 보고 판단해야 하는 문제입니다.

## 공개 벤치마크의 함정

새 모델이 나오면 "MMLU 90점" "코딩 벤치마크 1위" 같은 숫자가 따라옵니다. 이 숫자를 그대로 내 선택 근거로 쓰면 위험합니다. 이유가 몇 가지 있습니다.

첫째, 공개 벤치마크의 문제는 내 문제와 다릅니다. 수능 전국 1등이 우리 회사 상담을 제일 잘한다는 보장은 없습니다. 상담에 필요한 건 고난도 수학이 아니라, 주어진 근거 안에서만 답하고 애매하면 되묻는 능력입니다. 벤치마크가 재는 것과 내가 필요한 것이 어긋나면 그 점수는 나에게 의미가 약합니다.

둘째, 벤치마크 오염 가능성이 있습니다. 유명한 문제집은 학습 데이터에 섞여 들어가기 쉽습니다. 기출문제를 이미 외운 학생의 모의고사 점수를 믿기 어려운 것과 같습니다.

셋째, 리더보드에 아예 없는 모델이 내 태스크엔 더 나을 수 있습니다. 채널톡이 리더보드 밖 모델까지 직접 재 본 이유가 이것입니다. 순위표는 남의 태스크 순위이지 내 태스크 순위가 아닙니다.

결론은 하나입니다. 공개 점수는 후보를 추리는 참고 자료로만 쓰고, 진짜 선택은 내 태스크로 직접 재서 합니다.

## 내 태스크용 골든셋으로 재기

"직접 잰다"의 출발점은 골든셋입니다. 앞 레슨에서 만든, 실제 상담에서 뽑아 사람이 검수한 질문과 근거와 기대 정답의 모음이지요.

핵심 발상은 이렇습니다. 후보 모델들을 똑같은 골든셋에 세워 놓고, 똑같은 심판으로 채점합니다. 그러면 모델 사이의 차이만 남고, 문제 난이도나 채점 기준 같은 다른 변수는 상쇄됩니다. 육상 선수들을 같은 트랙에서 같은 심판이 재는 것과 같습니다.

여기서 반드시 지킬 규칙이 두 가지입니다.

하나, 채점하는 심판 모델은 고정합니다. 후보 모델(답을 만드는 쪽)만 바꾸고 심판은 그대로 둬야, 점수 차이가 후보의 실력 차이인지 심판이 달라진 탓인지 헷갈리지 않습니다.

둘, 골든셋은 모델 튜닝에 재사용하지 않습니다. 어떤 모델에 맞춰 프롬프트를 골든셋으로 다듬으면, 그 골든셋 점수만 오르고 실제로는 나아지지 않는 <Term id="overfitting">과적합</Term>이 생깁니다. 골든셋은 오직 재는 데만 씁니다.

## 품질과 비용과 지연의 삼각형

모델을 고를 때 우리는 사실 세 가지를 동시에 저울질합니다. 품질, 비용, 그리고 <Term id="latency">지연시간</Term>(응답 속도)입니다.

음식점을 떠올리면 쉽습니다. 맛있고, 싸고, 빠른 집을 다 만족시키는 곳은 드뭅니다. 보통 둘을 얻으면 하나를 내줍니다. 모델도 같습니다. 가장 똑똑한 모델은 대개 더 비싸고 더 느립니다.

그래서 하나의 종합 점수로 뭉개면 안 됩니다. "opus가 sonnet보다 낫다"가 아니라, "opus는 해결률이 4%포인트 높지만 비용이 세 배이고 p95 지연이 두 배"처럼 세 축을 따로 봐야 판단이 섭니다.

세 축을 같이 보면 자연스럽게 걸러지는 후보가 있습니다. 어떤 모델이 다른 모델보다 품질도 낮은데 비용까지 비싸다면, 그 모델은 고려할 이유가 없습니다. 이렇게 밀려나지 않고 남는, 즉 한쪽을 포기하지 않고는 다른 쪽을 더 좋게 만들 수 없는 후보들의 모음을 <Term id="pareto-frontier">파레토 경계</Term>라고 부릅니다. 최종 선택은 이 경계 위에 남은 후보들 중에서, 이 태스크가 품질과 비용 중 무엇을 더 중히 여기는지로 고릅니다.

지연을 잴 때 한 가지 주의할 점이 있습니다. 평균 지연만 보면 안 됩니다. 평균은 빠른데 100명 중 5명이 아주 오래 기다리는 경우를 놓치기 때문입니다. 그래서 평균 대신 <Term id="tail-latency">꼬리 지연</Term>(p95 같은 지표)을 봅니다. 사람이 기다리는 상담에서는 이 꼬리가 체감 품질을 좌우합니다.

## 여러 모델을 한 번에 벤치마킹하기

이제 코드로 옮깁니다. 후보 모델들을 같은 골든셋에 돌려, 각 모델의 해결률과 근거 충실성, 그리고 비용과 지연을 한꺼번에 재는 스크립트입니다.

먼저 답을 만드는 부분입니다. 후보 모델로 상담 답변을 한 번 생성하면서, 걸린 시간과 쓴 <Term id="token">토큰</Term> 수를 함께 기록합니다. 토큰 수는 비용 계산의 재료이고, SDK가 응답의 `usage`에 담아 줍니다.

```python
# benchmark_models.py
import time
from dataclasses import dataclass, field
from anthropic import Anthropic

from golden_set import golden   # 앞 레슨에서 만든 평가셋(질문, 근거, 기대 정답)
from judge import judge         # 앞 레슨의 LLM 심판. 심판 모델은 여기서 고정한다.

client = Anthropic()  # ANTHROPIC_API_KEY 환경변수에서 자동으로 읽는다

# 후보 모델과 100만 토큰당 단가(달러). 단가는 자주 바뀌므로 한곳에서 관리한다.
# opus는 가장 똑똑하고 비싸며, haiku는 가장 싸고 빠르고, sonnet은 그 중간이다.
CANDIDATES = [
    {"model": "claude-opus-5",    "in_per_mtok": 5.0, "out_per_mtok": 25.0},
    {"model": "claude-sonnet-5",  "in_per_mtok": 2.0, "out_per_mtok": 10.0},
    {"model": "claude-haiku-4-5", "in_per_mtok": 1.0, "out_per_mtok": 5.0},
]

SYSTEM = """당신은 고객 상담 에이전트입니다.
<근거> 안의 내용만 사용해 답하세요. 근거에 없으면 모른다고 하거나 되물으세요."""


def answer_once(model: str, question: str, context: list[str]) -> dict:
    """후보 모델로 답을 한 번 만들고, 지연시간과 토큰을 함께 잰다.
    모든 후보에 똑같은 시스템 프롬프트와 근거를 줘야 비교가 공정하다."""
    context_block = "\n".join(f"- {c}" for c in context)
    prompt = f"<근거>\n{context_block}\n</근거>\n\n<질문>\n{question}\n</질문>"

    start = time.perf_counter()
    resp = client.messages.create(
        model=model,
        max_tokens=1024,
        system=SYSTEM,
        messages=[{"role": "user", "content": prompt}],
    )
    latency_s = time.perf_counter() - start

    text = "".join(b.text for b in resp.content if b.type == "text")
    return {
        "text": text,
        "latency_s": latency_s,
        "in_tokens": resp.usage.input_tokens,    # 입력(프롬프트) 토큰
        "out_tokens": resp.usage.output_tokens,  # 출력(생성된 답) 토큰
    }
```

다음은 한 후보 모델을 골든셋 전체에 돌려 집계하는 부분입니다. 각 항목마다 답을 만들고, 고정된 심판으로 채점하고, 비용과 지연을 쌓습니다.

```python
@dataclass
class Result:
    model: str
    resolved: int = 0          # 해결로 판정된 건수
    grounded: int = 0          # 근거 충실 판정 건수
    total: int = 0
    cost_usd: float = 0.0      # 골든셋 전체를 한 번 도는 데 든 비용
    latencies: list = field(default_factory=list)


def benchmark(cand: dict) -> Result:
    r = Result(model=cand["model"])
    for item in golden:
        out = answer_once(cand["model"], item["question"], item["context"])
        # 심판은 항상 같은 모델(judge 안에 고정). 후보만 바뀐다.
        verdict = judge(item["question"], item["context"], out["text"])

        r.total += 1
        if verdict["resolution"] == "resolved":
            r.resolved += 1
        if verdict["grounded"]:
            r.grounded += 1

        # 비용 = 입력토큰 단가 + 출력토큰 단가. 토큰은 100만 단위라 1e6로 나눈다.
        r.cost_usd += (
            out["in_tokens"] / 1_000_000 * cand["in_per_mtok"]
            + out["out_tokens"] / 1_000_000 * cand["out_per_mtok"]
        )
        r.latencies.append(out["latency_s"])
    return r
```

마지막으로 결과를 표로 찍습니다. 지연은 평균이 아니라 p50(중앙값)과 p95(꼬리)를 봅니다. 특별한 라이브러리 없이 표준 기능만으로 백분위를 구합니다.

```python
def percentile(values: list[float], p: float) -> float:
    """정렬한 뒤 p 위치의 값을 고른다. p=0.95면 위에서 5%만 이보다 느리다."""
    s = sorted(values)
    k = int(round((len(s) - 1) * p))
    return s[k]


def report(results: list[Result], per_n: int = 1000) -> None:
    # 골든셋 1회분 비용을 상담 per_n건 기준으로 환산해 감을 잡는다.
    header = f"{'model':<18}{'해결률':>8}{'근거%':>8}{f'비용/{per_n}건($)':>14}{'p50(s)':>9}{'p95(s)':>9}"
    print(header)
    for r in results:
        cost_per_n = r.cost_usd / r.total * per_n
        print(
            f"{r.model:<18}"
            f"{r.resolved / r.total:>7.0%}"
            f"{r.grounded / r.total:>8.0%}"
            f"{cost_per_n:>14.2f}"
            f"{percentile(r.latencies, 0.50):>9.2f}"
            f"{percentile(r.latencies, 0.95):>9.2f}"
        )


if __name__ == "__main__":
    results = [benchmark(c) for c in CANDIDATES]
    report(results)
```

## 결과를 읽는 법

스크립트를 돌리면 이런 표가 나옵니다. 아래 숫자는 감을 주려는 예시일 뿐이고, 여러분의 골든셋에서는 전혀 다르게 나옵니다. 중요한 건 값이 아니라 읽는 법입니다.

| 모델 | 해결률 | 근거 충실성 | 비용/1000건 | p50 지연 | p95 지연 |
| --- | --- | --- | --- | --- | --- |
| claude-opus-5 | 88% | 97% | $4.10 | 3.1s | 6.8s |
| claude-sonnet-5 | 84% | 95% | $1.60 | 1.9s | 3.9s |
| claude-haiku-4-5 | 73% | 90% | $0.80 | 1.1s | 2.2s |

이 표에서 읽어야 할 것은 이렇습니다. opus는 품질이 가장 높지만 비용이 sonnet의 두 배가 넘고 꼬리 지연도 가장 깁니다. haiku는 가장 싸고 빠르지만 해결률이 뚝 떨어집니다. sonnet은 opus에 근접한 품질을 절반 이하 비용으로 냅니다.

여기서 판단이 갈립니다. 만약 우리 서비스의 합격선이 "해결률 80% 이상"이라면, haiku는 탈락이고 sonnet과 opus가 파레토 경계에 남습니다. 그리고 이 4%포인트를 위해 비용 두 배와 지연 두 배를 낼 가치가 있는지가 진짜 질문이 됩니다. 이 답은 코드가 아니라 프로덕트가 정합니다.

숫자 하나 더 보태면 판단이 쉬워집니다. 만약 하루 상담이 3만 건이라면, opus와 sonnet의 1000건당 차이 $2.5는 하루 $75, 한 달이면 2000달러가 넘는 차이입니다. 품질 4%포인트와 월 2000달러를 나란히 놓으면, 추상적이던 선택이 구체적인 저울질로 바뀝니다.

## 모델 라우팅: 쉬운 건 싼 모델로

표를 보고 "그럼 어려운 건 opus, 쉬운 건 haiku로 나눠 보내면 되잖아"라는 생각이 든다면, 정확합니다. 그게 모델 라우팅입니다.

발상은 단순합니다. 모든 요청에 가장 비싼 모델을 쓰지 말고, 요청의 난이도를 먼저 가늠해 쉬운 건 싼 모델로, 어려운 것만 비싼 모델로 보냅니다. 채널톡이 말하는 "멀티 LLM 비용 최적화"의 핵심 수단입니다.

여기서 꼭 짚어야 할 함정이 있습니다. 난이도를 가늠하는 그 판단 자체가 싸고 빨라야 합니다. 어려운지 아닌지를 재려고 매번 비싼 심판 모델을 돌리면, 아낀 돈을 판단 비용으로 다시 까먹습니다. 그래서 실전에서는 검색된 근거의 개수나 질문 길이 같은 값싼 신호, 또는 작은 분류 모델을 1차 판단에 씁니다.

```python
# router.py
from benchmark_models import answer_once


def looks_hard(question: str, context: list[str]) -> bool:
    """값싼 신호로 난이도를 가늠한다. 여기서는 예시로 두 가지만 본다.
    실전에서는 작은 분류기나 검색 점수 같은 더 나은 신호를 쓴다.
    핵심은 이 판단이 LLM 호출 없이 즉시 끝나야 한다는 것이다."""
    many_sources = len(context) >= 4          # 근거가 많으면 종합이 필요
    long_question = len(question) >= 80        # 길고 복잡한 질문
    return many_sources or long_question


def route_answer(question: str, context: list[str]) -> tuple[str, str]:
    """쉬운 요청은 haiku로, 어려운 요청만 opus로 보낸다."""
    model = "claude-opus-5" if looks_hard(question, context) else "claude-haiku-4-5"
    out = answer_once(model, question, context)
    return out["text"], model
```

라우팅을 넣었다면 반드시 다시 재야 합니다. 트래픽의 몇 퍼센트가 어느 모델로 갔는지, 그리고 라우팅을 켠 뒤 전체 해결률이 얼마나 떨어지고 전체 비용이 얼마나 줄었는지를 골든셋으로 확인합니다. 값싼 신호가 어려운 질문을 자꾸 haiku로 잘못 보내면, 아낀 비용보다 잃은 품질이 클 수 있습니다. 그 균형점을 숫자로 찾는 게 라우팅 튜닝입니다.

## 모델을 교체할 때

새 모델이 나왔거나, 더 싼 모델로 갈아타고 싶을 때가 옵니다. 이때 그냥 모델 문자열만 바꿔 배포하면 안 됩니다. 두 가지를 챙겨야 합니다.

첫째는 회귀 확인입니다. 앞 레슨의 <Term id="regression-gate">회귀 게이트</Term>를 그대로 씁니다. 교체 전 모델과 교체 후 모델을 같은 골든셋으로 나란히 돌려, 해결률과 근거 충실성이 통계적으로 유의하게 떨어지지 않았는지 신뢰구간으로 확인합니다. 골든셋이 작으면 몇 문제가 우연히 뒤집힌 것만으로 점수가 출렁이므로, "숫자가 조금 낮아졌다"가 아니라 "진짜 나빠졌다"를 가려야 합니다.

둘째는 <Term id="prompt-portability">프롬프트 이식성</Term>입니다. 지금 쓰는 프롬프트는 알게 모르게 지금 모델에 맞춰져 있습니다. 모델마다 지시를 해석하는 버릇이 다르기 때문에, 같은 프롬프트라도 새 모델에서는 다르게 동작할 수 있습니다.

구체적인 예를 들면 이렇습니다. 어떤 프롬프트 기법은 특정 모델에서만 통하거나, 심지어 새 모델에서는 아예 막혀 있기도 합니다. 예컨대 도구 호출을 강제하는 방식이나 답을 미리 채워 넣는 방식이 모델 세대에 따라 지원되지 않을 수 있습니다. 그래서 모델을 바꿀 때는 프롬프트를 그대로 옮겨 붙이지 말고, 새 모델에서 골든셋을 다시 돌려 점수를 확인하고 필요하면 프롬프트를 손봐야 합니다.

정리하면, 모델 교체는 "문자열 한 줄 수정"이 아니라 "새 후보를 벤치마킹하고 회귀 게이트를 통과시키는" 하나의 작은 실험입니다. 이 습관이 있으면 리더보드에 없는 모델도 겁내지 않고 시험해 볼 수 있습니다.

## opus, sonnet, haiku 어떻게 고르나

Anthropic 모델을 예로 세 모델의 성격을 정리하면 선택의 감이 잡힙니다. 다른 회사 모델도 대개 이런 등급 구조를 가집니다.

opus는 가장 똑똑하고 가장 비쌉니다. 애매한 의도를 풀거나, 여러 근거를 종합해 추론해야 하거나, 실수 비용이 큰 자리에 씁니다. 상담이라면 복잡한 클레임이나 예외 처리가 여기 해당합니다.

sonnet은 균형점입니다. opus에 근접한 품질을 훨씬 싼 비용과 빠른 속도로 냅니다. 대부분의 일상적인 상담 답변 같은 주력 경로의 기본값으로 두기 좋습니다.

haiku는 가장 싸고 빠릅니다. 대량으로 쏟아지는 단순 작업에 맞습니다. 앞 레슨에서 대량 표본을 채점하던 심판, 라우팅의 1차 판단, 간단한 분류나 태깅처럼 "많고 쉬운" 일을 haiku에 맡기면 전체 비용이 크게 내려갑니다.

실전 구성은 대개 이 셋을 섞습니다. 주력은 sonnet으로 두고, 어려운 소수만 opus로 승격하고, 대량의 부가 작업은 haiku로 처리하는 식입니다. 어느 조합이 우리 태스크에 맞는지는, 결국 골든셋으로 재서 정합니다.

## 흔한 함정

리더보드 점수를 그대로 믿는 것이 가장 흔합니다. 그 순위는 남의 태스크 순위입니다. 반드시 내 골든셋으로 다시 재세요.

품질만 보고 고르는 것도 흔합니다. 같은 품질이면 더 싸고 빠른 쪽이 낫고, 품질이 조금 낮아도 비용과 속도로 충분히 벌충되는 경우가 많습니다. 세 축을 같이 보세요.

지연을 평균으로만 재는 것도 위험합니다. 평균은 멀쩡한데 일부 사용자가 오래 기다리고 있을 수 있습니다. p95 같은 꼬리를 보세요.

모델을 교체하면서 프롬프트를 그대로 옮기는 것도 사고의 씨앗입니다. 새 모델에서 골든셋을 다시 돌려 확인하기 전에는 "품질이 같다"고 단정하지 마세요.

마지막으로, 벤치마킹을 한 번 하고 끝내는 것도 함정입니다. 모델도 가격도 계속 바뀝니다. 벤치마크 스크립트를 자산으로 남겨 두고, 새 모델이 나올 때마다 골든셋에 세워 보세요. 그게 채널톡이 리더보드 밖 모델까지 재 본 방식입니다.

## 직접 해보기

앞 레슨에서 만든 골든셋과 심판이 있다면, 이 레슨은 반나절이면 붙입니다.

1. `benchmark_models.py`를 붙여 opus와 sonnet과 haiku를 같은 골든셋으로 돌리고, 해결률과 근거 충실성과 1000건당 비용과 p50, p95 지연을 표로 뽑으세요.
2. 표를 보고 합격선(예: 해결률 80% 이상)을 정한 뒤, 파레토 경계에 남는 후보를 고르세요. 왜 그 후보인지 세 축의 숫자로 한 문단 설명을 써 보세요.
3. `looks_hard`로 라우팅을 넣고 다시 재세요. 라우팅 전후로 전체 해결률이 얼마나 떨어지고 비용이 얼마나 줄었는지 비교해, 그 거래가 남는 장사인지 판단하세요.

여기까지 하면 면접에서 "왜 이 모델을 골랐나요"라는 질문에, 리더보드가 아니라 여러분의 숫자로 답할 수 있습니다.

## 더 깊이 파고들 것

세 가지가 이 레슨의 자연스러운 확장입니다.

첫째, 라우팅의 1차 판단을 값싼 분류 모델로 학습시켜 정확도를 올리는 법입니다. 근거 개수 같은 단순 신호보다 훨씬 잘 걸러 냅니다.

둘째, 비용을 더 줄이는 설계입니다. 반복되는 시스템 프롬프트와 지식 문서를 재사용하는 <Term id="prompt-caching">프롬프트 캐싱</Term>과, 대량 채점 같은 급하지 않은 작업을 묶어 절반 값에 처리하는 배치 처리가 대표적입니다. 이건 뒤의 "컨텍스트 비용을 줄이는 설계" 레슨에서 정면으로 다룹니다.

셋째, 여러 후보를 자동으로 재서 새 모델이 나올 때마다 리포트를 뽑는 벤치마크 파이프라인을 CI에 걸어 두는 것입니다. 그러면 모델 선택이 일회성 조사가 아니라, 늘 갱신되는 시스템이 됩니다.
