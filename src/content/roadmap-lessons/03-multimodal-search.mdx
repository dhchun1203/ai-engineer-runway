## 이 레슨의 목표와 눈높이

이건 선행학습이 아닙니다. 채널톡 Applied AI Engineer가 실제로 설계하는 시스템, 그 깊이 그대로 갑니다.

앞 레슨에서 PDF와 시트와 웹을 지식으로 바꾸는 전처리 파이프라인을 만들었습니다. 그런데 실제 상담 창에는 글만 오지 않습니다. 결제 실패 화면 스크린샷, 영수증 사진, 설정 화면 캡처, 표가 통째로 박힌 이미지가 함께 옵니다.

지식베이스도 마찬가지입니다. 매뉴얼에는 버튼 위치를 가리키는 캡처가 있고, 요금표는 이미지로 붙어 있기도 합니다. 이걸 글만 다루는 검색으로는 못 찾습니다. 채용 공고의 주요 업무에 "멀티모달 지식 검색 시스템 설계"가 그대로 적혀 있는 이유입니다.

이 레슨을 끝내면 다음을 직접 만들 수 있습니다.

1. <Term id="vlm">VLM</Term>으로 이미지를 검색 가능한 글로 바꿔 기존 <Term id="rag">RAG</Term>에 태우는 캡셔닝 파이프라인
2. 이미지와 글을 같은 공간에 넣는 <Term id="embedding">임베딩</Term> 기반의 <Term id="multimodal">멀티모달</Term> 검색
3. 두 방식의 트레이드오프를 알고, 멀티모달 골든셋으로 품질을 재는 눈

## 왜 글만으로는 부족한가

기존 검색은 글자를 다룹니다. 질문도 글, 지식도 글이라 서로 견줄 수 있었습니다.

이미지가 끼면 이 전제가 깨집니다. 고객이 "이 화면에서 뭘 눌러야 하나요"라며 스크린샷 한 장만 올리면, 글자로 된 질문 자체가 없습니다. 반대로 답이 될 지식이 캡처 이미지 안에 그림으로만 들어 있으면, 글 검색은 그 안의 내용을 아예 보지 못합니다.

핵심 난관은 하나입니다. 이미지와 글은 담긴 그릇이 달라서 그대로는 서로 비교가 안 됩니다. 이 둘을 어떻게든 같은 잣대 위에 올려야 검색이 됩니다. 여기서 길이 두 갈래로 갈립니다.

## 두 갈래 길

첫째 길은 이미지를 글로 번역해 오는 것입니다. VLM에게 "이 이미지가 무엇인지 설명해 줘"라고 시켜 캡션과 화면 속 글자를 뽑아낸 뒤, 그 글을 기존 텍스트 검색에 그대로 태웁니다. 통역사를 세워 모두가 한국어로 말하게 만드는 셈입니다.

둘째 길은 이미지와 글을 처음부터 같은 공간에 넣는 것입니다. 이미지든 글이든 같은 차원의 벡터로 바꾸는 특수한 임베딩 모델을 써서, 뜻이 통하면 그림과 글이라도 벡터가 가깝게 나오도록 만듭니다. 통역을 거치지 않고 모두가 같은 언어를 쓰게 만드는 셈입니다.

둘은 배타적이지 않습니다. 실무에서는 흔히 섞어 씁니다. 먼저 각각을 제대로 이해한 뒤, 언제 무엇을 고를지 판단하는 게 이 레슨의 목표입니다.

## 접근 1: 이미지를 글로 바꿔 태우기

이 방식의 장점은 명확합니다. 앞 레슨에서 만든 텍스트 RAG를 그대로 재활용할 수 있습니다. 이미지를 글로 바꾸는 한 단계만 앞에 끼우면 됩니다.

이미지를 글로 바꿀 때는 두 가지를 함께 뽑아야 합니다. 하나는 캡션, 즉 이 이미지가 무엇인지에 대한 설명입니다. 다른 하나는 이미지 안에 실제로 보이는 글자입니다. 화면 속 글자를 읽어내는 이 일을 <Term id="ocr">OCR</Term>이라고 부르는데, 요즘은 VLM이 캡셔닝과 OCR을 한 번에 처리합니다.

여기서 결과를 자유 서술로 받으면 뒤에서 파싱하다 깨지기 쉽습니다. 그래서 앞 평가 레슨에서와 똑같이, 답을 미리 정한 빈칸(도구, tool)에 채워 내도록 강제해 <Term id="structured-output">구조화 출력</Term>으로 받습니다. 대량 색인이라 비용을 아껴 `claude-sonnet-5`를 쓰고, 표나 흐린 글자처럼 까다로운 이미지는 `claude-opus-5`로 올립니다.

```python
# caption.py
import base64
from anthropic import Anthropic

client = Anthropic()  # ANTHROPIC_API_KEY 환경변수에서 자동으로 읽는다

# strict=True로 스키마를 어기지 못하게 못박는다. tool_choice로 이 도구를
# 반드시 부르게 강제하면, 응답은 항상 이 구조의 JSON으로 온다.
CAPTION_TOOL = {
    "name": "describe_image",
    "description": "상담 지식용 이미지를 검색 가능한 텍스트로 정리한다.",
    "input_schema": {
        "type": "object",
        "properties": {
            "caption": {
                "type": "string",
                "description": "이미지가 무엇인지 한두 문장으로 설명",
            },
            "ocr_text": {
                "type": "string",
                "description": "이미지 안에 보이는 글자를 그대로 옮긴 것. 없으면 빈 문자열",
            },
            "ui_elements": {
                "type": "array",
                "items": {"type": "string"},
                "description": "버튼, 메뉴, 오류 메시지 등 눈에 띄는 화면 요소",
            },
            "keywords": {
                "type": "array",
                "items": {"type": "string"},
                "description": "고객이 이 이미지를 찾을 때 쓸 법한 검색어",
            },
        },
        "required": ["caption", "ocr_text", "ui_elements", "keywords"],
        "additionalProperties": False,
    },
    "strict": True,
}


def caption_image(path: str, media_type: str = "image/png") -> dict:
    with open(path, "rb") as f:
        # 이미지를 base64로 인코딩해 image 블록에 실어 보낸다.
        data = base64.standard_b64encode(f.read()).decode("utf-8")

    resp = client.messages.create(
        model="claude-sonnet-5",  # 대량 색인이라 비용을 아낀다. 까다로우면 opus로.
        max_tokens=1024,
        tools=[CAPTION_TOOL],
        # 이 도구를 반드시 부르게 강제 -> 응답이 항상 스키마대로 온다.
        tool_choice={"type": "tool", "name": "describe_image"},
        messages=[
            {
                "role": "user",
                "content": [
                    {
                        "type": "image",
                        "source": {
                            "type": "base64",
                            "media_type": media_type,
                            "data": data,
                        },
                    },
                    {
                        "type": "text",
                        "text": (
                            "이 이미지를 describe_image 도구로 정리하세요. "
                            "화면에 보이는 글자는 지어내지 말고 ocr_text에 그대로 옮기세요."
                        ),
                    },
                ],
            }
        ],
    )
    for block in resp.content:
        if block.type == "tool_use":
            # 직렬화된 문자열을 손으로 파싱하지 말고, SDK가 파싱한 input을 쓴다.
            return block.input
    raise RuntimeError("모델이 도구를 부르지 않았습니다")
```

여기 프롬프트의 "지어내지 말고 그대로 옮기세요"가 그냥 하는 말이 아닙니다. VLM도 결국 모델이라, 흐릿한 숫자를 그럴듯한 값으로 <Term id="hallucination">할루시네이션</Term>하기 쉽습니다. 영수증의 금액 하나를 잘못 읽으면 그게 색인에 박혀 이후 모든 검색을 오염시킵니다. 그래서 캡셔닝 결과도 사람이 표본으로 검수해야 합니다.

이제 뽑아낸 조각들을 하나의 검색 가능한 문서로 합칩니다. 캡션과 OCR 글자와 화면 요소와 키워드를 한 덩어리로 이어 붙여 임베딩과 텍스트 색인의 대상으로 만들고, 원본 이미지 경로와 종류는 <Term id="metadata">메타데이터</Term>로 붙입니다. 나중에 이미지만 걸러 보거나 답변에 근거 출처를 표시할 때 씁니다.

```python
# index_images.py
from caption import caption_image


def image_to_document(image_id: str, path: str) -> dict:
    fields = caption_image(path)

    # 캡션, OCR 글자, 화면 요소, 키워드를 한 덩어리로 이어 붙인다.
    # 이 text가 기존 텍스트 RAG의 임베딩과 색인에 그대로 들어간다.
    searchable = "\n".join(
        [
            fields["caption"],
            fields["ocr_text"],
            " ".join(fields["ui_elements"]),
            " ".join(fields["keywords"]),
        ]
    ).strip()

    return {
        "id": image_id,
        "text": searchable,
        "metadata": {
            "modality": "image",     # 이미지 출처임을 표시. 필터와 출처 표기에 쓴다
            "source_path": path,     # 답변에서 원본 이미지를 다시 보여줄 때 쓴다
            "ocr_text": fields["ocr_text"],
        },
    }
```

이 문서는 앞 레슨의 텍스트 청크와 같은 색인으로 흘러 들어갑니다. 그래서 이미지가 마치 처음부터 글이었던 것처럼 하나의 검색으로 함께 검색됩니다. 이게 캡셔닝 방식의 가장 큰 매력입니다. 새 검색 인프라가 필요 없습니다.

## 접근 2: 이미지와 글을 같은 공간에

캡셔닝은 강력하지만 손실이 있습니다. 통역을 거치면 원문의 뉘앙스가 조금씩 새듯이, 이미지를 글로 옮기는 순간 캡션이 놓친 정보는 영영 사라집니다. 색이나 배치나 미묘한 화면 상태처럼 말로 다 담기 어려운 것들이 그렇습니다.

멀티모달 임베딩은 통역을 건너뜁니다. 이미지도 글도 같은 차원의 벡터로 바꾸되, 뜻이 통하면 벡터가 가깝게 나오도록 학습된 특수한 모델을 씁니다. 그러면 "결제 실패 화면"이라는 글 질의의 벡터가, 실제 결제 실패 스크린샷의 벡터와 가까워집니다. 캡션이라는 중간 글 없이 바로 이어지는 것입니다.

한 가지 짚을 것은, 이 임베딩은 Anthropic API가 아니라 CLIP 계열이나 Voyage 같은 별도의 임베딩 모델이 담당한다는 점입니다. 개념의 뼈대는 어느 모델이든 같습니다. 이미지를 넣는 입구(embed_image)와 글을 넣는 입구(embed_text)가 서로 다른 문이지만, 둘 다 같은 공간의 벡터를 낸다는 것입니다.

```python
# multimodal_embed.py
# embed_image, embed_text는 "같은 모델"의 두 입구다. 둘 다 같은 차원의 벡터를 낸다.
# (구현체는 open_clip이나 Voyage 등. 여기선 개념 흐름에 집중한다.)
import numpy as np


def cosine(a, b) -> float:
    a = np.asarray(a, dtype=float)
    b = np.asarray(b, dtype=float)
    # 두 벡터가 이루는 각도의 가까움. 1에 가까울수록 뜻이 통한다.
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))


def build_image_index(image_paths: dict, embed_image) -> list[dict]:
    """색인 단계: 이미지들을 미리 벡터로 바꿔 저장해 둔다."""
    index = []
    for image_id, path in image_paths.items():
        index.append({"id": image_id, "path": path, "vector": embed_image(path)})
    return index


def search_images(query: str, index: list[dict], embed_text, top_k: int = 5):
    """질의 단계: 글 질의를 같은 공간의 벡터로 바꿔 가까운 이미지를 찾는다."""
    q = embed_text(query)
    scored = [(cosine(q, item["vector"]), item) for item in index]
    scored.sort(key=lambda pair: pair[0], reverse=True)
    return scored[:top_k]
```

여기서 조심할 함정이 하나 있습니다. 이미지와 글을 같은 공간에 넣었다고 해서 둘이 완벽히 포개지는 것은 아닙니다. 실제로는 이미지 벡터들끼리는 이미지끼리, 글 벡터들끼리는 글끼리 살짝 뭉쳐, 두 무리 사이에 틈이 생깁니다. 이 틈을 <Term id="modality-gap">모달리티 갭</Term>이라고 부릅니다.

이게 왜 문제냐면, 글 질의로 이미지를 찾을 때 점수의 절대값이 글끼리 비교할 때와 달라져서, 검색 결과를 하나의 순위표에 섞기가 까다로워지기 때문입니다. 그래서 실무에서는 이미지 검색과 글 검색을 따로 돌린 뒤 각각의 상위 후보만 모아 다시 정렬하는 식으로 다룹니다.

## 둘을 언제 쓰나

정답은 하나가 아니라 트레이드오프입니다. 표로 정리하면 이렇습니다.

| 기준 | 캡셔닝 후 텍스트 검색 | 멀티모달 임베딩 |
| --- | --- | --- |
| 기존 텍스트 RAG 재활용 | 그대로 재활용 | 별도 벡터 인프라 필요 |
| 색인 비용 | 이미지마다 VLM 호출로 비쌈 | 임베딩 한 번으로 저렴 |
| 화면 속 글자, 표 값 | OCR로 정확히 살림 | 세밀한 글자엔 약함 |
| 말로 담기 어려운 시각 정보 | 캡션이 놓치면 손실 | 그대로 벡터에 담김 |
| 설명 가능성 | 캡션을 사람이 읽고 검증 | 벡터라 왜 걸렸는지 보기 어려움 |
| 정보 손실 | 통역 손실 있음 | 통역 없이 직접 |

실무의 결론은 대개 이렇습니다. 화면 속 글자나 표 값이 답의 핵심인 상담(영수증, 설정값, 오류 메시지)에서는 캡셔닝과 OCR이 강합니다. 반면 "이거랑 비슷한 화면 찾아 줘"처럼 시각적 유사성이 중요한 경우엔 멀티모달 임베딩이 강합니다. 채널톡 상담은 글자가 핵심인 경우가 많아 캡셔닝을 기본으로 두되, 시각 유사 검색이 필요한 지점에 임베딩을 얹는 조합이 현실적입니다.

## 실무 아키텍처

시스템을 색인할 때와 질의할 때, 두 시점으로 나눠 생각하면 깔끔합니다.

색인할 때는 지식베이스와 상담 로그의 이미지를 한 번씩 처리해 둡니다. 캡셔닝 방식이면 각 이미지를 검색 가능한 문서로 바꿔 텍스트 색인에 넣고, 임베딩 방식이면 각 이미지를 벡터로 바꿔 <Term id="vector-search">벡터 검색</Term> 인덱스에 넣습니다. 무거운 계산을 미리 끝내 두는 것이 핵심입니다. 질의 때마다 다시 하면 느리고 비쌉니다.

질의할 때는 고객의 입력이 글일 수도, 이미지일 수도, 둘 다일 수도 있습니다. 글은 그대로 검색하고, 첨부 이미지는 즉석에서 캡셔닝하거나 임베딩해 질의로 씁니다. 그렇게 나온 후보들을 한데 모읍니다.

여기서 앞 단계에서 넉넉히 뽑고 뒤에서 추려 내는 <Term id="re-ranking">리랭킹</Term>이 특히 유용합니다. 캡셔닝 검색과 임베딩 검색에서 각각 상위 후보를 넉넉히 받은 뒤, 질문과의 관련성을 더 정교한 기준으로 다시 매겨 진짜 상위 몇 개만 남깁니다. 모달리티 갭 때문에 두 검색의 점수를 곧바로 섞기 어렵다는 문제를, 후보만 모아 다시 정렬하는 이 단계가 자연스럽게 풀어 줍니다.

## 멀티모달 골든셋으로 평가하기

감이 아니라 숫자로 확인해야 하는 건 여기서도 같습니다. 멀티모달 검색의 품질을 재려면 이미지가 포함된 <Term id="golden-set">골든셋</Term>이 필요합니다.

한 항목은 질문과 "이 질문엔 이 이미지(또는 문서)가 근거다"라는 정답 짝으로 이뤄집니다. 실제 상담 로그에서 이미지가 첨부된 대화를 뽑아 만드는 게 가장 좋습니다. 실제 분포를 반영하기 때문입니다.

검색은 순위를 매기는 일이라, 채점 지표로는 recall@k가 잘 맞습니다. "정답 이미지가 상위 k개 안에 들었는가"를 보는 것입니다. 되묻지 않고 단정하면 감점이었던 평가 레슨의 정신과 같습니다. 정답을 상위에 못 올리면 아무리 그럴듯해도 실패입니다.

```python
# eval_multimodal.py
# 멀티모달 골든셋: 질문과 "이 질문의 근거 이미지"를 사람이 미리 짝지어 둔 것.
golden = [
    {"query": "결제 실패 화면 어떻게 해결하나요", "relevant_ids": ["img-pay-err-01"]},
    {"query": "영수증에서 부가세는 어디 나오나요", "relevant_ids": ["img-receipt-tax-03"]},
    # ... 실제 상담 로그의 이미지 첨부에서 뽑아 수십, 수백 개로 늘린다.
]


def recall_at_k(search_fn, golden: list[dict], k: int = 5) -> float:
    """search_fn(query, k)가 (점수, item) 목록을 돌려준다고 가정."""
    hits = 0
    for case in golden:
        found = {item["id"] for _, item in search_fn(case["query"], k)}
        # 정답 이미지 중 하나라도 상위 k에 들면 성공.
        if found & set(case["relevant_ids"]):
            hits += 1
    return hits / len(golden)
```

이 지표가 있으면 캡셔닝만 쓸 때, 임베딩만 쓸 때, 둘을 리랭킹으로 합칠 때를 같은 골든셋으로 나란히 견줘 볼 수 있습니다. 캡셔닝 프롬프트를 바꿨을 때 recall이 올랐는지 떨어졌는지도 숫자로 잡힙니다. 어떤 조합을 프로덕션에 올릴지가 취향이 아니라 측정의 문제가 됩니다.

## 흔한 함정

캡션을 진실로 착각하는 것이 가장 흔합니다. VLM이 흐린 숫자나 표 값을 그럴듯하게 지어내면, 그 오류가 색인에 박혀 계속 잘못된 검색을 부릅니다. 프롬프트로 추측을 막고, 캡셔닝 결과를 표본으로 검수하세요.

모든 이미지를 질의 때마다 실시간으로 캡셔닝하는 것도 함정입니다. 지식베이스 이미지는 색인 때 한 번만 처리해 두면 됩니다. 실시간 처리는 고객이 방금 올린 첨부에만 하세요.

모달리티 갭을 무시하고 두 검색 점수를 곧바로 섞는 것도 위험합니다. 점수 척도가 달라 한쪽이 부당하게 밀립니다. 후보를 모아 리랭킹으로 다시 정렬하세요.

메타데이터를 안 붙이는 것도 나중에 후회합니다. 답변에서 근거가 된 원본 이미지를 다시 보여 주거나, 이미지만 걸러 검색하려면 색인 시점에 출처와 종류를 남겨 둬야 합니다.
