## 이 레슨의 목표와 눈높이

이건 선행학습이 아닙니다. 채널톡 Applied AI Engineer가 실제로 하는 일, 그 깊이 그대로 갑니다.

채널톡 CTO는 스택보다 "기술을 대하는 태도"를 본다고 말합니다. 그 태도가 코드에서 가장 또렷하게 드러나는 자리가 테스트입니다. 테스트가 있으면 겁 없이 고치고, 빠르게 디버깅하고, 프로덕션에 사고를 덜 냅니다. 채용 공고가 강조하는 빠른 가설검증도 결국 "바꿔도 안 깨진다는 안전망" 위에서만 빨라집니다.

그런데 AI 코드에는 특수한 벽이 하나 있습니다. 같은 입력에도 <Term id="hallucination">할루시네이션</Term>처럼 매번 다른 결과가 나올 수 있어서, 전통적인 "정답과 글자가 같은지" 방식이 통하지 않습니다.

이 레슨을 끝내면 다음을 직접 할 수 있습니다.

1. pytest로 <Term id="unit-test">단위 테스트</Term>를 쓰고, 외부 API와 LLM 호출을 <Term id="mocking">모킹</Term>해 빠르고 안정적으로 돌리기
2. 출력이 비결정적인 AI 코드를, 정답 비교가 아니라 계약과 스키마와 속성으로 검증하기
3. 이 테스트들을 <Term id="ci">CI</Term>의 <Term id="regression-gate">회귀 게이트</Term>로 걸어, 나빠지는 변경이 합쳐지지 못하게 막기

## 왜 테스트인가

테스트를 "숙제 검사"쯤으로 여기면 손해입니다. 테스트는 세 가지를 동시에 해 줍니다.

첫째는 회귀 방지입니다. 회귀란 예전에 잘 되던 게 어떤 변경 때문에 다시 망가지는 것입니다. 자동 테스트가 있으면, 지난달에 고친 버그가 오늘 리팩터링으로 되살아났을 때 사람이 눈치채기 전에 빨간불이 켜집니다.

둘째는 리팩터링 안전망입니다. 코드를 겁내면 손을 못 대고, 손을 못 대면 코드가 썩습니다. 테스트가 초록불이면 구조를 과감히 바꿔도 동작이 그대로임을 곧바로 확인할 수 있어, 오히려 더 빨리 개선됩니다.

셋째는 빠른 디버깅입니다. 테스트가 없으면 "어디서부터 잘못됐지"를 처음부터 뒤집니다. 작은 단위 테스트가 촘촘하면, 깨진 순간 어느 함수가 문제인지 바로 짚어 줍니다. 채널톡이 중시하는 빠른 디버깅이 여기서 나옵니다.

정리하면 테스트는 미래의 나에게 남기는 보험입니다. 지금 5분 더 쓰면, 나중에 다섯 시간짜리 사고를 막습니다.

## 테스트 피라미드

테스트라고 다 같은 테스트가 아닙니다. <Term id="test-pyramid">테스트 피라미드</Term>는 어떤 테스트를 얼마나 둘지를 알려 주는 지침입니다. 자동차 공장을 떠올리면 쉽습니다. 부품 하나하나를 검사하는 일은 많이, 부품을 조립해 맞물리는지 보는 일은 그보다 적게, 완성차를 도로에 몰아 보는 일은 가장 적게 합니다.

- 단위 테스트는 피라미드의 넓은 바닥입니다. 함수 하나, 클래스 하나가 홀로 잘 도는지 봅니다. 아주 빠르고(밀리초), 깨지면 원인이 명확합니다. 제일 많이 씁니다.
- 통합 테스트는 중간층입니다. 여러 조각이 맞물릴 때, 예를 들어 분류 함수와 라우팅 함수가 이어 붙었을 때 제대로 흐르는지 봅니다. 단위 테스트보다 느리고 수는 적습니다.
- E2E 테스트는 뾰족한 꼭대기입니다. 사용자가 메시지를 보내는 순간부터 답이 돌아오기까지, 시스템 전체를 진짜에 가깝게 몰아 봅니다. 가장 느리고 가장 잘 깨지므로(외부 요인이 많아서) 핵심 흐름 몇 개만 둡니다.

바닥을 넓게 가져가는 이유는 단순합니다. 위로 갈수록 느리고, 원인 추적이 어렵고, 사소한 이유로 헛되이 실패하기 때문입니다. AI 서비스에서는 특히 LLM을 진짜로 부르는 테스트가 이 꼭대기에 가까워서, 뒤에서 다룰 비용과 비결정성 문제를 함께 안고 있습니다.

## pytest 기초

파이썬 표준은 pytest입니다. 문법이 거의 없다시피 해서, 그냥 `assert`로 원하는 조건을 쓰면 됩니다. 먼저 테스트할 대상부터 봅시다. 분류 결과로 이 상담을 자동 응답에 맡길지 사람에게 넘길지 정하는 순수 함수입니다. 외부 호출이 없어 언제나 같은 입력에 같은 출력을 내므로, 테스트하기 가장 쉬운 종류입니다.

```python
# routing.py
def route(confidence: float, needs_human: bool) -> str:
    """분류 결과로 상담을 어디로 보낼지 정한다.
    사람이 필요하다고 표시됐거나 확신이 낮으면 사람에게 넘긴다."""
    if needs_human or confidence < 0.6:
        return "human"
    return "auto"
```

가장 단순한 테스트는 이렇게 생겼습니다. 함수 이름은 `test_`로 시작해야 pytest가 자동으로 찾아 줍니다.

```python
# test_routing.py
from routing import route


def test_low_confidence_goes_to_human():
    assert route(0.3, needs_human=False) == "human"


def test_high_confidence_goes_to_auto():
    assert route(0.95, needs_human=False) == "auto"
```

같은 함수를 값만 바꿔 여러 번 테스트할 때는, 복사해 붙이지 말고 파라미터화를 씁니다. 표 한 줄이 테스트 하나가 됩니다. 특히 경계값(여기서는 0.6 근처)을 꼭 넣으세요. 버그는 거의 언제나 경계에서 삽니다.

```python
# test_routing.py (이어서)
import pytest
from routing import route


@pytest.mark.parametrize(
    "confidence, needs_human, expected",
    [
        (0.95, False, "auto"),
        (0.30, False, "human"),
        (0.95, True, "human"),   # 확신이 높아도 사람 필요면 사람에게
        (0.60, False, "auto"),   # 경계값: 0.6은 통과
        (0.59, False, "human"),  # 경계 바로 아래: 막힘
    ],
)
def test_route(confidence, needs_human, expected):
    assert route(confidence, needs_human) == expected
```

여러 테스트가 똑같은 준비물(예: 미리 만든 가짜 설정, 임시 파일, 클라이언트)을 필요로 하면, 그 준비를 <Term id="fixture">픽스처</Term>로 한 번만 정의해 두고 필요한 테스트가 인자로 받아 씁니다. 실험할 때마다 매번 비커와 시약을 새로 세팅하지 않고, 조교가 미리 차려 둔 실험대를 받아 쓰는 셈입니다.

```python
# conftest.py  (pytest가 자동으로 읽는 공용 픽스처 파일)
import pytest


@pytest.fixture
def sample_conversation():
    """여러 테스트가 공유하는 예시 상담 데이터."""
    return {
        "id": "conv-001",
        "messages": ["3일 전에 산 건데 환불 되나요?"],
        "customer_tier": "vip",
    }


# test_something.py
def test_conversation_has_id(sample_conversation):
    # 인자 이름을 픽스처 이름과 똑같이 두면 pytest가 값을 넣어 준다.
    assert sample_conversation["id"] == "conv-001"
```

## 외부 API와 LLM 호출 모킹

이제 진짜 문제입니다. 위 `route`는 외부 호출이 없어 쉬웠지만, 실제 AI 코드는 LLM을 부릅니다. 이걸 테스트에서 매번 진짜로 부르면 세 가지가 나빠집니다. 느리고(네트워크 왕복), 돈이 들고(토큰 과금), 결과가 매번 달라져 테스트가 들쭉날쭉해집니다.

그래서 <Term id="mocking">모킹</Term>을 씁니다. 테스트하는 동안만, 진짜 LLM 호출을 미리 정한 가짜 응답으로 바꿔치기하는 것입니다. 영화에서 위험한 장면을 배우 대신 스턴트 대역이 찍는 것과 같습니다. 우리가 검증하려는 건 "LLM이 똑똑한가"가 아니라 "우리 코드가 LLM 응답을 제대로 다루는가"이므로, 대역으로 충분합니다.

먼저 테스트 대상 코드입니다. 고객 메시지를 정해진 구조로 분류하는 함수인데, 답을 자유 서술이 아니라 도구(tool)에 채워 받는 <Term id="structured-output">구조화 출력</Term>으로 강제합니다. 분류는 대량으로 도는 저가 경로라 비용을 아껴 `claude-sonnet-5`를 씁니다.

```python
# classifier.py
from anthropic import Anthropic

client = Anthropic()  # ANTHROPIC_API_KEY 환경변수에서 자동으로 읽는다

# strict=True로 스키마를 어기지 못하게 못박고, tool_choice로 이 도구를
# 반드시 부르게 강제한다. 그러면 응답이 항상 이 구조의 JSON으로 온다.
CLASSIFY_TOOL = {
    "name": "record_intent",
    "description": "고객 메시지의 의도를 분류해 기록한다.",
    "input_schema": {
        "type": "object",
        "properties": {
            "intent": {
                "type": "string",
                "enum": ["refund", "shipping", "bug", "praise", "other"],
            },
            "needs_human": {"type": "boolean"},
            "confidence": {"type": "number", "minimum": 0, "maximum": 1},
        },
        "required": ["intent", "needs_human", "confidence"],
        "additionalProperties": False,
    },
    "strict": True,
}


def classify(message: str) -> dict:
    resp = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=512,
        tools=[CLASSIFY_TOOL],
        tool_choice={"type": "tool", "name": "record_intent"},
        messages=[{"role": "user", "content": message}],
    )
    for block in resp.content:
        if block.type == "tool_use":
            # SDK가 파싱한 block.input을 그대로 쓴다. 직렬화된 문자열을
            # 손으로 파싱하지 않는다(모델별 이스케이프가 다를 수 있다).
            return block.input
    raise RuntimeError("모델이 분류 도구를 부르지 않았습니다")
```

이제 진짜 API를 부르지 않고 테스트합니다. pytest의 `monkeypatch`로 `client.messages.create`를 가짜 함수로 바꿔치기합니다.

```python
# test_classifier.py
import classifier


class _FakeBlock:
    type = "tool_use"
    input = {"intent": "refund", "needs_human": False, "confidence": 0.9}


class _FakeResp:
    content = [_FakeBlock()]


def test_classify_returns_parsed_tool_input(monkeypatch):
    # 진짜 LLM 대신 정해진 가짜 응답을 돌려주게 바꿔치기.
    monkeypatch.setattr(
        classifier.client.messages, "create", lambda **kwargs: _FakeResp()
    )

    result = classifier.classify("환불하고 싶어요")

    # 우리가 검증하는 건 "코드가 tool_use 블록에서 input을 꺼내 오는가"이다.
    assert result["intent"] == "refund"
    assert result["needs_human"] is False


def test_classify_raises_when_no_tool_call(monkeypatch):
    # 실패 경로도 테스트한다. 모델이 도구를 안 불렀을 때 우리 코드는?
    class _EmptyResp:
        content = []

    monkeypatch.setattr(
        classifier.client.messages, "create", lambda **kwargs: _EmptyResp()
    )

    import pytest
    with pytest.raises(RuntimeError):
        classifier.classify("아무거나")
```

여기서 중요한 판단이 하나 있습니다. 위 테스트는 "환불 메시지를 refund로 잘 분류하는가"를 검증하지 않습니다. 그건 가짜 응답이 이미 refund라고 정해 놨으니 당연한 결과일 뿐입니다. 모킹한 테스트로는 코드의 흐름(파싱, 에러 처리, 분기)만 검증할 수 있습니다. 모델이 실제로 똑똑하게 분류하는지는 다른 방식, 곧 평가로 봐야 합니다. 이 경계를 헷갈리면 "테스트는 다 초록불인데 프로덕션은 엉망"인 상황이 생깁니다.

## AI 코드 테스트의 특수성

전통적 테스트는 정답이 하나로 고정됩니다. `add(2, 3)`은 언제나 5이니 `assert add(2, 3) == 5`면 끝입니다.

LLM 출력은 다릅니다. "환불 정책 알려 주세요"에 대한 좋은 답은 표현이 무수히 많고, 같은 모델이라도 매번 문장이 조금씩 다릅니다. 그래서 기대 문자열과 글자가 같은지 맞추는 방식은 곧바로 무너집니다. 어제 통과하던 테스트가 오늘 한 단어 바뀌었다고 실패한다면, 그 테스트는 품질이 아니라 우연을 재고 있는 것입니다.

해법은 발상을 바꾸는 것입니다. "정답 문장을 맞혔는가"를 묻지 말고, "좋은 답이라면 반드시 지켜야 할 규칙을 지켰는가"를 물으세요. 규칙은 표현이 달라도 변하지 않습니다. 이 규칙 검증에는 세 갈래가 있습니다.

첫째는 형식과 스키마 검증입니다. 내용이 무엇이든 형식은 지켜야 합니다.

둘째는 계약과 속성 검증입니다. 어떤 입력이 오든 절대 깨지면 안 되는 불변식을 검사합니다.

셋째는 품질 평가입니다. 내용이 실제로 좋은지는 규칙만으로 판정하기 어려우니, 사람이나 심판 모델의 채점으로 넘깁니다. 이건 다음다음 절에서 다룹니다.

## 형식과 스키마 검증

가장 쉽고 값싼 방어선입니다. 구조화 출력을 쓰기로 했으면, 그 구조를 진짜로 지키는지 테스트로 못박습니다. 서류 심사에서 내용을 읽기 전에 빈칸이 다 채워졌는지부터 확인하는 것과 같습니다.

```python
# test_schema.py
import classifier

VALID_INTENTS = {"refund", "shipping", "bug", "praise", "other"}


def test_output_matches_contract(monkeypatch):
    monkeypatch.setattr(
        classifier.client.messages,
        "create",
        lambda **kwargs: type(
            "R", (), {"content": [type("B", (), {
                "type": "tool_use",
                "input": {"intent": "shipping", "needs_human": True, "confidence": 0.7},
            })()]},
        )(),
    )

    out = classifier.classify("배송이 아직도 안 왔어요")

    # 내용이 아니라 "계약"을 검증한다. 이 조건들은 답이 무엇이든 참이어야 한다.
    assert set(out.keys()) == {"intent", "needs_human", "confidence"}
    assert out["intent"] in VALID_INTENTS
    assert isinstance(out["needs_human"], bool)
    assert 0.0 <= out["confidence"] <= 1.0
```

`strict=True`가 이미 스키마를 강제하지만, 테스트로 한 번 더 못박아 두면 나중에 누군가 도구 정의를 잘못 고쳤을 때 곧바로 잡힙니다.

## 계약과 속성 기반 테스트

한 걸음 더 나아가면 <Term id="property-based-test">속성 기반 테스트</Term>가 있습니다. 예시를 손으로 몇 개 고르는 대신, 규칙(속성)을 선언해 두면 도구가 수백 가지 입력을 자동으로 만들어 그 규칙이 항상 지켜지는지 두들겨 봅니다. 자판기로 비유하면, 어떤 버튼을 누르든 "거스름돈은 절대 음수가 아니다"라는 규칙은 깨지면 안 됩니다. 이 규칙 하나로 온갖 입력을 검사하는 것입니다.

파이썬에서는 hypothesis 라이브러리를 씁니다. 앞의 `route` 함수에 적용해 봅시다.

```python
# test_routing_property.py
from hypothesis import given, strategies as st
from routing import route


@given(confidence=st.floats(min_value=0, max_value=1), needs_human=st.booleans())
def test_route_output_is_always_valid(confidence, needs_human):
    # 불변식 1: 결과는 언제나 이 둘 중 하나여야 한다.
    assert route(confidence, needs_human) in {"auto", "human"}


@given(confidence=st.floats(min_value=0, max_value=1))
def test_needs_human_never_auto(confidence):
    # 불변식 2: 사람이 필요하다고 표시되면 절대 auto로 보내지 않는다.
    # 이건 안전 규칙이라, 어떤 confidence가 와도 깨지면 안 된다.
    assert route(confidence, needs_human=True) == "human"
```

hypothesis는 여기에 0.6 같은 경계값, 0.0, 1.0, 아주 작은 수 같은 까다로운 입력을 스스로 만들어 넣습니다. 사람이 미처 떠올리지 못한 반례를 찾아 주는 게 이 방식의 힘입니다. AI 파이프라인에서는 특히 "출력은 항상 유효한 JSON이다", "점수는 항상 0에서 1 사이다", "PII는 답에 절대 그대로 나오지 않는다" 같은 불변식을 이렇게 지킵니다.

## 품질은 평가로 넘긴다

형식과 계약을 다 지켜도, 답의 내용이 정말 좋은지는 여전히 남습니다. "환불 가능합니다"가 사실은 틀린 안내라면 형식은 완벽해도 나쁜 답입니다. 이 판단은 규칙 몇 줄로 안 되고, 사람의 채점이나 채점을 대신하는 <Term id="llm-judge">LLM 심판</Term>이 필요합니다.

그래서 AI 시스템의 테스트는 두 층으로 갈립니다. 이 구분이 이 레슨의 핵심입니다.

- 결정적 테스트: 모킹으로 LLM을 가짜 응답으로 바꿔 코드 흐름, 형식, 계약, 속성을 검증합니다. 빠르고 공짜이며 결과가 항상 같아서, 모든 커밋마다 CI에서 돌립니다.
- 평가 테스트: 진짜 모델을 사람이 검수한 골든셋으로 돌려 정확성과 근거 충실성 같은 품질을 잽니다. 느리고 돈이 들고 결과가 흔들려서, 커밋마다가 아니라 따로(예: 밤마다, 또는 릴리스 직전) 돌립니다.

품질 채점을 감이 아니라 숫자로 하는 방법, 곧 골든셋 설계와 LLM 심판과 통계적 <Term id="regression-gate">회귀 게이트</Term>는 이 로드맵의 할루시네이션 평가 레슨에서 통째로 다룹니다. 여기서 기억할 것은 딱 하나입니다. 정답 문자열 비교로 품질을 테스트하려 들지 말고, 그 일은 평가 시스템에 맡기고, pytest는 형식과 계약과 흐름을 지키는 데 쓰라는 것입니다.

두 층을 잇는 다리는 이렇게 놓습니다. 평가 결과의 "구조"는 결정적 테스트로, 평가 점수의 "값"은 평가 게이트로 나눠 검증합니다.

```python
# test_eval_bridge.py
# 평가 함수(evaluate)가 뱉는 리포트의 '형식'은 결정적 테스트로 고정한다.
# 점수의 '값'이 기준을 넘는지는 평가 게이트가 따로 본다(할루시네이션 레슨).
from my_evals import evaluate  # 골든셋으로 에이전트를 채점하는 함수


def test_eval_report_shape(monkeypatch):
    monkeypatch.setattr(
        "my_evals.run_agent", lambda q, ctx: "미개봉이면 7일 이내 환불 가능합니다."
    )
    monkeypatch.setattr(
        "my_evals.run_judge",
        lambda **kw: {"score": 5, "grounded": True, "resolution": "resolved"},
    )

    report = evaluate([{"question": "환불 되나요?", "context": ["7일 이내 환불 가능"]}])

    assert "groundedness_rate" in report
    assert 0.0 <= report["groundedness_rate"] <= 1.0
```

## CI에서 자동으로 돌리기

테스트는 내 노트북에서만 돌면 반쪽입니다. <Term id="ci">CI</Term>는 코드를 올릴 때마다 서버가 자동으로 테스트를 돌려 주는 장치입니다. 공장 컨베이어 끝의 검문소처럼, 기준을 통과한 코드만 합쳐지게 합니다. 앞 레슨식으로 말하면 출고 검문소를 코드에 세우는 것입니다.

GitHub Actions로 짠 예시입니다. 핵심은 두 부류의 테스트를 분리하는 것입니다. 빠르고 공짜인 결정적 테스트는 모든 푸시마다 돌리고, 진짜 모델을 부르는 평가 테스트는 API 키가 필요하고 비용이 들므로 여기서 제외해 따로 돌립니다.

```yaml
# .github/workflows/test.yml
name: test
on: [push, pull_request]

jobs:
  fast-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      # -m "not eval": 진짜 LLM을 부르는 평가 테스트는 제외하고
      # 모킹된 결정적 테스트만 빠르게 돌린다.
      - run: pytest -m "not eval" --cov=. --cov-report=term-missing
```

평가 테스트에는 표시를 달아 두면 위 `-m "not eval"`로 걸러집니다.

```python
# test_quality_eval.py
import pytest


@pytest.mark.eval  # 진짜 모델을 부른다. 밤마다 도는 워크플로에서만 실행.
def test_resolution_rate_holds():
    ...  # 골든셋으로 해결률을 재고 기준 아래면 실패 (할루시네이션 레슨 참고)
```

이 분리가 실무에서 중요한 이유는 비결정성과 비용 때문입니다. 진짜 모델을 커밋마다 부르면 CI가 느려지고 돈이 새고, 답이 우연히 흔들려 <Term id="flaky-test">플래키 테스트</Term>가 됩니다. 플래키 테스트란 코드는 그대로인데 어쩌다 통과하고 어쩌다 실패하는 테스트입니다. 양치기 소년처럼 빨간불을 자꾸 거짓으로 울리면, 팀이 곧 테스트를 무시하기 시작합니다. 그래서 커밋 경로에는 결정적 테스트만 두는 것입니다.

## 커버리지 숫자의 함정

<Term id="code-coverage">코드 커버리지</Term>는 테스트가 코드의 몇 퍼센트 줄을 실행했는지 재는 지표입니다. 위 명령의 `--cov`가 이걸 출력합니다.

```bash
pytest -m "not eval" --cov=. --cov-report=term-missing
```

커버리지는 유용하지만 목표로 삼으면 위험합니다. 함정은 이것입니다. 어떤 줄이 "실행됐다"는 것과 그 줄이 "제대로 검증됐다"는 것은 다릅니다. 시험 범위를 100% 훑어봤다고 100점이 아니듯 말입니다.

극단적인 예를 봅시다.

```python
def test_useless_but_100_percent():
    # classify를 호출해서 모든 줄이 '실행'은 되지만,
    # 결과를 아무것도 검증하지 않는다. 커버리지 100%, 가치 0.
    classify("아무거나")  # assert가 없다
```

이 테스트는 커버리지를 채우지만 버그를 하나도 잡지 못합니다. 그래서 커버리지 숫자를 팀 목표(예: "무조건 90%")로 못박으면, 사람들이 assert 없는 껍데기 테스트로 숫자만 맞추는 부작용이 생깁니다. 커버리지는 "어디가 아직 테스트 안 됐나"를 찾는 지도로 쓰세요. 특히 안 덮인 줄(`term-missing`이 보여 줍니다)에서 위험한 분기, 에러 처리, 경계 조건을 우선 채우는 게 숫자를 5%p 올리는 것보다 값집니다. 목표는 높은 숫자가 아니라, 깨지면 안 되는 곳이 실제로 검증되는 것입니다.

## 채널톡식으로 묶으면

지금까지의 조각을 이으면 하나의 안전망이 됩니다. 순수 로직은 단위 테스트와 파라미터화로 촘촘히 덮고, LLM을 부르는 코드는 모킹으로 흐름과 계약을 검증하고, 절대 깨지면 안 되는 규칙은 속성 기반 테스트로 두들기고, 답의 품질은 평가 시스템에 넘기고, 이 모두를 CI 게이트로 걸어 나빠지는 변경을 막습니다.

이 구조가 채널톡이 말하는 빠른 디버깅과 프로덕션 품질의 토대입니다. 모호한 문제를 AI 문제로 바꿔 빠르게 가설검증을 반복하려면, 매번 "이 변경이 뭘 깨뜨렸지"를 손으로 확인해서는 속도가 안 납니다. 테스트가 그 확인을 자동화해 줄 때 비로소 실험이 빨라집니다.

## 흔한 함정

정답 문자열 비교로 LLM 출력을 테스트하려는 것이 가장 흔합니다. 표현이 조금만 달라도 깨져서, 얼마 못 가 팀이 그 테스트를 지웁니다. 형식과 계약을 재고, 품질은 평가로 넘기세요.

진짜 API를 커밋 경로에서 부르는 것도 흔합니다. 느리고 돈이 들고 플래키해집니다. 결정적 테스트는 모킹하고, 진짜 호출은 따로 격리해 돌리세요.

커버리지 숫자를 목표로 삼는 것도 위험합니다. assert 없는 껍데기 테스트를 부릅니다. 커버리지는 지도이지 성적표가 아닙니다.

실패 경로를 안 짜는 것도 흔합니다. 모델이 도구를 안 불렀을 때, 타임아웃이 났을 때, 스키마가 어긋났을 때 우리 코드가 안전하게 넘어지는지도 테스트해야 진짜 프로덕션 코드입니다.

## 직접 해보기

로드맵 앞 단계에서 만든(또는 만들) 작은 AI 함수 하나에 이 레슨을 붙여 보세요. LLM으로 무언가를 분류하거나 뽑아내는 함수면 좋습니다.

1. 그 함수가 부르는 LLM 호출을 `monkeypatch`로 모킹해, 정상 응답과 실패 응답(도구를 안 부른 경우)을 각각 테스트하세요. 흐름과 에러 처리를 검증하는 것이 목표입니다.
2. 함수 출력의 계약을 테스트로 못박으세요. 필수 키가 다 있는가, 값이 허용 범위 안인가, 타입이 맞는가. 여기에 hypothesis로 불변식 하나(예: "점수는 항상 0에서 1 사이")를 속성 기반 테스트로 추가하세요.
3. `pytest --cov`로 커버리지를 재고, 안 덮인 줄 중 위험한 분기 하나를 골라 테스트를 채우세요. 마지막으로 결정적 테스트만 도는 CI 워크플로를 하나 만들어, 진짜 모델을 부르는 평가 테스트는 `-m "not eval"`로 분리하세요.

여기까지 하면 면접에서 "AI 코드는 출력이 비결정적인데 어떻게 테스트했나요"라는 질문에, 계약과 모킹과 평가 분리로 답할 수 있습니다.

세 가지가 이 레슨의 자연스러운 확장입니다. 첫째, 골든셋과 LLM 심판으로 품질을 통계적으로 지키는 회귀 게이트는 할루시네이션 평가 레슨에서 이어집니다. 둘째, 스냅샷 테스트로 프롬프트나 스키마가 의도치 않게 바뀌었는지 감지하는 법입니다. 셋째, 계약 테스트를 팀 사이에 두어(예: 검색 모듈과 생성 모듈의 인터페이스), 한쪽이 형식을 바꾸면 상대의 테스트가 곧바로 빨간불이 되게 하는 법입니다. 각각을 작은 실험으로 만들어 지금의 테스트 스위트에 한 층씩 더해 보세요.
