    ]}

취소된 기록은 매출이 아니니 빼고 세요. 그래서 할 일은 네 가지예요. 세 표를 잇고, 취소를 빼고, 종목과 월로 묶어 더하고, 100만 원 이상만 남겨요.

```sql
SELECT
    s.sport_name AS 종목,
    e.enroll_month AS 수강월,
    COUNT(*) AS 수강인원,
    SUM(e.pay_amount) AS 매출
FROM sports s
LEFT JOIN courses c ON (c.sport_id = s.sport_id)
LEFT JOIN enrollments e ON (e.course_id = c.course_id
                            AND e.status <> '취소')
GROUP BY s.sport_id, e.enroll_month
HAVING SUM(e.pay_amount) >= 1000000
ORDER BY s.sport_name COLLATE "ko-x-icu", 수강월;
```

```text
   종목   | 수강월  | 수강인원 |    매출
----------+---------+----------+------------
 골프연습 | 2026-08 |       12 | 1264000.00
 골프연습 | 2026-09 |       10 | 1018000.00
 골프연습 | 2026-11 |       12 | 1384000.00
 수영     | 2026-11 |       15 | 1092500.00
(4 rows)
```

`pay_amount`는 `NUMERIC(10,2)`라서 합계도 `.00`까지 나와요. 이 결과가 어떻게 나오는지 다음 절에서 한 단계씩 돌려 봐요.

## 3. JOIN은 ON의 짝 규칙으로 잇고, LEFT JOIN은 왼쪽을 다 살린다

`ON`에는 외래 키와 기본 키가 같다는 규칙을 써요. 같은 이름의 열이 여러 표에 있으니 `s.sport_id`처럼 표 별칭을 붙여요.

```sql
FROM sports s
LEFT JOIN courses c ON (c.sport_id = s.sport_id)
```

`LEFT JOIN`은 짝이 없어도 왼쪽 행을 남기고 빈 칸을 NULL로 채워요. 수강 기록이 없는 수영 마스터즈반도 NULL 행 1개로 남아요.

<details>
<summary>자세히 보기</summary>

### `JOIN`은 `ON`의 짝 규칙으로 표를 옆으로 잇는다

`FROM sports s`의 `s`는 표 별칭이에요. 세 표를 함께 쓰면 `sport_id`처럼 같은 이름의 열이 여러 표에 있어서, `s.sport_id`, `c.sport_id`처럼 어느 표의 열인지 밝혀 줘요.

`ON`에는 짝을 짓는 규칙을 써요. 보통 한쪽의 외래 키와 다른 쪽의 기본 키가 같다는 조건이에요. 짝이 맞는 행끼리 옆으로 붙어 한 행이 돼요.

<Figure label="잇기 한 번마다 행 수가 바뀌어요">
  <Seq
    steps={[
      { title: "`FROM sports s`", body: "종목 4행에서 시작해요." },
      { title: "`LEFT JOIN courses c`", body: "종목 하나에 강좌가 여러 개라 14행으로 늘어나요." },
      { title: "`LEFT JOIN enrollments e`", body: "강좌마다 수강 기록이 붙어 189행이 돼요. 취소 아닌 기록 188행과 짝 없는 마스터즈반 1행이에요." },
    ]}
  />
</Figure>

별칭 없이 `SELECT sport_id`라고만 쓰면 `column reference "sport_id" is ambiguous` 오류가 나요. `sports`와 `courses` 둘 다에 있어서 어느 쪽인지 모르는 거예요.

### `LEFT JOIN`은 왼쪽을 다 살리고, 짝 없는 칸은 NULL로 채운다

그냥 `JOIN`(`INNER JOIN`과 같아요)은 양쪽에 짝이 있는 행만 남겨요. `LEFT JOIN`은 왼쪽 표의 행을 짝이 없어도 버리지 않아요.

수영 마스터즈반은 붙을 수강 기록이 없어요. `LEFT JOIN`이라 이 강좌는 살아남고, `enrollments`에서 와야 할 칸은 전부 NULL인 행 1개가 돼요.

<Figure label="수영 마스터즈반은 어떻게 되나">
  <Boxes
    row={[
      { title: "JOIN이면", tone: "neutral", lines: ["짝이 없어서 빠져요", "결과에 흔적이 없어요"] },
      { title: "LEFT JOIN이면", tone: "blue", lines: ["왼쪽 행이라 살아남아요", "`e.enroll_month`, `e.pay_amount`가 NULL"] },
    ]}
  />
</Figure>

같은 원리로 `RIGHT JOIN`은 오른쪽 표를, `FULL OUTER JOIN`은 양쪽 표를 짝이 없어도 다 살려요. JOIN 종류는 "어느 표를 다 살릴까"로 골라요.

</details>

## 4. LEFT JOIN에서 오른쪽 표의 조건은 ON에 쓴다

```sql
LEFT JOIN enrollments e ON (e.course_id = c.course_id
                            AND e.status <> '취소')
```

`WHERE`로 옮기면 NULL 행의 `status`가 NULL이라 `NULL <> '취소'`가 참이 아니어서 빠지고(189행이 188행), `INNER JOIN`과 같아져요.

<details>
<summary>자세히 보기</summary>

이 쿼리는 `e.status <> '취소'`를 `WHERE`가 아니라 `ON` 안에 `AND`로 붙였어요. 그래서 취소 기록은 짝짓기 단계에서 짝이 되지 못하고, 마스터즈반의 NULL 행은 그대로 남아요.

같은 조건을 `WHERE`로 옮기면 이야기가 달라져요. 다 이은 뒤에 거르는데, NULL 행의 `status`는 NULL이라 `NULL <> '취소'`가 참이 되지 않아요. 어제 `= NULL`이 0행이던 것과 같은 이유예요.

<Figure label="같은 조건, 다른 자리">
  <Boxes
    row={[
      { title: "ON에 쓰면", tone: "ok", lines: ["짝을 지을 때만 쓰는 조건", "취소 기록만 짝에서 빠져요", "NULL 행은 남아요(189행)"] },
      { title: "WHERE에 쓰면", tone: "red", lines: ["다 이은 뒤 거르는 조건", "NULL 행까지 빠져요(188행)", "`INNER JOIN`과 같아져요"] },
    ]}
  />
</Figure>

이번 문제는 NULL 행이 어차피 `HAVING`에서 빠지니 결과가 같아요. 그래도 `LEFT JOIN`에서 오른쪽 표의 조건은 `ON`에 쓴다고 기억해요. `WHERE`에 쓰면 애써 살린 행이 조용히 사라져요.

</details>

## 5. GROUP BY는 바구니를 만들고, COUNT(*)는 NULL 행도 센다

종목과 수강월 조합마다 바구니가 하나라, 마스터즈반의 NULL 바구니까지 17바구니예요.

```sql
GROUP BY s.sport_id, e.enroll_month
-- 수강월이 NULL인 바구니: COUNT(*)는 1, SUM(e.pay_amount)는 NULL
```

`SELECT`에는 묶은 열과 집계 함수만 와요.

<details>
<summary>자세히 보기</summary>

`GROUP BY s.sport_id, e.enroll_month`는 종목과 수강월 조합이 같은 행끼리 한 바구니에 담아요. 바구니 하나가 결과의 한 줄이 돼요. 4종목에 4개월이라 16바구니에, 수강월이 NULL인 마스터즈반 바구니가 하나 더 생겨 17바구니예요.

`COUNT`와 `SUM`은 여러 행을 숫자 하나로 줄이는 집계 함수예요. `GROUP BY`가 있으면 바구니마다 따로 계산해요.

<Figure label="수강월이 NULL인 바구니">
  <Boxes
    row={[
      { title: "`COUNT(*)`", tone: "amber", lines: ["행 자체를 세요", "NULL 행도 한 행이라 1"] },
      { title: "`SUM(e.pay_amount)`", tone: "blue", lines: ["NULL은 건너뛰어요", "더할 금액이 없어서 NULL"] },
    ]}
  />
</Figure>

`COUNT(e.course_id)`처럼 오른쪽 표의 열을 세면 NULL을 건너뛰어 0이 나와요. `LEFT JOIN` 뒤에 "몇 건인지" 셀 때는 `COUNT(*)` 대신 `COUNT(오른쪽 열)`을 써요.

### `SELECT`에는 묶은 열과 집계 함수만 온다

바구니 하나는 한 줄이라, 바구니 안에서 값이 여러 개인 열은 `SELECT`에 쓸 수 없어요. 강좌 이름 `c.course_name`을 같이 보려고 하면 이렇게 멈춰요.

```text
ERROR:  column "c.course_name" must appear in the GROUP BY clause or be used in an aggregate function
```

그런데 `s.sport_name`은 `GROUP BY`에 없는데도 돼요. `s.sport_id`가 `sports`의 기본 키라서, 번호로 묶으면 이름도 하나로 정해지기 때문이에요. INNER JOIN 풀이처럼 `GROUP BY s.sport_name`으로 이름 자체를 묶어도 돼요.

</details>

## 6. 바구니는 HAVING으로 거르고, 별칭은 ORDER BY에서 쓴다

`WHERE`는 묶기 전이라 집계 조건을 못 써요. 바구니 조건은 `HAVING`에 식 그대로 써요.

```sql
HAVING SUM(e.pay_amount) >= 1000000
ORDER BY s.sport_name COLLATE "ko-x-icu", 수강월;
```

17바구니 중 4개만 통과하고, NULL 바구니는 여기서 빠져요.

<details>
<summary>자세히 보기</summary>

### `HAVING`은 바구니를 거른다

행을 거르는 `WHERE`는 바구니를 만들기 전에 돌아요. 그래서 `WHERE SUM(e.pay_amount) >= 1000000`처럼 집계 조건을 쓰면 오류예요. 아직 더할 바구니가 없거든요.

```text
ERROR:  aggregate functions are not allowed in WHERE
```

바구니를 만든 뒤의 조건은 `HAVING`에 써요. 17바구니 중 합계가 100만 원 이상인 4개만 통과해요. NULL 바구니는 `NULL >= 1000000`이 참이 아니라서 여기서 빠져요.

<Figure label="거르는 자리가 두 곳이에요">
  <Boxes
    row={[
      { title: "WHERE", tone: "neutral", lines: ["묶기 전, 행 하나씩", "집계 함수는 못 써요"] },
      { arrow: "바구니에 담고 합계 내기" },
      { title: "HAVING", tone: "ok", lines: ["묶은 뒤, 바구니 하나씩", "합계, 개수로 걸러요"] },
    ]}
  />
</Figure>

`HAVING 매출 >= 1000000`처럼 별칭을 쓰면 `column "매출" does not exist` 오류가 나요. `HAVING`은 `SELECT`보다 먼저라 별칭이 아직 없어요. 식 `SUM(e.pay_amount)`를 그대로 다시 써요.

### `ORDER BY`에서는 별칭을 쓸 수 있다

`SELECT`까지 끝난 결과는 순서가 정해져 있지 않아요. 리플레이에서도 정렬 전에는 수영 2026-11 행이 맨 위에 있었어요. 원하는 순서가 있으면 꼭 `ORDER BY`를 써요.

`ORDER BY`는 `SELECT` 다음이라 별칭 `수강월`을 쓸 수 있어요. 앞 열이 같을 때 다음 열로 정렬해서, 같은 골프연습끼리는 수강월 순으로 놓여요.

`COLLATE "ko-x-icu"`는 이 열을 한국어 규칙으로 정렬하라고 정해 주는 말이에요. 그래서 골프연습이 수영보다 앞에 와요.

</details>

## 7. INNER JOIN 풀이도 결과는 같다, 그리고 오늘 만난 오류

`enrollments`에서 출발해 `JOIN`으로 잇고 취소를 `WHERE`로 걸러도 최종 4행은 같아요. 매출 0인 종목까지 보여야 하면 `LEFT JOIN` 풀이가 필요해요.

<details>
<summary>자세히 보기</summary>

### INNER JOIN 풀이와 비교하기

같은 문제를 수강 기록에서 출발해 풀 수도 있어요.

```sql
SELECT
    s.sport_name        AS 종목,
    e.enroll_month      AS 수강월,
    COUNT(*)            AS 수강인원,
    SUM(e.pay_amount)   AS 매출
FROM enrollments e
JOIN courses c ON e.course_id = c.course_id
JOIN sports  s ON c.sport_id  = s.sport_id
WHERE e.status <> '취소'
GROUP BY s.sport_name, e.enroll_month
HAVING SUM(e.pay_amount) >= 1000000
ORDER BY 종목, 수강월;
```

<Figure label="두 풀이의 차이">
  <Boxes
    row={[
      { title: "LEFT JOIN 풀이", tone: "blue", lines: ["`sports`에서 출발", "취소 조건은 `ON`에", "189행, 17바구니", "기록 없는 강좌도 한 행으로 남아요"] },
      { title: "INNER JOIN 풀이", tone: "amber", lines: ["`enrollments`에서 출발", "취소 조건은 `ON`이든 `WHERE`든 같아요", "200행에서 188행, 16바구니", "기록 없는 강좌는 처음부터 없어요"] },
    ]}
  />
</Figure>

`HAVING`이 100만 원 미만을 다 버리는 이 문제에서는 두 풀이의 결과가 같아요. 매출이 0인 종목이나 강좌까지 보여 줘야 하는 문제라면 `LEFT JOIN` 풀이가 필요해요.

### 오늘 만난 오류

| 메시지 | 원인 | 해결 |
| --- | --- | --- |
| `aggregate functions are not allowed in WHERE` | 집계 조건을 `WHERE`에 씀 | `HAVING`으로 옮김 |
| `column "c.course_name" must appear in the GROUP BY clause or be used in an aggregate function` | 묶지 않은 열을 `SELECT`에 넣음 | `GROUP BY`에 더하거나 집계 함수로 감쌈 |
| `column "매출" does not exist` | `HAVING`에 별칭을 씀 | `HAVING SUM(e.pay_amount)`처럼 식을 다시 씀 |
| `column reference "sport_id" is ambiguous` | 두 표에 같은 이름의 열 | `s.sport_id`처럼 표 별칭을 붙임 |
| `LEFT JOIN`인데 NULL 행이 사라짐 | 오른쪽 표 조건을 `WHERE`에 씀 | 그 조건을 `ON`으로 옮김 |

</details>

## 오늘 꼭 기억할 주의점

- `SELECT` 문은 `FROM`/`JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT` 순서로 돌아요. 별칭은 `ORDER BY`에서만 써요.
- `JOIN`은 `ON`의 규칙으로 짝을 지어요. 표가 여럿이면 `s.sport_id`처럼 표 별칭을 붙여요.
- JOIN 종류는 "어느 표를 짝이 없어도 다 살리나"로 골라요. `LEFT JOIN`은 왼쪽을 살리고 짝 없는 칸을 NULL로 채워요.
- `LEFT JOIN`에서 오른쪽 표의 조건은 `ON`에 써요. `WHERE`에 쓰면 NULL 행이 빠져 `INNER JOIN`이 돼요.
- `GROUP BY`를 쓰면 `SELECT`에는 묶은 열과 집계 함수만 와요.
- `COUNT(*)`는 행을 세고, `COUNT(열)`과 `SUM`은 NULL을 건너뛰어요.
- 행 조건은 `WHERE`(묶기 전), 바구니 조건은 `HAVING`(묶은 뒤)이에요. NULL과 비교한 조건은 참이 되지 않아 걸러져요.
- 순서가 필요하면 `ORDER BY`를 꼭 써요. 쓰지 않으면 순서는 정해져 있지 않아요.
