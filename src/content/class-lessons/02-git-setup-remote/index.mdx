어제는 터미널에서 Git을 처음 한 바퀴 돌았어요. 오늘은 그 바퀴를 **내 저장소를 GitHub에 연결하는 데까지** 넓혔어요.

어렵게 느껴져도 개발자라면 매일 쓰는 도구예요. 오늘 내용도 빠짐없이 다시 풀어 볼게요. 레슨 끝에 확인 퀴즈가 있고, 문항을 모두 풀면 [수업 복습](/class) 목록에 완료로 표시돼요.

## 1. rm -rf: 묻지도 않고, 휴지통도 없다

먼저 VS Code 안에서 바로 터미널을 여는 법이에요. 단축키는 `` Ctrl + ` ``예요. 숫자 1 왼쪽에 있는 백틱(`` ` ``) 키예요.

한 번 더 누르면 닫혀요. 코드를 보면서 바로 명령을 칠 수 있어서, 창을 오갈 일이 줄어요.

폴더를 통째로 지우는 `rm -rf`는 어제 배운 `rm -r`에 `-f`가 하나 더 붙은 거예요.

```bash
rm -rf old-project/
```

| 옵션 | 뜻 | 하는 일 |
| --- | --- | --- |
| `-r` | recursive(재귀) | 폴더 안의 폴더, 그 안의 파일까지 전부 |
| `-f` | force(강제) | "정말 지울까요?" 확인 없이 바로 |

두 개를 합치면 **"안에 뭐가 있든 묻지 말고 다 지워"** 라는 뜻이에요.

<TwistBox title="rm -rf . 은 정말 위험해요">

`rm`에는 휴지통이 없어요. 거기에 `-f`까지 붙으면 확인 질문도 없어요.

특히 `rm -rf .`처럼 점(`.`, 지금 있는 폴더)을 대상으로 주면, 내가 서 있는 폴더 안의 모든 게 한 번에 사라져요. 엉뚱한 폴더에 서 있었다면 대형 사고예요.

그래서 실행하기 전에 꼭 두 가지를 쳐 봐요.

```bash
pwd    # 지금 내가 어디 있는지
ls     # 무엇이 지워질지
```

</TwistBox>

## 2. git config: 값이 두 개로 꼬이면 지우고 다시 쓴다

어제 처음 한 번 등록했던 그 설정이에요. 커밋마다 "누가 만들었는지"로 기록돼요.

```bash
git config --global user.email "내 이메일 주소"
git config --global user.name "내 이름"
```

<Note title="이메일은 GitHub 계정과 같게" tone="info">

GitHub에서 커밋이 내 계정으로 잡히려면, 이메일은 **GitHub 계정에 등록된 이메일**과 같아야 해요.

</Note>

보통은 같은 명령을 다시 치면 값이 바뀌어요. 그런데 실수로 값이 **두 개 이상** 들어가 버리면 이렇게 거절당해요.

```bash
git config --global user.name "New Name"
# warning: user.name has multiple values
# error: cannot overwrite multiple values with a single value
```

이럴 땐 그 이름의 값을 전부 지운 뒤 다시 넣어요.

```bash
git config --global --unset-all user.name
git config --global user.name "내 이름"
```

`--unset-all`은 "이 항목에 들어 있는 값을 **모두** 지워"라는 뜻이에요. 지우고 새로 쓰니까 깔끔해요.

<Figure>
  <Trail label="user.name 칸:" values={["값 두 개 (덮어쓰기 거절)", "--unset-all (비어 있음)", "내 이름"]} tone="ok" />
</Figure>

설정은 이렇게 확인해요.

```bash
git config --global --list
# user.name=내 이름
# user.email=내 이메일 주소
```

`--global`을 붙이면 이 컴퓨터 전체에 적용된 설정만 보여 줘요. 빼고 `git config --list`라고 치면 저장소별 설정까지 섞여 나와요.

## 3. .git/hooks: 커밋 직전의 보안 검색대

훅(hook)은 **Git의 특정 순간에 자동으로 실행되는 스크립트**예요. 공항 보안 검색대를 떠올려 보세요. 비행기를 타기 직전에 반드시 한 번 거치고, 걸리면 못 타요.

훅도 똑같아요. 커밋하기 직전, push하기 직전에 자동으로 검사를 돌리고, 검사에 걸리면 그 동작을 막아요.

`git init`을 하면 `.git/hooks` 폴더에 예시 파일이 잔뜩 들어 있어요.

```bash
ls .git/hooks
# commit-msg.sample
# pre-commit.sample
# pre-push.sample
# ... (모두 .sample로 끝나요)
```

`.sample`로 끝나는 동안에는 **아무 일도 안 해요.** 쓰려면 두 가지를 해요.

1. 파일 이름에서 `.sample`을 지운다 (예: `commit-msg`)
2. 실행 권한을 준다 (`chmod +x .git/hooks/commit-msg`)

어제 배운 `chmod +x`가 여기서 쓰여요. 대표적인 훅은 세 가지예요.

| 훅 | 언제 돌아가나 | 주로 하는 일 |
| --- | --- | --- |
| `pre-commit` | 커밋 직전 | 코드 스타일 검사, 테스트 |
| `commit-msg` | 커밋 메시지를 쓴 직후 | 메시지 형식 검사 |
| `pre-push` | push 직전 | 전체 테스트 돌리기 |

직접 만들어 본 `commit-msg` 훅이에요. 커밋 메시지가 `feat:`, `fix:`, `docs:`로 시작하지 않으면 막아요.

```bash
#!/bin/sh
# 커밋 메시지가 feat:, fix:, docs: 로 시작하지 않으면 커밋을 막는다
if ! grep -qE '^(feat|fix|docs): ' "$1"; then
  echo "커밋 메시지는 feat:, fix:, docs: 중 하나로 시작해야 해요"
  exit 1
fi
```

`$1`에는 방금 쓴 커밋 메시지가 담긴 파일 경로가 들어와요. `exit 1`로 끝나면 Git이 "검사 실패"로 보고 커밋을 멈춰요.

실제로 돌려 보면 이렇게 돼요.

```bash
git commit -m "update"
# 커밋 메시지는 feat:, fix:, docs: 중 하나로 시작해야 해요   <- 커밋 안 됨

git commit -m "fix: typo"
# [main 15d9591] fix: typo                                     <- 통과
```

<Note title="훅은 저장소에 같이 안 올라가요" tone="info">

`.git` 폴더 안의 내용은 push해도 GitHub에 올라가지 않아요. 그래서 내가 만든 훅은 **내 컴퓨터에만** 있어요.

팀 전체가 같은 훅을 쓰고 싶으면 **husky** 같은 도구를 써요. 훅 파일을 저장소 안의 일반 폴더에 두고, 설치할 때 자동으로 연결해 주는 도구예요.

</Note>

## 4. U, A, M, D: 파일 옆 글자는 지금 있는 칸을 알려 준다

VS Code 왼쪽 파일 목록이나 소스 제어 탭을 보면, 파일 이름 옆에 알파벳이 붙어 있어요. 어제 배운 세 영역 중 어디에 있는지 알려 주는 표시예요.

| 표시 | 상태 | 뜻 |
| --- | --- | --- |
| `U` | Untracked | Git이 아직 추적하지 않는 새 파일 |
| `A` | Added | index(Staging Area)에 막 추가된 새 파일 |
| `M` | Modified | 추적 중인 파일이 수정됨 |
| `D` | Deleted | 파일이 삭제됨 |

터미널의 `git status --short`도 같은 정보를 보여 줘요. 표시가 살짝 달라요.

```bash
git status --short
#  M a.txt      <- 수정했지만 아직 add 전 (M이 오른쪽 칸)
# ?? new.txt    <- 새 파일 (VS Code의 U)

git add new.txt
git status --short
#  M a.txt
# A  new.txt    <- Staging에 추가됨 (A가 왼쪽 칸)
```

터미널에서는 새 파일이 `U`가 아니라 `??`로 보여요. 그리고 글자가 앉은 칸이 곧 영역이에요.

## 5. git log --all --graph: 모든 갈래를 한 장의 지도로

`git log --oneline`은 **지금 있는 브랜치(HEAD)에서 거슬러 올라갈 수 있는 커밋만** 보여 줘요. 다른 브랜치에만 있는 커밋은 안 보여요.

main에 있으면서 feature 브랜치에 커밋을 하나 해 둔 상황으로 실행해 봤어요.

```bash
git log --oneline
# 95bb6a2 main fix
# 36259ec first

git log --oneline --all
# 0d6d2eb feature work     <- feature 브랜치의 커밋도 보여요
# 95bb6a2 main fix
# 36259ec first
```

`--all`을 붙이면 HEAD가 어디에 있든 **모든 브랜치의 커밋**이 나와요.

목록만으로는 어느 커밋이 어느 갈래인지 헷갈려요. `--graph`를 붙이면 선으로 그려 줘요.

```bash
git log --oneline --all --graph
# * 0d6d2eb (feature) feature work
# | * 95bb6a2 (HEAD -> main) main fix
# |/
# * 36259ec first
```

읽는 법은 이래요.

- `*` 하나가 커밋 하나예요.
- `|/`는 아래쪽 `first` 커밋에서 두 갈래로 갈라졌다는 뜻이에요.
- 괄호 안은 그 커밋을 가리키는 브랜치예요. `HEAD -> main`은 "나는 지금 main에 있다"는 표시예요.

<PredictPrompt />

정답은 두 줄(`main fix`, `first`)이에요. `feature work`는 main에서 거슬러 올라가는 길에 없어서, `--all` 없이는 안 보여요.

## 6. HEAD는 "지금 여기" 스티커: checkout으로 과거에 붙인다

HEAD는 앨범에 꽂아 둔 **"지금 여기" 스티커**예요. 평소에는 브랜치에 붙어 있어요. 그래서 그래프에 `HEAD -> main`처럼 보였죠. 브랜치가 새 커밋으로 움직이면, 거기 붙은 HEAD도 같이 따라가요.

`git checkout` 뒤에 브랜치 이름 대신 **커밋 해시**를 주면, HEAD가 그 커밋으로 직접 옮겨 가요. 작업 폴더의 파일도 그 시점 모습으로 바뀌어요.

`first`, `second`, `third` 세 커밋이 있는 저장소에서 해 봤어요.

```bash
git log --oneline
# 1700d13 third
# 7469759 second
# 46d0572 first

git checkout 46d0572
# Note: switching to '46d0572'.
#
# You are in 'detached HEAD' state. ...
# HEAD is now at 46d0572 first

cat a.txt
# 1             <- 첫 커밋 때의 내용으로 돌아왔어요
```

해시 대신 `HEAD~1`(하나 전), `HEAD~2`(둘 전)처럼 상대 위치로도 옮길 수 있어요.

이동하자마자 Git이 **detached HEAD**라고 알려 줘요. 무섭게 들리지만 고장 난 게 아니에요. "지금 여기" 스티커가 브랜치에서 떨어져서, 커밋 하나에 **직접** 붙어 있다는 뜻이에요.

그래프로 보면 차이가 보여요.

```bash
git status
# HEAD detached at 46d0572

git log --oneline --all --graph
# * 1700d13 (main) third
# * 7469759 second
# * 46d0572 (HEAD) first      <- HEAD 옆에 화살표(->)와 브랜치 이름이 없어요
```

`HEAD -> main`이 아니라 그냥 `(HEAD)`예요. 이 상태에서 `git log --oneline`을 `--all` 없이 치면 `first` 한 줄만 나와요. HEAD에서 거슬러 올라갈 수 있는 커밋이 그것뿐이니까요.

과거 코드를 **구경하기만** 할 때는 아무 문제가 없어요. "그때는 잘 됐는데" 싶을 때 옛 커밋으로 가서 돌려 보는 용도로 써요.

### 그 상태에서 커밋하면 길을 잃어요

detached HEAD에서 커밋을 하면, 새 커밋은 생기지만 **어떤 브랜치도 그 커밋을 가리키지 않아요.**

```bash
echo x >> a.txt
git commit -am "experiment"
git log --oneline --all --graph
# * 1700d13 (main) third
# * 7469759 second
# | * 8a1091b (HEAD) experiment
# |/
# * 46d0572 first
```

여기서 main으로 돌아가면 Git이 경고해요.

```bash
git switch main
# Warning: you are leaving 1 commit behind, not connected to
# any of your branches:
#
#   8a1091b experiment
```

돌아온 뒤 그래프를 보면 `experiment`가 사라져 있어요. 책갈피(브랜치)가 없으니 목록에서도 안 보이는 거예요. 해시를 적어 두지 않았다면 찾기가 아주 어려워져요.

경고에 나온 해시로 브랜치를 만들면, 그 커밋에 책갈피가 생겨 다시 보여요.

```bash
git branch experiment 8a1091b
git log --oneline --all --graph
# * 8a1091b (experiment) experiment
# | * 1700d13 (HEAD -> main) third
# | * 7469759 second
# |/
# * 46d0572 first
```

처음부터 실험할 생각이었다면, 커밋하기 **전에** `git switch -c 새-브랜치`로 브랜치를 만들어 두는 게 가장 깔끔해요.

브랜치로 돌아올 때는 이렇게 해요.

```bash
git switch main      # 또는 git checkout main
git switch -         # 바로 전에 있던 곳으로 (cd - 와 같은 느낌)
```

<TwistBox title="switch는 커밋으로 바로 못 가요">

`git switch 46d0572`처럼 해시를 주면 거절당해요.

```bash
git switch 46d0572
# fatal: a branch is expected, got commit '46d0572'
# hint: If you want to detach HEAD at the commit, try again with the --detach option.
```

`switch`는 브랜치 전용이라서, 커밋으로 가려면 `git switch --detach 46d0572`처럼 "떨어뜨려도 된다"고 분명히 말해야 해요. `checkout`은 이 확인 없이 바로 옮겨 가요. 1회차에서 본 것처럼 checkout이 여러 일을 한꺼번에 하던 명령어라서 그래요.

</TwistBox>

## 7. GitHub 연결: 빈 저장소에 네 줄로 올린다

GitHub 웹사이트에서 New repository로 저장소를 만들어요. 이때 중요한 규칙이 하나 있어요. **내 컴퓨터에 이미 코드가 있다면, README와 .gitignore를 체크하지 말고 완전히 빈 저장소로 만들어요.**

GitHub에서 README를 같이 만들면, 원격 저장소에 내 컴퓨터에는 없는 커밋이 하나 생겨요. 그 상태로 push하면 이렇게 거절당해요.

```bash
git push -u origin main
#  ! [rejected]        main -> main (fetch first)
# error: failed to push some refs to ...
# hint: Updates were rejected because the remote contains work that you do not
# hint: have locally.
```

"원격에 내가 모르는 작업이 있다"는 뜻이에요. 빈 저장소로 만들면 이 문제가 처음부터 안 생겨요.

<Figure>
  <GateFlow
    gates={[
      { q: "GitHub에서 README나 .gitignore를 같이 만들었나?", out: "원격에 내 컴퓨터에는 없는 커밋이 생겨서 첫 push가 `rejected (fetch first)`" },
    ]}
    pass={{ text: "빈 저장소: 아래 네 줄로 연결하고 올려요", code: "git push -u origin main" }}
  />
</Figure>

연결하고 올리는 네 줄이에요.

```bash
git remote add origin https://github.com/my-id/my-project.git
git remote -v
git branch -M main
git push -u origin main
```

| 명령어 | 하는 일 |
| --- | --- |
| `git remote add origin <URL>` | 원격 저장소를 `origin`이라는 이름으로 연결 |
| `git remote -v` | 연결된 원격 주소 확인 |
| `git branch -M main` | 지금 브랜치 이름을 `main`으로 바꾸기 |
| `git push -u origin main` | 원격에 올리고, 짝(upstream)을 기억시키기 |

`git remote -v`는 주소를 두 줄로 보여 줘요. 받아올 때(fetch)와 올릴 때(push) 쓰는 주소예요. 보통은 같아요.

```bash
git remote -v
# origin  https://github.com/my-id/my-project.git (fetch)
# origin  https://github.com/my-id/my-project.git (push)
```

<Note title="git branch -M main은 습관처럼 쳐도 괜찮아요" tone="info">

예전 기본 이름인 `master`로 만들어진 저장소를 `main`으로 맞출 때 써요. 이미 `main`이면 아무 변화가 없어요.

</Note>

### -u는 짝을 기억시킨다

`-u`는 "내 main은 앞으로 origin의 main과 짝이야"라고 기억시켜요. 처음 push할 때 이렇게 알려 줘요.

```bash
git push -u origin main
# branch 'main' set up to track 'origin/main'.
#  * [new branch]      main -> main
```

<Figure>
  <Boxes
    row={[
      { title: "main", note: "내 컴퓨터의 브랜치", tone: "blue", lines: ["다음부터 `git push`, `git pull`만 쳐도 돼요"] },
      { arrow: "`-u`로 짝(upstream)을 기억해요" },
      { title: "origin/main", note: "GitHub의 main", tone: "rust", lines: ["`branch 'main' set up to track 'origin/main'.`"] },
    ]}
  />
</Figure>

이 짝을 **upstream**이라고 불러요. 한 번 정해 두면 다음부터는 `git push`, `git pull`만 쳐도 돼요.

`-u` 없이 연결만 한 저장소에서 `git push`만 치면 Git이 이렇게 물어요.

```bash
git push
# fatal: The current branch main has no upstream branch.
# To push the current branch and set the remote as upstream, use
#
#     git push --set-upstream origin main
```

`--set-upstream`은 `-u`의 긴 이름이에요. 결국 처음 한 번은 짝을 정해 줘야 한다는 뜻이에요.

### 연결 끊기

주소를 잘못 넣었거나 다른 저장소로 바꾸고 싶으면 연결을 지우고 다시 넣어요.

```bash
git remote remove origin
git remote -v       # 아무것도 안 나오면 끊긴 것
```

연결만 끊는 거라서, 내 커밋이나 GitHub에 이미 올라간 내용은 그대로예요.

## 8. vim: 모드를 바꿔야 글자가 써진다

터미널에서 일하다 보면 vim이라는 편집기가 불쑥 열릴 때가 있어요. 예를 들어 `git commit`을 `-m` 없이 치면 메시지를 쓰라고 편집기가 열려요(기본 편집기를 vim으로 정해 둔 경우).

처음 보면 글자도 안 써지고, 나가는 법도 몰라 당황해요. vim에는 **모드**가 있어서 그래요.

<Figure>
  <Boxes
    row={[
      { title: "명령 모드", note: "처음 열리면 여기", tone: "blue", lines: ["키를 누르면 글자가 아니라 명령으로 받아요", "`:w`, `:wq`, `:q`, `:q!`는 여기서 쳐요"] },
      { arrow: "`i`를 누르면" },
      { title: "입력 모드", note: "글자가 써져요", tone: "rust", lines: ["`Esc`를 누르면 다시 명령 모드로 돌아와요"] },
    ]}
  />
</Figure>

| 하고 싶은 것 | 키 |
| --- | --- |
| 입력 모드 들어가기 | `i` |
| 입력 모드 나가기 | `Esc` |
| 저장만 하기 | `:w` |
| 저장하고 나가기 | `:wq` |
| 나가기 (수정이 없을 때) | `:q` |
| 저장하지 않고 강제로 나가기 | `:q!` |

`:`로 시작하는 명령은 명령 모드에서 쳐요. 그래서 나갈 때는 **`Esc`를 먼저 누르고** `:wq`를 치고 Enter예요.

`w`는 write(쓰기), `q`는 quit(나가기), `!`는 "묻지 말고"라는 뜻이에요. `rm -rf`의 `-f`와 비슷한 느낌이에요.

## 9. 셀프 체크: 수정부터 push까지 말로 설명하기

오늘 노트의 마지막 질문은 이거였어요. **"파일을 수정하고 원격 저장소에 올리기까지의 루틴을 설명할 수 있니?"**

정답을 보기 전에 먼저 소리 내어 순서를 말해 보세요. 그다음 아래와 맞춰 봐요.

```bash
# 0. 처음 한 번만 (저장소를 만들고 GitHub와 연결할 때)
git init
git remote add origin https://github.com/my-id/my-project.git
git branch -M main

# 1. 파일을 수정한다 (VS Code에 M 표시가 뜬다)

# 2. 무엇이 바뀌었는지 확인
git status
git diff

# 3. 올릴 변경을 Staging에 담기 (M 표시가 Staging 쪽으로 옮겨 간다)
git add README.md

# 4. 커밋으로 남기기
git commit -m "docs: README에 설치 방법 추가"

# 5. 원격으로 올리기 (처음 한 번은 -u, 그다음부터는 git push만)
git push -u origin main
git push
```

택배로 말하면 이렇게 돼요.

## 오늘 꼭 기억할 주의점

- `rm -rf`는 확인도 휴지통도 없어요. `pwd`와 `ls`로 위치와 대상을 먼저 확인해요.
- `git config`에 값이 여러 개 들어가 꼬이면 `--unset-all`로 지우고 다시 넣어요.
- 훅은 `.sample`을 지우고 실행 권한까지 줘야 동작해요. 그리고 저장소에는 올라가지 않아요.
- `git checkout <해시>`는 구경용이에요. detached HEAD에서 커밋할 거라면 먼저 `git switch -c`로 브랜치를 만들어요.
- 내 컴퓨터에 코드가 있으면 GitHub 저장소는 **빈 채로** 만들어요. README를 같이 만들면 첫 push가 거절당해요.
- vim에서 막히면 일단 `Esc`, 그다음 `:wq`(저장하고 나가기) 또는 `:q!`(버리고 나가기)예요.
