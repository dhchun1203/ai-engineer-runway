## 1. Git과 GitHub는 다른 것이에요

### Git: 내 컴퓨터에서 도는 "세이브 도구"

게임의 세이브 파일을 떠올려 보세요. 보스 앞에서 저장해 두면, 지더라도 그 지점으로 돌아갈 수 있죠.

Git은 코드에 세이브 지점을 만들어 주는 도구예요. 리눅스를 만든 리누스 토발즈가 2005년에 만들었어요.

Git의 큰 특징은 **분산형**이라는 점이에요. 개발자마다 자기 컴퓨터에 전체 이력을 통째로 가진 저장소가 있어요.

그래서 인터넷이나 서버에 연결하지 않아도 지난 커밋을 보고 브랜치 작업을 할 수 있어요. 비행기 안에서도 Git은 잘 돌아가요.

### GitHub: 저장소를 올려 두고 함께 쓰는 서비스

GitHub는 Git 저장소를 인터넷에 올려 두는 웹 서비스예요. 2018년에 마이크로소프트가 인수했어요.

저장소를 보관하는 것 말고도 협업 기능이 많아요.

- **Pull Request**: "내가 고친 것 합쳐 주세요" 하고 검토를 요청하는 기능
- **Issues**: 할 일과 버그를 적어 두는 게시판
- **Actions**: 코드를 올릴 때마다 테스트나 배포를 자동으로 돌리는 기능

내가 올린 저장소들이 그대로 **개발자 포트폴리오**가 되기도 해요.

> Git은 내 컴퓨터에서 동작하는 도구, GitHub는 Git 저장소를 올려 두고 함께 쓰는 서비스예요. GitHub 없이도 Git은 쓸 수 있어요. 반대로 GitHub만 있고 Git이 없으면 아무것도 못 해요.

## 2. 저장소와 세 가지 영역

### 저장소의 정체는 .git 폴더

저장소(Repository)는 두 종류예요. 내 컴퓨터에 있는 **로컬 저장소**, GitHub 같은 곳에 있는 **원격 저장소**예요.

로컬 저장소의 실체는 프로젝트 폴더 안의 `.git`이라는 숨김 폴더예요. 모든 커밋 이력이 여기 들어 있어요.

그래서 `.git` 폴더를 지우면 이력이 전부 사라져요. 파일은 남지만, 그 파일이 어떻게 변해 왔는지는 하나도 남지 않아요.

### 세 가지 영역: 택배 보내기로 생각해요

Git에는 파일이 머무는 곳이 세 군데 있어요. 택배 보내는 과정과 똑같아요.

| 영역 | 택배로 치면 | 하는 일 |
| --- | --- | --- |
| Working Directory (작업 폴더) | 방 안에 흩어진 물건 | 실제로 파일을 편집하는 곳 |
| Staging Area (인덱스) | 택배 상자에 담아 둔 물건 | 다음 커밋에 넣을 변경만 골라 두는 곳 |
| Repository (저장소) | 송장 붙여 보낸 상자 | 커밋 이력이 저장되는 곳 |

방에 있는 물건을 전부 보내지는 않잖아요. 보낼 것만 골라 상자에 담고(add), 상자를 봉해서 송장을 붙여요(commit).

Staging Area는 진짜 폴더가 아니에요. `.git/index`라는 파일 하나로 "다음에 담을 목록"을 관리하는 논리적인 영역이에요.

```txt
Working Directory  --(git add)-->  Staging Area  --(git commit)-->  Repository
```

### 커밋은 사진 한 장, 그리고 차곡차곡 쌓여요

커밋은 그 순간 프로젝트 전체를 찍은 **스냅샷(사진)** 이에요.

그렇다고 매번 모든 파일을 새로 복사하지는 않아요. 바뀌지 않은 파일은 이전 것을 그대로 가리키기만 해서, 실제로는 수정된 내용만 새로 저장되는 셈이에요.

커밋은 계속 누적되고, 커밋마다 `361fe59` 같은 고유한 해시(ID)가 붙어요. 이 ID로 원하는 커밋으로 돌아갈 수 있어요.

## 3. add, commit, push, pull: 이력이 움직이는 길

명령어 네 개가 이력을 옮겨요.

```txt
add -> commit -> push / pull
```

- `git add`: 변경 중에서 이력에 남길 것만 골라 Staging Area에 올려요.
- `git commit`: Staging Area의 변경을 커밋 하나로 묶어 로컬 저장소에 남겨요.
- `git push`: 로컬 저장소의 이력을 원격 저장소로 올려요(업로드).
- `git pull`: 원격 저장소의 새 이력을 내 컴퓨터로 받아와요(다운로드).

### 원격 저장소는 왜 필요할까요

두 가지 상황을 떠올리면 돼요.

1. **여럿이 함께 일할 때**: 서로 다른 곳에 있는 개발자들이 원격 저장소 하나를 가운데 두고 작업을 주고받아요.
2. **혼자서 여러 곳에서 일할 때**: 사무실에서 push하고, 집에서 pull해서 이어서 작업해요.

## 4. 되돌리기: reset과 revert

실수로 커밋했을 때 되돌리는 방법이 두 가지예요. 기준은 하나예요. **그 커밋을 이미 가져간 팀원이 있느냐.**

| 명령어 | 언제 쓰나 | 비유 |
| --- | --- | --- |
| `git reset` | 변경 이력을 **가져간 팀원이 없을 때** | 아무도 안 본 일기장 페이지를 찢기 |
| `git revert` | 이미 **가져간 팀원이 있을 때** | 찢지 않고 "앞의 일기는 취소" 하는 정정 일기를 새로 쓰기 |

이미 친구가 복사해 간 일기장 페이지를 내 쪽에서만 찢으면, 둘의 일기장이 어긋나요. 그래서 공유된 이력은 revert로 고쳐요.

### git reset: 시간을 되감기

현재 브랜치(HEAD)를 지정한 커밋으로 옮겨요. 옵션에 따라 어디까지 되돌릴지가 달라져요.

`HEAD~1`은 "지금 커밋에서 하나 전"이라는 뜻이에요. `git reset --soft HEAD~1`이면 마지막 커밋 하나를 취소해요.

| 옵션 | 커밋 | Staging Area | 작업 폴더 |
| --- | --- | --- | --- |
| `--soft` | 취소 | 변경이 **남아 있음** | 그대로 |
| `--mixed` (기본값) | 취소 | 비워짐 | 변경이 **남아 있음** |
| `--hard` | 취소 | 비워짐 | 변경까지 **사라짐** |

택배로 다시 보면 이래요.

- `--soft`: 송장만 떼요. 물건은 상자에 담긴 그대로예요.
- `--mixed`: 상자에서도 꺼내 방에 내려놔요. 옵션 없이 `git reset`만 치면 이거예요.
- `--hard`: 물건을 아예 버려요. 되돌릴 수 없으니 정말 조심해요.

실제로 `--soft`를 해 보면, 커밋은 사라지고 변경은 Staging에 남아 있는 게 보여요.

```bash
git reset --soft HEAD~1
git status --short
# M  README.md        <- 맨 앞 M이 "Staging에 담긴 수정"이라는 뜻
```

### git revert: 반대로 고치는 새 커밋

지정한 커밋의 변경을 정반대로 적용한 **새 커밋**을 만들어요. 원래 커밋도 이력에 그대로 남아요.

```bash
git revert 7933e0e
git log --oneline
# e1ef341 Revert "docs: add second line"
# 7933e0e docs: add second line
# 361fe59 docs: add README
```

이력이 지워지지 않고 하나 더 쌓였죠. 팀원은 그냥 pull만 하면 돼요.

## 5. 브랜치와 GitFlow

### 브랜치는 "움직이는 책갈피"

브랜치는 특정 커밋을 가리키는 **움직이는 포인터**예요. 새 커밋을 만들면 책갈피가 자동으로 그 커밋으로 옮겨가요.

브랜치를 새로 만들면 본 작업과 분리된 독립적인 작업 줄기가 생겨요. 실험이 망해도 원래 줄기는 멀쩡해요.

```bash
git switch -c feature/jump     # 새 브랜치를 만들고 그쪽으로 이동
git checkout -b feature/jump   # 같은 일, 더 오래된 명령어(현업에서 더 자주 보여요)
```

`checkout`은 브랜치 이동 말고도 파일 되돌리기 같은 일을 함께 하던 명령어예요. 그래서 브랜치 전용으로 `switch`가 새로 생겼어요. 둘 다 알아 두면 돼요.

브랜치를 만들고 PR까지 가는 흐름은 [Git 브랜치와 PR 협업 흐름](/lesson/1-2-git-branch-and-pr) 레슨에서 한 바퀴 돌아볼 수 있어요.

### GitFlow: 브랜치를 나누는 팀의 약속

GitFlow는 Git으로 협업할 때 브랜치를 어떻게 나눌지 정한 전략이에요. 정답은 아니고, 팀에 맞게 고쳐서 써요.

가장 중요한 건 **main 브랜치**예요.

- main은 **항상 출시 가능한 완성본**이에요. 지금 당장 배포해도 되는 상태를 유지해요.
- main에 합치는 일은 보통 팀장이 관리해요.

나머지 작업은 main에서 갈라져 나온 브랜치에서 하고, 다 되면 검토를 거쳐 합쳐요.

## 6. winget: 명령어로 프로그램 설치하기

### winget이 뭔가요

winget은 Windows의 **패키지 매니저**예요. 앱스토어를 명령어로 쓰는 거라고 생각하면 돼요. 사이트에 들어가 설치 파일을 받고 "다음"을 누르는 대신, 한 줄로 설치해요.

```bash
winget install -i Git.Git
```

`-i`(`--interactive`)는 설치 옵션을 고르는 화면을 띄워 줘요. 설치 중에 이 세 가지를 확인해요.

- 기본 에디터: VS Code 등 평소 쓰는 편집기
- 기본 브랜치 이름: `main`
- PATH 설정: "Git from the command line..." (어느 폴더에서든 `git` 명령이 되게)

설치가 끝나면 터미널을 새로 열고 확인해요.

```bash
git --version
```

### winget search: 설치 전에 이름과 ID 확인

설치하기 전에 패키지 이름과 **ID**를 검색해서 확인해요.

```bash
winget search git                     # 이름, ID, 태그에 git이 들어간 패키지 검색
winget search --id Git.Git            # ID로 검색
winget search git --source winget     # 검색할 저장소 지정 (winget 또는 msstore)
winget search git --count 5           # 결과를 5개까지만
```

검색 결과는 이런 열로 나와요.

| 열 | 의미 |
| --- | --- |
| 이름 (Name) | 패키지 표시 이름 |
| ID | 패키지 고유 식별자(예: `Git.Git`), 설치할 때 이걸 써요 |
| 버전 (Version) | 최신 버전 |
| 일치 (Match) | 검색어와 일치한 부분 |
| 원본 (Source) | 패키지 출처(winget, msstore) |

이름이 비슷한 패키지가 정말 많아요. 그래서 설치는 **ID 기준**으로 하는 게 안전해요.

`-e`(`--exact`)를 붙이면 ID가 정확히 일치하는 것만 골라요.

```bash
winget install --id Git.Git -e
```

### winget 자주 쓰는 명령어

| 명령어 | 하는 일 |
| --- | --- |
| `winget search <검색어>` | 패키지 검색 |
| `winget show <ID>` | 상세 정보(버전, 설명, 설치 옵션) |
| `winget install <ID>` | 설치 |
| `winget list` | 설치된 프로그램 목록 |
| `winget upgrade` | 업그레이드할 수 있는 프로그램 목록 |
| `winget upgrade <ID>` | 특정 프로그램 업그레이드 |
| `winget uninstall <ID>` | 삭제 |

## 7. 터미널 기본 명령어

아래 명령어는 Git을 설치하면 함께 깔리는 **Git Bash**, macOS 터미널, 리눅스에서 똑같이 동작해요. 리눅스 서버에서도 그대로 쓰니까 지금 손에 익혀 둬요.

### 7-1. 파일 목록 보기: ls

```bash
ls          # 기본 목록
ls -a       # 숨김 파일까지 (.git, .gitignore 등 점으로 시작하는 파일)
ls -l       # 자세히 (권한, 크기, 날짜)
ls -al      # 숨김 파일 + 자세히 (가장 자주 써요)
```

`.git` 폴더는 이름이 점으로 시작해서 그냥 `ls`로는 안 보여요. 저장소인지 확인할 때 `ls -a`를 쳐 보는 이유예요.

### 7-2. ls -al 한 줄 읽는 법

`ls -al`은 이런 줄을 보여 줘요.

```txt
drwxr-xr-x  2 user group 4096 Oct 26 16:00 src
-rw-r--r--  1 user group   12 Oct 26 16:01 README.md
```

처음 보면 암호 같지만, 맨 앞 10글자만 읽으면 돼요. **첫 글자는 종류**예요.

| 맨 앞 글자 | 의미 |
| --- | --- |
| `d` | 폴더(directory) |
| `l` | 링크(바로가기, symbolic link) |
| `-` | 일반 파일 |

나머지 9글자는 **접근 권한**이에요. `rwx` 세 글자가 세 번 반복돼요.

- `r`: Read(읽기), `w`: Write(쓰기), `x`: Execute(실행), 권한이 없으면 `-`
- 세 묶음의 순서: 소유자(user), 그룹(group), 그 외(others)

`rwxr-xr--`를 세 글자씩 끊어 볼게요.

| 묶음 | 글자 | 뜻 |
| --- | --- | --- |
| 소유자 | `rwx` | 읽기, 쓰기, 실행 모두 가능 |
| 그룹 | `r-x` | 읽기, 실행만 가능 |
| 그 외 | `r--` | 읽기만 가능 |

그러니 위의 `README.md`(`-rw-r--r--`)는 일반 파일이고, 소유자만 고칠 수 있고 나머지는 읽기만 할 수 있어요.

권한은 `chmod`로 바꿔요. 예를 들어 스크립트 파일에 실행 권한을 주려면 이렇게 해요.

```bash
chmod +x script.sh
```

### 7-3. 이동과 경로

```bash
pwd         # 지금 내가 있는 위치 출력
cd <폴더>    # 폴더로 이동
cd ..       # 한 칸 위 폴더로
cd ~        # 홈 폴더로
cd -        # 바로 전에 있던 폴더로 돌아가기
```

`cd -`는 TV 리모컨의 "이전 채널" 버튼이에요. 두 폴더를 오갈 때 경로를 다시 칠 필요가 없어요.

### 7-4. 파일과 폴더 다루기

```bash
mkdir <폴더>        # 폴더 만들기
touch <파일>        # 빈 파일 만들기
cat <파일>          # 파일 내용 보기 (예: cat README.md)
cp <원본> <대상>     # 복사
mv <원본> <대상>     # 이동, 또는 이름 바꾸기
rm <파일>           # 파일 삭제
rm -r <폴더>        # 폴더 삭제 (안의 내용까지)
```

`mv`는 옮기는 명령인데, 같은 폴더 안에서 옮기면 결과적으로 이름이 바뀌어요. 그래서 이름 바꾸기도 `mv`로 해요.

<TwistBox title="rm에는 휴지통이 없어요">

윈도우에서 파일을 지우면 휴지통으로 가지만, `rm`은 그 자리에서 바로 지워요. 되살릴 방법이 없어요.

지우기 전에 `ls`로 대상을 꼭 확인하는 습관을 들여요.

</TwistBox>

### 7-5. echo와 리다이렉션

```bash
echo $SHELL                      # 지금 쓰는 셸 이름 출력
echo "Hello World"               # 글자 출력
echo "Hello World" > README.md   # 출력을 README.md에 저장 (덮어쓰기)
echo "Second line" >> README.md  # README.md 끝에 이어 쓰기
```

`echo $SHELL`을 치면 지금 쓰는 셸(명령을 받아 주는 프로그램)이 나와요. Git Bash라면 `/usr/bin/bash` 같은 bash 경로가, 요즘 macOS라면 `/bin/zsh`가 나와요.

`$`는 **변수를 꺼내 쓴다**는 표시예요. `SHELL`처럼 대문자로 된 것은 대부분 시스템이 미리 정해 둔 환경 변수예요.

`>`와 `>>`는 화면에 나올 글자를 파일로 보내는 **리다이렉션**이에요. 차이는 하나예요.

| 기호 | 하는 일 |
| --- | --- |
| `>` | 파일을 **새로 씀**(원래 내용은 사라짐) |
| `>>` | 파일 **끝에 덧붙임** |

<PredictPrompt />

아래를 차례로 실행하면 마지막에 무엇이 보일지 먼저 예측해 보세요.

```bash
echo "A" > note.txt
echo "B" >> note.txt
echo "C" > note.txt
cat note.txt
# C
```

`C` 한 줄만 남아요. 두 번째 줄까지는 `A`, `B` 두 줄이었지만, 세 번째 줄의 `>`가 파일을 통째로 새로 썼거든요.

### 7-6. history: 명령어 기록

```bash
history       # 실행했던 명령어 목록 (번호와 함께)
!15           # 15번 명령어 다시 실행
!!            # 바로 직전 명령어 다시 실행
```

긴 명령어를 다시 칠 필요가 없어요. `history`로 번호를 찾고 `!번호`로 다시 실행해요.

## 8. 단축키

터미널은 마우스로 커서를 옮길 수 없어서, 단축키를 알면 속도가 확 달라져요.

| 단축키 | 하는 일 |
| --- | --- |
| `Ctrl + u` | 입력 중인 줄 전체 지우기 |
| `Ctrl + w` | 단어 하나씩 지우기 |
| `Ctrl + a` / `Ctrl + e` | 줄 맨 앞 / 맨 끝으로 이동 |
| `Ctrl + c` | 실행 중인 명령 멈추기 |
| `Ctrl + l` | 화면 정리 (`clear`와 같음) |
| `Ctrl + r` | 명령어 기록 검색 |
| `↑` / `↓` | 이전 / 다음 명령어 |
| `Tab` | 파일, 폴더 이름 자동 완성 |

특히 `Tab`은 습관이 되면 좋아요. 이름 앞부분만 치고 `Tab`을 누르면 나머지를 채워 줘서, 오타도 함께 줄어요.

`Ctrl + r`을 누르고 `commit`이라고 치면, 예전에 쳤던 커밋 명령이 바로 떠요.

## 9. Git 설정과 첫 커밋 실습

### 처음 한 번만: 내 이름과 이메일 등록

커밋에는 "누가 만들었는지"가 기록돼요. 그래서 처음 한 번은 내 정보를 알려 줘야 해요.

```bash
git config --global user.name "이름"
git config --global user.email "내 이메일 주소"
git config --global init.defaultBranch main
git config --list      # 설정 확인
```

`--global`은 "이 컴퓨터의 모든 저장소에 적용"이라는 뜻이에요. 세 번째 줄은 새 저장소의 첫 브랜치 이름을 `main`으로 정해요.

### 한 바퀴 돌기

실습 폴더를 만들고 첫 커밋까지 가 볼게요. 출력은 실제로 실행해서 확인한 결과예요(해시는 사람마다 달라요).

```bash
mkdir git-practice && cd git-practice   # 실습 폴더를 만들고 들어가기
git init                                # 저장소 만들기 (.git 폴더 생성)
echo "Hello World" > README.md          # 파일 만들기
git status                              # 상태 확인
```

`&&`는 "앞 명령이 성공하면 뒤 명령을 실행"이라는 뜻이에요. `git status`는 이렇게 알려 줘요.

```txt
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
```

"Untracked"는 Git이 아직 이 파일을 관리하지 않는다는 뜻이에요. 방에 물건만 있고 상자에는 아무것도 안 담긴 상태예요. 이제 상자에 담고 봉해요.

```bash
git add README.md                       # Staging에 올리기
git commit -m "docs: add README"        # 커밋으로 남기기
git log --oneline                       # 커밋 기록 보기
# 361fe59 docs: add README
```

`-m` 뒤의 글자가 커밋 메시지예요. `docs:`처럼 앞에 종류를 붙이면 나중에 이력을 읽기 쉬워요.

### 무엇이 바뀌었는지 보기: diff와 restore

파일을 고친 다음에는 무엇을 바꿨는지 먼저 확인하는 게 좋아요.

```bash
echo "Second line" >> README.md
git diff
# +Second line          <- 아직 add 하지 않은 변경이 보여요
git add README.md
git diff                # 아무것도 안 나와요 (이미 Staging으로 갔으니까)
git diff --staged
# +Second line          <- add 한 변경은 여기서 보여요
```

`git diff`는 작업 폴더와 Staging 사이의 차이, `git diff --staged`는 Staging과 마지막 커밋 사이의 차이예요. add 하고 나서 `git diff`가 텅 비어도 놀라지 마세요.

파일을 고쳤는데 없던 일로 하고 싶으면 `git restore`를 써요.

```bash
git restore README.md   # 아직 add 하지 않은 수정을 버리고 마지막 상태로
```

### 자주 쓰는 명령어 모음

| 명령어 | 하는 일 |
| --- | --- |
| `git status` | 지금 변경 상태 확인 |
| `git diff` | 고쳤지만 아직 add 하지 않은 변경 보기 |
| `git diff --staged` | add 한 변경 보기 |
| `git add .` | 바뀐 파일 전부 Staging에 올리기 |
| `git commit -m "메시지"` | 커밋 만들기 |
| `git log --oneline` | 커밋 기록을 한 줄씩 보기 |
| `git branch` | 브랜치 목록 |
| `git switch -c <이름>` | 새 브랜치를 만들고 이동 |
| `git switch <이름>` | 브랜치 이동 |
| `git merge <이름>` | 그 브랜치를 지금 브랜치에 합치기 |
| `git restore <파일>` | 수정 내용 되돌리기 |

## 10. GitHub에 올리기와 .gitignore

### 원격 저장소와 연결하기

```bash
git clone <URL>                  # 원격 저장소를 통째로 복제해 오기
git remote add origin <URL>      # 지금 저장소에 원격 저장소 연결
git push -u origin main          # 원격으로 올리기 (처음 한 번만 -u)
git pull                         # 원격의 새 변경 받아오기
```

`origin`은 원격 저장소에 붙이는 별명이에요. 주소를 매번 치지 않으려고 이름을 붙여 둬요.

이미 GitHub에 있는 저장소를 가져올 때는 `clone`, 내 컴퓨터에서 먼저 만든 저장소를 올릴 때는 `remote add`를 써요.

`-u`는 "앞으로 이 브랜치는 origin의 main과 짝"이라고 기억시켜요. 처음 한 번 해 두면 다음부터는 `git push`, `git pull`만 쳐도 돼요.

### .gitignore: Git이 못 본 척할 파일

Git이 추적하지 않을 파일을 적어 두는 파일이에요. 저장소 맨 위 폴더에 `.gitignore`라는 이름으로 만들어요.

```txt
node_modules/
.env
*.log
.DS_Store
```

- `node_modules/`: 설치하면 다시 생기는 라이브러리 폴더라 올릴 필요가 없어요.
- `.env`: API 키 같은 **비밀 값**이 들어가는 파일이에요.
- `*.log`: `.log`로 끝나는 모든 파일이에요. `*`는 "아무 글자나"라는 뜻이에요.
- `.DS_Store`: macOS가 폴더마다 몰래 만드는 파일이에요.

<TwistBox title=".env는 한 번 커밋되면 이력에 남아요">

`.env`를 실수로 커밋했다가 지우는 커밋을 또 해도, 앞선 커밋 안에는 여전히 그 키가 남아 있어요. 누구든 이력을 거슬러 올라가 볼 수 있어요.

그래서 저장소를 만들자마자 `.gitignore`부터 만들어요. 이미 올라간 키는 지우는 것으로 끝나지 않고, **키를 새로 발급해서 바꿔야** 안전해요.

</TwistBox>

## 오늘 꼭 기억할 주의점

- `rm`은 휴지통이 없어요. 지우기 전에 `ls`로 대상을 확인해요.
- 커밋 메시지에는 **왜 바꿨는지**가 드러나게 써요. `feat:`(기능 추가), `fix:`(버그 수정), `docs:`(문서) 같은 머리말을 붙이면 좋아요.
- `git status`를 습관처럼 자주 쳐요. 지금 무엇이 어느 영역에 있는지 알려 줘요.
- 이미 push한 커밋은 `reset --hard`나 `push --force`로 함부로 고치지 않아요. 공유된 이력은 `revert`로 고쳐요.
