DB를 쓰려면 PostgreSQL 서버가 있어야 해요. 내 컴퓨터에 직접 설치하는 대신 Docker 컨테이너로 띄우면, 설치 과정 없이 명령 한 줄로 켜고 다 쓰면 지울 수 있어요.

그런데 컨테이너를 지우면 그 안의 데이터도 같이 사라져요. DB는 데이터를 오래 담아 두려고 쓰는 건데, 지울 때마다 사라지면 곤란해요. 그래서 오늘은 **볼륨부터 정하고**, 처음부터 볼륨을 붙여서 띄워요.

어제 교안으로 훑은 볼륨과 Compose를 오늘은 직접 손으로 해 봤어요. 실제로 만난 오류까지 같이 정리해요. 레슨 끝에 확인 퀴즈가 있고, 문항을 모두 풀면 [수업 복습](/class) 목록에 완료로 표시돼요.

## 2. 볼륨은 컨테이너 밖에 있는 보관함이다

볼륨은 컨테이너 밖에 있는 보관함이에요. 컨테이너를 지워도 볼륨은 남아요. 어제 배운 "남길 파일은 컨테이너 밖에 둔다"가 오늘 DB에 그대로 쓰여요.

```bash
docker volume ls                # 볼륨 목록
docker volume create [볼륨명]   # 볼륨 만들기
docker volume inspect [볼륨명]  # 볼륨 정보 보기

# 볼륨 지우기
docker volume rm [볼륨명]       # 이름으로 하나(또는 여러 개) 지우기
docker volume prune             # 안 쓰는 익명 볼륨 모두 지우기 (y/N 확인)
docker volume prune -a          # 안 쓰는 볼륨을 이름 있는 것까지 모두 지우기
```

</Hint>

### 볼륨은 왜 붙이지? (셀프 체크: 볼륨이 왜 필요한데?)

컨테이너를 지우면 그 안의 `/var/lib/postgresql`(데이터가 실제로 저장되는 폴더)도 같이 지워져요. 이 폴더를 컨테이너 밖의 볼륨 `pg-data`에 연결해 두면, 컨테이너를 지우고 **같은 `-v`로 다시 만들어도** 표와 데이터가 그대로 남아요.

DB는 데이터를 오래 담아 두려고 쓰는 거예요. 컨테이너는 쉽게 지우고 다시 만드는 물건이고요. 둘의 수명이 다르니까, 오래 남을 것(데이터)은 오래 남는 곳(볼륨)에 둬요.

### docker volume ls에 긴 ID 이름의 볼륨은 왜 생겼지?

`-v` 없이 DB 컨테이너를 켜면 Docker가 **이름 없는 볼륨**(익명 볼륨)을 자동으로 만들어요. 컨테이너를 지워도 남기 때문에, 여러 번 만들고 지운 만큼 쌓여요.

남길 데이터라면 처음부터 이름을 붙이는 게 좋아요. 쌓인 익명 볼륨은 9절의 `docker volume prune`으로 치워요.

### 볼륨을 붙인 채 비밀번호를 바꿔 다시 만들면?

바뀌지 않아요. `-e POSTGRES_PASSWORD`는 **데이터가 비어 있을 때 처음 한 번만** 읽어요. 이미 데이터가 든 볼륨을 붙이면 처음 정한 비밀번호가 그대로예요.

## 3. docker run 한 줄에 다섯 가지를 적는다

볼륨을 붙여 PostgreSQL 컨테이너를 띄워요. 옵션이 길어서 여러 줄로 나눠 써요.

```bash
docker run -d --name my-pg \
  -e POSTGRES_PASSWORD=admin \
  -p 5432:5432 \
  -v pg-data:/var/lib/postgresql \
  postgres:18
```

<Figure>
  <FanOut
    call="docker run ... postgres:18"
    tone="blue"

      { title: "뒤에서 켜기", result: "-d", why: "터미널을 붙잡지 않아요" },

      { title: "환경 변수", result: "-e", why: "`POSTGRES_PASSWORD=admin`" },
      { title: "포트 잇기", result: "-p", why: "내 PC `5432`를 컨테이너 `5432`로" },
      { title: "볼륨 잇기", result: "-v", why: "볼륨 `pg-data`를 데이터 폴더에" },
      { title: "이미지 (맨 끝)", result: "postgres:18", why: "빠지면 안 돼요" },
    ]}
  />
</Figure>

- `-v pg-data:/var/lib/postgresql`은 컨테이너 안에서 데이터가 저장되는 폴더를 볼륨 `pg-data`에 연결해요. **`postgres:18`부터는** 이 자리가 `/var/lib/postgresql`이에요.
- 줄 끝의 `\`는 "명령이 다음 줄로 이어진다"는 표시예요. 옵션이 길어지면 이렇게 나눠 써야 읽기 쉬워요.
- 맨 끝의 `postgres:18`은 어떤 이미지로 만들지 정하는 자리라 빠지면 안 돼요. 옵션을 다 쓰고 **마지막에** 와요.

켜졌는지는 `docker ps`로, 꺼진 것까지 보려면 `docker ps -a`로 확인해요.

```bash
docker ps      # 켜진 컨테이너
docker ps -a   # 꺼진 것까지 전부
```

## 4. SQL 파일 하나가 언제든 같은 상태를 다시 만든다

`pg_lab` 폴더에 `my_shop.sql`을 만들어요. DB를 만들고, 그 DB로 옮겨 가고, 표를 만들고, 상품 다섯 개를 넣어요.

```sql
-- 1. 데이터베이스 생성
DROP DATABASE IF EXISTS my_shop;

CREATE DATABASE my_shop;

-- 2. 새로 만든 데이터베이스에 접속(특정 DB를 사용하겠다.)
\c my_shop

-- 3. 상품 테이블 생성
CREATE TABLE product
(
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price INT NOT NULL,
    stock INT NOT NULL
);

-- 4. 상품 초기 데이터 입력
INSERT INTO product (name, price, stock) VALUES
('무선 이어폰', 35000, 100),
('게이밍 마우스', 28000, 85),
('27인치 모니터', 259000, 15),
('USB-C 허브', 19900, 200),
('노트북 거치대', 24000, 7);
```

이 파일이 만드는 표는 이렇게 생겼어요.

| 열 | 타입 | 제약 | 뜻 |
| --- | --- | --- | --- |
| `id` | `SERIAL` | `PRIMARY KEY` | 자동으로 1, 2, 3... 붙는 번호 |
| `name` | `VARCHAR(100)` | `NOT NULL` | 상품명 (100자까지) |
| `price` | `INT` | `NOT NULL` | 가격 |
| `stock` | `INT` | `NOT NULL` | 재고 |

파일의 네 덩어리는 차례로 이어져요. 맨 앞이 "지우고 시작"이라, 몇 번을 실행해도 끝 상태가 같아요.

<Figure>
  <Seq
    tone="rust"
    steps={[
      { title: "DROP DATABASE IF EXISTS my_shop", body: "있으면 지우고, 없으면 건너뛰어요. 늘 깨끗한 자리에서 시작해요." },
      { title: "CREATE DATABASE my_shop", body: "빈 DB를 새로 만들어요." },
      { title: "\\c my_shop", body: "만든 DB로 옮겨 가요. 이 뒤의 문장은 모두 `my_shop` 안에서 실행돼요." },
      { title: "CREATE TABLE, INSERT", body: "표를 만들고 상품 다섯 개를 넣어요. `id`는 적지 않아요." },
    ]}
  />
</Figure>

- 맨 위에서 `DROP DATABASE IF EXISTS`로 지우고 시작하는 이유는, 이 파일을 **몇 번을 실행해도 늘 같은 깨끗한 상태**로 만들기 위해서예요. DB가 없으면 지울 것도 없으니 건너뛰어요.
- `\c`는 SQL이 아니라 **psql 프로그램의 명령**이에요. 그래서 끝에 `;`가 없고, 이 파일은 psql로 실행해야 해요.
- `id`를 `SERIAL`로 만들었기 때문에 `INSERT`할 때 `id`는 적지 않아요. 번호는 DB가 알아서 붙여요.

## 5. 파일을 넣는 길은 두 가지: 복사해 두거나, 흘려 보내거나

`my_shop.sql`은 내 컴퓨터에 있고, `psql`은 컨테이너 안에 있어요. 파일을 psql에게 건네는 방법이 두 가지예요.

```bash
# 방법 1: 파일을 컨테이너 안으로 복사해 두고 실행
docker cp my_shop.sql my-pg:/tmp/my_shop.sql
docker exec -it my-pg psql -U postgres -f //tmp/my_shop.sql

# 방법 2: 내 폴더의 파일을 입력으로 흘려 보내기
docker exec -i my-pg psql -U postgres < my_shop.sql
```

      { title: "방법 2: <", note: "복사가 필요 없음", tone: "ok", lines: ["내 터미널이 파일을 읽어 psql의 입력으로 흘려 보내요", "경로 문제도 없어서 더 간단해요"] },
    ]}

</Hint>

처음 실행하면 문장마다 결과가 한 줄씩 나와요. 첫 줄의 `NOTICE`는 오류가 아니라 "지울 DB가 없어서 건너뛴다"는 안내예요. `INSERT 0 5`는 5행이 들어갔다는 뜻이에요.

```text
psql:my_shop.sql:2: NOTICE:  database "my_shop" does not exist, skipping
DROP DATABASE
CREATE DATABASE
You are now connected to database "my_shop" as user "postgres".
CREATE TABLE
INSERT 0 5
```

### 파일을 넘길 때는 왜 -it가 아니라 -i만 쓰지?

`-i`는 내 쪽 입력을 컨테이너로 보내고, `-t`는 터미널 화면을 붙여요. 사람이 직접 타이핑할 때는 둘 다 필요해요.

하지만 파일을 흘려 보낼 때는 입력이 키보드가 아니라 파일이에요. 화면을 붙이라는 `-t`와 맞지 않아 오류가 나요. 그래서 `-i`만 써요.

## 6. -d로 DB를 골라 들어가고, -c로 한 줄만 묻는다

`psql -U postgres`로 그냥 들어가면 기본 DB인 `postgres`에 들어가요. 오늘 만든 건 `my_shop`이니까 골라서 들어가요.

```bash
docker exec -it my-pg psql -U postgres -d my_shop
docker exec -it my-pg psql -U postgres -d my_shop -c "SELECT * FROM product"
```

## 7. Git Bash는 /로 시작하는 말을 Windows 경로로 바꿔 버린다

방법 1을 처음 쳤을 때 이런 오류가 났어요.

```text
psql: error: C:/Users/.../Temp/my_shop.sql: No such file or directory
```

분명 `/tmp/my_shop.sql`이라고 썼는데 `C:/Users/.../Temp/...`를 못 찾는다고 해요. Git Bash(UCRT64)는 `/`로 시작하는 인자를 **Windows 경로로 바꿔서** 넘겨요. 그래서 컨테이너 안의 `/tmp`가 Windows 임시 폴더 경로로 바뀌어 버렸어요.

<Figure>
  <Boxes

```bash
echo 'export MSYS_NO_PATHCONV=1' >> ~/.bashrc
echo 'export MSYS2_ARG_CONV_EXCL="*"' >> ~/.bashrc
source ~/.bashrc
```

## 8. 번호는 겹치지 않을 뿐, 빈틈이 없다는 약속은 없다

### NOT NULL인 열을 비우면?

거절돼요. `stock`을 빼고 넣어 봤더니 이런 오류가 났어요. 꼭 있어야 하는 값을 DB가 대신 지켜 주는 장치예요.

```text
ERROR:  null value in column "stock" of relation "product" violates not-null constraint
DETAIL:  Failing row contains (6, 키보드, 45000, null).
```

### SERIAL 번호는 항상 1씩 빈틈없이 늘까?

아니에요. DETAIL 줄을 보면 실패한 행이 이미 `6`번을 받았어요. **실패한 `INSERT`도 번호를 하나 써 버려요.** 그래서 그다음에 제대로 넣은 행은 6이 아니라 **7번**을 받아요.

<Figure>

</Figure>

번호는 "겹치지 않는 것"만 보장되고 "빈틈 없음"은 보장되지 않아요. 아래에서 직접 눌러 보세요. 파일을 다시 실행하면 DB를 통째로 지우고 만들어서 번호도 1부터 다시 시작해요.

<SerialSimulator />

<Hint>

해 볼 것: 파일 실행, stock 빠짐 두 번, stock 30 한 번, SELECT 순서로 눌러 보세요. 6, 7번이 비고 키보드는 8번이에요. 그다음 파일을 다시 실행하면 번호가 1~5로 돌아와요.

</Hint>

`PRIMARY KEY`라 번호가 겹치는 것도 막혀요. 이미 있는 `id` 1을 직접 적어 넣으면 `duplicate key value violates unique constraint "product_pkey"`로 거절돼요.

## 9. 볼륨 지우기: 쓰는 컨테이너부터 치워야 한다

순서가 중요해요. 볼륨을 쓰는 컨테이너가 남아 있으면(**꺼져 있어도**) 볼륨을 지울 수 없어요. 그래서 컨테이너를 먼저 지우고 볼륨을 지워요.

```bash
docker rm -f my-pg          # 1. 볼륨을 쓰는 컨테이너부터 지우기
docker volume rm pg-data    # 2. 그다음 볼륨 지우기
docker volume ls            # 3. 지워졌는지 확인
```

      { title: "docker volume rm pg-data", body: "이제 아무도 안 쓰니 지워져요." },
      { title: "docker volume ls", body: "목록에서 사라졌는지 확인해요." },

지우는 명령마다 지우는 범위가 달라요.

| 명령 | 지우는 것 |
| --- | --- |
| `docker volume rm 이름` | 이름을 적은 볼륨 |
| `docker volume prune` | 아무 컨테이너도 안 쓰는 **익명** 볼륨만 (긴 ID 이름들) |
| `docker volume prune -a` | 아무 컨테이너도 안 쓰는 볼륨 전부 (이름 있는 것 포함) |
| `docker compose down -v` | compose 파일에 선언한 볼륨과 익명 볼륨. `external`로 선언한 볼륨은 지우지 않음 |

<Note title="prune은 되돌릴 수 없어요">

`prune`은 실행하면 "정말 계속할까요? `[y/N]`"를 물어봐요. 오전에 쌓인 긴 ID 이름의 익명 볼륨은 `docker volume prune` 한 번으로 치울 수 있어요. 지운 볼륨 안의 데이터는 **되돌릴 수 없어요**.

</Note>

## 11. 오후: 긴 docker run을 compose.yaml 한 장으로 옮긴다

오전에 친 `docker run` 명령은 옵션이 다섯 개나 붙어서 길어요. 매번 이걸 치면 번거롭고, 하나만 빠뜨려도 다르게 만들어져요.

그래서 같은 내용을 `compose.yaml` 파일에 적어 두고, `docker compose up -d` 한 줄로 켜고 `down`으로 꺼요. 명령을 외우는 대신 파일을 읽으면 **어떻게 띄웠는지 바로 보여요**. 어제 배운 Compose가 여기서 쓰여요.

`docker run`의 옵션 하나하나가 `compose.yaml`의 한 자리로 옮겨져요.

| `docker run` | `compose.yaml` | 이번 값 |
| --- | --- | --- |
| 이미지 (맨 끝) | `image:` | `postgres:18` |
| `--name` | `container_name:` | `shop-pg` |
| `-e` | `environment:` | `POSTGRES_PASSWORD: admin` |
| `-p` | `ports:` | `"5433:5432"` |
| `-v` | `volumes:` (서비스 안) | `pg-data:/var/lib/postgresql` |
| (없음) | `volumes:` (맨 바깥) | 쓸 볼륨을 선언. `external: true` |

```yaml
services:                 # 실행할 컨테이너(서비스) 목록, 필수
  db:                     # 예: db, web (직접 정하는 이름)
    image: postgres:18          # 사용할 이미지
    container_name: shop-pg     # 컨테이너 이름 (생략 시 자동 생성)
    environment:
      POSTGRES_PASSWORD: admin  # 환경 변수 (-e)
    ports:                      # 포트 연결 (-p), 문자열로 감싸는 것을 권장
      - "5433:5432"
    volumes:                    # 볼륨 연결 (-v)
      - pg-data:/var/lib/postgresql

volumes:                  # 사용할 볼륨 선언 (최상위)
  pg-data:
    external: true
```

```bash
docker compose up -d     # compose.yaml대로 켜기 (뒤에서)
docker compose ps        # 이 폴더의 compose 컨테이너 보기
docker compose down      # 끄고 컨테이너 지우기

docker exec -it shop-pg psql -U postgres -d my_shop -c "SELECT * FROM product"
```

## 12. Compose에서 헷갈린 다섯 가지

### 서비스 이름 db와 container_name의 shop-pg는 뭐가 다르지?

`db`는 compose 파일 안에서 이 서비스를 부르는 이름이고, `shop-pg`는 `docker ps`에 보이는 실제 컨테이너 이름이에요.

`container_name`을 안 쓰면 compose가 `폴더이름-서비스이름-번호`로 이름을 붙여요. 어제 본 `cafe-web-1`이 그거예요. 이름을 정해 뒀기 때문에 `docker exec -it shop-pg ...`처럼 바로 부를 수 있어요.

### 포트를 왜 5432:5432가 아니라 5433:5432로 했지?

`:` 앞은 내 컴퓨터의 문, 뒤는 컨테이너 안의 문이에요. 내 컴퓨터의 5432번은 오전에 띄운 `my-pg`가 이미 쓰고 있어서, 같은 번호로 열면 `port is already allocated`로 겹쳐요. 그래서 **바깥 문만** 5433으로 바꿨어요.

컨테이너 안의 PostgreSQL은 그대로 5432에서 기다려요. `docker exec`로 안에서 들어갈 때는 바깥 포트와 상관없어요.

### 맨 아래 external: true는 뭘 하지?

"이 볼륨은 이미 밖에 있으니 그걸 그대로 써라"는 뜻이에요. Docker 문서에 따르면 이때 compose는 볼륨을 새로 만들지 않고, **없으면 에러를 내요**.

`external`이 없으면 compose는 `프로젝트이름_pg-data`처럼 앞에 이름을 붙인 **새 볼륨**을 만들어요. 그러면 오전에 `docker run -v pg-data:...`로 만든 볼륨과 다른 보관함이 돼요.

### docker compose down을 하면 데이터도 지워질까?

`down`은 컨테이너를 끄고 지우지만 **볼륨은 남겨요**. 데이터는 볼륨에 있으니 다시 `up -d`하면 그대로예요. 볼륨까지 지우는 건 `down -v`예요.

단, Docker 문서에 따르면 `external`로 선언한 볼륨은 `down -v`로도 지워지지 않아요. 이번 `pg-data`는 `external: true`라서, 지우려면 `docker volume rm pg-data`로 직접 지워야 해요(9절).

**들여쓰기가 곧 구조**예요. 같은 단계의 키는 같은 칸에 맞추고, 한 단계 들어갈 때마다 더 들여 써요.

## 오늘 꼭 기억할 주의점

- **볼륨부터 정하고 띄워요.** `-v` 없이 켠 DB는 컨테이너와 함께 데이터가 사라지고, 긴 ID의 익명 볼륨만 쌓여요.
- **비밀번호(`-e POSTGRES_PASSWORD`)는 빈 볼륨일 때 한 번만 읽혀요.** 데이터가 든 볼륨을 붙이면 처음 비밀번호 그대로예요.
- 이미지 이름은 `docker run`의 **맨 끝**이에요. 줄을 나눌 때는 줄 끝에 `\`.
- SQL 파일 맨 앞의 `DROP DATABASE IF EXISTS` 덕분에 몇 번을 실행해도 같은 상태가 돼요. `\c`는 psql 명령이라 `;`가 없어요.
- `-f` 뒤 경로는 **컨테이너 안** 기준이라 `docker cp`가 먼저예요. `<`로 흘려 보낼 때는 `-it`가 아니라 **`-i`만**.
- Git Bash에서 `/tmp`가 `C:/Users/...`로 바뀌면 `//tmp`를 쓰거나 `~/.bashrc`에 `MSYS_NO_PATHCONV=1`을 넣어요.
- `SERIAL` 번호는 겹치지 않을 뿐 빈틈은 생겨요. 실패한 `INSERT`도 번호를 써요.
- 볼륨은 **쓰는 컨테이너를 지운 뒤에** 지워져요. `prune`으로 지운 데이터는 되돌릴 수 없어요.
- Compose에서 `external: true`면 기존 볼륨을 그대로 쓰고, `down -v`로도 지워지지 않아요.
- 에러는 맨 앞 단어(`bash:`, `docker:`, `psql:`)로 어디서 멈췄는지부터 봐요.
