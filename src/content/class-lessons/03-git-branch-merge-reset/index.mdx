## 1. 명령 이어 치기: &&는 앞이 잘 돼야 넘어간다

add와 commit을 매번 두 줄로 치기 번거롭다면 한 줄로 이을 수 있어요.

```bash
git add . && git commit -m "docs: README.md 추가"
# [main (root-commit) 3989fcb] docs: README.md 추가
#  1 file changed, 1 insertion(+)
```

이을 때 쓰는 기호에 따라 뜻이 달라요.

| 기호 | 뜻 |
| --- | --- |
| `&&` | 앞 명령이 **성공했을 때만** 뒤 명령을 실행. 실패하면 거기서 멈춤 |
| `;` | 앞 명령이 성공하든 실패하든 뒤 명령도 실행 |
| `&` | 하나만 쓰면 전혀 다른 뜻. 앞 명령을 뒤에서(백그라운드로) 돌려 놓고 바로 넘어감 |

커밋할 게 없는 상태에서 직접 비교해 봤어요.

```bash
git commit -m "again" && echo "뒤 명령"
# nothing to commit, working tree clean     <- 실패해서 echo는 실행 안 됨

git commit -m "again" ; echo "뒤 명령 실행됨"
# nothing to commit, working tree clean
# 뒤 명령 실행됨                             <- 실패해도 실행됨
```

`&&`는 "앞이 잘 됐으면 그다음"이라서 안전해요. add가 실패했는데 commit이 엉뚱하게 돌아가는 일을 막아 줘요.

## 2. .gitignore: Git이 못 본 척할 목록

1회차에서 본 `.gitignore`는 **Git이 못 본 척할 파일 목록**이에요. 프로젝트 맨 위 폴더에 둬요. 쓰는 이유는 세 가지예요.

- **비밀 정보 보호**: `.env`, API 키
- **쓸데없는 용량 빼기**: `node_modules/`, 빌드 결과물
- **내 컴퓨터에만 있는 파일 빼기**: 로그, `.DS_Store`, 편집기(IDE) 설정

### 쓰는 법

```text
# 주석은 # 로 시작하는 한 줄
Logs/
node_modules/
.env
*.log
# ! 로 시작하면 예외: 위에서 뺀 것 중 이건 다시 추적
!important.log
```

- `Logs/`처럼 끝에 `/`를 붙이면 그 폴더 전체예요.
- `*.log`는 `.log`로 끝나는 모든 파일이에요.
- `!important.log`는 "`*.log`로 뺐지만, 이 파일만은 추적해"라는 **예외**예요.

`Logs/a.txt`, `app.log`, `important.log`, `.env`를 만들어 두고 상태를 보면 예외 하나만 살아남아요.

```bash
git status --short
# ?? .gitignore
# ?? important.log     <- 예외라서 보여요. 나머지는 전부 숨었어요
```

<TwistBox title="예외 줄 끝에 주석을 달면 예외가 꺼져요">

`.gitignore`의 주석은 **줄 맨 앞의 `#`만** 주석으로 쳐요. 줄 중간의 `#`은 그냥 글자예요.

그래서 이렇게 쓰면 예외가 먹히지 않아요. 직접 돌려 봤어요.

```bash
# .gitignore 내용
# *.log
# !important.log   # 예외 처리

git status --short
# ?? .gitignore          <- important.log가 안 보여요
```

Git은 두 번째 줄을 "`important.log   # 예외 처리`라는 이름의 파일"로 읽어요. 그런 파일은 없으니 예외가 없는 셈이에요. 주석은 꼭 **따로 한 줄에** 써요.

</TwistBox>

### 관리하는 법

- 프로젝트를 시작할 때 **가장 먼저** 만들어 두고, 뺄 게 새로 생기면 한 줄씩 더해요.
- `.gitignore` 파일 자체는 커밋해서 팀과 같이 써요. 그래야 모두 같은 파일을 빼요.

### 이미 추적 중인 파일은 계속 추적돼요

`.gitignore`는 **아직 추적하지 않는 파일**에만 통해요. 이미 커밋한 파일은 나중에 목록에 넣어도 계속 추적돼요.

```bash
echo config.json >> .gitignore    # 목록에 넣고
echo v2 > config.json             # 파일을 고쳐 보면
git status --short
#  M .gitignore
#  M config.json                  <- 여전히 수정으로 잡혀요
```

추적을 끊으려면 `git rm --cached`를 써요. `--cached`는 "Staging(index)에서만 빼고, 내 폴더의 파일은 그대로 둬"라는 뜻이에요.

```bash
git rm --cached config.json
# rm 'config.json'
git status --short
#  M .gitignore
# D  config.json      <- 저장소에서 빠질 예정(파일은 폴더에 그대로 있어요)
```

이걸 커밋하면 그다음부터 `config.json`은 Git이 못 본 척해요.

<Note title="비밀키는 처음부터 빼요">

이미 커밋된 비밀키는 파일을 지워도 **이력에 남아요.** 1회차에서 본 것처럼, 지우는 커밋을 또 해도 앞 커밋 안에는 키가 그대로예요.

그래서 `.env` 같은 파일은 첫 커밋 전에 `.gitignore`에 넣어 둬요. 이미 올라갔다면 키를 새로 발급해 바꿔야 안전해요.

</Note>

## 3. 커밋 메시지: 맨 앞 타입이 이름표다

커밋 메시지는 `타입: 제목` 꼴로 써요. 맨 앞 타입만 봐도 "이 커밋이 무슨 종류의 일인지" 알 수 있게요.

| 타입 | 뜻 |
| --- | --- |
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 모양(띄어쓰기, 세미콜론 등). 동작은 그대로 |
| `refactor` | 동작은 같고 코드 구조만 더 좋게 |
| `test` | 테스트 코드 추가나 수정 |
| `chore` | 빌드, 설정 같은 기타 작업 |
| `rename` | 파일이나 폴더 이름 바꾸기 |
| `remove` | 파일 삭제 |

예를 들면 `docs: README.md 추가`, `feat: .gitignore 파일 생성`이에요. 어제 만든 commit-msg 훅이 바로 이 형식을 검사하는 훅이었어요.

헷갈리기 쉬운 짝은 `style`과 `refactor`예요. 둘 다 동작은 안 바뀌어요. 겉모양만 다듬으면 `style`, 코드 짜임새를 바꾸면 `refactor`예요.

팀마다 타입 구성이 조금씩 달라요. 새 프로젝트에 들어가면 그 팀의 규칙부터 확인해요.

## 4. git clone: 이력까지 통째로 복사해 온다

GitHub에 이미 있는 저장소를 내 컴퓨터로 가져올 때 써요.

```bash
git clone https://github.com/my-id/my-project.git
git clone https://github.com/my-id/my-project.git my-folder   # 폴더 이름을 정해서
```

- 파일만이 아니라 **커밋 이력까지** 통째로 복제해요.
- 저장소 이름으로 폴더가 생겨요. 뒤에 이름을 주면 그 이름으로 만들어요.
- `origin`이 **자동으로** 연결돼요. 어제처럼 `git remote add`를 따로 칠 필요가 없어요.

```bash
git clone <URL> c1
# Cloning into 'c1'...
# done.
cd c1
git remote -v
# origin  <URL> (fetch)
# origin  <URL> (push)
```

어제 배운 것과 정리하면 이래요. 이미 GitHub에 있으면 `clone`, 내 컴퓨터에서 먼저 만들었으면 `remote add`예요.

## 5. git log 읽기: 내 main과 원격 main은 따로 움직인다

clone한 저장소에서 커밋을 하나 더 하고 log를 보면 이렇게 나와요.

```bash
git log --oneline
# fe2a9e6 (HEAD -> main) docs: Logs 폴더 제외
# f99921f (origin/main) feat: .gitignore 파일 생성
# 4bb7219 docs: README.md 추가
```

맨 앞 7자리는 **커밋 해시(ID)를 줄인 것**이에요. 커밋마다 붙는 고유 번호예요. 괄호 안은 그 커밋을 가리키는 책갈피예요.

`HEAD -> main`이 `origin/main`보다 한 줄 위에 있죠. **내 main이 원격보다 커밋 하나 앞서 있다**는 뜻이에요. 그러니 `git push`를 해야 해요. `git status`도 같은 말을 해 줘요.

```bash
git status
# On branch main
# Your branch is ahead of 'origin/main' by 1 commit.
#   (use "git push" to publish your local commits)
```

<Hint>

터미널 기본 색으로 보면 로컬 `main`은 초록색, 원격 `origin/main`은 빨간색으로 보여요. 색만 봐도 어느 쪽인지 알 수 있어요.

</Hint>

## 6. git reset: 세 옵션은 지우는 범위가 다르다

1회차에서 reset은 "시간을 되감기"라고 배웠어요. 오늘은 세 옵션이 **어디까지 되감는지**를 다시 정리했어요. 되감을 지점은 해시로 정해도 되고, 상대 위치로 정해도 돼요.

```bash
git reset --soft 7ac7366     # 해시로 지점을 정해도 되고
git reset --soft HEAD~1      # 상대 위치로 정해도 돼요
```

세 옵션 모두 HEAD(커밋)는 옮겨요. 차이는 **그 뒤로 얼마나 더 지우느냐**예요. 오른쪽으로 갈수록 많이 지워요.

<Figure label="마지막 커밋을 취소했을 때 README.md의 변경은 어디에 남나">
  <Boxes
    row={[

      { title: "--hard", tone: "red", lines: ["HEAD(커밋): 옮김", "Staging: 비움", "작업 폴더: **비움**, 고친 내용이 사라짐", "결과: 아무것도 없음"] },
    ]}
  />
</Figure>

마지막 커밋 하나를 세 방식으로 각각 취소하고 상태를 봤어요.

```bash
git reset --soft HEAD~1
git status --short
# M  README.md          <- M이 왼쪽 칸: 변경이 Staging에 남아 있어요

git reset HEAD~1        # 옵션 없음 = --mixed
# Unstaged changes after reset:
# M	README.md
git status --short
#  M README.md          <- M이 오른쪽 칸: Staging에서는 빠지고 폴더에만 남았어요

git reset --hard HEAD~1
# HEAD is now at 8760dde docs: 두 번째 줄
git status --short
#                       <- 아무것도 없어요. 고친 내용까지 사라졌어요
```

어제 배운 `git status --short`의 왼쪽 칸, 오른쪽 칸 읽기가 여기서 쓰여요.

- `--soft`: 커밋만 취소하고, 메시지를 고쳐 **다시 커밋하고 싶을 때** 써요.
- `--hard`: 작업한 내용까지 **버릴 때** 써요. 정말 조심해요.

<Note title="이미 push한 커밋은 reset 말고 revert">

이미 push해서 팀원이 가져간 커밋은 reset 대신 **`git revert`로** 고쳐요. 1회차에서 본 "찢지 말고 정정 일기를 새로 쓰기"예요.

</Note>

## 7. git reflog: HEAD의 발자국 일지

`reset --hard`로 커밋을 날렸다고 끝이 아니에요. Git은 **HEAD가 움직일 때마다** 따로 일지를 써 둬요. 그게 `reflog`예요.

커밋, reset, checkout처럼 HEAD를 옮긴 일이 전부 남아요. 이 일지는 **내 컴퓨터에만** 있고, push해도 올라가지 않아요.

### 실제로 살려 봤어요

"중요한 내용"을 커밋한 뒤, 실수로 `reset --hard`를 했어요.

```bash
git log --oneline -2
# c3224e8 (HEAD -> main) docs: 중요한 내용 추가
# fe2a9e6 docs: Logs 폴더 제외

git reset --hard HEAD~1
# HEAD is now at fe2a9e6 docs: Logs 폴더 제외   <- 커밋이 사라졌어요
```

이제 reflog를 봐요.

```bash
git reflog
# fe2a9e6 HEAD@{0}: reset: moving to HEAD~1
# c3224e8 HEAD@{1}: commit: docs: 중요한 내용 추가
# fe2a9e6 HEAD@{2}: commit: docs: Logs 폴더 제외
# f99921f HEAD@{3}: commit: feat: .gitignore 파일 생성
# 4bb7219 HEAD@{4}: commit (initial): docs: README.md 추가
```

`HEAD@{0}`이 지금, `HEAD@{1}`이 한 단계 전이에요. 한 단계 전에 "중요한 내용" 커밋(`c3224e8`)이 보이죠. 그리로 다시 reset하면 돼요.

```bash
git reset --hard HEAD@{1}      # 또는 git reset --hard c3224e8
# HEAD is now at c3224e8 docs: 중요한 내용 추가
```

어제 detached HEAD에서 길 잃은 커밋도 같은 방법으로 찾을 수 있어요. reflog에는 그 해시도 남아 있거든요.

<Note title="커밋하지 않은 건 못 살려요">

reflog는 **커밋**의 기록이에요. 커밋한 적 없는 변경은 일지에 없어서 되살릴 수 없어요.

```bash
echo "저장 안 한 작업" >> README.md
git reset --hard
tail -1 README.md
# 중요한 내용          <- "저장 안 한 작업"은 사라졌고, 되찾을 방법이 없어요
```

그래서 `reset --hard` 전에는 꼭 `git status`로 아직 커밋하지 않은 변경이 없는지 봐요. 아깝다면 커밋하거나, 아래에서 배울 stash로 맡겨 두고 해요.

</Note>

## 8. 브랜치: 책갈피를 하나 더 꽂는다

1회차에서 브랜치는 **특정 커밋을 가리키는 움직이는 책갈피**(포인터)라고 했어요. 책갈피를 하나 더 꽂으면 독립된 작업 줄기가 생겨요. 따로 빼서 일하는 이유는 이래요.

- main을 **늘 안정된 상태로** 지킬 수 있어요.
- 기능마다 브랜치를 나눠 **여럿이 동시에** 일할 수 있어요.
- 기능 단위로 리뷰(PR)를 받고 합치기 쉬워요.
- 실험하다 망해도 **브랜치를 버리면 그만**이에요.

### 만들기만 할까, 만들고 옮겨 갈까

```bash
git branch feature/login        # 만들기만 (이동은 안 함)
git branch                      # 목록 보기
#   feature/login
# * main                        <- 별표가 지금 있는 곳. 아직 main이에요

git checkout -b feature/signup  # 만들고 바로 이동
# Switched to a new branch 'feature/signup'
git branch
#   feature/login
# * feature/signup
#   main
```

`git branch 이름`은 책갈피만 꽂고 그 자리에 그대로 있어요. `git checkout -b`는 꽂고 바로 그 책갈피로 넘어가요. 1회차에서 본 `git switch -c`와 같은 일이에요.

## 9. git stash: 하던 작업을 서랍에 맡긴다

작업하다가 **급하게 다른 브랜치로 가야 하는데**, 아직 커밋하기엔 애매할 때가 있어요. 그대로 옮기려 하면 Git이 막을 수 있어요.

```bash
git checkout feature/login
# error: Your local changes to the following files would be overwritten by checkout:
# 	README.md
# Please commit your changes or stash them before you switch branches.
# Aborting
```

"커밋하거나 stash해라"라고 Git이 직접 알려 주죠. stash는 **아직 커밋하지 않은 변경을 서랍에 잠깐 넣어 두고, 작업 폴더를 깨끗하게** 만들어 줘요. 옷 가게 탈의실 앞에 짐을 잠깐 맡기는 것과 같아요.

<Figure>
  <Boxes
    row={[
      { title: "작업 폴더", tone: "blue", lines: ["`README.md`를 고치는 중", "이대로는 `checkout`이 막혀요"] },
      { arrow: "`git stash`" },
      { title: "서랍 (stash)", tone: "amber", lines: ["`stash@{0}`", "WIP on main: b695196 B"] },
    ]}
    below={[{ title: "깨끗해진 작업 폴더", tone: "ok", lines: ["이제 `git checkout feature/login`이 돼요", "돌아와서 `git stash pop`으로 꺼내 다시 적용해요"] }]}
  />
</Figure>

```bash
git stash
# Saved working directory and index state WIP on main: b695196 B
git checkout feature/login
# Switched to branch 'feature/login'     <- 이제 옮겨져요
```

### 서랍 보기, 꺼내기

```bash
git stash list
# stash@{0}: WIP on main: b695196 B
```

| 명령어 | 하는 일 |
| --- | --- |
| `git stash` | 변경을 서랍에 넣기 |
| `git stash list` | 서랍 목록 보기 |
| `git stash pop` | 꺼내서 적용하고, **서랍에서 지우기** |
| `git stash apply` | 꺼내서 적용하되, **서랍에 그대로 두기** |
| `git stash -u` | 새로 만든(untracked) 파일까지 함께 넣기 |

`pop`과 `apply`는 둘 다 꺼내서 적용해요. 차이는 꺼낸 뒤 목록에 남느냐예요.

```bash
git stash apply
git stash list
# stash@{0}: WIP on main: b695196 B         <- apply는 그대로 남아요

git stash pop
# Dropped refs/stash@{0} (29f0fdf...)
git stash list
#                                            <- pop은 지워져서 아무것도 없어요
```

<Note title="새 파일은 기본으로 서랍에 안 들어가요">

`git stash`만 치면 **Git이 이미 추적하는 파일의 변경만** 들어가요. 새로 만든 파일은 그대로 남아요.

```bash
git status --short
#  M README.md
# ?? new.txt

git stash
git status --short
# ?? new.txt          <- 새 파일은 서랍에 안 들어갔어요

git stash pop
git stash -u          # 이번엔 -u 를 붙여서
git status --short
#                     <- 새 파일까지 모두 들어갔어요
```

</Note>

## 10. git merge: 받는 쪽에 서서 끌어온다

merge는 "**다른 브랜치를 지금 내 브랜치로 가져와 합쳐**"라는 명령이에요. 그래서 합쳐질 대상(보통 main)으로 먼저 이동해요.

```bash
git checkout main
git merge feature/login     # feature/login 을 main 으로 가져와 합치기
```

반대로 feature/login에 서서 `git merge main`을 치면, main의 내용이 feature/login으로 들어와요. 방향을 헷갈리지 않게 "나는 지금 받는 쪽에 서 있다"고 기억해요.

### Fast-forward: 책갈피만 앞으로

feature를 따로 빼서 일하는 동안 **main에 새 커밋이 없었다면**, 합칠 것도 없어요. main 책갈피(포인터)를 feature 끝으로 옮기기만 하면 돼요.

<Figure label="Fast-forward: main에 새 커밋이 없을 때">
  <Trail label="합치기 전 main:" values={["A", "B (main)"]} tone="blue" />
  <Trail label="feature/login:" values={["B에서 갈라져", "C", "D (feature)"]} />
  <Trail label="합친 뒤:" values={["A", "B", "C", "D (main, feature)"]} tone="ok" />
</Figure>

직접 해 보면 Git이 `Fast-forward`라고 알려 줘요.

```bash
git merge feature/login
# Updating dc67246..d6e0dc5
# Fast-forward
#  login.txt | 2 ++

git log --oneline --graph --all
# * d6e0dc5 (HEAD -> main, feature/login) D
# * 37ecf4f C
# * dc67246 B
# * 377c0b8 A
```

그래프가 한 줄이에요. **merge 커밋이 따로 생기지 않고**, main과 feature/login이 같은 커밋을 가리켜요.

### 3-way merge: 양쪽 다 새 커밋이 있을 때

feature에서 일하는 동안 **main에도 새 커밋(E)이 생겼다면**, 책갈피만 옮겨서는 안 돼요. E가 사라지니까요.

이때 Git은 세 곳을 비교해요. 그래서 3-way(세 방향)라고 불러요. 비교한 결과로 두 줄기를 묶는 **merge 커밋**(M)을 새로 만들어요.

<Figure label="3-way merge: 양쪽에 새 커밋이 있을 때">
  <Trail label="main:" values={["A", "B", "E (main)"]} tone="blue" />
  <Trail label="feature/login:" values={["B에서 갈라져", "C", "D (feature)"]} />
  <Boxes
    row={[
      { title: "B", note: "두 브랜치가 갈라진 공통 조상" },
      { title: "E", note: "main의 끝", tone: "blue" },
      { title: "D", note: "feature의 끝", tone: "rust" },
    ]}
    below={[{ title: "M (merge 커밋)", note: "세 곳을 비교한 결과로 새로 만들어요", tone: "ok", lines: ["부모가 E와 D 둘이라, 두 줄기가 여기서 묶여요"] }]}
  />
</Figure>

```bash
git merge feature/login
# Merge made by the 'ort' strategy.
#  login.txt | 2 ++

git log --oneline --graph --all
# *   c759821 (HEAD -> main) Merge branch 'feature/login'
# |\
# | * d6e0dc5 (feature/login) D
# | * 37ecf4f C
# * | 5aa7a3c E
# |/
# * dc67246 B
# * 377c0b8 A
```

맨 위 `Merge branch 'feature/login'`이 새로 생긴 merge 커밋이에요. `ort`는 Git이 합칠 때 쓰는 방식의 이름이라 신경 쓰지 않아도 돼요.

<Hint>

merge 커밋에도 메시지가 필요해서, `-m` 없이 치면 메시지를 쓰라고 편집기가 열릴 수 있어요. 어제 배운 vim이 열리면 `Esc` 다음 `:wq`예요.

</Hint>

### --no-ff: Fast-forward여도 merge 커밋 남기기

Fast-forward는 깔끔하지만, 나중에 보면 "여기서부터 여기까지가 로그인 기능이었다"는 흔적이 없어요. 흔적을 남기고 싶으면 `--no-ff`(no fast-forward)를 붙여요.

```bash
git merge --no-ff feature/login
# Merge made by the 'ort' strategy.

git log --oneline --graph --all
# *   75a68d2 (HEAD -> main) Merge branch 'feature/login'
# |\
# | * d6e0dc5 (feature/login) D
# | * 37ecf4f C
# |/
# * dc67246 B
# * 377c0b8 A
```

같은 상황인데 이번엔 갈래와 merge 커밋이 그래프에 남았어요.

<PredictPrompt />

main에 서 있고, feature를 만든 뒤 main에는 커밋을 하나도 안 했어요. feature에는 커밋이 3개 있어요. `git merge feature`(옵션 없이)를 하면 merge 커밋이 생길지 예측해 보세요.

정답은 "안 생긴다"예요. main에 새 커밋이 없으니 Fast-forward로 책갈피만 앞으로 옮겨요.

### 직접 눌러 보기: 합치기 시뮬레이터

위 실습과 같은 그림(main에 A, B, feature/login에 C, D)에서 시작해요. 버튼 하나가 명령 한 번이고, 출력 창의 글자는 위에서 실제로 돌린 결과 그대로예요. 뒤의 `#`는 왜 그렇게 됐는지예요.

## 11. 충돌: 같은 줄을 서로 다르게 고치면 Git이 묻는다

**같은 파일의 같은 부분을** 두 브랜치에서 서로 다르게 고친 뒤 merge하면, Git이 어느 쪽을 골라야 할지 몰라 멈춰요. 이게 충돌이에요.

main에서는 인사말을 "환영합니다"로, feature/login에서는 "로그인해 주세요"로 같은 줄을 고친 뒤 합쳐 봤어요.

```bash
git merge feature/login
# Auto-merging README.md
# CONFLICT (content): Merge conflict in README.md
# Automatic merge failed; fix conflicts and then commit the result.

git status
# You have unmerged paths.
#   (fix conflicts and run "git commit")
#   (use "git merge --abort" to abort the merge)
#
# Unmerged paths:
# 	both modified:   README.md      <- 양쪽 다 고친 파일
```

`both modified`가 충돌 난 파일이에요. 파일을 열면 Git이 두 내용을 나란히 적어 둬요.

```text
제목
<<<<<<< HEAD
인사말: 환영합니다
=======
인사말: 로그인해 주세요
>>>>>>> feature/login
```

  <Boxes
    row={[
      { title: "<<<<<<< HEAD 부터 =======", note: "지금 내 브랜치(main)의 내용", tone: "blue", lines: ["인사말: 환영합니다"] },
      { title: "======= 부터 >>>>>>> feature/login", note: "가져오려는 브랜치의 내용", tone: "rust", lines: ["인사말: 로그인해 주세요"] },
    ]}
  />
</Figure>

### 푸는 순서

<Figure>
  <Seq
    steps={[
      { title: "최종 내용으로 직접 고치기.", body: "충돌 난 파일을 열어 `<<<<<<<`, `=======`, `>>>>>>>` 표시 줄을 모두 지워요. 한쪽을 고르든, 둘을 섞든 내가 정해요." },
      { title: "`git add <파일>`.", body: "\"해결했다\"고 Git에게 알려요." },

```bash
# README.md 를 "인사말: 환영합니다, 로그인해 주세요" 로 고친 뒤
git add README.md
git status
# All conflicts fixed but you are still merging.
#   (use "git commit" to conclude merge)

git commit
# [main 3f56b12] Merge branch 'feature/login'
```

<Note title="VS Code 버튼은 1번만 대신해 줘요" tone="info">

VS Code에서 충돌 파일을 열면 표시 위에 "현재 변경 사항 수락", "수신 변경 사항 수락" 같은 버튼이 떠요. 눌러서 고르면 1번을 대신해 줘요. 그래도 add와 commit은 해야 해요.

</Note>

### 그만두고 싶으면: git merge --abort

충돌이 너무 복잡해서 일단 멈추고 싶으면 merge 전 상태로 되돌릴 수 있어요.

```bash
git merge --abort
git status --short
#                     <- 아무 변경도 없어요
cat README.md
# 제목
# 인사말: 환영합니다   <- merge 하기 전 main 내용 그대로
```

## 12. GitFlow: 충돌은 develop으로 합치는 순간에 난다

1회차에서 GitFlow는 "브랜치를 나누는 팀의 약속"이라고 했어요. 오늘은 브랜치 종류를 다 봤어요.

| 브랜치 | 하는 일 |
| --- | --- |
| `main` | 출시된 완성본 |
| `develop` | 개발한 기능을 모아 합치는 곳 |
| `feature/*` | 기능 하나를 만드는 곳 (예: `feature/login`) |
| `release/*` | 출시 전에 마지막으로 다듬는 곳 |
| `hotfix/*` | 출시된 main의 급한 버그를 고치는 곳 |

정답이 아니라 팀에 맞게 고쳐 쓰는 틀이에요.

feature 브랜치는 **develop에서** 갈라져 나오고, 다 만들면 PR을 거쳐 develop으로 합쳐요. 충돌은 대개 **이 merge 순간**에 나요. 여러 feature에서 같은 파일을 건드렸을 때예요.

<Figure>
  <Boxes
    row={[
      { title: "feature/login", tone: "rust", lines: ["develop에서 갈라져 나와요"] },
      { arrow: "PR을 거쳐 합쳐요" },
      { title: "develop", tone: "blue", lines: ["기능을 모아 합치는 곳"] },
      { arrow: "PR을 거쳐 합쳐요", dir: "left" },
      { title: "feature/signup", tone: "rust", lines: ["develop에서 갈라져 나와요"] },
    ]}
    below={[{ title: "충돌이 나는 자리", tone: "red", lines: ["두 feature가 같은 파일을 건드렸다면, develop으로 합치는 이 순간에 부딪혀요", "feature가 **오래 살수록** develop은 계속 앞으로 가서 충돌이 커져요"] }]}
  />
</Figure>

### 줄이는 법

- feature 브랜치가 **오래 살수록 충돌이 커져요.** develop은 그동안 계속 앞으로 가니까요.
- 그래서 develop의 새 변경을 내 feature로 **자주 가져와 맞춰요**(feature에 서서 develop을 merge).
- 충돌은 보통 **PR을 올리기 전에 feature 쪽에서** 풀고, 깨끗한 상태로 리뷰를 받아요.

## 13. 브랜치 삭제: -d는 조심성 있게, -D는 강제로

merge가 끝난 브랜치는 지워서 목록을 깔끔하게 해요.

```bash
git branch --delete feature/login   # -d 와 같아요. 병합이 끝난 브랜치만 지워져요
# Deleted branch feature/login (was 9831e9a).

git branch -D feature/try           # 병합 여부와 상관없이 강제로 지우기
# Deleted branch feature/try (was 6a63b78).
```

`-d`는 조심성이 있어요. 아직 합치지 않은 브랜치를 지우려 하면 거절해요. `-d`로 지울 때 걸리는 곳은 두 군데예요.

<Figure label="git branch -d 의 문지기 둘">
  <GateFlow
    gates={[
      { q: "아직 합치지 않은 커밋이 있나?", code: "git branch -d feature/try", out: "`not fully merged`로 거절. 정말 버려도 될 때만 `-D`(대문자)" },
      { q: "지금 서 있는(체크아웃한) 브랜치인가?", code: "git switch feature/login 한 뒤", out: "`cannot delete branch`로 거절. 다른 브랜치로 옮긴 뒤 지워요" },
    ]}
    pass={{ text: "브랜치(책갈피)만 지워져요", code: "Deleted branch feature/login (was 9831e9a)." }}
  />
</Figure>

아직 합치지 않은 브랜치를 `-d`로 지우려 하면 이렇게 나와요.

```bash
git branch -d feature/try
# error: the branch 'feature/try' is not fully merged
# hint: If you are sure you want to delete it, run 'git branch -D feature/try'
```

"거기에만 있는 커밋이 사라질 수 있다"는 경고예요. 정말 버려도 될 때만 `-D`(대문자)를 써요.

지금 서 있는(체크아웃한) 브랜치는 지울 수 없어요. 다른 브랜치로 옮긴 뒤 지워요.

```bash
git switch feature/login
git branch -d feature/login
# error: cannot delete branch 'feature/login' used by worktree at '.../my-project'
```

## 오늘 꼭 기억할 주의점

- `&&`는 앞이 성공해야 뒤를 실행해요. `;`는 무조건, `&` 하나는 전혀 다른 뜻이에요.
- `.gitignore`는 이미 추적 중인 파일엔 안 통해요. `git rm --cached`로 추적을 끊어요. 주석은 줄 끝이 아니라 따로 한 줄에 써요.
- 비밀키는 첫 커밋 전에 ignore해요. 한 번 커밋되면 이력에 남아요.
- `reset --hard`는 작업 폴더까지 지워요. 날린 커밋은 `reflog`로 살릴 수 있지만, 커밋 안 한 변경은 못 살려요.
- 이미 push해서 팀원이 가져간 커밋은 reset 말고 `revert`예요.
- `git stash`는 새 파일을 안 넣어요. 새 파일까지 맡기려면 `-u`예요.
- merge는 **받는 쪽 브랜치에 서서** 실행해요.
- 충돌이 나면 표시를 지워 고치고, `add`, `commit` 순서로 마무리해요. 막히면 `git merge --abort`예요.
- 브랜치는 `-d`로 지우고, `-D`는 정말 버려도 될 때만 써요.
