14회차부터 16회차까지 docker 명령이 스무 개 넘게 나왔어요. 이름으로 외우면 막힐 때 떠오르지 않아요. 그래서 이 페이지는 **"지금 하고 싶은 일"에서 거꾸로** 명령을 찾게 묶었어요.

예제는 16회차 그대로예요. `SportsCenter` 폴더의 `docker-compose.yaml`, 서비스 `db`, 컨테이너 `sportscenter-db`, 볼륨 `pgdata`예요. 출력과 오류 문장은 Docker로 직접 돌려서 확인한 것만 실었어요.

## 1. 명령 한 줄은 "누구에게, 무엇을, 어디에"를 차례로 말한다

16회차에서 제일 많이 친 명령을 끊어 읽어 볼게요. 어떤 docker 명령이든 이 순서를 벗어나지 않아요.

옵션은 명령마다 붙는 게 정해져 있어요. 켤 때(`run`), 들어갈 때(`exec`), 기록 볼 때(`logs`)로 나누면 헷갈리지 않아요.

### 줄 끝 `\` 뒤에 빈칸이 있으면 명령이 둘로 쪼개진다

긴 명령은 줄 끝에 `\`를 두고 다음 줄로 이어 써요. 터미널이 `>`를 띄우고 기다렸다가 한 줄처럼 실행해요.

```bash
docker run -d --name sportscenter-db \
  -e POSTGRES_PASSWORD=admin \
  -p 5432:5432 postgres:18
```

눈에 안 보이는 빈칸 하나가 `\` 뒤에 붙으면, 첫 줄이 혼자 실행되고 둘째 줄은 `-e`라는 명령으로 읽혀요. 그래서 오류가 두 개 한꺼번에 나와요.

```text
docker: invalid reference format

Run 'docker run --help' for more information
bash: line 2: -e: command not found
```

## 2. 무엇이 생기고 무엇이 사라지는지 먼저 안다

docker 명령이 다루는 물건은 넷이에요. 물건마다 만들고, 보고, 없애는 명령이 짝으로 있어요.

| 물건 | 만들기 | 보기 | 없애기 |
| --- | --- | --- | --- |
| 이미지 | `docker pull postgres:18` | `docker images` | `docker rmi postgres:18` |
| 컨테이너 | `docker run ...` / `docker compose up -d` | `docker ps`, `docker ps -a` | `docker rm 이름` / `docker compose down` |
| 볼륨 | `docker volume create pgdata` (또는 `-v`, compose가 알아서) | `docker volume ls`, `docker volume inspect 이름` | `docker volume rm 이름` / `docker compose down -v` |
| 네트워크 | `docker compose up -d`가 알아서 | `docker compose config` 맨 아래 | `docker compose down`이 알아서 |

`docker images`의 태그 `18`은 PostgreSQL 18이라는 뜻이에요. 숫자로 적어 두면 누가 받아도 같은 버전이에요.

### 지우는 명령마다 사라지는 범위가 다르다

가장 많이 헷갈리는 곳이에요. "데이터가 남느냐"만 기억하면 돼요.

| 명령 | 컨테이너 | 볼륨 속 데이터 | 이미지 |
| --- | --- | --- | --- |
| `docker stop` / `docker compose stop` | 꺼지기만 해요 | 남아요 | 남아요 |
| `docker rm 이름` | 사라져요 | 남아요 | 남아요 |
| `docker compose down` | 사라져요(네트워크도) | **남아요** | 남아요 |
| `docker compose down -v` | 사라져요 | **사라져요** | 남아요 |
| `docker volume rm 이름` | 쓰는 중이면 거절 | 사라져요 | 남아요 |
| `docker rmi 이미지` | 쓰는 컨테이너가 있으면 거절 | 남아요 | 사라져요 |

그래서 지우는 순서는 **쓰는 쪽부터**예요. 컨테이너, 볼륨, 이미지 순서로 지워요. 거꾸로 하면 이런 문장이 나와요.

| 순서를 어기면 | 문장 속 단서 |
| --- | --- |
| 켜진 컨테이너를 `rm` | `container is running: stop the container before removing or force remove` |
| 컨테이너가 붙잡은 볼륨을 `volume rm` | `volume is in use - [컨테이너 ID]` |
| 컨테이너가 쓰는 이미지를 `rmi` | `unable to delete ... (must be forced) - container ... is using its referenced image` |

마지막 것은 **꺼진 컨테이너가 남아 있어도** 나요. `docker ps -a`로 꺼진 것까지 보고 먼저 `rm`해요. 이미지는 다음에도 쓸 거라면 지우지 않고 둬요. 지우면 다음에 `pull`부터 다시 받아요.

## 3. 켜고 끄기: 켜짐과 꺼짐 사이를 오갈 뿐, 지우는 건 `rm` 하나

`docker`와 `docker compose`가 같은 이름의 명령을 갖고 있어요. 차이는 **대상**이에요. `docker stop sportscenter-db`는 컨테이너 하나를, `docker compose stop`은 이 폴더 compose 파일에 적힌 서비스 전부를 꺼요.

| 하고 싶은 일 | 컨테이너 하나 | compose 프로젝트 전체 |
| --- | --- | --- |
| 끄기 | `docker stop sportscenter-db` | `docker compose stop` |
| 다시 켜기 | `docker start sportscenter-db` | `docker compose start` |
| 껐다가 바로 켜기(설정 다시 읽기) | `docker restart sportscenter-db` | `docker compose restart` |
| 꺼진 것까지 보기 | `docker ps -a` | `docker compose ps -a` |

## 4. 안을 들여다보는 법: 알고 싶은 것으로 고른다

| 알고 싶은 것 | 명령 |
| --- | --- |
| 지금 켜진 게 뭐지? 이름은? 포트는? | `docker ps` (`NAMES`, `PORTS`, `STATUS` 칸) |
| 왜 꺼졌지? 준비됐나? | `docker logs --tail 5 sportscenter-db` |
| 새 기록이 생기는지 지켜보기 | `docker logs -f sportscenter-db` (멈출 때 `Ctrl + C`) |
| 안에서 여러 명령을 쳐 보기 | `docker exec -it sportscenter-db bash` (나올 때 `exit`) |
| 안에서 명령 하나만 | `docker exec sportscenter-db ls /tmp` (치고 바로 끝나요) |
| DB에 바로 들어가기 | `docker compose exec db psql -U postgres -d sportscenter` (나올 때 `\q`) |
| 쿼리 한 줄만 묻기 | `docker compose exec db psql -U postgres -d sportscenter -c "SELECT ..."` |
| 볼륨이 실제로 어디 있지? | `docker volume inspect sportscenter_pgdata`의 `Mountpoint` |
| compose 파일을 Docker가 어떻게 읽었지? | `docker compose config` (6절) |
| 이 옵션 뭐였지? | 명령 뒤에 `--help` |

PostgreSQL 기록은 길어서 `docker logs`만 치면 화면이 넘쳐요. 14회차처럼 `ready to accept connections`를 확인할 때는 `--tail`로 끝만 보면 돼요. `-f`와 같이 써서 `docker logs -f --tail 1 ...`로 치면 끝 한 줄부터 지켜볼 수 있어요.

`--help`를 붙이면 맨 위 `Usage` 줄에 쓰는 모양이 나와요. `[OPTIONS]`처럼 대괄호로 싼 건 빼도 되는 자리예요. 예를 들어 `docker cp --help`에는 꺼내는 모양과 넣는 모양이 두 줄로 나와요.

```text
Usage:  docker cp [OPTIONS] CONTAINER:SRC_PATH DEST_PATH|-
        docker cp [OPTIONS] SRC_PATH|- CONTAINER:DEST_PATH
```

## 5. 파일은 두 길로 들어가고, 꺼낼 때도 `cp`를 쓴다

15회차에서 SQL 파일을 컨테이너 안 `psql`에 먹이는 길을 두 개 봤어요. 파일이 컨테이너 **안으로 복사되느냐, 흘러만 가느냐**가 달라요.

<Figure label="SQL 파일을 컨테이너 안 psql에 먹이는 두 길">
  <Boxes

    ]}
  />
</Figure>

`docker cp`는 **보내는 쪽을 앞에, 받는 쪽을 뒤에** 써요. 컨테이너 쪽은 `이름:경로`예요. 그래서 순서만 바꾸면 거꾸로 꺼내 와요. 14회차 nginx의 설정 파일을 꺼내 읽어 보면 이렇게 돼요.

```bash
docker cp sports.sql sportscenter-db:/tmp/sports.sql   # 넣기
docker cp web:/etc/nginx/nginx.conf ./nginx.conf       # 꺼내기
docker exec -i sportscenter-db psql -U postgres < sports.sql   # 복사 없이 붓기
```

보낼 파일 이름이 틀렸거나 다른 폴더에서 치면 맥에서는 `lstat ...: no such file or directory`가 나와요. `ls`로 지금 폴더에 그 파일이 있는지 봐요.

### `-it`는 키보드용, `<`로 붓는 파일에는 `-i`만

`psql`을 열 때 늘 `-it`를 쓰다 보니 파일을 부을 때도 손이 붙이기 쉬워요. 그러면 바로 거절돼요.

```text
cannot attach stdin to a TTY-enabled container because stdin is not a terminal
```

`-i`는 입력 통로, `-t`는 사람이 보는 화면이에요. 파일을 부으면 입력은 있지만 화면을 붙일 키보드가 없어서 `-t`가 거절당해요. 직접 칠 땐 `-it`, 파일을 부을 땐 `-i`예요.

## 6. YAML은 칸으로 말하고, 오류는 줄과 칸 번호로 답한다

16회차 `docker-compose.yaml`은 칸 수로 "누가 누구 안에 있는지"를 말해요. `services` 안에 `db`, `db` 안에 `image`, `environment`가 있어요. 같은 칸에서 시작하는 줄끼리 같은 단계예요.

- 한 단계를 2칸으로 하든 4칸으로 하든, **같은 단계끼리 칸이 맞으면** 똑같이 읽혀요. 그래도 Docker 문서와 수업 자료를 따라 2칸으로 써요.
- **탭은 쓸 수 없어요.** 편집기에서는 빈칸과 똑같아 보여서 더 무서워요.
- `이름: 값`은 쌍점 뒤에 한 칸을 띄워요. 목록은 `- 값`이에요.

16회차 파일의 5, 6번째 줄(`container_name`, `image`)을 일부러 틀려서 `docker compose config`에 넣어 봤어요. 오류 끝의 `L5.C1`은 "5번째 줄 1번째 칸"이에요.

```text
# 5번째 줄을 탭으로 들여씀
go-yaml load error in scanner (while scanning for the next token) at L5.C1: found character that cannot start any token

# 6번째 줄 image만 2칸으로 당김
go-yaml load error in scanner at L7.C16: mapping values are not allowed in this context

# 6번째 줄을 image:postgres:18 로 붙여 씀
go-yaml load error in scanner (while scanning a simple key) at L6.C5-L7.C5: could not find expected ':'
```

두 번째와 세 번째는 **틀린 줄보다 한 줄 아래**를 가리켜요. YAML이 틀린 줄을 "값"으로 읽고 넘어갔다가 다음 줄에서 말이 안 맞아 멈추기 때문이에요. 오류 줄 번호가 멀쩡해 보이면 바로 위 줄을 봐요.

### `docker compose config`는 `up` 하기 전의 맞춤법 검사

오류가 없으면 Docker가 알아들은 내용을 전부 펼쳐 보여 줘요. 내가 안 적은 칸은 기본값으로 채워지고, 순서는 바뀌어도 괜찮아요.

```text
name: sportscenter
services:
  db:
    container_name: sportscenter-db
    environment:
      POSTGRES_PASSWORD: admin
    image: postgres:18
    networks:
      default: null
    ...
networks:
  default:
    name: sportscenter_default
volumes:
  pgdata:
    name: sportscenter_pgdata
```

맨 아래를 보면 내가 적은 `pgdata`의 진짜 이름이 `sportscenter_pgdata`예요. 16회차에서 `docker volume ls`에 이 이름이 보였던 이유예요. 프로젝트 이름(`name:`, 없으면 폴더 이름)이 앞에 붙어요.

## 7. 같은 일, `docker run` 한 줄과 compose 파일 한 장

`docker run`의 옵션 하나가 compose 파일의 칸 하나로 옮겨 가요. `-d`만 예외로 `docker compose up -d`에 붙어요.

| `docker run`의 옵션 | `docker-compose.yaml`의 `db` 안 |
| --- | --- |
| `--name sportscenter-db` | `container_name: sportscenter-db` |
| `-e POSTGRES_PASSWORD=admin` | `environment:` 아래 `POSTGRES_PASSWORD: admin` |
| `-p 5432:5432` | `ports:` 아래 `- "5432:5432"` |
| `-v pgdata:/var/lib/postgresql` | `volumes:` 아래 `- pgdata:/var/lib/postgresql` |
| 맨 끝 `postgres:18` | `image: postgres:18` |

### `container_name`을 빼면 이름이 바뀐다

`container_name` 줄을 지우고 `up -d` 하면 이름이 `프로젝트-서비스-번호`, 즉 `sportscenter-db-1`이 돼요. 그러면 예전 이름으로 부르는 명령이 이렇게 실패해요.

```text
Error response from daemon: No such container: sportscenter-db
```

`docker compose exec db ...`처럼 **서비스 이름**으로 부르면 컨테이너 이름이 뭐든 상관없어요. compose 명령에는 서비스 이름(`db`), 그냥 `docker` 명령에는 컨테이너 이름을 써요. 지금 이름은 `docker compose ps`의 `NAME` 칸에 있어요.

### 하고 싶은 일로 찾는 명령표

| 하고 싶은 일 | `docker run`으로 켰다면 | compose로 켰다면 |
| --- | --- | --- |
| 이미지 미리 받기 | `docker pull postgres:18` | `docker compose pull` |
| 설정이 맞는지 보기 | | `docker compose config` |
| 켜기 | `docker run -d --name ... postgres:18` | `docker compose up -d` |
| 무엇이 켜졌나 | `docker ps` | `docker compose ps` |
| 켜 둔 프로젝트 목록 | | `docker compose ls` |
| DB 들어가기 | `docker exec -it sportscenter-db psql -U postgres` | `docker compose exec db psql -U postgres` |
| 기록 끝만 보기 | `docker logs --tail 3 sportscenter-db` | `docker compose logs --tail 3` |
| 끄기 / 다시 켜기 | `docker stop` / `docker start` + 이름 | `docker compose stop` / `start` |
| 데이터는 두고 치우기 | `docker rm sportscenter-db` | `docker compose down` |
| 데이터까지 치우기 | `docker rm` 뒤 `docker volume rm pgdata` | `docker compose down -v` |

compose 명령은 모두 **compose 파일이 있는 폴더**에서 쳐요. 다른 폴더에서 치면 `no configuration file provided`가 나와요(16회차). `docker compose logs`는 서비스가 여럿일 수 있어서 줄마다 앞에 이름이 붙어요.

## 8. 인터넷 자료의 긴 이름은 같은 명령이다

공식 문서나 블로그에서는 `docker container ls`처럼 무엇에 대한 명령인지 앞에 붙인 이름을 자주 써요. 결과는 똑같으니 어느 쪽을 쳐도 돼요.

| 수업에서 친 것 | 같은 명령 |
| --- | --- |
| `docker ps` | `docker container ls` |
| `docker images` | `docker image ls` |
| `docker rm`, `docker rmi` | `docker container rm`, `docker image rm` |
| `docker exec`, `docker cp` | `docker container exec`, `docker container cp` |

## 꼭 기억할 주의점

- 명령은 누구에게(`docker`, `docker compose`), 무엇을, 어디에 순서예요. 기억이 안 나면 뒤에 `--help`.
- 줄 끝 `\` 뒤에 빈칸이 있으면 `invalid reference format`과 `command not found`가 같이 나요.
- `docker compose down`은 데이터를 남기고, `down -v`는 데이터까지 지워요.
- 지울 때는 쓰는 쪽부터: 컨테이너, 볼륨, 이미지. 꺼진 컨테이너도 이미지를 붙잡고 있어요.
- 키보드로 칠 땐 `-it`, `<`로 파일을 부을 땐 `-i`만.
- YAML은 탭 금지, 같은 단계는 같은 칸, 쌍점 뒤 한 칸. 오류 줄 번호가 멀쩡하면 바로 위 줄을 봐요.
- compose 명령에는 서비스 이름(`db`), `docker` 명령에는 컨테이너 이름(`sportscenter-db`).
