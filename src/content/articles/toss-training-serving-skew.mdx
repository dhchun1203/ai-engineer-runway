## 먼저 알아 둘 개념

이 기사는 모델 코드가 아니라 모델에 넣는 입력값이 어긋난 이야기예요. 아래 다섯 가지를 알면 따라가기 쉬워요.

### 학습과 서빙의 입력 차이

<Term id="training-serving-skew">학습과 서빙의 입력 차이</Term>는 모델이 연습할 때 본 입력과 실전에서 받는 입력이 다른 현상이에요. 연습 문제집과 실제 시험지가 슬쩍 다른 상황을 떠올리면 돼요.

모델이 아무리 같아도 입력이 다르면 예측도 달라져요.

### 시점 기준 조인

<Term id="point-in-time-join">시점 기준 조인</Term>은 학습 데이터를 만들 때 사건이 일어난 시각 이전의 가장 최근 값만 붙이는 방법이에요. 시험 당일까지 공개된 자료만 보고 답을 쓰게 하는 규칙과 같아요.

미래의 정보가 섞이는 것을 막아 주는 장치예요.

### 블루/그린 전환

<Term id="blue-green-switch">블루/그린 전환</Term>은 쓰는 쪽과 준비하는 쪽을 따로 두고, 준비가 끝나면 한 번에 바꾸는 방식이에요. 손님이 먹는 접시는 그대로 두고 주방에서 새 요리를 다 차린 뒤 통째로 바꿔 내는 모습과 비슷해요.

바꾸는 도중의 어중간한 상태를 사용자가 보지 않아도 돼요.

### TTL

<Term id="ttl">TTL</Term>은 저장소에 넣은 값의 유효 기간이에요. 우유 팩의 소비기한처럼 기간이 지나야 자동으로 사라져요.

따로 지우지 않으면 기간이 끝날 때까지는 계속 조회돼요.

### 업서트

<Term id="upsert">업서트</Term>는 같은 키가 있으면 덮어쓰고 없으면 새로 넣는 쓰기 방식이에요. 명단에 이름이 있으면 그 줄을 고치고, 없으면 한 줄을 더하는 것과 같아요.

새 데이터에서 빠진 키는 건드리지 않아서, 옛 값이 지워지지 않고 남을 수 있어요.

## 핵심 내용 정리

### 어떤 문제였나

추천 모델은 두 장면에서 피처를 만나요. 학습 때는 지난 추천 이력 옆에 사람과 물건의 특징값을 붙여 공부하고, 서비스 때는 요청이 오는 즉시 온라인 저장소에서 같은 종류의 값을 가져와 점수를 매겨요.

기사에 따르면 이 두 길에서 같은 요청에 서로 다른 피처가 쓰이는 일이 있었고, 기사는 이를 학습과 서빙의 입력 차이라고 불러요. 문제는 모델이 아니라 피처 저장소에 값이 올라가고 갱신되는 방식에서 나왔어요.

### 왜 어려웠나

피처 표는 파티션이라는 묶음 단위로 만들어 온라인 저장소에 올려요. 그런데 올리는 작업이 끝나는 시각이 표마다 제각각이라, 기사의 예처럼 매시간 만드는 표라면 같은 요청에서 한 표는 10시 묶음을 쓰고 다른 표는 아직 9시 묶음을 쓸 수 있어요. 학습 데이터는 요청 시각만으로 묶음을 골라서 이런 엇갈림을 알 수 없었어요.

겉으로 쉬운 해법이 하나 있었어요. 서비스에서 쓴 피처 값을 전부 로그로 남기면 정확하지만, 기사에 따르면 하루 수십 TB 규모가 예상되어 비용 부담이 컸고 여러 실험이 동시에 도는 환경이라 더 그랬어요.

숨은 문제도 둘 더 있었어요. 업로더가 서비스 중인 테이블의 행을 하나씩 덮어쓰다 보니 업로드 중에는 새 값과 옛 값이 섞여 나갔는데, 로그에 남는 파티션 표시는 테이블당 하나뿐이라 기록과 실제가 어긋났어요.

또 사용자와 상품 조합으로 만드는 피처는 행동이 없으면 새 데이터에서 아예 빠지는데, 업서트 방식이라 옛 값이 지워지지 않고 TTL이 끝날 때까지 서비스에 남았어요. 기사의 예로, 6월 1일 조회 기록은 집계상 6월 8일에 사라지지만 TTL이 7일이면 6월 14일까지 나갈 수 있었어요. 학습 데이터에서는 값이 비어 있는데 서비스에서는 약 2주 전 행동이 보이는 셈이에요.

### 어떻게 풀었나

핵심 장치는 세 가지예요.

첫째, 값 대신 번호표를 남겨요. 요청마다 실제로 쓴 파티션 정보만 로그에 기록하고, 학습할 때 그 파티션에서 값을 다시 꺼내요. 이를 위해 과거 파티션을 학습 기간만큼 보관하고 덮어쓰지 않아야 해요.

둘째, 손님용 칸과 준비용 칸을 나눠요. 준비용 칸에 새 묶음을 다 올린 뒤에야 실제 값과 묶음 표시를 같이 블루/그린 방식으로 바꿔서, 올리는 중에 두 묶음이 뒤섞이지 않아요. 바꾸는 일은 표마다 따로 해요. 기사는 행마다 묶음 번호를 붙이는 안도 정확하지만 업로더, 로깅, 학습 코드를 다 고쳐야 해서 효과가 불확실하다고 보았다고 해요.

셋째, 빠진 데이터를 명시적으로 지워요. TTL이 끝나기를 기다리지 않도록, 전환 전에 적재 영역에서 옛 묶음과 새 묶음을 견줘요. 사라진 행은 삭제하고, 새 행과 바뀐 행은 반영하며, 똑같은 행은 그대로 둬서 쓰기를 줄여요.

### 무엇이 달라졌나

기사에 따르면 학습 대상 행 가운데 서빙 파티션과 연결된 비율은 사용자 피처가 약 89퍼센트, 상품 피처가 약 94퍼센트였어요. 조합 피처는 분석 대상 노출의 약 75퍼센트에서 서빙 때 값을 학습에서 똑같이 다시 만들어 냈고, 여기에는 학습과 서빙 양쪽에 피처가 없는 경우도 들어 있어요.

중간 분석에서 조합 피처 값이 조회된 노출의 비율은 14.4퍼센트에서 6.0퍼센트로 내려갔어요. 전체 지면을 합산해 기존 모델과 견준 온라인 실험에서는 클릭률이 상대 -0.86퍼센트, 전환율이 상대 +0.91퍼센트로 움직였고, 둘 다 우연으로 보기 어려운 차이였어요.

구매 사용자 비율, 사용자당 주문 수 같은 목표 지표와 매출 가드레일 지표는 의미 있게 달라지지 않았어요. 기사는 추천이 더 좋아졌다고 확인한 것은 아니고, 목표 지표를 떨어뜨리지 않은 채 입력의 엇갈림을 줄였다고 정리해요. 클릭률은 유의하게 내려갔다는 점도 함께 기억해 둬요.

## 취업과 면접 포인트

첫째는 모델이 같아도 입력이 다르면 결과가 달라진다는 관점이에요. 성능이 이상할 때 모델부터 의심하지 않고 학습 데이터와 서비스 입력이 같은지 먼저 비교하는 습관을 보여 줄 수 있어요.

둘째는 비용을 따져 고르는 판단이에요. 전부 로그로 남기는 정확한 방법이 있어도, 이미 보관 중인 파티션을 활용해 로그 비용을 줄인 선택을 설명할 수 있어요.

셋째는 결과를 정직하게 읽는 태도예요. 지표 하나가 내려가고 다른 하나가 올라가도, 목표 지표가 변하지 않았다면 개선이라고 단정하지 않고 "입력 차이를 줄였다"고 말하는 절제가 신뢰를 줘요.

면접에서는 이렇게 말해 볼 수 있어요.

- "학습 데이터와 서비스 입력이 같은 값인지 로그로 비교해 보고, 어긋나면 피처 쿼리뿐 아니라 저장소의 갱신과 조회 과정까지 점검합니다."
- "피처 값을 통째로 쌓지 않고 어느 파티션을 읽었는지만 기록해 두면, 학습 때 같은 값을 다시 찾아 쓸 수 있어 로그 비용이 훨씬 가볍습니다."
- "원본에서 사라진 데이터가 TTL 때문에 서비스에 남지 않는지, 삭제를 명시적으로 처리하는지 확인합니다."

## 스스로 확인하기

1. 같은 요청인데 학습 때와 서비스 때 피처가 달라진 첫 번째 이유는 무엇일까요?
2. 모든 피처 값을 로그로 남기는 방법 대신 토스가 선택한 방법은 무엇이고, 그 방법이 성립하려면 무엇을 보관해야 할까요?
3. 업서트와 TTL 조합이 어떻게 학습과 서비스의 값을 어긋나게 만들었을까요?

1. 테이블마다 온라인 저장소에 올라가는 시각이 달라서, 한 요청 안에서도 어떤 테이블은 최신 파티션을, 다른 테이블은 이전 파티션을 썼어요. 학습 데이터는 요청 시각만으로 파티션을 골라서 이 차이를 반영하지 못했어요.
