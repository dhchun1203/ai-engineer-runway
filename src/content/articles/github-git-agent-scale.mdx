## 먼저 알아 둘 개념

이 기사는 Git 서버 안쪽 구조를 다뤄요. 세 가지 말만 알면 읽을 수 있어요.

### 크리티컬 패스

<Term id="critical-path">크리티컬 패스</Term>는 여러 일이 동시에 진행될 때 전체 시간을 정하는 가장 긴 줄이에요. 푸시가 느리다면 그 줄 위의 일부터 줄여야 해요.

### 복제와 쿼럼

<Term id="replication-quorum">복제와 쿼럼</Term>은 같은 데이터를 여러 서버에 복사해 두고, 쓰기를 확정하려면 일정 수 이상의 서버가 동의해야 하는 방식이에요. 안전하지만 가장 느린 서버가 속도를 정하는 단점이 있어요.

### 저장소와 계산 분리

<Term id="storage-compute-separation">저장소와 계산 분리</Term>는 데이터를 보관하는 곳과 처리하는 서버를 따로 두는 설계예요. 창고와 판매대를 나누면 손님이 몰릴 때 판매대만 늘리면 되는 것과 같아요.

## 핵심 내용 정리

### 어떤 문제였나

기사는 개발자와 에이전트가 같은 저장소에서 동시에 일하면서 Git에 걸리는 부하의 모양이 바뀌었다고 말해요. 기사가 든 수치로는 월간 Git 활동이 2025년 9월 2,182억 건에서 2026년 8월 4,733억 건으로 두 배 넘게 늘었고, 2026년 9월 커밋은 73억 8천만 건으로 1년 전의 다섯 배가 넘어요.

푸시는 한 달 6억 9천만 건에서 33억 5천만 건으로 4.9배가 되었고, 가장 바쁜 저장소 하나는 2026년 8월에 요청이 약 10억 건이었다고 해요. CI와 코드 스캔이 같은 브랜치 끝을 분당 수천 번씩 내려받는 일도 있다고 해요.

### 왜 어려웠나

기사는 지금 구조의 약점을 이렇게 짚어요. 저장소마다 여러 파일 서버에 전체 복사본이 있고(기본은 다섯 대), 이 복사본이 원본이면서 읽기를 받아 주는 층도 겸해요. 모든 복사본이 모든 쓰기에 참여하기 때문에 푸시는 가장 느린 복사본만큼만 빨라요.

그래서 읽기를 늘리려고 복사본을 늘리면 쓰기가 느려져요. 복사본 하나를 잃으면 읽기 용량이 줄고, 쿼럼을 잃으면 쓰기가 완전히 멈춰요. 게다가 압축이나 청소 같은 정리 작업이 실제 요청을 받는 서버에서 같이 돌아요.

기사가 꼽은 병목은 이 밖에도 있어요. 에이전트는 동작마다 커밋하듯 저장하니 에이전트의 작업 속도는 푸시 한 번이 끝나는 속도에 묶이고, 병합 큐나 릴리스 트레인은 병합을 한 참조로 몰아넣어요.

### 어떻게 풀었나

첫째 장치는 합의를 꼭 필요한 곳에만 쓰는 거예요. 기사에 따르면 참조 갱신만 모두의 동의가 필요하고, 객체 저장과 연결 검사와 비밀 정보 스캔은 다른 쓰기와 나란히 돌릴 수 있어서 푸시의 크리티컬 패스가 짧아져요. 압축과 청소는 별도 작업자가 영구 저장소에서 직접 맡아서, 바쁜 저장소도 푸시를 늦추지 않고 뒤에서 정리할 수 있어요.

둘째 장치는 원본과 읽기 층의 분리예요. 저장소의 정본은 Azure Blob Storage에 두고, 읽기는 캐시를 쥔 계산 작업자가 맡아요. 작업자 하나를 잃는 일은 캐시가 비는 정도의 일이고, 대체 서버가 정본에서 채우며 곧바로 일할 수 있어요. 릴리스나 새 에이전트 무리처럼 순간적으로 몰리는 부하에는 계산만 늘렸다 줄이면 돼요.

기사는 이 과정에서 브랜치 보호, 필수 리뷰, 감사 로그, 공개 범위 제어 같은 통제 기능을 지킨다는 원칙도 세워요. 개발자가 이미 믿는 작업 흐름을 같은 모양으로 더 큰 규모에 제공하는 것이 목표라고 해요.

### 무엇이 달라졌나

기사에 따르면 내부 벤치마크에서 새 설계는 쓰기 처리량이 최대 35배 높아요(무엇과 비교한 수치인지는 밝히지 않아요). 또한 읽기 용량은 따로 늘릴 수 있어요. 이전 작업은 점검 시간 없이 서비스를 켠 채로 진행하고 있어요.

다만 이 글은 전체 출시 결과가 아니라 방향과 원칙을 소개하는 글이고, 더 자세한 구조는 후속 글에서 다룬다고 해요.

## 취업과 면접 포인트

시스템 설계 면접에서 "읽기와 쓰기가 모두 늘어나면 어떻게 하나요?"를 받으면 서버를 늘린다고만 답하기 쉬워요. 이 기사는 복사본 수가 읽기 용량과 쓰기 속도를 동시에 묶어 버리는 구조가 문제였고, 그 둘을 떼어 놓는 방향으로 재구축 중이라는 좋은 사례예요.

또 하나는 "무엇이 정말 합의가 필요한가"를 따지는 습관이에요. 합의가 필요한 일과 나란히 해도 되는 일을 구분하면 느린 경로가 짧아져요. AI 에이전트가 만드는 부하가 설계 전제를 바꾼다는 관점도 요즘 현업이 관심 갖는 주제예요.

## 스스로 확인하기

1. 기사가 설명한 지금 구조에서 읽기용 복사본을 늘리면 쓰기가 왜 느려지나요?
2. 푸시의 크리티컬 패스를 줄이려고 어떤 일을 합의에서 빼 나란히 돌리나요?
3. 저장소와 계산을 분리하면 작업자 서버를 잃었을 때 무엇이 쉬워지나요?
