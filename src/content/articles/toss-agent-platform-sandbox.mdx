## 먼저 알아 둘 개념

이 기사는 "AI가 짠 코드를 어디서 어떻게 돌려야 안전한가"를 다뤄요. 아래 세 가지를 알면 읽기 쉬워요.

### 샌드박스

<Term id="sandbox">샌드박스</Term>는 프로그램이 만질 수 있는 파일과 네트워크를 울타리 안으로 좁힌 실행 공간이에요. 놀이터 모래판 안에서만 놀게 하는 것과 비슷해요.

AI가 만든 코드는 무슨 일을 할지 미리 알기 어려워서 이런 울타리 안에서 돌려요.

### 에이전트 하네스

<Term id="agent-harness">하네스</Term>는 모델에게 일을 시키고, 모델이 요청한 도구를 대신 돌려서, 나온 값을 다시 모델 앞에 가져다 놓는 일을 반복하는 바깥 틀이에요. 선수 옆에서 도구를 전달해 주는 매니저 같은 역할이에요.

모델은 글만 내놓기 때문에 실제로 명령을 실행하는 쪽은 이 틀이에요.

### 영구 볼륨

<Term id="persistent-volume">영구 볼륨</Term>은 서버가 꺼졌다 새로 떠도 남아 있는 별도 저장 공간이에요. 사무실을 옮겨도 창고에 맡긴 짐은 그대로인 것과 같아요.

새 서버가 같은 볼륨을 다시 붙이면 하던 작업을 이어 갈 수 있어요.

## 핵심 내용 정리

### 어떤 문제였나

기사는 “지난달과 같은 기준으로 비교해줘”라는 요청을 예로 들어요. 이런 일은 지난 쿼리를 찾고 기간을 바꾸는 과정을 사람이 되풀이해야 하는데, AI Platform 팀은 이를 에이전트가 하게 만들고 싶었어요. 토스는 전자금융 관련 감독 규정에 맞춰 내부망과 인터넷망이 나뉘어 있어서, 에이전트가 코드를 돌리고 데이터를 분석하는 일도 내부망 안에서 해야 했어요.

여기에 두 가지가 더 붙었어요. 모델이 만든 코드가 상관없는 파일을 읽거나 바꿀 수 있다는 걱정, 그리고 지난 작업을 계속 쓸 수 있어야 한다는 요구예요. 늘 빈 환경에서 출발하면 사용자가 분석 기준을 처음부터 다시 설명해야 하니까요.

### 왜 어려웠나

울타리를 치려면 "누가 무엇을 볼 수 있는가"를 파일 읽기 도구 하나가 아니라 실행되는 모든 것에 걸어야 해요. 쉘 명령과 스크립트가 도구를 거치지 않고 파일을 만질 수 있기 때문이에요. 그래서 기사는 접근 제한을 프로세스 단위로 건다고 설명해요.

또 하나는 키 문제예요. 에이전트가 사내 서비스를 부르려면 인증 정보가 필요한데, 그 값을 에이전트가 도는 환경 안에 두면 코드가 읽어 갈 수 있어요.

### 어떻게 풀었나

구조를 풀어 볼게요. 사용자 한 명당 쿠버네티스 Pod 하나를 두고 여러 에이전트와 대화가 그 Pod를 함께 써요. OpenSandbox가 Pod의 생성과 수명을 관리하고, 실행 환경(Runtime)은 하네스를 시작하기 전에 bubblewrap으로 격리 공간부터 만들어요.

에이전트마다 따로 VM을 띄우는 대신 bubblewrap으로 리눅스 네임스페이스를 나누는 쪽을 골랐어요. VM마다 이미지와 볼륨을 준비하는 부담이 있었고, 환경은 하나로 돌려 쓰고 에이전트별로 접근 범위만 달리 주고 싶다는 이유도 있었어요. 대신 호스트 커널을 함께 쓰므로 VM 수준의 커널 격리는 아니라고 기사가 밝혀요.

울타리 규칙은 세 가지예요.

- 에이전트의 작업 폴더, 사용자가 허락한 폴더, 그 대화의 상태 경로만 연결하고 참고용 자료는 보기만 하고 고칠 수 없게 해요.
- 프로세스와 네트워크 공간을 따로 나누고, HTTP 통신은 프록시를 거치게 해요.
- 하네스는 권한이 낮은 사용자로 돌고, 격리를 만드는 데 실패하면 실행을 멈춰요.

키는 이렇게 다뤄요. 하네스에는 진짜 키 대신 자리표시 값만 넣어 두고, 요청이 밖으로 나갈 때 OpenSandbox의 인증 프록시가 진짜 값으로 바꿔 줘요. 기사에 따르면 프록시가 다룰 수 있는 HTTP(S) 연결에서만 이렇게 해요.

모델 호출은 GenAI Gateway, 도구 호출은 MCP Gateway를 지나가고, 하네스는 플랫폼 DB의 접속 정보를 받지 않아요.

### 무엇이 달라졌나

일하던 파일과 대화 진행 상태는 영구 볼륨에 저장하고, 새 Pod가 뜨면 그 볼륨을 다시 붙여요. 같은 에이전트와 나누는 대화들은 작업 폴더를 함께 쓰므로 이전 대화에서 만든 스크립트가 남아 있어요. 대화 상태는 대화마다 따로라서 새 대화는 이전 조건을 자동으로 물려받지 않고, 사용자가 다시 말해 줘야 해요.

기록은 두 종류예요. 이어서 재개할 때는 하네스가 저장한 자기 상태를 쓰고, 기록 열람용으로는 OpenResponses 형식의 공통 실행 기록을 따로 남겨요. 다른 하네스로 넘길 때는 공통 기록을 요약해서 새 대화에 전달하는데, 재개할지 넘길지는 요청할 때 구분해요.

기사는 한계도 분명히 적어요. 접근 제한은 결과가 맞는지 검증하지 않고, 쓰기 가능한 폴더 안의 실수는 막지 못해요.

키를 숨기는 것이 권한을 줄이는 것은 아니어서, 게이트웨이와 각 서비스가 권한 검사를 따로 해야 해요. 이어서 재개해도 메모리 속 상태나 이미 일어난 바깥 동작은 되돌려지지 않아요.

## 취업과 면접 포인트

AI 에이전트를 서비스에 붙인다는 말은 결국 "모델이 만든 코드를 누구 권한으로, 어디서 돌리나"라는 질문에 답하는 일이에요. 이 기사는 규제가 있는 환경에서 그 답을 어떻게 설계했는지 보여 줘요.

면접에서 쓸 한 마디는 이래요. "도구 단위가 아니라 프로세스 단위로 접근을 막고, 지원되는 HTTP 연동에서는 비밀 키를 에이전트 환경에 두지 않고 밖의 프록시가 끼워 넣게 합니다."

또 하나 눈여겨볼 점은 선택의 근거예요. VM 대신 bubblewrap을 고르면서 무엇을 포기하는지 함께 말하면 설계 판단을 설명하는 답이 돼요.

## 스스로 확인하기

1. 접근 제한을 파일 읽기 도구가 아니라 프로세스 단위로 거는 이유는 무엇일까요?
2. 하네스 환경에 진짜 API 키를 두지 않고 자리표시 값을 쓰면 무엇이 좋아지고, 무엇은 여전히 따로 챙겨야 하나요?
3. 같은 에이전트의 새 대화에서 이전 대화의 조건이 자동으로 이어지지 않는 이유와 그 영향은 무엇인가요?

1. 쉘 명령과 스크립트는 도구를 거치지 않고도 파일을 만질 수 있어서예요. 프로세스 단위로 걸면 그 경로까지 같이 막혀요.

3. 대화 상태를 대화마다 따로 저장하기 때문이에요. 작업 폴더의 파일은 남지만 조건은 사용자가 다시 말해 줘야 해요.
