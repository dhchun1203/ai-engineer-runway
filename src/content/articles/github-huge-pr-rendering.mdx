## 먼저 알아 둘 개념

이 기사는 아주 긴 화면을 부드럽게 보여 주는 이야기예요. 아래 두 가지 말이 열쇠예요.

### 가상화

<Term id="list-virtualization">가상화</Term>는 긴 목록 전체를 한꺼번에 그리지 않고, 지금 화면에 보이는 부분만 그리는 기법이에요. 스크롤하면 보이는 부분이 바뀌고 나머지는 그리지 않아요.

두루마리 편지를 읽을 때 창문 크기만큼만 펼쳐 보는 것과 같아요. 다만 전체 두루마리가 얼마나 긴지 알아야 스크롤바 위치를 맞출 수 있어요.

### 스크롤 앵커링

<Term id="scroll-anchoring">스크롤 앵커링</Term>은 위쪽 내용의 높이가 바뀌어도 사용자가 읽던 자리가 화면에서 밀리지 않게 붙잡아 주는 기법이에요. 이게 없으면 읽다가 글이 갑자기 튀어요.

책을 읽는 중에 누가 앞쪽 쪽수를 늘렸는데도, 내가 보던 줄이 그 자리에 그대로 있는 것과 같아요.

## 핵심 내용 정리

### 어떤 문제였나

기사는 diff와 그에 달린 대화가 아주 커져도 리뷰 화면이 빠르고 매끄러워야 한다고 말해요. 글에는 백만 줄이 넘는 PR에 수백 개의 인라인 리뷰 댓글이 달린 극단적인 경우가 나오고, 글쓴이는 코드만 있다면 가상화로 충분하지만 댓글이 끼면 달라진다고 설명해요.

### 왜 어려웠나

코드 줄은 높이가 정해져 있어서 미리 계산할 수 있어요. 반면 기사는 댓글의 높이를 마크다운이 줄바꿈되는 모양, 펼쳐지는 영역, 답글 입력창, 이미지가 불러와지는 속도 같은 실행 중 요인이 정한다고 말해요. 기사의 표현대로 그려 보기 전에는 댓글이 얼마나 큰지 알 수 없어요.

높이를 모르면 전체 길이도, 스크롤바 위치도, 지금 어디를 그려야 하는지도 흔들려요. 기사는 또 이런 문제가 부하가 걸린 상태에서, 특정 엔진에서, 특정 스크롤 위치에서만 나타나서 손으로 재현하기 어렵다고 해요.

### 어떻게 풀었나

첫째 장치는 높이 계산을 둘로 나눈 거예요. 코드 쪽은 미리 계산해 두고 댓글이 변해도 다시 만들지 않아요. 댓글 같은 동적인 블록은 필요할 때 천천히 재고, 픽셀 위치가 아니라 어느 파일 몇 번째 줄인지로 구분해서 보관해요.

기사에 따르면 블록의 높이는 유효하게 잰 값이 있으면 그 값, 아니면 조건이 맞는 캐시 값, 둘 다 없으면 추정값으로 정해요.

둘째 장치는 측정 시점이에요. 기사는 `ResizeObserver`가 블록의 높이를 직접 화면 배치에 써 넣는 설계를 피드백 고리 때문에 버렸다고 해요. 대신 스크롤이 가라앉은 한가한 틈에 화면 주변 약 2400픽셀 안에서 측정하고, 화면에 올라와 있는 블록은 예외로 같은 프레임 안에서 바로 보정해요. 이때도 한 프레임에 한 번까지만, 스크롤하는 동안에는 하지 않는다고 해요.

높이를 고칠 때는 읽던 위치가 흔들리지 않게 앵커링을 쓰고, 기사의 규칙대로 포인터나 휠의 관성과 싸우지 않고 그 프레임이 끝난 뒤에 한꺼번에 보정해요.

셋째 장치는 데이터 흐름이에요. 기사는 구조를 먼저 보내고 내용을 나중에 보내기, 필요할 때까지 건당 작업 미루기, 최근 diff 캐시하기를 꼽아요. 예를 들어 구문 강조는 별도 스레드에서 돌려요.

넷째 장치는 눈에 안 띄는 버그를 잡는 상시 계측이에요. 기사에 따르면 가짜 서버로 정해진 흐름을 돌리며 앱 자체의 계측값을 읽는 헤드리스 프로브와, 실제 앱을 사람 없이 큰 PR 작업으로 몰아가는 오토파일럿, 이렇게 두 길로 변경, 측정, 개선 고리를 돌렸어요. 성공 기준은 댓글 사이에 채워지지 않은 틈이 없고, 비어 있는 댓글 블록이 없고, 실제 스레드 내용이 올라와 있는 것이에요.

### 무엇이 달라졌나

기사는 백만 줄 diff와 수백 개의 댓글 스레드가 있는 PR이 열리고, 스크롤되고, 보통 크기의 PR처럼 동작한다고 밝혀요. 댓글은 잘리지 않고 전부 보이며, 방금 떠났던 PR로 돌아오면 있던 자리에 있다고 해요.

## 취업과 면접 포인트

프론트엔드 면접에서 "긴 목록을 어떻게 빠르게 보여 주나요?"를 받으면 가상화를 말하는 데서 끝내기 쉬워요. 이 기사는 한 걸음 더 가서, 높이를 미리 알 수 없는 항목이 섞일 때 어떻게 하는지 보여 줘요.

한 가지를 더 가져가면 좋아요. 이 팀은 사람이 손으로 재현하기 어려운 버그를 계측과 자동화된 시나리오로 잡았다고 해요. 어려운 문제를 만났을 때 먼저 재현과 측정 장치부터 만든다는 이야기는 면접에서 설득력이 있어요.
