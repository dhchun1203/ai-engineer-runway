## 먼저 알아 둘 개념

이 기사는 코드를 합치기 전에 도는 자동 검사를 빠르게 만든 이야기예요. 아래 다섯 가지 말만 알고 가면 훨씬 술술 읽혀요.

### CI

<Term id="ci">CI</Term>는 PR을 올릴 때마다 서버가 자동으로 타입 검사, 린트, 테스트를 돌려 주는 장치예요. 검사를 통과한 변경만 본 코드에 합쳐져요.

공항 보안 검색대를 떠올리면 쉬워요. 모든 승객(PR)이 반드시 거쳐야 하니까, 검색대가 느리면 비행기가 아무리 많아도 줄만 길어져요.

### 러너

<Term id="runner">러너</Term>는 CI 검사를 실제로 돌리는 빌린 컴퓨터예요. 검사할 때마다 한 대를 켜서 코드를 받고, 도구를 설치하고, 일을 마치면 돌려줘요.

빌린 시간만큼 돈이 나가요. 그래서 기다리는 시간뿐 아니라 러너를 쓴 총시간(러너 분)도 중요한 숫자예요.

### 크리티컬 패스

여러 일이 동시에 돌아갈 때, 전체가 끝나는 시간은 가장 오래 걸리는 줄이 정해요. 이 줄을 <Term id="critical-path">크리티컬 패스</Term>라고 불러요.

카레를 만든다고 해 봐요. 밥이 다 되기까지 30분이 걸리는데, 그동안 채소 썰기를 5분에서 2분으로 줄여도 저녁 먹는 시간은 그대로예요.

밥 짓는 줄을 줄여야 비로소 저녁이 빨라져요. 반대로 아주 짧은 일이라도 이 줄 맨 앞에 놓이면, 뒤에 선 모든 일을 붙잡아 둬요.

### 샤드

테스트가 아주 많으면 컴퓨터 한 대로 돌리기엔 너무 오래 걸려요. 그래서 테스트를 여러 묶음으로 나눠 여러 러너에서 동시에 돌리는데, 그 한 묶음이 <Term id="test-shard">샤드</Term>예요.

시험지 더미를 채점자 여러 명에게 나눠 주는 것과 같아요. 다만 채점자마다 자리를 잡고 펜을 꺼내는 준비 시간이 있고, 가장 늦게 끝나는 사람이 끝나야 모두 끝나요.

### 캐시

<Term id="cache">캐시</Term>는 지난번에 만든 결과를 보관해 뒀다가 다시 꺼내 쓰는 거예요. 보통은 새로 만드는 것보다 빨라요.

하지만 창고에서 꺼내 오는 데도 시간이 들어요. 창고가 멀고 짐이 크면, 차라리 동네 가게에서 새로 사는 게 빠를 때도 있어요. 이 기사에도 딱 그런 장면이 나와요.

## 핵심 내용 정리

기사에 따르면 이 일은 CTO가 CI 비용을 줄여 달라는 과제를 맡기면서 시작됐어요. 기왕이면 더 빠르게도 만들어 달라는 주문과 함께요.

배경은 이래요. 에이전트 덕분에 코드를 쓰는 속도는 크게 빨라졌는데, 그 코드를 검증하는 CI는 같은 속도로 따라가지 못했어요. 모든 PR이 CI를 지나야 하니, 개발이 빨라질수록 CI 앞의 줄이 길어진 거예요.

줄이 길어지면 두 가지가 나빠져요. 인프라 비용이 오르고, 사람과 에이전트 모두 검사 결과를 받기까지 더 오래 기다려요. 그래서 팀은 PR이 CI를 기다리는 시간, 그리고 러너를 쓴 시간을 목표 숫자로 잡았어요.

결과부터 말하면, 기사에 따르면 연초보다 테스트가 4배 가까이 늘었는데도 PR 대기 시간은 6분이 넘던 것이 5분 남짓으로 줄었어요. 테스트 하나당 쓰는 러너 시간은 대략 절반이 됐고요.

개선은 크게 네 갈래예요. 코드는 대부분 TypeScript지만, 방법 대부분은 다른 언어에도 그대로 통해요.

### 1. 더 빠른 기계와 도구로 바꾸기

먼저 GitHub Actions 기본 러너에서, CPU와 저장장치와 캐시 설비가 더 좋은 외부 러너로 옮겼어요. 기사에 따르면 옮기기 전후 이틀을 비교했을 때 잡(job) 평균이 34% 빨라졌고, `tsc` 같은 작업은 52%나 빨라졌어요.

다음은 타입 검사예요. 네이티브로 새로 만든 TypeScript 컴파일러(`tsgo`)로 바꾸자, 기사에 따르면 타입 검사 시간의 주간 중앙값이 73% 줄었어요. 타입 검사가 더는 병목이 아니게 된 거예요.

린트도 손봤어요. 일부 자체 린트 규칙이 타입 정보를 필요로 해서, 린트를 돌릴 때마다 코드 전체의 타입 관계를 새로 계산하느라 느리고 메모리도 많이 먹었어요.

이 규칙들을 코드의 문법 구조(AST)만 보고 판단하도록 다시 쓰자 린트가 TypeScript 없이 돌게 됐어요. 기사에 따르면 API 린트는 68%, 저장소 전체 린트는 55% 빨라졌어요.

덤도 있었어요. 문법만 보는 규칙이 되니 더 빠른 린터인 Oxlint로 옮기기 쉬워졌고, 옮긴 뒤 린트에 쓰는 러너 시간이 한 번 더 줄었어요.

### 2. 다른 일을 막고 선 작은 잡 다듬기

Linear의 CI는 매번 먼저 이 PR이 어느 경로를 건드렸는지, 똑같은 입력으로 이미 통과한 적은 없는지를 확인해요. 할 필요 없는 검사를 건너뛰어 러너를 아끼려는 거예요.

문제는 이 작은 확인 잡들이 크리티컬 패스 맨 앞에 놓인다는 점이었어요. 기사에 따르면 API 테스트 샤드 8개가 모두 이 확인이 끝나야 출발해요. 몇 초짜리 일이라도 여기서 늦으면 뒤에 선 모든 일이 같이 늦어져요.

그래서 이렇게 고쳤어요.

- 변경 감지 잡이 필요도 없는 코드 전체를 내려받고 있었어요. 받아 오는 이력의 깊이를 제한하고, 코드가 아예 필요 없는 잡은 내려받기를 없애고, 나머지는 필요한 만큼만 얕게 받게 했어요. 기사에 따르면 변경 감지 잡의 중앙값이 26초에서 8초로, 가장 나빴던 경우는 138초에서 37초로 줄었어요.
- 외부 러너는 GitHub 네트워크 바깥에 있어서, 가끔 코드 내려받기가 멈춘 채 한참 버티곤 했어요. 연결이 너무 느리면 30초쯤 만에 포기하고 잠시 뒤 다시 시도하게 바꾸고, 저장소 사본을 미리 보관해 두고 쓰는 방식으로 교체했어요.
- 테스트 결과를 기록해 두는 캐시 표시 쓰기가 머지 직전 마지막 검사 안에 들어 있어서, 테스트가 다 통과했는데도 머지가 기다려야 했어요. 이 쓰기를 아무것도 막지 않는 별도 잡으로 빼자 PR마다 42초가 줄었어요.

기사에 따르면 이것들을 합쳐 API PR의 필수 검사가 약 1분 짧아졌어요.

### 3. 매번 반복하던 준비 줄이기

CI에서는 몇 초짜리 검사도 러너 켜기, 패키지 설치, 빌드 준비가 붙으면 몇 분짜리 일이 돼요. 요리 자체보다 장 보기와 설거지가 더 오래 걸리는 셈이에요.

- 공용 도구를 미리 깔아 둔 CI 기본 이미지를 만들었어요. 샤드마다 Postgres 클라이언트를 7~8초씩 설치하던 일이 사라졌어요.
- 여러 패키지가 한 저장소에 모인 구조(모노레포)인데, API 테스트가 모든 패키지를 설치하고 있었어요. API 패키지와 그 의존성만 설치하게 하자, 기사에 따르면 44~73초 걸리던 설치가 16초에서 18초 사이로 줄었어요.
- 가장 흥미로운 장면은 `node_modules` 캐시예요. 캐시를 써 보니 되살리는 데만 약 28초가 걸렸는데, 필요한 것만 새로 설치하면 약 7.5초면 끝났어요. 게다가 캐시 열쇠가 자주 바뀌는 lockfile에 묶여 있어 잘 맞지도 않았어요. 그래서 캐시를 버리고 매번 새로 설치하기로 했어요.

기사에 따르면 이 세 가지로 샤드 하나의 준비 시간이 110~140초에서 70초 안팎으로, 약 44% 줄었어요.

준비 줄이기는 샤드 밖에서도 이어졌어요.

- 매번 DB 마이그레이션 이력을 처음부터 다시 돌리던 것을, 스키마가 안 바뀐 PR에서는 미리 만들어 둔 스키마 스냅샷을 불러오게 했어요. 기사에 따르면 컨테이너 하나당 약 12초가 1~2초가 됐어요.
- 짧은 독립 검사 7개가 저마다 러너를 켜고, 코드를 받고, 설치를 반복하고 있었어요. 이걸 잡 2개로 묶고 그 안에서 7개를 동시에 돌리자, 기사에 따르면 한 달에 약 8만 7천 러너 분(전체 CI 사용량의 11.8%)이 절약됐어요.

### 4. 테스트를 더 잘게 나눠 동시에 돌리기

테스트 도구 Vitest는 테스트를 파일 단위로 샤드에 나눠 줘요. 그래서 아주 큰 테스트 파일 몇 개가 한 샤드를 붙잡고 있으면, 다른 샤드가 다 끝나도 전체는 그 샤드를 기다려야 해요.

팀은 큰 파일을 작게 쪼갠 뒤 샤드 수를 4개에서 8개로 늘렸어요. 기사에 따르면 일주일 뒤 가장 느린 샤드가 5.25분에서 4.33분으로 줄었어요.

가장 큰 한 방은 격리 설정이었어요. Vitest는 기본으로 테스트 파일마다 모든 것을 새로 불러와서, 샤드마다 무거운 준비를 되풀이하고 있었어요. 팀은 안전하다고 확인된 파일만 모듈을 함께 쓰도록(`isolate: false`) 따로 묶었어요.

기사에 따르면 이것만으로 가장 느린 샤드가 300초대에서 약 195초로 줄고, 한 달 비용이 약 17% 줄었어요.

대신 테스트끼리 상태를 나눠 쓰면, 한 테스트가 남긴 흔적이 다른 테스트를 망칠 수 있어요. 그래서 파일마다 여기는 함께 써도 안전하다고 명시적으로 표시해야만(opt-in) 들어갈 수 있게 했고, 안전하게 정리할 수 없는 파일은 격리된 쪽에 남겨 뒀어요.

마지막으로, 요즘은 테스트 대부분을 에이전트가 쓰기 때문에 에이전트용 스킬도 이 규칙을 따르도록 고쳤어요. 사람만 규칙을 알면 안 되고, 코드를 쓰는 AI도 알아야 하는 시대라는 뜻이에요.

### 교훈: 샤드는 준비가 가벼울 때만 이득이에요

샤드를 두 배로 늘리면 준비 시간도 두 배로 들어요. 기사에 따르면 준비가 샤드당 2분 안팎이던 시절이라면, 8샤드는 준비에만 러너 시간 15~19분을 썼을 거예요. 테스트 자체보다 준비가 더 비싼 셈이죠.

3번에서 본 준비 줄이기 덕분에 8샤드가 이득이 됐어요. 기사에 따르면 준비를 줄이기 전 4샤드의 준비 합계가 8.3분이었는데, 줄인 뒤 8샤드의 준비 합계는 7.5분이에요. 샤드는 두 배인데 준비 비용은 오히려 적어진 거예요.

기사에 따르면 이 개선이 없었다면 지금 테스트는 약 11분, 지금 대기 시간의 두 배 가까이 걸렸을 거예요. 테스트가 매주 약 2,000개씩 늘고 있어서, CI를 빠르게 유지하는 일은 한 번으로 끝나지 않고 계속 이어지는 일이라고 해요.

## 취업과 면접 포인트

첫째는 관점이에요. AI가 코드를 빨리 써 주는 시대에는 코드를 쓰는 속도보다 검증하는 속도가 병목이 돼요. 이 흐름을 알고 있으면, AI 코딩 도구가 팀에 무엇을 새로 문제로 만드는지 묻는 질문에 한 단계 깊게 답할 수 있어요.

둘째는 측정부터 하는 습관이에요. 이 팀은 감으로 고치지 않고 중앙값, p90, 최악값, 러너 분 같은 숫자로 전후를 비교했어요. 그리고 전체 시간을 정하는 크리티컬 패스부터 봤어요. 몇 초짜리 작은 잡이라도 그 줄 위에 있으면 먼저 고칠 가치가 있어요.

셋째는 캐시가 늘 빠르다는 믿음을 버리는 판단력이에요. `node_modules` 캐시를 재 보니 새로 설치하는 쪽이 빨랐고, 그래서 과감히 버렸어요. 통념이 아니라 측정으로 결정하는 거예요.

넷째는 위험한 최적화를 다루는 태도예요. 테스트끼리 상태를 나눠 쓰는 설정은 효과가 가장 컸지만 정확성을 해칠 위험도 가장 컸어요. 그래서 한 번에 전체에 켜지 않고, 안전한 파일만 명시적으로 들어오게(opt-in) 하고 나머지는 격리해 뒀어요.

면접에서는 이렇게 말해 볼 수 있어요.

- "CI를 빠르게 하려면 먼저 크리티컬 패스를 찾겠습니다. 옆길의 잡을 아무리 줄여도 전체 대기 시간은 그대로이기 때문입니다."
- "캐시는 복원 비용과 적중률을 재 보고 결정합니다. 새로 만드는 쪽이 더 빠른 경우도 있습니다."
- "정확성을 해칠 수 있는 최적화는 opt-in으로 조금씩 넓히고, 안전하지 않은 부분은 격리해 둡니다."

## 내 학습과 연결

로드맵 레슨 [AI 코드에 자동 테스트 붙이기](/roadmap/automated-testing)의 "CI에서 자동으로 돌리기" 부분이 이 기사의 바로 앞 단계예요. 그 레슨은 GitHub Actions로 CI를 세우는 예시와 함께, 빠르고 공짜인 결정적 테스트는 푸시마다 돌리고 진짜 모델을 부르는 평가 테스트는 비용 때문에 따로 돌리는 분리를 다뤄요.

이 기사는 그렇게 세운 CI가 커졌을 때 무슨 일이 생기는지를 보여 줘요. 레슨에서 비싼 테스트를 커밋 경로에서 빼는 법을 배웠다면, 이 기사는 같은 생각을 대기 시간과 러너 시간 전체로 넓힌 실전편이라고 보면 돼요.
