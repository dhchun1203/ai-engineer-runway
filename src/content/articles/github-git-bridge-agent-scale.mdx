## 먼저 알아 둘 개념

이 기사는 같은 저장소를 여러 서버가 나눠 들고 있을 때 쓰기를 어떻게 안전하고 빠르게 처리하느냐를 다뤄요. 세 가지를 알고 가면 좋아요.

### 복제와 쿼럼

<Term id="replication-quorum">복제와 쿼럼</Term>은 같은 데이터를 여러 서버에 복사해 두고, 과반 같은 일정 수가 동의해야 쓰기를 확정하는 방식이에요. 한 서버가 죽어도 데이터가 남지만, 동의를 기다리는 시간이 생겨요.

### 참조

<Term id="git-reference">참조(reference)</Term>는 Git에서 브랜치나 태그처럼 "지금 이 이름이 어느 커밋을 가리키는가"를 적어 둔 메모예요. 책의 목차에서 장 제목 옆에 적힌 쪽수와 비슷해요.

커밋과 파일 내용은 한번 만들면 바뀌지 않지만, 이 메모는 푸시할 때마다 바뀌어요. 그래서 여러 서버가 순서를 맞춰야 하는 일의 중심은 이 메모 갱신이라고 볼 수 있어요.

### 저장소와 계산 분리

<Term id="storage-compute-separation">저장소와 계산 분리</Term>는 데이터를 오래 보관하는 곳과 그 데이터를 꺼내 일하는 서버를 따로 두는 설계예요. 창고와 판매대를 나누면 손님이 몰릴 때 판매대만 늘리면 되는 것과 같아요.

### 락 경합

<Term id="lock-contention">락 경합</Term>은 여러 작업이 같은 자물쇠를 잡으려고 줄을 서서 서로를 늦추는 일이에요. 화장실이 하나뿐인 사무실에서 모두가 한 줄로 기다리는 모습이에요.

## 핵심 내용 정리

### 어떤 문제였나

기사에 따르면 GitHub는 지난 1년 동안 Git 트래픽이 빠르게 늘었고, 이유로 에이전트의 작업 증가, 데이터센터와 지역 전력의 한도, 물리적 공급망의 제약을 들어요. 남은 용량은 안전하게 옮길 시간은 줬지만 천천히 옮길 여유는 주지 않았다고 해요.

그래서 먼저 데이터부터 옮기고 구조는 나중에 고치기로 했어요. 저장 방식과 호스팅을 한꺼번에 바꾸는 건 위험하다고 본 거예요. 기사는 Git 작업이 GitHub의 핵심 기능이고 거의 모든 것이 저장소 데이터에 기대고 있어서, 데이터와 서비스와 의존 대상이 먼저 옮겨져야 했다고 설명해요.

기사에 따르면 지금은 거의 모든 저장소(99.99999퍼센트)가 GitHub 자체 데이터센터와 Azure 양쪽에 복사본을 둬요. 대부분의 저장소는 복사본 다섯 개 중 둘이 Azure에 있고, Git 트래픽의 약 절반을 Azure가 처리해요. 남은 저장소는 플랫폼에서 가장 붐비는 축에 속한다고 해요.

### 왜 어려웠나

현재 방식에서 쓰기는 과반이 동의하면 확정되지만, 시스템은 건강한 복사본 전부의 응답을 (제한 시간까지) 기다려요. 그래서 가장 느린 복사본이 쓰기 지연을 정해요.

쓰기마다 저장소 전체에 거는 자물쇠를 확정 때까지 쥐고 있어서, 같은 복사본이 처리량 상한도 정해요. 기사에 따르면 Azure의 대상 지역 복사본은 GitHub 데이터센터에서 약 1,000마일 떨어져 있어 왕복이 약 25밀리초이고, 쓰기 한 번에 왕복이 여러 번 필요해요. 기사는 상한에 가까운 저장소는 푸시할 때마다 점점 더 밀릴 것이라고 설명해요.

여기서 병목의 정체가 보여요. 서로 다른 브랜치에 쓰는 일인데도 저장소 전체 자물쇠 하나를 두고 줄을 서는 거예요.

### 어떻게 풀었나

첫째 장치는 합의 범위를 좁히는 거예요. 기사에 따르면 Git이 요구하는 일관성은 참조마다 따로 적용돼요. 한 참조의 갱신이 받아들여진 뒤에는 어떤 클라이언트도 그보다 오래된 값을 보면 안 되는데, 이는 빨리 감기 푸시, 강제 푸시, 삭제 모두에 해당해요.

그래서 순서 맞추기를 저장소 전체가 아니라 참조 단위로 했어요. 같은 참조에 쓰는 일끼리만 서로 기다리고, 다른 브랜치에 쓰는 일은 동시에 진행할 수 있어요. 각 쓰기가 지역 사이 지연을 치르는 건 그대로예요. 기사는 이렇게 하면 동시에 쓰이는 참조 수에 거의 비례해 처리량 상한이 오른다고 설명해요.

둘째 장치는 읽기를 따로 키우는 거예요. 기사에 따르면 대부분의 저장소는 읽기가 쏠려 있어서, 쓰기 한 번당 읽기가 대략 100번에서 1,000번 사이라고 해요. 지금은 읽기와 쓰기가 같은 복사본의 자원을 두고 다퉈요.

그래서 오브젝트 스토리지(Azure Blob Storage)를 합의 참가자로 세워요. 임시 계산 서버가 앞에 서서 쓰기를 스토리지로 흘려보내는 가상 쓰기 복사본이에요. 이 복사본은 읽기를 처리하지 않고, 쓰기가 스토리지에 안전하게 남은 뒤에야 확인 응답을 줘요. 서로 다른 참조에 대한 여러 쓰기를 묶어 한 번의 네트워크 입출력으로 보내기도 해요.

읽기는 가상 읽기 복사본이 맡아요. 필요할 때 늘어나고, Blob Storage에서 캐시를 덥혀 가며 합의에 끼지 않은 채 읽기만 처리하고, 뒤에서 스토리지와 맞춰 가요.

### 무엇이 달라졌나

기사에 따르면 실제와 비슷한 트래픽으로 한 내부 테스트에서, 서로 다른 참조에 쓰는 경우 처리량이 3배에서 4배 높고 지연은 더 낮았어요. 운영 환경에서 잰 값이 아니라 내부 테스트 결과예요.

가상 읽기 복사본에 대해서는 부하 테스트 도구가 먼저 한계에 닿았다고 해요. 기사는 이 부분에 구체적인 처리량 숫자를 주지 않아요.

남은 과제도 분명해요. 뒤에서 맞추는 방식은 일부 읽기에는 충분하지만 모든 읽기에 그렇지는 않아서, 바뀐 참조 상태와 데이터만 읽는 순간에 바로 가져오는 방식을 다음 단계로 둬요. 그리고 쓰기 합의 자체가 다음 한계로 남아 있어요. 기사는 Git 객체가 한번 만들면 바뀌지 않고 내용으로 이름이 붙어 순서 합의가 필요 없으니, 쓰기에서 순서가 필요한 부분은 아주 작다고 보고, 최종 구조는 다음 글에서 다룬다고 예고해요.

## 취업과 면접 포인트

첫째는 병목을 "범위"로 푸는 사고예요. 느린 건 하나의 자물쇠가 너무 넓은 범위를 덮고 있어서였고, 범위를 참조 단위로 좁히니 서로 상관없는 일이 병렬로 돌았어요.

둘째는 읽기와 쓰기의 비율을 보고 설계를 나누는 습관이에요. 읽기가 압도적으로 많다면 읽기만 따로 키우는 구조가 자연스러워요.

셋째는 측정의 출처를 구분하는 태도예요. 이 기사는 운영 수치와 내부 테스트 수치를 나눠 적어요. 면접에서도 "이건 테스트에서 나온 값"이라고 말할 수 있으면 신뢰가 가요.

면접에서는 이렇게 말해 볼 수 있어요.

- "한 자물쇠 때문에 서로 상관없는 요청이 줄을 서면, 자물쇠의 범위부터 줄여 볼 수 있습니다."
- "읽기가 쓰기보다 훨씬 많으면 읽기 복사본을 합의와 분리해 따로 늘립니다."
- "개선 수치는 테스트 환경 값인지 운영 값인지 구분해서 보고합니다."

3. 가상 읽기 복사본이 합의에 끼지 않는 이유와, 그 방식의 남은 약점은 무엇일까요?
